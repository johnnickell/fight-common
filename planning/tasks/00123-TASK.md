# Introduce an Optional Metadata-Aware MCP Capability Contract

## Outcome

Replace the semantic responder's Resource/Skill concrete-class checks for central result metadata with one
optional metadata-aware capability contract. Existing `McpCapability` implementations remain compatible, while
capabilities that need metadata for pre-disclosure serving budgets can declare that requirement without another
concrete-type branch in the responder. This is a bounded standalone refactor, normally one PR.

John approved this direction after the MCP v1.3 architecture exploration, together with the separately owned
provider-lifecycle change in [TASK-00124](00124-TASK.md). He approved scheduling both after
[TASK-00121](00121-TASK.md) and [TASK-00122](00122-TASK.md), before v1.3 release qualification. This record
captures that decision; it does not authorize implementation, publication or release.

## Scope

- In scope:
  - One optional Application-owned contract for capabilities that receive the responder's actual central result
    metadata before handling. `McpMetadataAwareCapability` is the proposed name; settle the exact declaration
    against current source without introducing additional context/options abstractions.
  - Adapt `McpResourceDiscovery` and `McpSkillDiscovery` using their existing `handleWithMetadata()` behavior,
    and replace only the corresponding concrete-type branch in `McpResponder::dispatch()`.
  - Preserve central metadata ownership, request-local delivery, pre-advertisement/pre-open budget validation,
    final encoded-result enforcement and direct semantic call behavior.
  - Product contract evidence, compatibility classification, affected consumer documentation and terminology.
- Out of scope:
  - Modifying the mandatory methods of the existing public `McpCapability` interface, removing existing public
    methods/constructors or requiring existing custom capabilities to implement the new optional contract.
  - Generalizing progress execution into the metadata contract, changing `McpToolInvocation` execution binding,
    protected input/confirmation, SSE, OAuth, authorization, routes or framework adapters.
  - Dynamic-provider validation timing, owned by TASK-00124; request bounds and Resource-link/combined-journey
    implementation, owned by TASK-00121/TASK-00122.
  - A plugin framework, universal invocation context, container lookup, options bag, facade or namespace move.
  - New business messages, storage, downstream Agent OS/Pi work, release tooling or publication.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer registers an existing custom capability | N/A; composition | Existing semantic capability handling | N/A; protocol results are not domain events | The unchanged base interface remains sufficient; registration, validation and handling retain their contracts. |
| Consumer registers a capability needing central metadata | N/A; protocol coordination | Handle the selected request with actual central metadata | N/A | Optional contract selection supplies the metadata without requiring the responder to know the capability class. |
| Resources or Skills validates a serving budget | N/A; read-only | Existing discovery/get/read operation | N/A | Account for actual central metadata before disclosure or opening content; reject unsafe budgets without partial success. |
| Two responders share one capability | N/A | Independent requests under different server identities | N/A | Each request uses only its responder's metadata; no cached identity or authority crosses requests. |
| A capability fails | N/A at this boundary | Existing error translation | N/A | Preserve safe protocol errors, once-owned diagnostics and the absence of protected public details. |

No aggregate, business mutation, schema migration or application transaction is introduced. A downstream Tool
retains its existing business effects; this refactor neither adds nor changes their guarantees.

## Validation and permissions

Keep the actual configured server identity owned by `McpResponder`, including its reserved metadata key and final
response construction. The new contract conveys protocol representation inputs, not credentials, principals,
permission decisions or HTTP objects. Do not allow a capability to replace central identity or treat metadata as
an authorization context.

Preserve the distinction between pre-disclosure validation and final result enforcement: checking final encoding
alone cannot replace the existing checks before advertising descriptors or opening content. Keep metadata local
to each call rather than binding a responder identity into a shared capability at construction. Direct
`handle()`/semantic calls must retain their documented behavior and not invent a configured server identity.

The interface change is additive: existing `McpCapability` implementers must not gain a mandatory method or change
their existing signature. Preserve Resource/Skill public methods and constructor shapes. Review the actual public
operation promises in `compatibility/manifest.json`; deliberately classify the new declaration and whether its
implementation/call surface is public or package-internal. Do not infer implementability from PHP syntax alone.
The result must provide the optional capability extension described here, not a private class whitelist in disguise.

HTTP safeguards, current availability, shared Resource ownership and business authorization remain unchanged.
The progress-execution branch has a different reason to change and remains outside this contract.

  implementing the new contract or changing their signatures. Existing public construction/call patterns remain.
