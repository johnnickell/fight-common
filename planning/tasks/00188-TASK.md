# Separate Task disclosure projection from aggregate lifecycle rules

## Outcome

Remove public-view construction and visibility-context-dependent revision encoding from Domain Task without
weakening atomic revision ordering or privacy. John accepted this separation on 2026-11-02. Normally one
behavior-preserving refactoring PR across the Task aggregate, Query projection and live-delivery integration.

## Scope

- Inspect Task::view(), revision(), revisionValue(), publicState(), constructor revision bookkeeping and all
  GetTask/McpTasks/subscription consumers, including TASK-00171's guarded-disclosure repair contracts.
- Domain retains lifecycle invariants and state-bound lifetime/public-change/expiry-order evidence necessary
  for atomic comparison. Do not update counters in a separate transaction or infer order from arrival time.
- An Application projection capability owns safe Query-view construction. Public comparison encoding belongs
  outside the aggregate; if it needs a cryptographic implementation boundary, use an inward capability and
  Adapter implementation rather than Domain knowledge of HMAC framing or a concrete adapter dependency.
- Preserve which committed changes advance public order versus private-only versions; public equality/order
  must not reveal private mutation gaps. Domain state changes must not depend on serializing a transport view.
- Keep MCP field/timestamp/envelope mapping in the appropriate semantic/presentation owner, not Domain.
  No new public caller setup sequence, revision mode flags or options bag is permitted.
- Preserve current identity/visibility epoch/lifetime binding, expiry sub-order, bounded counters, rollback/
  clock-skew rejection, bytewise comparison and all encoded bounds. Do not disclose incarnation/key/counters.
- Update direct tests, current Task projection/live docs, CONTEXT, classification and CHANGELOG; coordinate
  later typed values with TASK-00189 without inventing compatibility for development snapshots.
- Out of scope: wire/revision-format changes, new client merge semantics, weakening the disclosure guard,
  caching authority, independent revision storage, exactly-once delivery or deployed-client qualification.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |

| Authorized client follows/reconnects | No new mutation | Shared GetTask path | Existing subscription frames | Same ordering comparison and protected byte-handoff behavior. |

## Validation and permissions

Keep current read, whole-state, comparison-scope and field/disclosure grants independent. Fresh authorization is
not a cached allow. Projection/encoding must run at a point preserving the existing final checks and guarded live
handoff. No Domain value confers access; disappearance/revocation closes or withholds according to current contracts.

## Acceptance criteria

- [ ] Task no longer constructs public views or HMAC-masked public revision tokens.
- [ ] Required lifetime/counter/expiry evidence remains atomically state-bound; private-only mutations do not leak through public gaps.
- [ ] Application projection and any encoding port/adapter have clear ownership without adding forwarding layers or caller sequencing.
- [ ] Equal public revisions mean identical public state within the same comparison scope; committed order dominates earlier expiry views.
- [ ] Changed visibility/lifetime, clock rollback, exhaustion, denied/withheld state and complete encoded-budget behavior remain unchanged.
- [ ] Poll/live/reconnect and guarded-fragment/native-write behavior preserve existing authorization, ordering and failure contracts.
- [ ] Current docs/classification and complete verification/independent acceptance evidence exist.
