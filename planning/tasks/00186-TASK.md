# Separate Notice repository transactions and recovery reads

## Outcome

Replace NoticeStore's combined persistence/transaction/recovery interface with a Domain NoticeRepository,
existing TransactionalUnitOfWork and a cohesive Application recovery-read port. Preserve ordering and loss
proofs, not merely method names. John approved this correction on 2026-11-02; normally one refactoring PR.

## Scope

- Inspect/migrate NoticeStore, DbalNoticeStore, NoticeRecorder, NoticeRemover, NoticeRecovery, NoticeReader
  composition and actual recovery/subscription/publication consumers.
- Put aggregate identity lookup/append/removal behind `Domain/Mcp/Notice/NoticeRepository`; keep transaction
  control out of that contract. Use descriptive `$noticeRepository` and `$transactionalUnitOfWork` collaborators.
- Compose separate DBAL repository and TASK-00184 unit of work on one dedicated connection. Keep namespace lock,
  identity comparison, position allocation, relationship writes/deletion and bounded loss evidence atomic.
- Separate coherent recovery-window/feed reconstruction into an Application-owned read capability implemented
  by a DBAL reader. Reuse the existing authorized NoticeReader where responsibilities genuinely match; do not
  merge live browsing and locked continuity proof solely because both read notices.
- Preserve namespace incarnation, high-water/lost-through meanings, removal of exact incarnations, confidential
  continuations, conservative cross-scope uncertainty and independent current authorization.
- Keep consumer read calls simple: the recovery reader owns its required coherent read transaction/lock rather
  than requiring a caller-managed begin/read-state/read-rows/commit sequence. This is not a write repository
  implementing UnitOfWork under a different name.
- Remove only provisional obsolete APIs after current tagged inventory; update public/internal classification,
  tests, safe-notice/inspection/recovery/subscription/publication guides, CONTEXT, examples and CHANGELOG.
- Out of scope: changes to notice payload/schema, retention eligibility, polling cadence, outbox/replay promises,
  unifying Notice and Task domain rules or exposing global counters across concealed scopes.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Producer records admitted safe notice | RecordNotice | Existing inspection | NoticeRecorded after commit | Same deduplication, commit-ordered allocation and related writes. |
| Authorized operator removes exact retained incarnations | RemoveNotices | Existing inspection/recovery | No new event | Same atomic deletion and conservative loss watermark. |
| Authorized caller polls/reconnects | No business mutation | RecoverNotices and existing notice Queries | None | Same bounded whole notices, continuation and complete/incomplete/uncertain result. |

## Validation and permissions

Keep separate recording, removal, inspection/recovery and publication decisions. Removal checks the complete
selection/content as required; unknown/denied/replaced targets retain safe indistinguishability. Recovery cannot
infer continuity from empty rows or disclose hidden namespace activity. Consumer policy remains consumer-owned.
