# Invoke validated CQRS MCP Tools with safe semantic output

## Outcome

Deliver the complete selected-Tool invocation use case. An available, explicitly registered MCP Tool receives only
validated `tools/call.params.arguments`, maps them explicitly to an existing consumer command or query, and returns
schema-conformant, public-safe semantic output. Unknown and unavailable Tools are concealed consistently, expected
selected-Tool failures become complete error Tool results, and unexpected failures remain generic and centrally
diagnosed.

## Scope

- In scope:
  - `tools/call` capability handling over TASK-00106's registry and the same request-scoped availability decision
    used by `tools/list`, with availability checked before argument validation or Tool invocation.
  - A dedicated selected-Tool invoker that reflects `#[Validation]` beside `#[McpToolInfo]`, calls the existing
    `ValidationService` over exactly `tools/call.params.arguments`, and passes the resulting `ApplicationData` to
    `McpTool::handle()`.
  - Input-schema/rule consistency evidence, runtime input and structured-output schema conformance, compatible safe
    text presentation, and rejection of nonconformant Tool output before public response construction.
  - Package-owned query-backed and mutation-backed Tools. Query Tools explicitly map to an existing Query and use
    `QueryBus::fetch()`; mutation Tools explicitly map to an existing Command and preserve
    `CommandBus::execute(): void`.
  - Truthful mutation acknowledgement using only data already known to the Tool, such as a caller-generated
    identifier, and an existing follow-up Query only when it is genuinely required for truthful output.
  - Explicit public-safe typed-failure mapping, selected-Tool validation/business failures, central integration for
    semantic success and failure classification, and once-only redaction-aware diagnostics for an unclassified
    `Throwable`.
  - Optional CQRS envelope observability using a namespaced canonical-Tool/correlation baseline and a strictly
    scalar, namespaced consumer audit extension through existing message/filter seams. Existing consumers that do
    not compose the feature retain normal bus behavior.
  - A non-streaming no-op reporter needed to exercise the accepted Tool contract without a progress token. Live
    reporter selection, SSE emission, and cancellation behavior remain owned by TICKET-00025.
  - Maintainer-requested revision: add immutable `Domain/Value/Basic/StrictJson` and use it throughout MCP
    request metadata, schemas, mirrors, invocation and output instead of exposing PHP generic objects. Preserve
    JSON object/list/scalar distinctions, safe bounded construction and protocol behavior. Existing `JsonObject`,
    unrelated cache sentinels and JSend remain unchanged.
  - End-to-end acceptance ownership for TICKET-00024, additive compatibility-manifest classification, and
    consumer-facing Tool implementation/invocation documentation.
- Out of scope:
  - Tool-created JSON-RPC, raw JSON, HTTP or framework responses, routes, authentication, authorization policy,
    Agent attributes, permission strings, principal models, credentials, or transport headers.
  - Reflective command/query hydration, arbitrary Action invocation, changing `CommandBus::execute()` to return a
    value, or adding a read solely to manufacture a mutation result.
  - Live progress/SSE and disconnect cancellation from TICKET-00025, protected `input_required` state/resumption
    from TICKET-00026, OAuth resource-server support from TICKET-00027, and Fight Access Control adoption.

## Use cases and contracts

| Use case | Actor and trigger | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|---|
| Invoke a query-backed Tool | Available selected Tool receives schema-conformant arguments | N/A | One consumer-defined existing Query through `QueryBus::fetch()` | N/A: queries do not mutate business state | Return only a safe semantic projection whose structured and text representations agree. |
| Invoke a mutation-backed Tool | Available selected Tool receives schema-conformant arguments | One consumer-defined existing Command through void `CommandBus::execute()` | N/A by default; one existing follow-up Query only when required for truthful output | Consumer-defined events only | Execute one write and return only a truthful known acknowledgement; do not invent a command result. |
| Reject an unknown or unavailable Tool | Client names an absent Tool or availability conceals a registered Tool | N/A | N/A | N/A | Produce the same semantic protocol failure in both cases without validation, invocation, or disclosure. |
| Reject invalid selected-Tool input or an expected business failure | A known available Tool receives invalid arguments or its mapped use case rejects them | No dispatch when validation fails | No dispatch when validation fails | N/A before dispatch | Return a complete `isError: true` Tool result with only explicitly public-safe detail. |
| Contain an unexpected failure | Tool selection, invocation, or output processing throws an unclassified `Throwable` | No additional command | No diagnostic query | N/A | Log once through consumer-supplied redaction-aware diagnostics and return only the generic internal semantic failure. |

## Validation and permissions

Resolve the Tool and apply the same metadata-only availability service used for discovery before validating
arguments. An unavailable Tool must follow the identical semantic path and public message as an unknown Tool.
Neither path may reveal registry membership, a principal, permissions, or the consumer's policy reason.

For a selected available Tool, validate the input against its declared input schema and reflect `#[Validation]`
from `handle()`. Invoke `ValidationService` over exactly the `arguments` object; an empty rule list still returns
`ApplicationData` containing the original arguments. Schema conformance and validation rules are distinct checks,
and fixtures must prove their consistency instead of treating one as evidence for the other. Do not pass the
framework request, JSON-RPC id, headers, credentials, or raw unvalidated arguments to the Tool.

Validate `McpToolOutput` structured content against the declared output schema and require compatible safe text
presentation before the central responder creates MCP representation. Only explicitly registered typed failures
may expose sanitized actionable detail as a complete error Tool result. Do not classify every Domain or
Application exception as public-safe. An unclassified `Throwable` becomes the generic internal failure and is
diagnosed exactly once without exposing credentials, raw arguments, personal data, paths, stack traces, or internal
class/storage details.

Common makes no authorization decision. Consumer authentication and permission enforcement happen before or
around invocation; Fight Access Control owns any Agent-aware availability/invocation implementation. Optional
envelope metadata is limited to canonical Tool/correlation identity plus scalar namespaced consumer audit values.
Reject unnamespaced, non-scalar, credential-bearing, raw-argument, authorization-decision, or canonical-key
overwriting extensions.

## Acceptance criteria

- [x] A known available Tool is selected exactly once, receives `ApplicationData` produced from exactly
  `tools/call.params.arguments`, and never receives a framework request, JSON-RPC id, principal, credential,
  header set, or raw unvalidated arguments.
- [x] Input schema conformance and `#[Validation]` runtime rules are independently enforced; empty rules preserve
  the original arguments as validated `ApplicationData`, and either rejection occurs before Tool/bus dispatch.
- [x] A package-owned query-backed Tool maps explicitly to one existing Query, calls `QueryBus::fetch()` once, and
  returns only public-safe structured content conforming to its output schema with compatible text presentation.
- [x] A package-owned mutation-backed Tool maps explicitly to one existing Command, calls void
  `CommandBus::execute()` once, and returns only a truthful known acknowledgement. A follow-up read is absent unless
  its necessity and one-read/write behavior are explicitly proved.
- [x] Direct invocation of an unavailable Tool is indistinguishable from an unknown Tool and performs no
  validation, Tool call, command, query, event, metadata enrichment, or diagnostic disclosure.
- [x] Selected-Tool validation failures and explicitly mapped public-safe business failures become complete
  `isError: true` semantic Tool results. Unclassified failures are logged once and become only the generic internal
  error through TASK-00104's central responder.
- [x] Nonconformant structured output, unsafe text, or disagreement with the declared output schema is rejected
  centrally and never emitted as a successful Tool result.
- [x] Optional envelope observability adds only namespaced canonical Tool/correlation metadata and validated scalar
  namespaced consumer audit fields; handlers remain transport-neutral and consumers that do not compose the
  integration retain existing bus behavior.
- [x] The no-op reporter emits no progress and carries no result content; live progress, response selection, and
  cancellation remain unclaimed for TICKET-00025.
- [x] Package-owned fixtures cover both query-backed and mutation-backed behavior, validation and schema failures,
  output safety, one-read/write discipline, availability concealment, expected/unexpected failures, and metadata
  isolation without requiring Fight Access Control adoption.
- [x] Every public addition is classified in `compatibility/manifest.json`, its promised operations are explicit,
  and existing command/query bus, validation, JSend and released consumer behavior remains unchanged. The approved
  pre-release MCP representation migration to StrictJson is documented explicitly; protocol outcomes remain covered.

- [x] `StrictJson` owns immutable, validated JSON representation and typed object navigation; MCP components no
  longer reference `stdClass` or perform object casts. Empty objects/lists, null versus missing, numeric keys,
  nested isolation, unsafe input rejection and wire compatibility have direct tests. The new type and revised
  unreleased MCP signatures are manifest-classified and documented.
