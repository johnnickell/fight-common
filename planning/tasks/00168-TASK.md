### Approved negotiation and invocation contract

Tasks are explicitly composed; no aggregate provider silently enables optional capabilities. Client declaration is
per request under io.modelcontextprotocol/clientCapabilities.extensions, and server/discover advertises
io.modelcontextprotocol/tasks only when actual complete handling is wired. The server selects ordinary or Task results
per supported tools/call; a client's declaration neither requires asynchronous execution nor grants authority.
Unsupported request methods must not acquire Task results. No invented client task-preference flag is added.

Check current Tool availability and required client support before entering an asynchronous-effecting branch. A
non-declaring client that cannot receive a synchronous result receives -32021 with the required capability shape;
checking only after the Tool created/dispatched inaccessible work is insufficient. Each tasks/get/update/cancel call
also checks its own current declaration. Consumer operations remain responsible for business permission and execution.

Classify the public McpTool::handle return-contract change deliberately, including implementations/subtypes/interactive
resume paths and callers; McpResult currently cannot construct resultType:task. Preserve ordinary implementations,
result/error/input semantics and current failure-mapping/metadata boundaries. No assumption of binary/source-compatible
widening or release exception is authorized. If support constraints require an unapproved break, surface it rather than
silently changing the dependency floor or public contract. Exact additive APIs/adaptation are implementation design.

Only acknowledge a handle after durable creation and resolvable current state through the actual read path, not just
an in-memory object or queued submission. The creation response is flat resultType:task plus Task metadata; tasks/get
returns resultType:complete plus the detailed state variant. Check current disclosure permission for the response too;
creation rights do not imply ongoing result access. Response loss can leave committed work/handle uncertainty.

### Approved HTTP, state and outcome contract

Extend actual guarded HTTP composition, preserving Origin/POST/media negotiation, complete mirror validation,
invocation admission/authentication integration, central diagnostics and native response behavior. For
tasks/get/update/cancel, Mcp-Name mirrors params.taskId and Mcp-Method matches the method. Define absent/mismatched/
duplicate/invalid mirror handling consistently; a routing header/handle is not authority. Protocol results are not JSend.

Use shared QueryBus reads and supplier Commands, never Tool/presenter SQL or parallel policy. Return every required
field for the selected permitted state; no truncation of outstanding input or substitution of an empty successful
result to conceal protected data. Current permission governs status/input/result/error disclosure, including after
reconnect, changed policy and original Tool catalog changes. Listing/availability, prior access and retained IDs are
not grants. Invalid/nonexistent taskId yields safe -32602; internal failure stays distinct, using safe -32603 mapping.
Do not infer expiry merely from absence or expose raw private exception messages as stored protocol errors.

Preserve original operation semantics: completed includes a Tool result with isError:true; failed contains the actual
safe JSON-RPC execution error. Nested terminal results are original operation results, not a new Tool invocation,
flattened get-result substitute, arbitrary internal exception or Workflow/review success. Reuse recorded contract
context from TASK-00166 to avoid reinterpreting a retained result against unrelated current Tool definitions.

Validate finite identities, metadata, state messages, input maps and final encoded responses. Include structured/text
companions, nested result/error, escaping/multibyte content, central metadata and the outer JSON-RPC envelope; existing
McpResult boundedComplete alone does not cover that envelope. Reject safely before disclosure, not by silent truncation
or loss of original outcome semantics. Qualify application-valid stored data that exceeds an outer serving budget.

Use real consumer execution fixtures to show durability is separate from dispatch, worker start and external effects.
No implicit transaction with a consumer job system, worker engine, mandatory outbox, exactly-once effects or automatic
retry is introduced. Document failures before/after commit, submission failure and uncertain effect/response recovery.
Original request/stream disconnect does not cancel durable work; request-scoped progress cancellation remains a separate
existing contract. Tasks do not acquire ongoing progress/message streams. Live full-state notifications belong to
TICKET-00052 and remain outside the general retained notice feed/Mercure.
