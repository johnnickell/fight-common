# Separate Task repository persistence from transaction ownership

## Outcome

Replace the aggregate-shaped Application TaskStore with Domain `Mcp/Task/TaskRepository` and a separate injected
`TransactionalUnitOfWork`, using the DBAL implementation from TASK-00184. Keep all current durable Task semantics.
John approved the architectural correction on 2026-11-02. Normally one independently reviewable refactoring PR.

## Scope

- Migrate `Application/Mcp/Task/Service/TaskStore`, `Adapter/Mcp/Task/Dbal/DbalTaskStore`, TaskLifecycle,
  TaskInputLifecycle, TaskCancellationLifecycle, fixtures, actual consumers and maintained composition examples.
- Domain TaskRepository owns aggregate load/save/removal, not commit, connection access, disclosure policy or
  protocol output. Remove the provisional Store contract rather than rename it while retaining UnitOfWork inheritance.
- Use `$taskRepository` and `$transactionalUnitOfWork` for those collaborators. Preserve committed read versus
  serialized mutation behavior without requiring public consumers to understand storage internals.
- Compose repository and unit of work on the same dedicated DBAL connection. Keep Task namespace serialization
  before current admission/lookups and through actual commit, dirty-read rejection and unowned-write rejection.
- Preserve logical expiry versus physical deletion, state/input/cancellation/revision coherence, bounded creation/
  transition deduplication, terminal winners, whole-selection removal and storage uncertainty/failure categories.
- Handle necessary committed reads through an honest inward capability/repository contract; no arbitrary second
  store or reporting methods bolted onto the write repository. Preserve the public Query behavior.
- Update product tests, internal/public classification, durable Task/input/cancellation/live composition docs,
  CONTEXT, affected README examples and CHANGELOG. Handler ownership moves separately in TASK-00187.
- Out of scope: new Task state/input/protocol behavior, schema changes, retention policy, ORM binding, external
  job atomicity, caller transaction enlistment, automatic retry or historical development-snapshot compatibility.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Producer creates/updates retained work | CreateTask, RecordTaskState | GetTask | TaskChanged after commit | Same coherent state and retry/version fences. |
| Supplier/consumer manages durable input and cancellation | Existing Task input/cancellation Commands | GetTaskInput, GetTaskCancellation | Existing TaskChanged facts | Same single-use input, independent intent and committed acknowledgment. |
| Authorized operator removes selected Task data | RemoveTasks | Existing reads | TaskDataRemoved for actual deletion | Same all-or-nothing deletion and bounded lifetime guarantees. |

## Validation and permissions

Keep independent creation/update/read/input/cancellation/removal admissions, whole-state disclosure, current
comparison scope and denial/missing/expired meanings. Admission runs at the existing protected point, including
retries. Rejected outer transactions never commit/roll back unrelated work. Disconnect is not cancellation.

## Acceptance criteria

- [ ] Domain TaskRepository and DBAL repository have explicit aggregate persistence responsibilities and no transaction inheritance.
- [ ] Application callers inject existing TransactionalUnitOfWork separately; a single concrete Store implementing both roles is not the replacement.
- [ ] Shared connection, real commit, namespace lock, committed reads, dirty-read rejection and unowned-write rejection remain proven.
- [ ] Input consumption, cancellation intent, comparison/revision data, expiry and terminal/removal races preserve existing behavior.
- [ ] Uncertain commits and post-commit failures remain distinguishable; no hidden retry, upsert restoration or new delivery guarantee appears.
- [ ] Owned source/examples use explicit capability names; provisional old APIs are removed directly subject to current tagged inventory.
- [ ] Current docs/classification and full-gate/independent acceptance evidence exist.
