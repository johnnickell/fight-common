## Approved API and compatibility decision

**Approved decision:** add
`ResultSet::strict(int $page, int $perPage, int $totalRecords, ArrayList $records): self`, returning the existing
`ResultSet` with method-level generic inference from `ArrayList<T>` to `ResultSet<T>`. Keep all four arguments
required and retain their existing constructor names for named calls. Do not add defaults, accept Pagination in
place of metadata, introduce a parallel result type, or require records to implement Arrayable.

This is additive next-minor scope under [ADR 0009](../adr/0009-public-api-manifest-baseline.md),
[ADR 0010](../adr/0010-behavioral-contract-authority.md) and
[ADR 0011](../adr/0011-non-structural-compatibility-policy.md). Preserve the released public constructor, its
parameter names, permissive behavior, collection exposure and existing output schema. Do not enforce new validation
on that path, automatically migrate repositories, newly deprecate the constructor, emit runtime warnings, or fix
its floating-point limitations in this slice. A separate incompatible change needs explicit compatibility resolution;
unchanged PHP signatures alone cannot justify a behavioral break. No exact version, release or certification is assigned.

Retain the existing empty-total convention: **totalPages is 1 when totalRecords is 0**, including on the strict path.
Validation is at construction only. Retain the exact supplied mutable ArrayList and existing record identities;
`records()` and caller-held references can subsequently change its contents. No immutable snapshot, defensive/deep
copy, permanent cardinality/element guarantee or validation provenance is added to the shared ResultSet type.

John explicitly approved this additive API, one-page empty convention and construction-only/shared-list contract
in this planning conversation. The TASK is decision-complete and `ready-for-agent`; approval does not start work.
The builder must not choose between strict constructor enforcement, a parallel DTO or this factory during implementation.

## Validation and permissions

The approved strict-path contract is fully bounded:

- Require `page >= 1`, `perPage >= 1`, `totalRecords >= 0` and
  `records->count() <= perPage` **and** `records->count() <= totalRecords` at construction.
  A zero total therefore requires an empty list. Reject zero/negative bounds, negative totals and either excessive
  count with `Fight\Common\Domain\Exception\DomainException`; exception prose is diagnostic, not stable API.
- Native `int`/`ArrayList` boundaries remain PHP-owned: wrong arguments from strict callers raise native TypeError;
  weak callers retain PHP scalar coercion. This is neither an HTTP parser nor raw-string input validation.
- Empty lists are valid with zero or positive totals, on page one, within the reported range or beyond totalPages.
  Partial pages are valid. Do not require count to equal perPage or a computed last-page remainder, enforce
  `page <= totalPages`, or infer a count/row snapshot by checking offset against total. No cross-field page-position
  rule, including rejecting a nonempty out-of-range page solely for that position, is introduced.
- For positive totals, compute ceiling division exactly with integer-only arithmetic, for example
  `intdiv(totalRecords - 1, perPage) + 1`; return 1 for zero totals. Avoid floating-point division/ceil/casts and
  overflow-prone `totalRecords + perPage - 1`. The strict path must not first traverse unsafe legacy page arithmetic
  and then overwrite its result. Preserve legacy behavior while arranging safe strict initialization internally.
- Do not calculate or constrain an offset: ResultSet does not expose or execute one. Positive native maximum page,
  size and total values remain admissible when the local count bounds hold, even where Pagination::strict() would
  reject an unrepresentable request offset. No new platform floor or arbitrary cap is permitted.
- Preserve scalar, class/interface-typed, object and dynamic/mixed ArrayLists and `TRecord` inference. The existing
  `ItemTypeMethods` trait already supplies public `itemType(): ?string`, initialized from the supplied ArrayList.
  Surface and document that accessor rather than adding a duplicate. Return its declared type string, or null for
  a dynamic list; do not infer a concrete type from the first element or restrict records to presentation values.
- Preserve records()/item identity, ordering, count/isEmpty/iteration and the existing toArray()/jsonSerialize()
  keys and types (`page`, `per_page`, `total_pages`, `total_records`, `records`). Arrayable projection remains a
  JSend presentation requirement, not a ResultSet construction requirement.

An inconsistent local tuple rejects, but construction never certifies that count and rows were read atomically,
that totals are current, or that a page is complete. Do not add a transaction/lock or promise database snapshots.
Later mutation through either list reference can invalidate initial count bounds; document and test that limitation
rather than advertising all ResultSet instances as continuously validated. Permissions are N/A here and remain
consumer-owned; invalid metadata must not trigger an unbounded fallback query.
