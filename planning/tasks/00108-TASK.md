# Orchestrate request-scoped MCP progress and cooperative cancellation

## Outcome

Deliver the reusable Application-layer execution behavior behind progressive MCP Tool calls. A valid protocol
progress token is associated with a live request-scoped `McpProgressReporter`; an absent token selects the no-op
reporter. The orchestrator preserves ordered progress before the final semantic response, observes advisory
cancellation set by the outer transport, and prevents duplicate or late output without claiming forced interruption
or rollback.

## Scope

- In scope:
  - Protocol-semantic progress-token shape validation for `tools/call`, accepting only the protocol-defined string
    or integer forms and associating the unchanged token with that request's reporter notifications.
  - A live implementation of TASK-00106's already accepted minimal `McpProgressReporter` contract and orchestration
    of exactly one TASK-00107 Tool invocation through it.
  - Strictly increasing finite numeric progress, optional numeric total and human-readable status, deterministic
    rejection of invalid or non-increasing reports before delivery, and exact token preservation.
  - Request-related progress notification representation, ordering before the final TASK-00104 semantic responder
    message, once-only completion, and suppression of reports after completion.
  - A request-scoped cancellation state set by an outer delivery adapter when its client connection closes;
    `isCancelled()` gives the Tool an advisory safe-point signal and all later client output is suppressed.
  - Package-owned query-backed and mutation-backed fixtures proving equivalent semantic Tool output with live and
    no-op reporters, expected and unexpected failure after progress, cancellation, and work already dispatched.
  - Additive compatibility-manifest classification and consumer-facing documentation for public additions.
- Out of scope:
  - HTTP response-mode selection, SSE serialization, response headers, flushing, disconnect detection, framework
    responses, server emission, and buffering control, which belong to [TASK-00109](00109-TASK.md).
  - Consumer routes, authentication, principals, permission policy, worker/runtime policy, gateway configuration,
    or deployment-specific timeouts.
  - Forced thread/process interruption, transaction rollback, undoing a dispatched command, durable Tasks,
    subscriptions, partial Tool-result streaming, legacy HTTP+SSE/session behavior, or a Streamable HTTP
    `notifications/cancelled` message for request-stream closure.
  - Generator-backed deferred Tool execution or transport callbacks, partial results, or framework response objects
    in `McpToolOutput`.

## Validation and permissions

An absent progress token is valid and selects the no-op reporter. A present token must be a string or integer; an
array, object, boolean, null, floating-point value, or malformed metadata placement fails protocol validation before
Tool invocation. The client owns uniqueness across active requests; Common preserves and scopes the supplied token
without inventing a global session or accepting a token from another request.

The live reporter accepts only finite numeric progress that strictly increases for that request. Optional total and
status values must satisfy the already accepted public contract and cannot smuggle partial/final content. A
duplicate, decreasing, non-finite, or otherwise invalid report is rejected before delivery as a Tool contract
failure and contained by the existing safe central failure boundary. After final completion, later reports are
rejected without delivery. After cancellation, later progress and final responses are suppressed because the outer
transport has reported that no more client output is possible.

Failure behavior is state-specific. Selected-Tool input validation completes before Tool invocation and therefore
before any progress; its failure remains TASK-00107's complete `isError` Tool result with no progress delivered.
After progress and while delivery is open, an expected public-safe business failure becomes one final complete
`isError` Tool result. A late output-schema conformance failure, reporter-contract violation, response-preparation
failure, or unclassified `Throwable` is diagnosed once and becomes one sanitized final JSON-RPC error. After
completion, no duplicate final is delivered. After cancellation, no client-visible failure or final is delivered
and any diagnostic remains server-side.

Common makes no authentication or authorization decision. TASK-00105's consumer-supplied Origin and invocation
guards and TASK-00107's availability-before-invocation behavior remain authoritative. Cancellation observation is
advisory application input: a Tool may stop at a business-safe checkpoint, but Common neither rolls back work nor
promises that a command already dispatched can be undone.

## Acceptance criteria

- [x] Semantic `tools/call` execution without a progress token receives exactly the no-op reporter, delivers no
  progress notification, invokes the selected Tool once, and preserves the ordinary final semantic response.
- [x] A valid string or integer progress token selects exactly one live request-scoped reporter, is preserved
  without coercion in every related notification representation, and never leaks into Tool input or CQRS payload.
- [x] Valid progress reports are represented as request-related `notifications/progress` messages in strictly
  increasing order before the final response; completion delivers the final semantic responder message once.
- [x] Selected-Tool input validation finishes before invocation and progress; rejection delivers TASK-00107's
  complete `isError` Tool result with no progress. An expected public-safe business failure after earlier progress
  also delivers one complete `isError` Tool result.
- [x] A late output-schema conformance failure, reporter-contract violation, response-preparation failure, or
  unclassified `Throwable` after progress delivers one centrally classified, public-safe final JSON-RPC error and
  is logged at most once while delivery remains open.
- [x] The same failure after cancellation delivers nothing; a report after completion cannot create another
  progress or final message, and neither path converts earlier progress into partial success.
- [x] Duplicate, decreasing, non-finite, malformed, late, or content-bearing progress cannot be delivered.
- [x] Progress carries only numeric work, optional total, and human-readable status. Structured output, text
  output, application Views, and every other partial/final result remain in `McpToolOutput` and the final response.
- [x] When an outer adapter marks the request cancelled, `isCancelled()` becomes true, no later progress or final
  response is delivered, and fixtures prove both early cooperative stop and already-dispatched work without a
  rollback claim.
- [x] Cancellation is request-scoped and race-safe: closure and completion cannot produce duplicate finals,
  cross-request cancellation, post-completion progress, or a Streamable HTTP `notifications/cancelled` message.
- [x] TASK-00106's stable reporter interface is not broadened speculatively. Any implementation convenience remains
  private until TASK-00109 adapter proof establishes that a public change is unavoidable and additive.
- [x] Every public addition is classified in `compatibility/manifest.json`, its promised operations are explicit,
  and `CONTEXT.md` plus affected consumer documentation accurately describe the implemented boundary.
