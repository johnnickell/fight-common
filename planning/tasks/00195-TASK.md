# Configure projection checkpoint storage

## Outcome

A consumer selects the projection checkpoint table, explicitly installs its schema and runs existing checkpoint
load/advance/reset operations against that selection. Preserve durable projector-scoped progress and concurrent
monotonicity. This is a complete persistence slice, normally one PR, consuming TASK-00194's working safe naming
mechanism rather than creating a second validation/quoting policy.

## Scope

In scope:

- Explicit checkpoint table configuration with `projection_checkpoints` retained as the exact default.
- Schema definition, explicit installation/existing checks, loads, first saves, monotonic updates, duplicate-key
  recovery and both insert/update/reset race paths using the configured table.
- Reuse the Adapter naming mechanism supplied by TASK-00194 with coherent schema/runtime composition.
- Existing public construction/named-argument compatibility, saved fields, projector identities and behavior.
- Real configured-name persistence/concurrency evidence, relevant documentation and CONTEXT.md alignment.

Out of scope: Event Store changes owned by TASK-00194, publication tables/joint journey owned by TASK-00196,
MCP/ORM naming changes, automatic migrations/renames/data movement, qualified names, implicit configuration,
new reset semantics, projector business policy, read-model schema ownership and unrelated refactoring.

## Use cases and contracts

Actor: consumer integrator/operator, followed by an existing projection worker or authorized administrative caller.

| Use case | Commands | Queries | Events | Expected side effects |
| --- | --- | --- | --- | --- |
| Select a checkpoint table and explicitly install/reuse it | N/A: composition/deployment, not a bus Command | Existing schema inspection | None | Existing installer creates selected storage when invoked; configuration alone changes no data/schema |
| Resume projection after reopening persistence | Existing ProjectionRunner coordination, unchanged | Existing checkpoint load and Event Store polling | Existing projected events, unchanged | Read the configured checkpoint, not a default-table row |
| Save successful projection progress, including racing workers | Existing checkpoint save; no new bus Command | Existing load/duplicate-key recovery reads | No additional events | Advance only the configured projector-scoped checkpoint without regression |
| Explicitly reset one projector for a rebuild | Existing reset operation | Existing subsequent load | None added | Reset only the selected projector in the configured table; consumer still coordinates worker/read-model cleanup |
| Reject unsupported naming or change selection | N/A: composition | No new public Query | None | Safe rejection or new selection; never transfer old checkpoints |

[ADR 0002](../adr/0002-projection-delivery.md) retains checkpoint advancement after successful handling, at-least-once
projection, monotonic saves, explicit zero reset and consumer-owned worker/read-model coordination. Table selection
must not change projector identity or imply that a read model was rebuilt.

## Validation and permissions

Apply TASK-00194's ordinary-name validation/quoting without weakening its restrictions or introducing a second
fallback/global configuration system. Keep bound data separate from identifiers. Reject unsafe, qualified or
otherwise unsupported selections safely. Preserve the DBAL 4.4/schema exception's finite existing scope.

Consumers own composition, database privileges, worker scheduling and permission to reset/rebuild. Configuration
confers no new authority and adds no HTTP, UI, authentication or application permission surface. Preserve missing
storage errors, backward-save rejection and concurrent insert/update/reset outcomes. An absent checkpoint still
has its existing meaning within selected storage; it does not prove old storage was migrated or cleared.
