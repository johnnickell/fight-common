# Supply and admit durable Task input

## Outcome

Trusted producers retain supported input requests; authorized clients answer them through shared Commands and
`tasks/update`; consumers can observe accepted answers without repeated submissions admitting the same input twice.
John approved this single TASK as the complete decomposition of [TICKET-00050](../tickets/00050-TICKET.md).
Ordinary forms, destructive-confirmation safeguards, persistence and method handling form one complete PR outcome.

TASK-00168, which owns complete extension activation and combined Tool-start HTTP journeys. No reverse dependency on
activation, removal, cancellation, live delivery, Mercure or introspection is introduced.

## Use cases and contracts

Names below describe responsibilities, not final PHP classes. Preserve `CommandBus::execute()`, `QueryBus::fetch()` and
`EventDispatcher::trigger()`. Client tasks/update supplies input, not producer status or an operation result.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Trusted producer requests supported input | Issue requests through shared lifecycle | Current producer/state checks | Safe committed input facts where defined | Persist bound contracts and valid input_required state atomically |
| Client retrieves outstanding requests | N/A; read only | Shared currently authorized state Query | N/A; not a receipt | Return all permitted outstanding requests within bounds, without private runtime rules |
| Client answers some/all active requests | Submit Task input responses | Current admission/contract checks | Safe accepted-input facts where defined | Atomically admit validated active batch and update outstanding state before acknowledgment |
| Client repeats or supplies unknown/superseded keys | Same Command | Fresh access and active-key checks | No invented acceptance fact for ignored input | Ignore inactive keys without replacement, redispatch or validation bypass for active entries |
| Consumer observes/continues accepted input | Authorized continuation/admission operation where mutation is needed | Protected accepted-answer/state reads | Consumer business facts remain separately owned | Expose durable accepted input without repeat admission; consumer owns execution/reconciliation |
| Confirmation is partly accepted or refused | Same input Command with bound confirmation semantics | Confirmation group/current access checks | No destructive-approval fact inferred | Wait for all required acceptances, or retire group on any decline/cancel without destructive continuation |
| Input races terminal transition or fails after admission | Input and TASK-00166 producer Commands | Coherent shared state | Only actual committed facts | Preserve terminal winner and consumed/admitted state; never manufacture execution or rollback |

### Approved persistence and request-identity direction

Extend TASK-00166's actual DBAL state and shared Queries rather than another interaction database. Retain server-authored
validation and binding material privately, distinct from disclosed form descriptions. Requests use accepted supported
form/confirmation contracts, including their original schema/runtime rules; never reconstruct authority from a client
form, answer or mutable replacement operation definition. Apply relevant current form capability requirements when
serving protocol requests; Tasks negotiation alone does not enable arbitrary server-to-client interactions.

A key identifies one immutable request for the Task's lifetime. Answered/superseded keys cannot identify a different
request later, even after payload removal or repeated input rounds. Bound outstanding requests, retained answers and
lifetime bookkeeping without silently forgetting non-reuse guarantees or accumulating unbounded payload archives.
Define exhaustion/overflow and request supersession behavior. Exact key representation and bounded bookkeeping are
implementation details; timestamps or a reused JSON-RPC ID do not establish request identity.

Support partial response maps. Remaining unanswered requests stay outstanding and input_required is not prematurely
cleared. Validate all active entries before atomically admitting that submission's active batch. An invalid active
entry must not partially consume other valid entries. Ignore unknown, answered and superseded keys, including when
mixed with active responses, without applying them, replacing accepted answers or invoking their content validators.
Still validate overall envelope/access/size safety: ignored entries cannot evade finite parsing/work/input bounds.
Define empty/all-ignored acknowledgments and safe terminal/unavailable outcomes explicitly under the extension.

### Approved validation and continuation direction

McpInputResponses::validate currently requires exactly all request keys. Reuse form/schema/action validation via a
deliberate Task-specific adaptation; do not globally relax that contract or route durable Task answers through the
ordinary opaque-state retry flow. Preserve accept-only content validation and typed decline/cancel distinctions.
Private runtime-rule errors must not become client-facing diagnostics. No arbitrary PHP object deserialization or
client-supplied validation rule execution is introduced.

Atomically record accepted answers and coherent outstanding-request/state changes before acknowledgment, using the
shared lifecycle concurrency mechanism. Concurrent identical/conflicting answers have one admission outcome; losing
or repeated submissions cannot replace accepted input, redispatch it or reopen terminal state. Expose accepted input
through an authorized continuation contract, with Commands owning any consumption/admission mutation and Queries
remaining read-only. Document how consumers observe accepted answers, distinguish acceptance from execution and
reconcile uncertain effects. A read/acknowledgment is neither execution receipt nor proof that work continued.

Consumers own scheduling, continuation meaning, business authorization and external-effect reconciliation. No Common
worker/outbox/automatic retry engine or exactly-once effect promise follows. Define failures before/after durable
admission, consumer failure and response loss. A failed or uncertain continuation cannot restore consumed confirmation
or authorize blind redispatch. If post-commit safe facts are emitted, subsequent delivery failure leaves accepted
state durable and recoverable under current permission; full answers/forms/private bindings stay out of general feeds.

### Approved destructive-confirmation direction

Bind neutral caller, Task, operation/original arguments, request contract, confirmation group and expiry. Consumer
policy decides destructiveness and required approval meaning; Task-read access is not affirmative permission.
Partial affirmative responses never authorize destructive continuation. Every required confirmation must accept;
any decline/cancel retires that confirmation group without destructive continuation, including races with other
acceptances. Retirement must not silently become whole-Task cancellation or erase unrelated input groups.

Use a durable single-use admission boundary before affirmative continuation, with full binding and current checks.
Failure/disconnect after acquisition cannot restore or automatically retry a consumed confirmation. Reuse existing
confirmation invariants, not an assumed second consumer store or unproven cross-store atomicity. Existing
McpConfirmationStore/stateless consumers remain compatible; ordinary stateless tokens remain deliberately replayable.
Exact adaptation is implementation design, with explicit evidence for all changed public behavior.

Ordinary decline/cancel remains typed input for consumer interpretation. Neither ordinary refusal, confirmation
retirement nor tasks/update acknowledgment proves cancelled status, worker completion or business approval.

## Validation and permissions

Reauthorize producer issuance, request disclosure, answer admission and continuation at their applicable boundaries.
Task-read permission, prior request/answer, human permission, capability declarations and SUPER_ADMIN labels are not
mutation grants. Check current scope/binding before protected response validation or disclosure; conceal denied/unknown
Task state, request definitions, accepted content and private diagnostics. A caller must not answer another caller's
confirmation or transplant a response across Tasks/operations/contracts/groups.

Validate active form actions/content against retained server-authored contracts; bound keys/maps, messages, schemas,
private context, answers, storage and encoded output including escaping/multibyte data. Oversized input/output rejects
safely without silent request truncation or partial batch acceptance. Retention/unavailable state follows TASK-00166;
no late answer recreates removed/expired work or invents a reason for absence. Reconcile actual DBAL transaction ownership:
reject unsupported enclosing transactions before mutation, never touch unrelated caller work or treat savepoint release
as durable acknowledgment. Exact limits/schema/atomic mechanisms remain documented implementation details.

## Acceptance criteria

- [ ] Real trusted issuance → reconstructed shared Query → partial/full response admission → protected consumer
  observation/outcome works on SQLite/MySQL/PostgreSQL through production handlers/adapters, not a second store.
- [ ] Lifetime keys cannot be reused for different requests; repeated rounds/supersession/retired payloads and bounded
  bookkeeping/exhaustion are qualified without silently forgetting identity guarantees.
- [ ] Partial, empty/all-ignored, mixed active/ignored, invalid and oversized submissions behave as documented. All active
  validation precedes atomic batch admission; ignored entries neither execute nor bypass envelope/access/bounds checks.
- [ ] Concurrent duplicate/conflicting responses admit once and preserve accepted answers/outstanding state. Late input
  racing completed/failed/cancelled producer outcomes cannot reopen terminal state or double-apply accepted input.
- [ ] Confirmation binding, partial acceptance, any-refusal group retirement, expiry and single-use acquisition prevent
  unauthorized destructive continuation. Failure after admission never restores consumed confirmation.
- [ ] Current issuance/read/admission/continuation permissions, revocation, cross-scope substitution and protected
  validation material are safe; no raw rule/exception diagnostics or general-feed full-state/answer disclosure occurs.
- [ ] Pre-commit rollback, uncertain acknowledgment, unsupported enclosing transactions and post-commit delivery/consumer
  failures preserve truthful durable state without touching unrelated caller work or claiming exactly-once effects.
- [ ] Real tasks/update method handling checks per-request capability, validates bounded parameters, delegates to shared
  Commands and returns correct safe acknowledgment/errors without advertising partial extension support.
- [ ] Existing ordinary stateless replay and exact-key validation remain unchanged; existing destructive-confirmation
  refusal/binding/consumption behavior stays compatible. Supported forms do not expand into URL/arbitrary requests.
- [ ] Compatibility/schema classification, docs/CONTEXT.md, exact owned-code coverage and full ./bin/build pass with
  retained evidence. Final combined Tool-start HTTP proof remains explicitly owned by TASK-00168.
