# Introduce DBAL unit of work and separate execution transaction mechanics

## Outcome

Provide `Adapter/Persistence/Doctrine/DbalTransactionalUnitOfWork` implementing the existing Application
`TransactionalUnitOfWork` without an ORM dependency. Migrate execution recording/removal to that contract and
separate reusable DBAL transaction mechanics from execution-specific serialization. Normally one refactoring PR.
John approved this bounded direction on 2026-11-02; the architecture review inspected `77237f6741af`.

## Scope

- Inspect `Application/Repository/TransactionalUnitOfWork`, `Application/Mcp/Execution/RecordingTransaction`,
  `Adapter/Mcp/Execution/Dbal/DbalRecordingTransaction`, its four repositories, ObservationRecorder and DetailRemover.
- Use the existing inward contract directly; remove the provisional empty RecordingTransaction interface after
  migrating owned callers. Keep execution repositories separate and Domain-owned.
- Implement DBAL transaction ownership, callable-result propagation, exception cleanup, closed-state behavior,
  rejection of caller/nested transactions and truthful uncertain begin/commit/rollback outcomes.
- Keep execution's version-row serialization before admission/lookups and through actual commit. Participating
  repositories share the same connection/ownership boundary; they cannot accept unrelated active transactions.
- Isolate execution lock/schema validation and capability-specific storage failure translation at an explicit
  adapter-owned seam. A cohesive bounded implementation/composition choice is allowed; no table names, raw SQL,
  mode flags or generic options bags may enter handlers or the public Application transaction contract.
- Do not retain an execution transaction facade that merely renames the generic capability. Any remaining
  execution adapter collaborator must own real lock/schema/failure behavior, not forwarding alone.
- Preserve current `ObservationStorageFailed::outcomeUncertain()` and post-commit failure meanings. Inspect actual
  source and tagged promises before selecting failure translation; do not classify lost acknowledgment as rollback.
- Update composition examples, tests, deliberate public/internal classification and affected execution/transaction
  documentation, CONTEXT and CHANGELOG. Use descriptive collaborator names throughout changed code.
- Out of scope: ORM adapter replacement, nested/savepoint support, combining execution with unrelated business
  transactions, schema/data-format changes, outboxes, retries or exactly-once delivery promises.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Producer records admitted session/phase/detail evidence | RecordSessionObservation, RecordPhaseObservation, RecordProtectedDetail | Existing reads unchanged | ObservationRecorded after commit | Same atomic subject/evidence/content writes and retry behavior. |
| Authorized operator removes protected content | RemoveCapturedDetail | Protected reads unchanged | No new event | Same serialized removal, retained identity and retry-restoration rejection. |
| DBAL transaction callback succeeds or fails | N/A; infrastructure capability | N/A | N/A | Commit once or clean up owned work; return result or truthful failure. |

## Validation and permissions

Admission still precedes concealed lookups under serialization, including retries. Read/removal grants remain
independent. Rejected caller transactions leave unrelated work untouched. No transaction API grants permission,
and no external delivery occurs merely because commit succeeded.

## Acceptance criteria

- [ ] DbalTransactionalUnitOfWork uses DBAL Connection, implements the existing contract and needs no EntityManager.
- [ ] Execution handlers/coordinators inject TransactionalUnitOfWork rather than a replacement inward subtype or alias.
- [ ] Four recording repositories retain shared-connection ownership and actual-commit atomicity with required locking.
- [ ] Caller/nested transactions reject before owned work; callback failures roll back only owned work and preserve intended throwable categories.
- [ ] Uncertain outcomes close the boundary without claiming absence; fresh connections can reconcile committed data.
- [ ] Matching retries, protected-removal races and post-commit event/failure behavior remain unchanged.
- [ ] Focused product evidence, current wiring/docs and full-gate evidence exist without new generic setup obligations for use-case callers.
