# Add Lexical E.164 Phone Numbers

existing SMS APIs. Deliver the strict lexical value, optional adoption/preserved addressing evidence, public
classification and documentation together in one independently reviewable PR under

## Scope

- In scope: final immutable Domain/Value/Internet/E164PhoneNumber with named fromString construction and existing
  Value/ValueObject equality, hash, exact string and JSON representation/reconstruction conventions.
- In scope: whole-string leading-plus/nonzero-first-ASCII-digit grammar with at most fifteen total digits,
  predictable DomainException rejection and no arbitrary minimum or automatic local-number conversion.
- In scope: direct normal/boundary/failure/value evidence; optional explicit toString adoption through existing SMS
  message/factory/service and controlled transport/provider translation; preserved non-E.164 string addressing.

  accepted need, new dependencies, live sending/provider qualification and packaging/release-process tests.

## Validation and permissions

The approved lexical grammar is equivalent to `\A\+[1-9][0-9]{0,14}\z`: one plus, a nonzero first ASCII digit,
then zero to fourteen ASCII digits, with no other bytes. The fifteen-digit bound excludes the plus. Retain data as
strings, never numeric casts or native-integer phone representations. Do not trim whitespace, strip separators,
convert a national prefix, infer a country or otherwise silently repair malformed input.

Reject empty/plus-only input, a leading zero, missing/double/embedded plus, letters, Unicode digit/lookalike forms,
whitespace/control bytes, punctuation, extensions and sixteen-or-more digits with DomainException. Unprefixed
short codes and alphanumeric sender IDs are not E164PhoneNumber values but remain supported by the existing string
SMS boundary. A short plus-prefixed sequence satisfying the grammar is accepted: no arbitrary minimum length or
number-assignment rule is added to distinguish it. The value promises lexical form, not an assigned or dialable number.

fromString/toString/JSON reconstruction retains the accepted string exactly; equality/hash follow the existing
same-concrete-type string conventions. Optional adoption calls toString explicitly before invoking string-based
SMS APIs. Preserve SmsMessage constructor/create/getTo/getFrom, SmsFactory::createMessage and SmsService signatures,
body/media behavior and provider addressing translation. Existing strings such as a leading-zero international-like
form are not newly rejected by SMS simply because the new value would reject them.

Lexical validity is not permission to contact, expose or trust the number and does not establish SMS capability.
Validation/encoding is not redaction; HTTP/App failure presentation remains separately owned.
