# Deprecate released public properties in favor of getters

## Outcome

Consumers of Fight Common's released runtime values can read their state through typed getter methods instead
of public properties. Deprecate the old direct-property interfaces without breaking existing consumers during
the project's compatibility window. John explicitly requested this chore after the TASK-00147 public-property
inventory and then excluded the entire `Standards` namespace from the changes.

This is a standalone additive/deprecation chore, normally one PR. It covers **50 public readonly properties in
14 runtime classes**, whose source files were unchanged between tag `v1.4.0` and the inventory baseline
`1109832e9da1cba168e17a240d717798afaa3dc2`. It does not remove those properties or claim private backing yet.
Deprecated public APIs remain supported for at least one released minor before removal in the next major,
as required by the [project profile](../agents/project-profile.md#identity-and-architecture). The implementation
must record the actual first deprecating release when known; do not infer eligibility merely from a tag or assume
a future version number. Actual property removal/private conversion belongs to a separately authorized change.

In scope:

- Add one typed, side-effect-free getter per listed property, with a documented old-property → new-method map.
  Use the owning class's conventions consistently; preserve return types, nullability, immutable object identity,
  array value semantics and existing security/presentation boundaries. Do not add duplicate naming aliases.
- Mark the direct-property APIs deprecated in source API documentation and consumer migration guidance, naming
  the corresponding getters and the supported deprecation/removal window. This is not runtime warning emission.
- Migrate owned runtime callers, relevant examples and ordinary tests to getters. Retain deliberate compatibility
  tests for legacy reads; distinguish remaining legacy-contract probes from missed application call sites.
- Keep the same public readonly storage during this additive stage; getters delegate to that state. Preserve
  constructor/named-argument/factory APIs, validation, defaults, direct reads, object/array serialization and wire
  shapes. No duplicate state, magic-property bridge or visibility change is needed to introduce getters.
- Align relevant API manifest entries, component docs, CONTEXT and deprecation/release notes with actual behavior,
  without claiming a release has shipped.

Out of scope:

- **The entire `Fight\Common\Standards` namespace**, including
  `RequireTypeDocCommentSniff::$strict`, its ruleset/XML configuration and corresponding documentation. John
  explicitly excluded Standards; no exception decision or configuration migration blocks this chore.
- Unreleased Execution properties and message repairs owned by [TASK-00147](00147-TASK.md); unrelated test-double
  state; changing validation, authorization, redaction, size limits or business behavior.
- Private conversion/removal of released properties, breaking serialization or constructor changes, automatic
  runtime deprecation notices, new setters, packaging/release-process tests, release certification or publication.

## Validation and permissions

No new request actor, route, authorization capability or database schema is introduced. Existing factories and
constructors continue rejecting invalid input exactly as before. Getters must not bypass validation, expand safe
HTTP response data, leak OAuth claims into presentation/logging, alter token acceptance or change MCP limits.
Array-valued reads must retain the established copy/snapshot behavior; getter use cannot open a mutation path.
No data migration or rollback protocol is required for additive methods; removing callers' use of a getter remains
possible while the original public interface is still supported.
