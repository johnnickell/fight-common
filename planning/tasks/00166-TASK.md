# Record and retrieve durable asynchronous Task state

## Outcome

Consumers can create a durable asynchronous Task handle, report trusted progress/outcomes and retrieve currently
authorized state through shared Commands and Queries. Deliver an actual reusable application lifecycle with DBAL
persistence and reconstruction across processes, not interfaces awaiting a later storage TASK. This is the first
approved slice of [TICKET-00049](../tickets/00049-TICKET.md); it has no unfinished implementation blockers.

The lifecycle supplies input/cancellation implementations under TICKET-00050/00051 and the later complete MCP
activation in TASK-00168. It does not wait for those consumers or advertise an incomplete protocol extension.
A Task is not a consumer job, Workflow, planning TASK, review verdict or execution authority.

## Scope

- In scope: typed lifecycle/state/payload contracts, routed creation and trusted-update Commands, authorized current-state
  Query, actual DBAL schema/storage on SQLite/MySQL/PostgreSQL and explicit runtime composition.
- In scope: all five states, outstanding-input storage, original result/error semantics, timestamps, TTL/polling metadata,
  independently supplied current permissions, atomicity, retry/concurrency and safe bounded projection.
- In scope: compatibility/schema classification, documentation/CONTEXT.md, meaningful tests, exact coverage and full build.
- Out of scope: protocol activation/Tool return changes (TASK-00168), authorized removal (TASK-00167), client input admission
  and cancellation intent (TICKET-00050/00051), optional live delivery (TICKET-00052) and consumer UI/deployment.
- Out of scope: workers/schedulers, mandatory outbox/Event Store/projection, job execution/exactly-once external effects,
  automatic recording into the general notice feed, new permissions/identity issuer or authoritative Workflow state.

## Use cases and contracts

Operation names are responsibilities, not final PHP APIs. Preserve `CommandBus::execute(): void`, `QueryBus::fetch()`
and `EventDispatcher::trigger()`. Use an application-generated sufficiently unguessable identity supplied before
creation, separate from the originating JSON-RPC request, job and planning identity. Generation/possession grants nothing.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|

| Trusted producer reports progress/outcome | Record validated transition | Internal state/admission checks | Safe post-commit facts where defined | Atomically replace permitted state and corresponding payload without reopening terminal state |

### State, persistence and outcome contract

Support working, input_required, completed, failed and cancelled, with state-owned invariants rather than handlers
reconstructing policy from getters. Store status-specific payloads atomically with state; readers cannot observe a
terminal state paired with a previous or missing required result/error. Retain input maps for later supported admission
without implementing client tasks/update here. TICKET-00050 owns input-key lifetime/admission mechanics and confirmation
reuse; it must integrate with these invariants rather than create a second state store.

Preserve the original operation's protocol semantics: completed includes Tool results with isError:true; failed carries
a safely mapped JSON-RPC execution error, not any arbitrary business failure or exception string. Store sufficient
operation/contract context to validate the eventual result against the originating contract without re-executing work
or silently interpreting it against an unrelated changed definition. Exact representation remains implementation design.
Safe projection may reject disclosure; it must not fabricate a successful empty result or relabel business outcome.
Status, input, results and errors may each contain protected information; safe identifiers do not make them public.

Use direct reusable DBAL persistence/read adapters on real SQLite/MySQL/PostgreSQL, not an asynchronous projection or
mandatory Event Store. Bound input maps, status/result/error data and stored representation; current-state reads are not
history/list endpoints. Preserve source-independent creation/update timestamps and coherent metadata; timestamps alone
are not concurrency fences. Define a race-safe state/version mechanism so stale progress/input/outcome updates cannot
overwrite newer incompatible state or reopen a terminal winner. Consumers provide evidence for outcomes; silence,
disconnect, TTL or a handle alone cannot establish execution, cancellation or business success.

Creation acknowledgment follows actual durable commit and reconstructable state. Reconcile TransactionalUnitOfWork
with the selected DBAL connection; a separate ORM unit of work does not automatically enlist DBAL writes. Reject
unsupported enclosing transactions before writes, do not commit/roll back unrelated caller work, and do not equate
savepoint release with durable commit. Qualify rollback/commit failures and uncertain response loss. No transaction
with an external job system or automatic dispatch guarantee is introduced.

Define creation/update identity binding, same-content retry versus conflicting reuse and comparison lifetime, including
concurrent retries. Recheck admission on repeats. Do not derive business idempotency from a JSON-RPC ID, keep unbounded
hidden payload copies or promise exactly-once consumer effects. TASK-00167 later removes retained comparison material;
these contracts must allow truthful loss of retry guarantees without silently recreating removed work.

TTL is the extension's duration from creation, in integer milliseconds or null for unlimited; polling advice is optional
integer milliseconds. Validate supported ranges/overflow, changes and absence without inventing zero/default meanings.
Document logical availability versus physical deletion. A read never performs cleanup, renews retention or cancels work.
This TASK defines truthful available/unavailable outcomes; TASK-00167 owns public bounded removal. Consumers select
retention policy/schedules. Expiry, storage failure and missing data are not interchangeable or proof of a job outcome.

Safe lifecycle facts, if defined, follow actual commit through existing dispatch contracts. Later dispatch/subscriber
failure cannot erase state or masquerade as rollback. Full result/error/input bodies must not leak through generic
facts/diagnostics or enter the general retained notice feed. No outbox/replay/completeness promise follows.

## Validation and permissions

Consumer composition supplies trusted scope, caller/producer context and independent creation/update/read decisions.
Recheck current permission for each operation, including repeats and every read after reconnect. Handle possession,
client capability declarations, human access, intended recipients and SUPER_ADMIN labels grant nothing. A producer
update is not a public generic status setter; reading a Task does not authorize changing it.

Validate identity, transitions, status-specific payloads, original result/error contracts, TTL/timestamp/polling fields
and finite input/output bounds before mutation/disclosure. Protect input and final payloads independently where policy
requires; denied/unknown/cross-scope outcomes must not reveal concealed data, private conflict values or exceptions.
Keep storage failure explicit rather than returning empty/missing success. Consumer-safe projection is required;
JSON validity alone is not redaction. Exact APIs, schema, limits and failure mapping remain implementation details.
