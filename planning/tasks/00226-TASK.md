# Remove deprecated contracts and migrate their supported replacements

## Outcome

Consumers can move off eligible deprecated contracts without accidentally losing supported canonical replacements.

## Scope

Build a tag-linked removal inventory before deleting. Work in component batches, including old MCP spellings, property reads, table constants and earlier eligible deprecations. The strict construction TASK owns permissive `Pagination` and `ResultSet` construction. Preserve non-deprecated APIs and dependency floors. No consumer-owned migration or release execution.

## Use cases and contracts

A consumer integrator replaces old imports, configured identities and calls; consults migration guidance for saved objects, workers and data. No new commands, queries, events or permissions; canonical operations retain their promises.

## Validation and permissions

Verify an actually released deprecation window per item, canonical declaration/alias ownership, retained behavior and any storage or service-wiring consequences. Hold unresolved eligibility rather than inferring removal authority. Do not run consumer-data migrations.

## Acceptance criteria

- [ ] Inventory identifies each removal, released deprecation, exact replacement or no replacement, and consumer hazard where relevant.
- [ ] Canonical contracts, manifest and representative consumer wiring or saved-data checks pass; changed behavior is documented for TASK-00229.

## Verification and evidence

Run focused contract and consumer checks plus `./bin/build` with exact Unit coverage. Preserve the baseline diff and evidence per component.

## Coordination

Coordinate shared manifest changes with TASK-00220. If a component needs an independently delivered follow-up, obtain scoped planning approval rather than hiding it in this batch. Branch `feature/task-00226-remove-deprecated-contracts`; PR title `TASK-00226 — Remove deprecated contracts and migrate their supported replacements`.
