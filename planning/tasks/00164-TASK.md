# Follow authorized Prompt catalog changes through MCP

## Outcome

Clients explicitly requesting Prompt catalog changes receive authorized standard notifications through the working
live MCP path when the real Prompt capability is composed and enabled. Deliver optional Prompt registration/list/get
→ recorded safe change → live notification integration in one normal PR, without constructing Prompt bodies to notify.

John approved this third slice completing [TICKET-00047](../tickets/00047-TICKET.md)'s decomposition. Its blockers are
[TASK-00162](00162-TASK.md) for live delivery/tracking/recovery and [TASK-00157](00157-TASK.md) for actual Prompts.
[TASK-00163](00163-TASK.md) subscriber inspection is independent. Ordinary Prompts and Tool/Resource subscriptions
retain no reverse dependency on this integration.

## Scope

- In scope: optional `promptsListChanged` support, truthful flags/acknowledgment, explicit permitted retained-change
  mapping, current Prompt-notification authorization and actual live HTTP composition with list/get and other families.
- In scope: metadata/body/provider non-disclosure, generic tracking compatibility, bounded output, safe failures,
  compatibility, docs/CONTEXT.md, relevant integrated evidence and full local verification.
- Out of scope: Prompt content execution or automatic retrieval, new Prompt/catalog database, polling policy/store,
  Prompt-specific subscriber Queries, new filter vocabulary, Task notifications, Mercure or consumer deployment.
- Out of scope: automatic change detection/guaranteed recording of every catalog change, protected bodies/arguments,
  templates/Completion, receipt/processing proof, remembered subscriptions or a reverse Prompt-serving dependency.

## Use cases and contracts

Labels express responsibilities, not final PHP APIs. Reuse TASK-00162's actual subscription transport/lifecycle and
shared notice Queries rather than a second source or authorization policy. Business recording remains an explicit
separate Command owned by TASK-00158; protocol notification is not a new authoritative domain event.

### Approved optional integration mechanics

Compose with the actual TASK-00157 Prompt catalog/providers and TASK-00162 subscription path. Advertise list-change
support only when that combination is enabled and can honor it. A request without `promptsListChanged: true` receives
no Prompt change notifications. An absent/disabled family is not acknowledged as supported. Mixed Tool/Resource/Prompt
filters retain requested-subset semantics; no caller's request enables a missing capability or grants authority.

Keep acknowledgment first, exact standard subscription ID correlation and ordinary graceful closure. Reuse the generic
requested/accepted tracking representation and finite stream/frame/resource limits; do not require TASK-00163 to add
Prompt-specific presentation or create a new lifecycle store. Qualify registry flag composition without loosening
validation for unrelated/unsupported families. Existing subscription-free Prompt list/get remains fully usable.

Translate only explicitly mapped, safe retained changes into the standard catalog-change signal. Consumer composition
owns catalog mutation/change capture and safe source metadata. This does not automatically monitor every provider or
promise that every catalog/access change produced a notice. A permitted signal is not a full Prompt revision, body,
argument set, permission grant or guarantee that the next retrieval returns identical data.

Recheck current authority for the notification itself immediately before emission, including queued changes. Generic
family availability or permission to retrieve some Prompt does not authorize revealing concealed catalog activity.
Honor TASK-00157's current discovery/retrieval access boundaries without constructing bodies, invoking content providers
or automatically fetching linked Resources. Later list/get requests independently authorize; prior listing or a
notification is not a grant. No new principal, SUPER_ADMIN policy or human-to-Agent permission implication.

## Validation and permissions

Reuse the actual subscription filter, source and bounded presentation contracts. Validate mapped notice shape and
supported Prompt family, preserve standard method/metadata spelling and exact request-ID type. Enforce finite encoded
JSON/SSE frames including escaping and metadata. Unsupported/malformed input or mapping/provider/policy failure must
not become a misleading successful notification or private diagnostic leak. Use the live path's documented safe
closure/failure behavior; do not emit arbitrary new notification types.

No Prompt body, concealed definition/name, supplied argument, credentials, protected Tool/output data or full Task
state enters generic notices/stream metadata. Structural validation is not universal redaction; consumers still own
source metadata selection. Inspection policy remains separate. Delivery failure leaves recorded notices intact and
recovery uses TASK-00161 rather than claimed stream replay or processing acknowledgments.
