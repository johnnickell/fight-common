# Atomically resume destructive MCP confirmations

## Outcome

Deliver the complete destructive-confirmation use case over TASK-00111's protected interaction envelope. A
consumer-designated destructive Tool may request confirmation only from a capable client, and a valid affirmative
retry atomically consumes consumer-stored state before `resume()`. Replay, concurrent double resume, and reuse after
any acquired resume outcome fail closed without a second business dispatch.

## Scope

- In scope:
  - A destructive-confirmation mode over TASK-00111's versioned-AEAD caller/Tool/original-argument/requested-key/
    schema/expiry bindings and its static capability and current-availability gates.
  - A minimal Application-owned port for a consumer-provided atomic one-time interaction store. Its operation must
    acquire-and-consume exactly one matching unexpired confirmation without a read-then-delete race.
  - Confirmation issue/resume orchestration that first reevaluates current availability before restored-state
    disclosure or response validation, persists no Common business policy, and atomically consumes one exact state
    before affirmative `resume()`. Once consumed it is never restored after success, decline/cancel, expected
    rejection, `Throwable`, cancellation/disconnect, or response-construction failure.
  - Keyed `ElicitResult` envelope/key/action validation, accept-only restricted-schema content validation, safe
    `decline`/`cancel` behavior, invalid/tampered/expired/mismatched state rejection, already-consumed and
    replay rejection, and deterministic contention behavior when retries race.
  - Package-owned destructive mutation fixtures, atomic-store contract tests, integrated semantic transcripts,
    TICKET-00026 acceptance reconciliation, compatibility-manifest classification, and consumer documentation.
- Out of scope:
  - Deciding which actions are destructive, confirmation language or business policy, authorization, principal or
    permission models, store technology/retention/operations, distributed transaction guarantees, rollback, durable
    task lifecycle, route/session ownership, OAuth resource-server behavior, or framework-specific UI.
  - Replacing the consumer store with `NonceRepository`, `MutableCache`, an HMAC nonce, a process-local check, or a
    non-atomic get/delete sequence.
  - Retrofitting one-time semantics onto TASK-00111's ordinary additional-input mode.

## Validation and permissions

The consumer explicitly selects confirmation mode and supplies both the neutral caller-binding value and an
implementation of the atomic store port. Common supplies only interaction mechanics and MCP representation. It
does not infer destructiveness, evaluate authorization, resolve a principal, define approval language, or make
consumer business decisions.

Retry first applies TASK-00111's bounded opaque-state processing solely to identify the candidate Tool, then current
availability/concealment before restored-state disclosure or response validation. Next validate keyed `ElicitResult`
envelopes, expected keys, and actions; validate restricted-schema content only for an affirmative `accept`. An
affirmative retry atomically acquires and consumes the exact bound state immediately before `resume()`.
`decline`/`cancel` atomically retire it and return terminal safe interaction output without `resume()` or destructive
dispatch. Once acquisition succeeds, state remains consumed after expected failure, `Throwable`, transport-neutral
cancellation/disconnect, or response-construction failure; automatic retry/rollback is forbidden.

The store contract must distinguish successful acquisition from absent, expired, mismatched, already-consumed, and
contended state internally while preserving one safe public rejection shape where detail would aid replay or
enumeration. A store failure fails closed. Neither authentication credentials nor HMAC nonce state may become an
interaction key, and no new generic permission or principal abstraction enters Fight Common.

## Acceptance criteria

- [ ] A consumer-designated destructive Tool can issue a confirmation only after TASK-00111's static capability gate
  before `handle()`, with protected state bound to caller, Tool, original arguments, requested keys/schema,
  confirmation mode, and expiry; every retry reevaluates current availability before restored-state disclosure.
- [ ] The consumer-provided store exposes and proves one atomic acquire-and-consume operation; no Common adapter or
  fixture implements confirmation with a racy read-then-delete sequence.
- [ ] A valid affirmative retry validates its keyed `ElicitResult` envelope/keys and accept-only restricted content,
  atomically consumes the exact matching state before `resume()`, and dispatches the destructive command at most once.
- [ ] Once acquired, confirmation state remains consumed after success, expected rejection, unexpected
  `Throwable`, a transport-neutral cancellation signal before/during resume, stream-closure simulation, or response-
  construction failure; Common performs no automatic retry or rollback.
- [ ] A valid `decline`/`cancel` response contains no accept-only content, atomically consumes/retires the
  confirmation, returns safe terminal output, and calls neither `resume()` nor a destructive bus; invalid action/
  content or missing/extra-key combinations fail closed without consuming a different state.
- [ ] A Tool revoked between rounds is concealed as unknown before restored-state disclosure, response validation,
  store acquisition, `resume()`, command, query, or event dispatch.
- [ ] Tampered, expired, caller-mismatched, Tool-mismatched, argument-mismatched, replayed, already-consumed,
  store-failed, and concurrently losing retries all fail closed before `resume()` or bus dispatch.
- [ ] Concurrent retry evidence proves exactly one winner and at most one command/event side effect without relying
  only on a sequential mock; public errors disclose no store, caller, Tool, argument, or policy detail.
- [ ] HMAC authentication/nonces, Bearer authentication composition, ordinary interaction behavior, command/query
  contracts, and consumer authorization policy remain unchanged.
- [ ] Every public addition is classified in `compatibility/manifest.json`; TASK-00111 and this TASK together cover
  every TICKET-00026 requirement with behavior-focused compatibility evidence.

## Verification and evidence

Use focused contract tests for atomic acquire-and-consume semantics, expiry and binding comparison, keyed response
envelopes/actions, accept-only content, decline/cancel, retry-time availability revocation, already-consumed/replay
behavior, store failure, and a coordinated concurrent race with exactly one winner. Pair Tool, command-bus, event,
store, and diagnostic spies to prove consumption precedes `resume()` and no
loser or invalid request dispatches. Prove that an acquired state remains consumed when `resume()` returns an
expected error, throws unexpectedly, or final response construction fails. Use a transport-neutral cancellable
reporter/fake, not an HTTP/SSE adapter, to signal cancellation after atomic acquisition both before and during a
fixture's `resume()`. In both cases prove the exact state remains consumed, no automatic retry occurs, and no later
contender dispatches; when cancellation arrives before `resume()`, prove no `resume()` or bus dispatch occurs.

Exercise the complete confirmation behavior through the semantic dispatcher and central responder. Before evidence
is TASK-00111's versioned-AEAD ordinary retry with no one-time store. After evidence is a transcript/race matrix for
confirmation request, affirmative success, decline/cancel, invalid action/content, replay, concurrent contention,
revoked-between-rounds, expiry, every binding mismatch, store failure, and both cancellation points, plus unchanged-
authentication evidence. Save artifacts and the complete `./bin/build` log and
independently captured exit under the TASK's ignored run directory. This library change has no useful visual UI.
