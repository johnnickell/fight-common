# Establish MCP protocol semantics and truthful capability discovery

## Outcome

Establish the framework-neutral MCP `2026-07-28` semantic model, central responder, server identity, and
capability registry. A configured consumer can obtain truthful `server/discover` output, semantic capability
dispatch, and deterministic protocol failures without exposing an HTTP endpoint or creating an implicit
pass-through security policy. This shared foundation is the explicit prerequisite for the guarded endpoint and
later Tool capability.

## Scope

- In scope:
  - Framework-neutral MCP request, per-request metadata, server identity, capability registration/dispatch, and
    response/error contracts in the Application layer.
  - MCP `2026-07-28` JSON-RPC parsing and validation, inline protocol-version negotiation, `server/discover`,
    truthful capability advertisement, deterministic method dispatch, and centralized protocol errors.
  - Composition-time rejection of missing server identity, duplicate methods, or contradictory capability
    advertisement, plus package-owned capability fixtures that prove future capabilities can register without
    expanding a tools-only dispatcher.
  - Capability-owned mirror declarations that let TASK-00105 validate later Tool-provided `x-mcp-header`
    requirements without coupling this foundation to TICKET-00024.
  - Additive compatibility-manifest classification and behavior evidence for every public declaration added by
    this TASK.
- Out of scope:
  - Any constructible PSR/native HTTP endpoint, direct HTTP JSON response, Origin policy, invocation limiting, or
    header/body mirror enforcement, which belong to [TASK-00105](00105-TASK.md).
  - `tools/list`, `tools/call`, tool schemas, validation, availability filtering, progress/SSE, cancellation,
    protected interactions, and OAuth resource-server support, which belong to later TICKETs.
  - Consumer routes, TLS/gateway configuration, authentication, principals, credentials, authorization policy,
    framework responses, and framework service-provider wiring.
  - Legacy MCP sessions, `initialize`, GET/DELETE endpoint behavior, and legacy HTTP+SSE compatibility.

## Validation and permissions

Validate JSON decoding, JSON-RPC version and id rules, method and outer-parameter shapes, supported MCP version,
and capability-specific outer parameters before calling a capability handler. The reusable protocol handler
implements `server/discover` and rejects unknown methods through the central responder; registered capability
handlers own only their declared methods. Per-request MCP metadata may carry protocol, method, correlation, and
declared transport-mirror information needed by Common, but it must not become an opaque principal or credential
carrier.

Server identity and capability registration are explicit consumer configuration. Duplicate method ownership,
missing identity, or advertised capabilities that do not match registered handlers fail composition. Application
authorization is intentionally N/A: consumer authentication and authorization run before or around Common, and a
capability invoked by this foundation owns no consumer policy. The generic foundation must not select a route,
authenticate a caller, resolve a principal, or invent permission strings.

## Acceptance criteria

- [x] A valid MCP `2026-07-28` `server/discover` request returns the configured server identity and capabilities
  derived from registered handlers; an unregistered capability is never advertised.
- [x] A valid supported method dispatches exactly once to its registered capability and returns one semantic
  MCP/JSON-RPC result independent of JSend, HTTP, and framework-native response classes.
- [x] Malformed JSON, invalid JSON-RPC, unsupported protocol versions, unknown methods, and invalid outer
  parameters are rejected without capability dispatch through the central responder, including protocol-faithful
  behavior when no usable request id exists.
- [x] Missing server identity, duplicate method ownership, and contradictory capability metadata fail during
  composition rather than producing a misleading discovery response.
- [x] Public MCP contracts contain no route, framework request/response, credential, principal, Agent, permission,
  or authorization-policy type, and existing JSend/HTTP/CQRS behavior remains unchanged.
- [x] No constructible HTTP endpoint or pass-through origin/invocation policy exists in this TASK; the first
  endpoint is the guarded composition owned by TASK-00105.
- [x] Every public addition is classified in `compatibility/manifest.json`, its promised operations are explicit,
  and its observable protocol behavior has a package-owned fixture.
