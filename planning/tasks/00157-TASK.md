# Discover and retrieve authorized MCP Prompts

## Outcome

Authorized callers can discover consumer-supplied Prompts and retrieve complete parameterized text/Resource-link
messages through the existing guarded MCP HTTP composition. Deliver explicit registration, current authorization,
protocol pagination, argument/output validation, bounded presentation and the complete list/get journey together.
This is the single approved vertical TASK completing [TICKET-00044](../tickets/00044-TICKET.md)'s decomposition under
[EPIC-00010](../epics/00010-EPIC.md), normally one PR rather than a partially usable discovery-only capability.

John approved this scope and the initial mechanics below. There are no unfinished blockers: reuse existing

## Scope

- In scope: explicit bounded catalog/definition and content-provider registration, authorized `prompts/list` and

- In scope: deterministic protocol catalog pagination, authenticated stateless continuation, truthful cache hints,

- Out of scope: additional-input round trips, system/developer roles, embedded Resource/document bodies, image/audio

  consumer Prompt authoring/UI, mandatory catalog database/template engine and actual client deployment qualification.

### Approved initial mechanics

- Explicit bounded catalog of consumer-supplied definitions and content providers. Validate identities, declared
  arguments, supported descriptive metadata and conflicting ownership. Listing does not construct Prompt bodies;
  invoke only the selected content provider after current authorization and successful argument validation.
- Prompt arguments are protocol string-valued fields, not Tool-style arbitrary JSON schemas. Enforce declared
  names/required arguments and finite count/name/value/total bounds. Missing required, undeclared, wrong-type and
  oversized arguments reject before content processing. Preserve valid optional absence and empty strings according
  to the declared contract rather than silently coercing values. Unsupported interaction state does not enable a
  multi-round-trip Prompt flow.
- Deterministic catalog ordering and stateless authenticated continuation tokens following existing discovery
  conventions. Apply current access before disclosure/pagination; bind continuation to the relevant visible catalog
  and serving parameters and safely reject stale continuation after relevant catalog/access changes. Tokens contain
  no concealed catalog or authority. Define start/end/restart behavior explicitly and prove bounded pages terminate
  correctly, including empty catalogs and an entry too large for its budget. No per-connection discovery history.
- Default private, zero-TTL listing metadata. Cache hints, Prompt identities and continuation tokens never authorize
  retrieval. Any supported override remains explicit consumer policy, not a cross-caller disclosure default.
- Reuse existing Resource metadata validation and bounded-result/central-metadata support. Validate complete output
  roles/content/link metadata and final encoded response bounds, including escaping and applicable protocol metadata
  and envelope overhead. Raw text length alone is insufficient. Existing `McpResult` bounded-result support does
  not itself bound the outer JSON-RPC envelope; qualify the actual composed response and document the budgets.
- Static instruction content needs no invented business Query. Application-backed providers use shared Query use
  cases through `QueryBus::fetch()`, not adapter SQL or duplicate permission policy. Consumer provider code is trusted
  application composition, not sandboxed remote execution. No content store or template engine is prescribed.

Return complete messages with only `user`/`assistant` roles and text/Resource-link content. Reject unsupported roles,
blocks or malformed metadata rather than dropping them and claiming completeness. Resource metadata must itself be
safe to disclose; its URI is not a grant or a request to fetch network/filesystem content. Subsequent Resource reads
retain their own current permission, independently of Prompt access. A Skill reference does not load/activate the
Skill. Hosts own message insertion, approval and model use; repeated retrieval promises no deterministic model result.

Compose through the current capability registry, semantic responder, guarded HTTP and consumer authentication/
resource-server seams. Registry recognition of Prompt methods is not their implementation. No second endpoint,
principal/token-issuer model or automatic activation of other capabilities. Keep list-change false/unadvertised;
TICKET-00047 owns optional future subscription integration. Ordinary HTTP/progress SSE is not that capability.

## Validation and permissions

Consumer composition supplies current authentication/access decisions; untrusted Prompt arguments and transport
metadata are not authority. Apply current availability independently to listing and direct retrieval. A caller need
not list before retrieving an allowed Prompt, and listing membership grants no continuing permission. Validate
outer request shape, declared arguments and finite bounds before provider processing; validate the complete result
before disclosure. Protect metadata/arguments as well as bodies and preserve application-level Query authorization.

Unknown/denied identities must not disclose hidden definitions, argument metadata or content through errors.
Provider/storage/availability failures cannot become successful empty catalogs or Prompts. Use current safe protocol
failure conventions and consumer redaction-aware diagnostics, never raw exception messages, credentials or protected
input/output. No business mutation Command or domain event belongs to serving instructions. Structural validation
is not universal semantic redaction or a guarantee that an instruction is safe for automatic execution.
