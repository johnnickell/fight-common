# Refresh Common's PHP runtime and documentation trust stores

## Outcome

Refresh Common-owned build environments to patched PHP and documentation TLS trust stores, with verified
actual runtime inputs rather than assuming a normal Docker build refreshes them. This is one bounded,
high-priority security maintenance PR, not a library-code vulnerability repair or consumer deployment.

John approved this concrete scope and live TASK creation on 2026-10-22 after the linked article was checked
against upstream advisories and the local images. Scope acceptance does not authorize implementation,
publication, release or deployment. No known TASK dependency exists. John subsequently invoked Build for TASK-00174 in the main checkout;
Work is authorized for scoped implementation and local verification, with independent stages dispatched separately.

## Diagnosis and reproduction

At clean checkout `47a7f58`, safe local diagnostics used existing Docker images with no repository mount,
no network, no pull and a read-only container filesystem:

```bash
docker run --rm --pull=never --network=none --read-only fight-common php -v
docker run --rm --pull=never --network=none --read-only fight-common-docs-python-3.13.7 \
  python -c 'import sys, certifi; from importlib.metadata import version; print(sys.version); print("certifi", certifi.__version__); print("pip", version("pip"))'
```

Observed on 2026-10-22:

- PHP **8.5.7**, built June 11, 2026; image
  `sha256:6331e2b7dbb95f58b8cbae1b8ed5bb9db5fee087f63b0b1c6082098ff080a283`.
- Python **3.13.7**, certifi **2026.07.22**, pip **25.2**; docs image
  `sha256:5ea16cfe7628a5e1fa6e75f821fcad45dde1c44bc010edb26565f1ef4e378838`.
- `etc/docker/php/Dockerfile` uses `php:8.5-cli`; `bin/build` builds without `--pull`, so a cached base
  can remain old. No exploit or fresh-build/cache reproduction was attempted.
- `etc/docker/python/requirements.txt` pins `certifi==2026.7.22`; its Dockerfile pins the Python base
  by digest. Pulling that same digest cannot refresh its OS or pip-vendored trust bundle.
- `composer.json` simulates PHP 8.5.4 for dependency resolution; this does not identify or patch the
  executing interpreter and is not itself the target of this repair.

Expected: the actual Common PHP build runtime is upstream PHP **8.5.12 or later on the existing stable
8.5 line**, or has explicit equivalent vendor patch evidence for both CVEs; documentation certifi is
**2026.10.19 or later**, with OS and pip-vendored trust stores separately checked and refreshed as needed.
A version-only claim about distro backports is insufficient.

Sources:

- [Original report](https://dly.to/ywMUdBWlrup).
- [PHP advisory and fixed releases](https://www.php.net/archive/2026.php): CVE-2026-109618 and
  CVE-2026-109619 affect request memory/error handling; patched 8.5 release is 8.5.12.
- [PHP Foundation explanation](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security).
- [Certifi advisory GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2):
  the installed/pinned version falls within the affected range; recommended fixed version is 2026.10.19.

Confidence is high in the two affected-version findings. This proves neither exploitability of Common's
isolated CLI jobs nor compromise. OS/pip-vendored trust-store contents still require direct inspection.
Consumer deployments and developer-host trust stores were not audited. Live/archive TASKs and their known
PR references had no matching repair owner at allocation; hosted issue/PR ownership was not queried.

## Scope

- In scope:
  - Patched Common PHP build image and a reliable base-refresh procedure for existing build entry points.
  - Updated documentation certifi pin and rebuilt docs image; inspect and refresh affected OS and
    pip-vendored trust bundles in Common-owned images, including the digest-pinned Python base as needed.
  - Minimal contributor guidance for refreshing/verifying those images and separately patching consumer
    web runtimes; preserve existing build/release boundaries and evidence requirements.
- Out of scope:
  - Product API changes, public PHP support-floor changes, broad dependency upgrades, or changing Composer's
    simulated platform merely to imitate a runtime update.
  - Consumer deployments, production restarts, host-wide incident response, secret rotation, new services,
    unrelated incidents from the article, release certification, signing or publication.
  - Exploit execution, TLS-verification bypasses, and new packaging/configuration tests in product suites.
