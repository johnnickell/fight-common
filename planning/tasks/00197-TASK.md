# Record executions in configurable tables

## Outcome

A consumer independently configures all five execution persistence tables, explicitly installs/validates the
selected schema and records/reconstructs executions through the existing recording and repository contracts.
Preserve transaction serialization, atomic related writes, retries and protected-content persistence. Deliver a
usable recording path, not a configuration-only foundation. This TASK normally owns one PR and supplies the real
configured recording path consumed by TASK-00198.

## Scope

In scope:

- Individual overrides with exact current defaults: `fight_execution_schema`, `fight_execution_sessions`,
  `fight_execution_phases`, `fight_execution_observations` and `fight_execution_contents`. Partial configuration
  intentionally leaves omitted tables at their current defaults.
- Execution schema definition, explicit install/validation/initialization, version checks, foreign-key/self-reference
  targets and index/constraint handling using the selected names, preserving consumer-owned unrelated schema.
- The execution recording transaction's state-table serialization/version check and all session, phase,
  observation and protected-content repository SQL, including lookup/reconstruction/retry and existing removal
  primitives. Generic DBAL transaction mechanics retain their existing owner and contracts.
- Reuse TASK-00194's safe Adapter identifier validation/quoting mechanism; minimally generalize its demonstrated
  Adapter seam if needed without coupling execution to an Event Store service or inward persistence contracts.
- Preserve existing construction/named-argument compatibility, versioned payloads, identity, usage provenance,
  relationships, timestamp precision, transaction outcomes and safe/protected data separation.
- Focused and real-platform evidence, recording composition documentation and affected CONTEXT.md alignment.

Out of scope: execution inspection reader conversion and complete query/removal/MCP journeys (TASK-00198), new
Commands/Queries/Events, qualified names, implicit global/environment configuration, mandatory prefixes, migrations,
automatic renames/data transfer, column/payload changes, stronger event delivery or unrelated architecture refactors.
Do not create temporary APIs or compatibility bridges for development-only intermediate snapshots.

## Use cases and contracts

Actors: consumer integrator/operator and existing trusted instrumentation producer. No table name enters through
an untrusted MCP request; configuration is an explicit composition concern.

| Use case | Commands | Queries | Events | Expected side effects |
| --- | --- | --- | --- | --- |
| Select some/all names and explicitly install/validate execution storage | N/A: composition/deployment, not a bus Command | Existing schema inspection | None | Existing installer creates/initializes selected storage when invoked; configuration alone performs no DDL |
| Record session, phase, observation and linked protected content | Existing recording Commands | Existing repository relationship/retry reads | Existing safe committed facts, unchanged | Atomically write related records under the selected execution state lock |
| Reconstruct records after reopening storage | No new Command | Existing repository reads | None added | Read selected data tables and preserve saved record meanings |
| Retry a recording or encounter transaction/storage failure | Existing recording operation | Existing identity/content comparison | Existing post-commit behavior, unchanged | Deduplicate same content, reject conflict, roll back confirmed failures and preserve uncertainty/recovery boundaries |
| Supply unsupported identifiers or change storage selection | N/A: composition | No new public Query | None | Safe rejection or different selected storage, never movement of old data |

## Validation and permissions

Apply the shared ordinary-name validation and platform quoting consistently to schema/runtime/relationship paths;
keep values bound separately. Reject unsafe, qualified or otherwise unsupported names without SQL interpretation
or default fallback. Exact configuration APIs, identifier grammar/limits and collision handling remain implementation
design within the accepted shared naming contract, not a second policy or global registry.

Consumers retain trusted producer admission, current scope/relationship checks, connection/schema choice and database
privileges. Configuration confers no recording, disclosure or removal authority. Preserve current partial/versioned
schema rejection, idle deployment connection requirements, caller/nested transaction rejection, rollback/reuse,
closure and uncertain-outcome semantics. A changed table selection neither proves old records absent nor reconciles
a lost commit acknowledgment. Preserve existing retry evidence and protected-content removal semantics.
