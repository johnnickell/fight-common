# Add Immutable JSON Snapshots

## Outcome

Consumers can opt into immutable JsonObject snapshots of mixed JSON-encodable input, reconstruct them through an
explicit snapshot-aware text boundary and access fresh mutable representations without changing the retained value.
Deliver construction, reconstruction, isolation/compatibility evidence and documentation together in one
independently reviewable PR under [TICKET-00033](../tickets/00033-TICKET.md) and
[EPIC-00008](../epics/00008-EPIC.md).

John approved this single feature TASK, its representation/failure contracts, additive reconstruction approach and
code-first testing clarification on 2026-10-06. There are no blockers or dependencies on TASK-00127 or TASK-00128.
No execution priority is assigned. Approval creates a planning record, not implementation or publication authority.

## Scope

- In scope: additive snapshot construction on the existing Domain/Value/Basic/JsonObject, provisionally
  `fromSnapshot(mixed)`, and additive snapshot-aware text reconstruction, provisionally `fromSnapshotString()`.
- In scope: detached construction-time JSON capture, fresh data/JSON outputs, stable string/equality/hash behavior,
  explicit native numeric precision, encoding-option policy, depth/Unicode/representation checks and failure contracts.
- In scope: strict separation from legacy factories/helpers, existing Doctrine compatibility evidence, preserved
  StrictJson/MCP evidence, API/behavior classification, docs/values.md and CONTEXT.md.
- Out of scope: changing legacy fromData/fromString/helpers in the minor, automatic Doctrine hydration or MCP
  migration, a new database type/schema, arbitrary-precision decimal JSON, general JSON canonicalization, semantic
  key-order-independent equality, retained PHP class identity/methods, arbitrary deep cloning, non-JSON state,
  redaction, sandboxing serializers, new runtime dependencies, packaging/release-process tests or certification.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer snapshots mixed JSON-encodable input | N/A; value construction | N/A; local JSON capture | N/A; no domain mutation | Capture scalars, arrays, ordinary objects and supported JsonSerializable output without retaining caller-owned mutable state. |
| Caller mutates original nested objects/references | N/A; caller-owned mutation | N/A; local value access | N/A; no domain mutation | Snapshot string/hash and equality against an unchanged comparison value remain stable. |
| Caller mutates data or jsonSerialize output | N/A; caller-owned mutation | N/A; local value access | N/A; no domain mutation | Future outputs are independent, including nested objects; retained snapshot meaning is unchanged. |
| Consumer imports snapshot JSON text | N/A; value reconstruction | N/A; local decoding | N/A; no domain mutation | Preserve object/list/scalar/null and supported native numeric types through the opt-in text factory. |
| Input cannot encode or independently reconstruct | N/A; value construction | N/A; no external read | N/A; no domain mutation | Reject predictably without partial output, lossy substitution or an accepted unusable snapshot. |
| Consumer serializer throws during capture | N/A; caller serialization | N/A; local invocation | N/A; no Common event | Preserve the original throwable; Common cannot undo caller-defined serializer effects. |
| Existing consumer retains legacy APIs or StrictJson | N/A; existing value capability | N/A; existing representations | N/A; no domain mutation | Preserve supported behavior without mandatory migration. |

Snapshot capture/access itself has no network or persistence effect and adds no business messages, query type or
event. Custom JsonSerializable code runs at construction and may have caller-owned effects. Reads must not invoke
that code again. This is not a guarantee of one callback per object identity when an object occurs repeatedly in the
input graph, nor a rollback/sandbox guarantee. The captured value represents JSON output, not PHP class identity,
shared-reference topology or non-JSON state.

## Validation and permissions

The approved representation/reconstruction contract is:

- Capture JSON during construction and independently reconstruct every mutable output. Use object-mode decoding
  so empty/numerically named objects remain objects, lists remain arrays, and scalars/null retain their kinds.
  Never rely on a shallow clone or copy-on-write arrays to detach nested mutable objects/references.
- Preserve native integers and finite floats, including the distinction between `1` and `1.0`. Deliberately establish
  and document native numeric precision, including capture/reconstruction under differing `serialize_precision`.
  Changes to ambient numeric formatting after capture must not change retained string/equality/hash. No arbitrary-
  precision decimal or recovery of precision already lost by the caller is promised.
- The snapshot-aware text factory rejects integer literals outside the native integer range instead of silently
  converting them to floats or strings. Document native float text conversion/normalization and supported limits;
  do not imply exact decimal lexemes or general preservation of source JSON whitespace.
- Use PHP codec depth 512 and verify both encoding and decoding boundaries. Reject any input whose captured
  representation cannot reconstruct under that limit, even if the encoder alone accepts it. Document the actual
  container-depth boundary rather than confusing the codec setting with a root-zero node-depth promise.
- Preserve zero-fraction floats. Allow only presentation-only encoding options on snapshot paths; reject controls
  that coerce types/shape or replace/omit invalid values. Document the supported option set and its effect on string
  representation/equality. Include encode/prettyPrint and outer json_encode behavior in the boundary assessment;
  caller-controlled outer encoding is not permission to mutate the snapshot or a guarantee against external lossy flags.
- Codec/representation failures use fixed-message DomainException, retaining underlying causes where available.
  Consumer serializer throwables propagate unchanged, including identity/code/previous cause; do not accidentally
  wrap a consumer JsonException as a codec failure or convert PHP Error into successful data.
- Keep existing fromData/fromString and helpers unchanged. Explicit snapshot-aware text reconstruction is necessary:
  legacy fromString uses associative decoding and legacy encoding, which collapse empty/numeric-key objects and
  zero-fraction float representations. Existing Doctrine hydration remains legacy; do not advertise it as restoring
  snapshot mode or faithfully round-tripping every new snapshot representation. No persisted-data rewrite is required.

Exact factory spelling/signatures, the presentation-option allowlist and internal storage design remain routine
implementation choices within these approved requirements. Preserve existing ValueObject representation equality:
no independent semantic/key-sorting equality is introduced. Equal string representations of the same concrete type
must retain coherent hashes, including cross-path comparisons where representations actually match. Equality with a
separately mutable legacy comparison value cannot itself be promised invariant when that other value changes.

Authorization is N/A to a local JSON value. Consumers own which input/serializers they trust and which data they
publish. Snapshot isolation is neither permission nor redaction; fixed wrapper messages do not make arbitrary
consumer exceptions or their causes public-safe. Do not add HTTP/Application failure coupling or runtime deprecation
warnings through this TASK.
