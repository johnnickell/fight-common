# Protect and resume ordinary MCP input_required interactions

## Outcome

Deliver the complete ordinary additional-input use case for an interactive MCP Tool. A capable client receives an
`input_required` result with a stateless versioned-AEAD opaque `requestState`, then retries `tools/call` with a fresh
JSON-RPC id and keyed `inputResponses`. Common privately opens state only to recheck the canonical Tool's current
availability; only if still available does it restore the original validated arguments and invoke `resume()` without
repeating initial metadata or validation declarations. A Tool concealed or revoked between rounds is returned as
unknown without state disclosure or resume.

## Scope

- In scope:
  - A framework-neutral interactive-Tool contract extending TASK-00107's selected-Tool invocation seam with an
    explicit ordinary additional-input result and `resume()` behavior. Its static metadata declares form
    elicitation as required so the invoker can gate the first `handle()` before entering any Tool branch.
  - Verification that the current request declares the MCP form-elicitation capability before Common invokes the
    interactive Tool or emits an `input_required` result. A missing capability becomes protocol error `-32021`, with
    the required capability in safe error data, before an input request or consumer use-case dispatch.
  - Stateless versioned-AEAD opaque state binding neutral caller identity, canonical Tool name, original validated
    arguments, requested-input contract/response keys, ordinary mode, and expiry; no server-side interaction record.
    Enforce a strict documented request-state byte limit before cryptographic processing. Use an active encryption
    key plus a bounded validation key ring for rotation; emitted tokens identify only protocol/key version, and a
    retired or unknown key version fails closed. No plaintext or otherwise reversibly client-visible bound value is
    permitted.
  - Parsing `inputResponses` as a keyed map of MCP `ElicitResult` values. Common validates the map and expected keys
    first; `accept` requires content conforming to the retained restricted elicitation schema and runtime rules,
    while `decline` and `cancel` require no accept-only content. The typed response map reaches ordinary `resume()`
    for all three actions so the Tool can produce its safe terminal semantic outcome.
  - Private AEAD opening only as needed to identify the candidate Tool, followed by a fresh TASK-00107
    availability/concealment decision on every retry before restored-state disclosure or response validation, then
    `resume()` with the restored original `ApplicationData`, typed responses, and the existing reporter contract.
  - MCP-semantic representation of the input request and retry result through TASK-00104's central responder,
    package-owned query- and mutation-neutral fixtures, compatibility-manifest classification, and consumer-facing
    documentation.
- Out of scope:
  - Destructive-action classification, one-time confirmation storage, atomic consumption, replay rejection for a
    confirmation, or concurrent confirmation arbitration; TASK-00112 owns that complete use case.
  - Treating ordinary integrity-bound state as a one-time token. Consumers must classify destructive or otherwise
    replay-sensitive actions for TASK-00112's confirmation mode.
  - HTTP route ownership, authentication, authorization, principal or permission models, HMAC nonce reuse, live
    SSE/progress/cancellation changes, durable MCP tasks, rollback, persistence selection, or framework-specific UI.

## Validation and permissions

Initial invocation order is current availability resolution, static interactive-capability gating, initial schema/
`ValidationService` processing, then `handle()`. Retry order is bounded token parsing, private AEAD authentication/
opening only as needed to identify the candidate Tool, current availability/concealment reevaluation, caller/binding/
expiry checks, keyed `ElicitResult` envelope/key/action validation, accept-only restricted-schema content validation,
then `resume()`. `McpToolInfo` and initial `#[Validation]` remain on `handle()` and are not duplicated on `resume()`.

Ordinary `decline` and `cancel` are valid response actions, not malformed state: they pass no accept-only content and
reach `resume()` for the Tool's safe terminal decision. They must not be reinterpreted as confirmation. A concealed
or revoked Tool, invalid state, invalid response, or unsupported client never reaches `resume()`.

Capability evidence belongs to the current semantic request. A server capability advertisement, an earlier
request, or route configuration cannot substitute for the client's declared form-elicitation capability. Common
receives only a stable, neutral caller-binding value from the consumer. It does not resolve a principal, infer a
permission, decide which operation needs input, or expose consumer policy.

State protection is independent of request authentication: versioned AEAD supplies authenticated confidentiality and
integrity; `NonceRepository`, HMAC nonces/credentials, Bearer tokens, and transport headers are never reused. Bound
values are neither plaintext nor client-reversibly exposed. Enforce the documented request-state byte limit before
cryptography; rotate with an active key and bounded validation key ring, failing closed for retired/unknown versions.
Ordinary state remains stateless and non-one-time, so destructive or replay-sensitive work uses TASK-00112.
Invalid state and invalid responses must be publicly indistinguishable where more detail would expose protected data.

## Acceptance criteria

- [x] An available interactive Tool can return one protocol-conformant `input_required` result containing a safe
  requested-input schema and protected `requestState`, without dispatching its mapped command or query.
- [x] After current availability resolution and before initial validation or `handle()`, Common verifies the current
  request's form-elicitation capability; an incapable client receives `-32021` and calls no `handle()`, `resume()`,
  command, query, or event handler.
- [x] Protected state binds the neutral caller identity, canonical Tool, original validated arguments, requested
  contract/keys, ordinary mode, and expiry using deterministic canonicalization and versioned AEAD authenticated
  confidentiality. A strict pre-cryptography size limit, stateless operation, active-key rotation, retired-key
  rejection, and absence of plaintext or reversibly visible bound data are proved.
- [x] A valid fresh-id retry privately opens state, reevaluates current Tool availability before restored-state
  disclosure or response validation, accepts exactly the requested keyed `ElicitResult` values, validates restricted-
  schema content only for `accept`, and invokes `resume()` once for `accept`, `decline`, or `cancel`.
- [x] A Tool made unavailable after `requestState` issuance is indistinguishable from unknown and receives no
  restored-state disclosure, response validation, `resume()`, command, query, or event dispatch.
- [x] `resume()` does not redeclare or rerun `McpToolInfo` or initial `#[Validation]`; replacement initial arguments,
  raw request data, credentials, headers, principals, and permissions never enter the Tool contract.
- [x] Oversized, malformed, tampered, retired-key, expired, caller-mismatched, Tool-mismatched, argument-mismatched,
  or invalid envelope/key/action/accept-content retries fail closed before `resume()` or bus dispatch and reveal no
  protected state. Ordinary valid replay is not misrepresented as one-time state.
- [x] Existing non-interactive Tools, selected-Tool validation, command/query buses, HMAC authentication/nonces,
  direct JSON behavior, and progress reporting remain unchanged.
- [x] Every public addition is classified in `compatibility/manifest.json`, with explicit promised operations and
  behavior-focused compatibility evidence.

### Implementation decisions

- `Tool\Interaction` owns the interactive subtype, explicit input result/form values, typed response map and
  Application state-protection port. `Adapter\Mcp\Sodium\SodiumMcpStateProtector` supplies optional
  `ext-sodium` XChaCha20-Poly1305 AEAD behind that port; no authentication or HMAC nonce implementation changed.
- Static `requiresFormElicitation` metadata must match the interactive interface. Current request capability gating
  precedes initial schema/rules/handle, and retries open state privately, recheck availability, then check bindings
  and validate responses before resume. Initial metadata/Validation declarations are not duplicated or rerun.
- Ordinary tokens are bounded to 65536 bytes before cryptography, use an active positive integer key version and at
  most four dedicated 32-byte validation keys, and default to 300 seconds (validated range 1–900). State includes
  original and validated arguments, exact requested form contracts/runtime rules, caller, canonical Tool,
  ordinary mode/method, expiry and issuing ID. Bytewise object-key canonicalization retains list order and scalar
  types. Valid ordinary replay remains allowed; TASK-00112 still owns destructive single-use confirmation.
- The documented form profile supports flat primitive fields, string enums/titled enums, and bounded string-enum
  multi-selects. Unsupported `format`, legacy `enumNames`, nested objects/arbitrary arrays, references and patterns
  fail closed rather than being ignored. Server-authored runtime rules remain independently enforced. Exact-key
  rejection follows this TASK's accepted policy rather than MCP's advisory ignore-extra/reprompt behavior.
- Central response metadata enrichment now preserves the input-required result kind. Complete output, failure
  mapping, per-call reporter behavior and existing non-interactive contracts otherwise retain their behavior.
- Nine new declarations are explicitly manifest-classified: eight public (with independent operation promises)
  and one internal schema implementation. Three behavioral contract IDs link normative docs to direct fixtures;
  the existing Tool signature change is identified as the approved pre-release migration, not silently additive.
