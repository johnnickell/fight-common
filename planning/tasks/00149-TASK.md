# Record separately protected execution detail

## Outcome

Trusted producers can record linked protected messages, tool arguments/results and bounded process-output segments
without placing their bodies in the safe observation ledger. Deliver typed capture metadata, Commands, separately
stored database-backed content, atomic links and safe events through the shared recording path. This third vertical
slice completes the approved recording scope of [TICKET-00040](../tickets/00040-TICKET.md), not the later read/removal
or MCP journeys of [EPIC-00009](../epics/00009-EPIC.md).

Blocked by [TASK-00147](00147-TASK.md) and [TASK-00148](00148-TASK.md), which supply admitted session/phase/activity
recording and persistence. No global execution priority is assigned. John approved initial DBAL-backed protected
content on SQLite, MySQL and PostgreSQL, not a filesystem/object-storage adapter or consumer capture service.

## Scope

- In scope: typed/versioned linked messages, tool arguments/results and process-output segments with content type,
  bounded body/segment sizes and capture-completeness metadata. Preserve supplied unavailable/expired markers.
- In scope: trusted recording admission, logical FK-linked storage separation, atomic content/link/identity writes,
  same-content retries/conflicts, safe events/errors and schema evolution preserving existing summaries.
- In scope: storage-level independent removal evidence and explicit retained-record retry behavior, including
  coordination with TICKET-00042's future public removal Commands and protected detail Queries.
- Out of scope: those public read/removal APIs, MCP mutation Tools, automatic transcript/output capture, universal
  redaction, hidden reasoning, full-capture guarantees, external file storage, dashboard UI, consumer permission
  policy, retention eligibility/jobs, archive workflows and guaranteed event delivery.

## Use cases and contracts

Operation labels describe behavior rather than final PHP APIs, exact columns or a required three-table layout.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Trusted producer records protected content linked to admitted observations | Record observation/detail through shared Commands | Internal relationship/admission checks; public protected reads belong to TICKET-00042 | Safe committed detail/reference facts only | Persist separately protected body, capture metadata and related links/identity atomically |
| Producer records partial output or unavailable content metadata | Same typed recording operations | Internal validation | Safe capture/reference facts, not body content | Preserve bounded segments and honest supplied completeness/absence information |

| Storage conformance removes protected detail independently | No public removal Command in this TASK; test through the owned storage boundary/fixture | Internal reconstruction of remaining records | No new public deletion event contract here | Demonstrate preserved session/phase summaries, integrity and documented retry limits |

Extend TASK-00147/00148's actual persistence and recording mechanism rather than duplicating it. A Command's related
database-backed bodies, links, capture metadata and retry identity changes must commit together. No dangling link
may claim available content after rollback or deletion. No transaction with external files or the observed work
is promised; the initial adapter deliberately keeps captured bytes in separately protected database storage.

Detail deletion must not require removing session/phase summaries. Coordinate retained comparison material with
body removal so retry mechanics do not become an undeclared copy of protected content in safe records. Document
exactly which retained identity/comparison records support deduplication/conflict detection and what ceases to be
guaranteed when those records are removed. No indefinite retry protection, retained-content lease or silent
reconstruction of deleted bodies is promised. Storage-level evidence belongs here; TICKET-00042 owns application
removal authorization and the full later deletion/retry journey, without blocking this TASK in reverse.

## Validation and permissions

Consumers supply trusted producer identity, current scope/admission decisions, capture selection and pre-submission
redaction. Validate every session/phase/activity/detail relationship within that scope, not merely by ID existence.
A permission to record or a safe timeline link is not permission to read a protected body. Preserve the separate
read-authorization boundary for later Queries without inventing a Common role hierarchy or automatic Agent access.

Validate content kind/type, version, finite sizes and segment/capture metadata. Keep absent, partial and unavailable
content distinguishable; preserve an explicit consumer-supplied expired marker without inferring expiry from a
missing row alone. Reject invalid/oversized/conflicting submissions safely. No raw body may enter safe summaries,
extensions, events, retry diagnostics or public exceptions. Structural checks do not prove arbitrary captured text
is secret-free, and no test may claim automatic redaction or complete capture.

## Acceptance criteria

- [ ] Linked messages, tool arguments/results and bounded output segments reconstruct from real separately stored
  DBAL data on SQLite, MySQL and PostgreSQL, with versions, content types and capture-completeness metadata intact.
- [ ] Current trusted admission, scope/reference consistency, versions and finite limits reject invalid submissions
  without partial writes or protected-data disclosure; retries do not bypass current admission.
- [ ] Same-content retries deduplicate; changed-content retries conflict, including concurrent submissions and
  changed bodies/metadata under the same producer-scoped identity. Original recording time remains stable.
- [ ] Injected failures demonstrate atomic content/link/identity changes and rollback, including no falsely available
  content after partial failure. Commit precedes acknowledgment; later event failure does not erase committed data.
- [ ] Safe observations, metadata intended for safe inspection, events and public errors contain no protected bodies.
  Typed recording preserves Agent/model/producer distinctions and never mutates consumer Workflow authority.
- [ ] Storage-level removal preserves session/phase summaries and referential integrity; supplied expired markers
  remain distinguishable from other absence. Tests establish the documented retained-record retry boundary before
  and after removal without promising indefinitely retained data or automatic restoration.
- [ ] Schema evolution preserves earlier session/phase/activity records, timestamp/full UUID representation and
  supported DBAL compatibility. Public additions are classified and existing recording/bus behavior remains supported.
- [ ] Documentation and CONTEXT.md cover capture metadata, safe/protected storage, finite limits, composition,
  removal/retry boundaries and consumer ownership, with public protected reads/removal explicitly left to TICKET-00042.
- [ ] Relevant behavior suites, exact owned-code coverage and the complete local `./bin/build` gate pass with retained
  evidence; integrated recording evidence covers the three accepted TICKET-00040 slices without claiming later Queries.
