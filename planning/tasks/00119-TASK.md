# Serve Validated Immutable Skill Revisions as Resources

## Outcome

A consumer supplies a complete immutable Skill revision, Common validates its structure/frontmatter/manifest,
and an authorized client retrieves selected revision files through the existing guarded Resources endpoint.
Root `SKILL.md`, nested references, ordinary templates, scripts and binary assets retain exact bytes and separate
Resource addresses. This is one complete provider-to-endpoint use case, normally one PR, not a contracts-only
prefactor. Do not advertise the Skills extension until [TASK-00120](00120-TASK.md) supplies both list and get.

## Scope

- In scope:
  - A neutral static-revision contract and validation path for explicit consumer-supplied content. Root `SKILL.md`
    and every member appear exactly once in a complete manifest; each has an individually readable Resource URI.
  - Full JSON-representable frontmatter parsing/preservation, required Agent Skills fields and URI/root/name
    agreement, exact raw byte sizes and SHA-256 digests, and consistent immutable manifest/file-reader identity.
  - Safe parser integration behind an inward-owned contract if a runtime parser dependency is used. Reject
    ambiguous or unsupported input rather than execute it, silently drop authored fields or normalize source bytes.
  - Contribution of revision files to TASK-00118's shared Resource provider composition, with one Resource method
    owner and lazy individual-file retrieval through the existing guarded endpoint.
  - Current whole-Skill availability applied to Resource discovery and every direct file read, including retained
    historical URIs, without partial manifests or duplicate variants merely for access filtering.
  - Finite validation, parsing, member-count, metadata, aggregate raw-content and per-file/result bounds, with
    validated overrides consistent with the existing Resource serving limits and pinned interoperability rules.
  - Focused behavior/endpoint evidence, applicable Resource checks, compatibility classification and documentation.
- Out of scope:
  - `skills/list`, `skills/get`, extension advertisement/merging and completed Skills conformance, owned by
    TASK-00120. This slice serves valid Skill content as ordinary Resources, not a partially advertised extension.
  - Catalog storage, atomic publication implementation, retention/current-pointer policy, managed/custom rules,
    Agent OS permissions, principal models, Pi client/session/cache behavior and actual host activation.
  - Directory RPC, dynamic Skills, URI-template resolution, server rendering, execution, mandatory archives,
    filesystem mounts, automatic URL fetching, subscriptions/listChanged and federation.
  - Tools, shared HTTP request-body limits and combined endpoint acceptance owned by
    [TICKET-00030](../tickets/00030-TICKET.md); no new endpoint, framework adapter, release or deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer supplies a structured static revision | N/A; validation is not a publication command | Inspect explicit members, frontmatter and raw bytes | N/A; no domain mutation | Accept one consistent revision or reject it before exposure; no catalog write or execution. |
| Client discovers permitted Skill files as Resources | N/A; read-only | Existing `resources/list` plus whole-Skill availability | N/A; no domain mutation | Expose only permitted descriptors without reopening/re-hashing all files on each request. |
| Client requests root instructions and then one supporting file | N/A; read-only | Separate `resources/read` requests | N/A; no domain mutation | Return only requested immutable revision bytes, including text/binary assets. |
| Consumer denies a Skill after earlier discovery/read | N/A; policy change is external | Fresh whole-Skill decision on each list/read | N/A; no Common permission event | Conceal its file descriptors and deny new direct/historical reads before content opening. |
| Consumer supplies a new revision while retaining an old one | N/A; publication is external | Exact revision lookup | N/A; no domain mutation | Serve distinct addresses; old addresses never silently return new bytes. |
| Provider supplies malformed or inconsistent content | N/A; no mutation | Structural/integrity/bounds validation | N/A; no domain mutation | Safe rejection without traversal, arbitrary I/O, truncated success or fallback to another revision. |

These operations are not new business CQRS messages. Providers may use existing consumer queries; Common adds no
schema migration, publishing command, Workflow transition or domain event. Validation may read supplied content
once to establish a bounded snapshot; that is distinct from mandatory client prefetch or repeated corpus loading.
Diagnostics and optional caches are technical effects. Reading scripts, templates or nested `SKILL.md` files does
not render, execute or activate them, and preserving `allowed-tools` grants no execution authority.

## Validation and permissions

Validate the required root `SKILL.md`, required frontmatter fields and naming constraints, complete unique member
set, URI/root/name agreement and relative paths contained within the revision. Preserve ordinary nested paths;
reject missing/duplicate members, out-of-root or repeatedly decoded escapes and ambiguous registered URI ownership.
Use only explicitly supplied content; a URI authority is not a DNS destination, path mount or automatic fetch.

Preserve every authored JSON-representable frontmatter field, including unknown fields, `license`, `metadata` and
`allowed-tools`. Reject duplicate keys, unsupported values, executable tags/includes and excessive parser expansion
without silently rewriting data. Keep parser dependencies out of Domain/Application implementations except through
the project's permitted contracts. Exact library selection and public types remain routine implementation design.

Manifest sizes/digests cover original raw bytes before JSON escaping or Base64. Preserve Unicode, line endings and
frontmatter source bytes. Manifest and readers must describe the same immutable revision; reject inconsistent or
mutable provider output safely, and never substitute latest/local/other-origin content. Consumer storage owns
atomic publication and retention; Common validates and exercises the supplied contract, not arbitrary databases.

Use finite defaults and validated overrides for parsing/metadata, file count, aggregate and individual bytes and
encoded output. Ensure accepted files fit configured Resource budgets, including encoding expansion. Reject excess
rather than split/truncate a manifest or verified file. Snapshot validation may inspect bytes, but ordinary metadata
discovery must not require re-reading/re-hashing every file. No fixed numeric values are approved by this TASK.

Apply the current injected whole-Skill decision to all file discovery and reads, not a stored authorization bit.
The collaborator receives neutral metadata, not credentials, permission names or a principal model. URI/digest
possession, authentication, immutable bytes and freshness are not permission. Deny the whole Skill rather than
redact a manifest or manufacture caller-specific variants. Private cache reuse must not bypass current authority.
Invalid publication inputs fail safely; runtime unknown/unavailable files retain indistinguishable central Resource
errors, and unexpected failures use generic internal responses with sanitized diagnostics, never Tool `isError`.
