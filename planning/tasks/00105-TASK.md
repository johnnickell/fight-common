# Serve guarded stateless MCP requests through PSR HTTP

## Outcome

Deliver the first constructible stateless MCP endpoint as a consumer-owned POST route delegates to reusable
PSR-7/15/17 seams. The endpoint requires consumer-configured origin and invocation policies and validates every
standard and declared custom header/body mirror before capability dispatch. It emits a direct JSON response and
rejects browser-origin, transport-consistency, and invocation-limit failures with the accepted HTTP/JSON-RPC
behavior while retaining consumer ownership of routes, caller identity, thresholds, exemptions, and authorization
policy.

## Scope

- In scope:
  - Required neutral `McpOriginPolicy` and invocation-guard contracts, explicit exact scheme-host-port allow-list
    and native-only deny-all origin implementations, and composition-time failure when either required policy is
    absent.
  - Complete pre-dispatch mirror validation for protocol version, method, tool name when present, and every
    registered capability/schema-declared `x-mcp-header` value; one Common validator owns the rules after
    adapters extract headers.
  - PSR HTTP request extraction and direct `application/json` response emission for POST-only stateless requests;
    no JSend or framework response is created by a capability.
  - Streamable-HTTP content negotiation for POST requests: the client advertises both `application/json` and
    `text/event-stream` in `Accept`, even though this TASK selects direct JSON and TICKET-00025 owns SSE.
  - Ordered endpoint enforcement: supplied Origin must pass before capability selection, parsed transport mirrors
    must agree before capability dispatch, and the neutral invocation guard must allow the request before the
    selected capability executes.
  - Central response mapping for origin rejection, invocation denial, mirror/protocol failure, and unexpected
    sanitized internal errors, plus consumer wiring examples for the supported framework and framework-free paths
    with explicit server identity, capabilities, origin policy, guard, and authentication composition around a
    consumer-owned route. These are composition examples, not new framework route owners.
  - Additive compatibility-manifest classification and behavior evidence for every public declaration added by
    this TASK, and end-to-end acceptance ownership for TICKET-00023.
- Out of scope:
  - Defining a caller-key format, thresholds, quotas, exemptions, backing store, distributed rate-limit behavior,
    trusted-proxy policy, route, firewall, authentication mechanism, principal type, or authorization decision.
  - Tool discovery/invocation, availability filtering, schemas, progress/SSE, cancellation, protected
    interactions, and OAuth resource-server behavior owned by TICKET-00024 through TICKET-00027.
  - Credential or authorization data in per-request MCP metadata and divergent framework-specific subsets of the
    mirror-validation rules.

## Use cases and contracts

| Use case | Actor and trigger | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|---|
| Serve a valid stateless request | Native MCP client posts valid JSON with no Origin and consistent mirrors | N/A unless the registered capability chooses a consumer command | N/A unless the registered capability chooses a consumer query | N/A at the safeguard boundary | Treat absent Origin as valid, allow the neutral guard to evaluate its consumer-owned caller key, dispatch only after all mirrors agree, and return direct JSON without session state. |
| Accept an allowed browser Origin | Browser MCP client supplies an exact allow-listed scheme-host-port Origin | N/A unless selected later | N/A unless selected later | N/A | Continue to mirror validation and guarding without Common interpreting forwarded-host or principal policy. |
| Reject a disallowed browser Origin | Browser MCP client supplies an Origin the configured policy denies | N/A | N/A | N/A | Return HTTP 403 before capability or tool selection and perform no capability side effect. |
| Reject an invocation-limit denial | Configured guard denies the current request | N/A | N/A | N/A | Return HTTP 429 and a JSON-RPC error when a usable id exists; do not select or invoke a capability. |
| Reject inconsistent transport mirrors | Client omits, malforms, or disagrees on a standard or declared custom mirror | N/A | N/A | N/A | Return the centralized protocol failure before capability dispatch; adapters cannot waive or partially implement the check. |

## Validation and permissions

An absent Origin is valid. A supplied Origin must be parsed as an exact origin and accepted by the configured
policy; path, query, fragment, wildcard, suffix, or inferred forwarded-host matching must not weaken an exact
scheme-host-port allow-list. Native-only composition uses an explicit deny-all policy rather than a missing or
implicit pass-through implementation. Trusted-proxy and forwarded-header trust remains consumer/framework
configuration.

The Common mirror validator checks `MCP-Protocol-Version`, `Mcp-Method`, applicable `Mcp-Name`, and every
`Mcp-Param-*` mirror derived from a registered `x-mcp-header` declaration. Missing, malformed,
duplicated/ambiguous, incorrectly encoded, or body/header-mismatched values are rejected according to
the accepted protocol contract before capability dispatch. Exact primitive and non-ASCII encoding, optional/null
semantics, and JSON-RPC error codes must be derived from the pinned MCP `2026-07-28` authority and captured in
conformance fixtures; implementation must not guess when the specification is ambiguous.

All HTTP field names are matched case-insensitively, including the suffix of dynamic `Mcp-Param-*` names. Normalize
field names for lookup/collision detection rather than depending on the casing preserved by a PSR implementation.
Two `x-mcp-header` declarations that differ only by field-name case are a composition error. JSON Schema property
names remain case-sensitive, and decoded method, capability name, and parameter values are compared using their
MCP/body semantics rather than lowercased as header names.

The PSR endpoint accepts only POST in this stateless profile. GET and DELETE receive HTTP 405 with `Allow: POST`
and do not enter semantic dispatch. A POST must advertise both `application/json` and `text/event-stream` in its
`Accept` header; invalid or incomplete negotiation is rejected before capability dispatch. Direct JSON remains
the selected response mode for this TASK, while progress-token SSE belongs to TICKET-00025.

The invocation guard is neutral and request-scoped: the consumer implementation owns and derives its caller key,
thresholds, exemptions, storage, and policy. Common passes only neutral operation metadata to the guard, maps its
allow/deny result, and never passes a principal, credential, or raw HTTP request through the public guard contract.
Common makes no authorization decision. Authentication and authorization failures remain consumer-owned
pre-dispatch behavior.

## Acceptance criteria

- [ ] Composition fails without an explicit origin policy or invocation guard; there is no implicit pass-through
  implementation.
- [ ] A valid MCP `2026-07-28` POST produces `application/json` direct output with no protocol session,
  `initialize`, legacy GET/DELETE, or legacy HTTP+SSE behavior.
- [ ] GET, DELETE, and other non-POST requests return HTTP 405 with `Allow: POST`, without semantic capability
  dispatch or session behavior.
- [ ] POST requires an `Accept` header listing both `application/json` and `text/event-stream`; omission or an
  incomplete media-type set is rejected before semantic capability dispatch even though this TASK returns direct
  JSON only.
- [ ] Missing Origin and an exact allow-listed Origin can reach dispatch, while a supplied disallowed Origin
  returns HTTP 403 before any capability or tool is selected.
- [ ] Native-only deny-all rejects every supplied Origin while continuing to accept a request with no Origin.
- [ ] Guard allowance permits dispatch; guard denial returns HTTP 429 with the protocol-defined JSON-RPC error
  when a usable request id exists and never invokes the selected capability.
- [ ] Protocol version, method, applicable tool name, and every declared custom `x-mcp-header` are validated as a
  complete `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name`/`Mcp-Param-*` mirror set; omission, malformed or
  ambiguous values, field-name casing variants, case-insensitive declaration collisions, primitive/non-ASCII
  encoding, optional/null handling, undeclared schema properties, and mismatches are covered before capability
  dispatch without lowercasing case-sensitive JSON property names or mirrored values.
- [ ] Header extraction differences are confined to adapters and all supported composition examples delegate the
  complete validation set to Common rather than implementing framework-specific subsets.
- [ ] Documentation shows consumer-owned route/authentication composition with explicit server identity,
  capabilities, origin policy, and guard, and it does not introduce a principal, credential, permission, or
  authorization-policy contract in Common.
- [ ] An unexpected `Throwable` is logged once through a consumer-supplied redaction-aware diagnostic path and
  becomes only the generic public-safe internal JSON-RPC error; credentials, raw arguments, personal data, paths,
  stack traces, and internal class/storage details are not exposed.
- [ ] TICKET-00023's successful request, discovery, protocol-error, Origin, guard, mirror, direct-JSON,
  compatibility, and policy-free-boundary acceptance is covered end to end.
- [ ] Every public addition is classified in `compatibility/manifest.json`, its promised operations are explicit,
  and existing JSend, PSR HTTP, HMAC, framework, and consumer APIs remain behaviorally unchanged.

transcripts and dispatch-spy counts. Save those artifacts and the complete `./bin/build` log/exit receipt under the
TASK's ignored run directory. Run the canonical `./bin/build` before publication and surface warnings, notices,

## Coordination

TASK-00104 is the required base and owns the stable semantic protocol/capability/response seam. Use
dependency-ordered SUBTASKs for neutral policies, mirror validation, handler integration, adapter extraction,
fixtures/compatibility, and documentation inside this one PR. This TASK owns integration and final acceptance for

“Framework wiring examples” means consumer-composition documentation for the supported framework and
framework-free paths, reusing PSR seams where they are complete. It does not authorize five new route owners or
native endpoint adapters. If a supported path cannot express the guarded direct-JSON endpoint through an existing
seam and a new public adapter becomes necessary, record the evidence and reconcile that material scope before
expanding implementation.

If protocol evidence contradicts the accepted 403/429 or mirror requirements, or a supported composition cannot
delegate the complete validation contract, stop and return the exact decision/evidence gap rather than weakening
the safeguard.
