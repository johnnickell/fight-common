# Add Strict Pagination Construction

## Outcome

Consumers can opt into strict construction of the existing Pagination type with dependable positive bounds,
supported ordering directions and representable integer offsets. Existing repositories accept the result without
signature changes, while the legacy constructor remains functional during the minor transition. Deliver factory,
behavior/compatibility evidence and migration documentation together in one independently reviewable PR under
[TICKET-00032](../tickets/00032-TICKET.md) and [EPIC-00008](../epics/00008-EPIC.md).

## Scope

- In scope: an additive public named factory on Domain/Repository/Pagination, strict bound/direction validation,
  checked offset arithmetic, preserved accessors/type and legacy constructor compatibility.
- In scope: direct strict/legacy behavior tests, existing repository consumption evidence, public API/behavioral
  classification, affected repository documentation, CONTEXT.md and opt-in minor-to-major migration guidance.

  dependencies, framework support changes, release tooling or packaging tests.

Construction performs no I/O or database/schema writes. A Pagination describes query bounds, not permission to
execute a query or evidence that every database/provider accepts those bounds. Consumers retain repository policy,
field eligibility and provider-specific restrictions. This feature introduces no business messages or new events.

## Validation and permissions

The approved strict-path contract is:

- Omitted/null page and per-page values resolve to the existing DEFAULT_PAGE and DEFAULT_PER_PAGE values.
  Explicit zero or negative bounds reject rather than selecting a default.
- Positive resolved bounds yield offset `(page - 1) * perPage` and limit `perPage`. Check representability using
  integer-safe logic before multiplication; page one has offset zero even at the maximum supported integer limit.
- ASC/DESC direction tokens normalize case-insensitively. Unsupported directions reject rather than becoming ASC.
  Preserve field associations and do not turn direction validation into global field policy or SQL sanitization.
- Invalid bounds/directions and unrepresentable offsets use DomainException. Define the exact factory spelling,
  signature and PHP type-boundary behavior consistently with these requirements during implementation; a missing
  method, accidental float-assignment TypeError or arbitrary coercion is not the promised validation failure.
- Keep legacy constructor behavior, including null/zero defaults and unknown-direction-to-ASC normalization.
  Do not describe the addition as repairing legacy negative bounds or overflow. Document their limitations without
  creating a new perpetual promise for every incidental unsafe behavior.

Authorization is N/A to value construction and remains consumer-owned. Deprecation guidance is documentation/
PHPDoc only in this TASK; incompatible enforcement or removal waits for an authorized major transition after at
least one released minor of functional deprecation support. No exact release number or removal operation is assigned.
