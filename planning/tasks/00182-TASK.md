# Separate validation construction from execution

## Outcome

Give validation-rule construction one cohesive internal owner while retaining existing public coordinator,
parser and service contracts. Consumers keep their convenience methods and supplied coordinator; execution
still owns one invocation's queue, context, result and cleanup. Normally one compatible refactoring PR.

John approved planning this recommendation on 2026-11-02 after the architecture report at develop `521a71c`.
This is a standalone chore, not a reopening of [TASK-00127](00127-TASK.md)'s completed exception-safe reuse
repair. Planning grants no execution/publication.

## Scope

- In scope: `ValidationCoordinator`, `ValidationService`, the actual `RulesParser` output/callers, a cohesive
  internal rule/validator construction owner, direct tests, deliberate internal classification and affected docs.
- Keep every public `add...Validation`, `addValidator`, `validate`, reset and parser contract functional with the
  same parameter names/defaults and rule meanings. Existing convenience methods may delegate to preserve a
  useful released promise, but do not add an extra public forwarding layer.
- Share construction knowledge between convenience registration and the parsed-rule path. Keep special
  required/equal/same-field specifications and argument coercion with that construction knowledge; the queue/
  execution lifecycle must not become a second catalog. Avoid adding compiler plus factory layers if one
  cohesive owner suffices. Private implementation names remain an engineering choice within this boundary.
- Out of scope: new rules, a public plugin/options system, new public API deprecations, tighter parsing, domain
  policy changes, stale-state bug repair already accepted, concurrency/reentrancy promises, dependency/schema
  changes or widening into unrelated modules.

| Use case | Commands | Queries | Events | Expected side effects |

No business messages or durable/external effects are added. Consumer-defined validator side effects are not
sandboxed, undone or rerun for cleanup by this task.

## Validation and permissions

Preserve accepted input-key/rule shapes, parser output, custom error formats, rule arguments/coercion, field
specification distinctions, accumulation/ordering and original throwable identity. Validation does not imply
sanitization, authorization or public-safe diagnostics. Keep the same consumer-injected coordinator and custom
validator semantics; finally-based cleanup covers preparation and execution failures without draining work.

## Acceptance criteria

- [ ] Current public construction/convenience/parser/service methods and parameter names remain compatible;
  supplied coordinator and custom-validator behavior are retained.
- [ ] Rule-to-validator construction has one cohesive internal owner used by existing registration paths;
  execution remains focused on invocation state rather than duplicated rule assembly.
- [ ] Required/same/equal-field behavior, rule argument conversion, error data/order and parser formats remain
  unchanged, including supported custom error messages and regular-expression rule handling.
- [ ] Ordinary success/failure and preparation/execution exceptions clear queued work exactly as promised by
  TASK-00127; original failures remain original and later sequential invocations contain no stale rules/errors.
- [ ] Construction extraction does not add a public options bag, speculative plugin abstraction or a new
  consumer setup sequence; new internals are explicitly classified.
- [ ] Meaningful direct/service tests, affected validation guide/CONTEXT descriptions and complete full-gate
  evidence exist; no supported behavior is weakened to reduce class size or satisfy coverage.
