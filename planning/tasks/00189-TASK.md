# Model Task identity and values with the existing ValueObject contract

## Outcome

Give Task a meaningful scoped identity and make its value objects extend the existing ValueObject hierarchy,
with actual value equality and reconstruction semantics rather than readonly DTO labeling. John explicitly
required ValueObject inheritance on 2026-11-02. Normally one Task Domain/API refactoring PR.

## Scope

- Inspect TaskDefinition, TaskState, TaskInputBatch, TaskInputs, TaskSelection, their Commands/Queries/events,
  TaskRepository, projection and DBAL hydration. Classify each as aggregate, nested entity, value or Application data.
- Introduce `Domain/Mcp/Task/TaskId` using the existing ValueObject/Identifier contracts as appropriate; preserve
  exact 32-lowercase-hex identity and trusted scope semantics. Do not replace it with an incompatible UUID format.
- Replace ambiguous identity strings at Domain/repository boundaries with meaningful types; keep wire/database
  representations explicit at their boundaries. Scope remains part of actual identity selection, not authority.
- Make types classified as values extend ValueObject directly or through a meaningful value base. Task remains
  an aggregate, and input group lifecycle state must not become a value solely because it is immutable.
- Design stable fromString/toString, same-concrete-type equality, hash and JSON contracts from each concept's
  semantics. Inspect ValueObject/Value and typed collections before inheriting defaults; override jsonSerialize
  where needed to preserve existing structured encoding rather than silently turn embedded objects into strings.
- Preserve meaningful unknown/null/empty, object/list, form/result/error and source representation distinctions.
  Do not use a generic JSON wrapper as a substitute for a named domain concept or add IDs for every string field.
- Update owned callers, real values in tests, DBAL codecs, public/internal classification, Task guides, CONTEXT,
  examples and CHANGELOG. Shared low-level values already extending ValueObject stay unchanged.
- Out of scope: changing Task lifecycle/payload/identity bytes, new authorization, schema migrations, broad
  primitive-wrapper proliferation or compatibility aliases for earlier untagged snapshots.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Producer constructs/changes a coherent Task | Existing Task Commands | Existing Task Queries | Existing Task facts | Same admitted lifecycle using typed identity and meaningful values. |
| Consumer compares/reconstructs a Task value | N/A; value operation | N/A | N/A | Stable equality/hash/string/JSON behavior with invalid input rejected. |
| Persistence/message boundary encodes/decodes Task data | Existing message contracts | Existing read contracts | Existing event representations | Same external bytes/shape and integrity validation. |

## Validation and permissions

Construction validates the owned concept and rejects malformed values without normalization that changes
identity. Value construction/equality never grants producer/read/input/removal authority. Keep separate grants,
finite bounds, safe errors and existing transaction/post-commit behavior.

## Acceptance criteria

- [x] A documented classification identifies Task's aggregate, identity, nested state, values and Application projections without technical Domain buckets.
- [x] TaskId prevents accidental interchange while retaining exact scope/identity bytes across messages and persistence.
- [x] Every Task type classified as a value extends ValueObject (directly or through a meaningful value base) and fulfills its inherited contract.
- [x] Equality/hash/reconstruction reflect domain semantics; structurally similar but semantically different values remain distinct.
- [x] Nested JSON encoding remains deliberately compatible with current wire/storage shapes; inherited string serialization causes no silent drift.
- [x] Lifecycle, retry, input/cancellation, public revision privacy/order and encoded bounds remain unchanged.
- [x] Callers, classification/docs, direct/journey tests and full-gate/independent acceptance evidence are complete.

## Verification and evidence

Prove independently constructed equal/unequal values, wrong-type comparisons, hash agreement, string/JSON

production constants. Run focused checks then full `./bin/build` with exact coverage; save log/exit/warnings/
