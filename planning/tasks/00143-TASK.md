# Present Safe Errors Through PSR-15

## Outcome

A consumer explicitly composes production-safe PSR-15 error handling, receiving safe JSend responses and owned,
redaction-aware diagnostics without changing the published legacy middleware. Deliver the shared HTTP
classification/projection policy through this complete usable adapter path, not a mapper-only prefactor.

John approved this feature TASK and its recommended contracts on 2026-10-06 under
[TICKET-00039](../tickets/00039-TICKET.md) and [EPIC-00008](../epics/00008-EPIC.md).
[TASK-00142](00142-TASK.md) supplies the application vocabulary. No priority is assigned. This is additive
next-minor planning; no implementation/worktree, exact release or immediate legacy-default repair is authorized.

## Scope

- In scope: shared safe classification/public projection, validated HTTP metadata, explicit diagnostic ownership,
  usable opt-in PSR-15 middleware and existing PSR-17/native JSend envelope composition.
- In scope: category and consumer-subtype recognition, existing validation reconciliation, deliberate public
  customization, trusted-only development configuration if offered, safe fallback/failure behavior, legacy
  compatibility, public classification, documentation/CONTEXT.md and complete verification.
- Out of scope: application authentication/authorization policy, permission names, automatic retry/rollback,
  Domain/Application HTTP fields, a generic policy engine, raw exception serialization, MCP/OAuth mapping changes,
  framework-global activation, downstream migrations, persistence/schema changes and legacy-default replacement.
- Out of scope: Symfony/Laravel lifecycle integrations owned by TASK-00144/TASK-00145, release certification,
  packaging/release-process tests, publication and deployment.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer opts into safe middleware | N/A; composition | N/A; composition | N/A; no mutation | Install explicit safe handling; old constructor/service behavior remains available. |
| Downstream handler throws a declared refusal | Existing consumer command, if any | Existing consumer query, if any | N/A; no invented event | Return fixed safe fail data and the declared category's HTTP outcome. |
| Unknown Throwable/server failure reaches the boundary | Existing workflow unchanged | Existing workflow unchanged | N/A; no invented event | Generic error response and one owned redaction-aware reporting path. |
| Consumer supplies public data or protocol metadata | N/A; projection | N/A; local reads | N/A; no mutation | Validate deliberately selected data/headers rather than copying diagnostic context. |
| Projector, encoder or reporter fails | N/A; technical failure | N/A; no business query | N/A; no domain mutation | Fail safely without leaking the original failure or presenting success. |

Response creation and diagnostics are technical effects. Consumers retain route policy, identity, authorization,
transaction/recovery semantics and whether any retry is appropriate. HTTP presentation does not undo earlier effects.

### Shared mapping

| Declared category | HTTP | JSend |
|---|---|---|
| AuthenticationRequired | 401 | fail |
| PermissionDenied | 403 | fail |
| ResourceNotFound | 404 | fail |
| StateConflict | 409 | fail |
| ResourceGone | 410 | fail |
| PreconditionFailed | 412 | fail |
| InvalidInput | 400 | fail |
| Existing structured ValidationException | 400 | fail |
| RuleViolation | 422 | fail |
| RateLimitExceeded | 429 | fail |
| ServerError / unknown Throwable | 500 | error |
| ServiceUnavailable | 503 | error |

These mappings apply only to the new safe path. Existing validation constructors/maps and legacy HTTP behavior remain
unchanged. Recognize declared category intent, including intended consumer subtypes; arbitrary ApplicationException
subtypes, generic lookup/auth/storage failures and timeouts do not automatically become client failures. Do not infer
status from integer exception codes, diagnostic text or a previous Throwable. A recognized class is not permission
to publish getMessage(), fields, causes or context.

Shared HTTP policy belongs in Adapter; retain Application's existing JSend semantic envelope and transport-neutral
application exceptions. Use ADR 0023's capability-first paths. Exact public names and interface shapes remain routine
implementation design within these accepted contracts, not permission to duplicate classification in each framework.

## Validation and permissions

Fixed safe defaults cover every recognized category and unknown Throwable. Custom public message/data uses an
explicit projection boundary and safe serialization, never arbitrary exception objects, entities or getErrors()
forwarding. Existing structured validation defaults to a safe 400 refusal; field/message disclosure requires a
deliberate safe-data policy. Do not silently reclassify every validator as syntax-only or every rule as 422.

HTTP-only routing, method/content negotiation, size rejection and gateway outcomes remain transport-owned. Provide
an explicit validated translation seam for supported outcomes rather than one Application exception per status or
unrestricted exception-header forwarding. Native framework recognition belongs to the following framework TASKs.
Consumer-configured authentication challenges are required for supported 401 composition; never invent universal
Bearer credentials/schemes. Preserve validated Allow for supported method failures and applicable retry metadata.
Nullable/zero/native-integer retry hints from TASK-00142 are not automatic retry authority; deliberately validate
any public header conversion, including large values and invalid/injected metadata. Document safe failure for missing
required metadata rather than emitting an apparently correct but protocol-incomplete response.

Establish one explicit diagnostic owner per composition. Redact before arbitrary secrets reach logger formatters;
blind PSR-3 exception-context forwarding is not redaction. Retain useful diagnostic/cause information through the
trusted reporting boundary without making it public. Exercise reporter failures and prevent recursive reporting or
unsafe fallback. Do not claim delivery of a log when its sink fails; define and document that failure behavior.

New safe handling is production-safe by default. Development details are optional; if offered, require explicit
trusted configuration and test both modes. Query parameters, headers, cookies and unrelated framework settings must
not accidentally enable disclosure. Production fallback remains safe when projection/encoding/reporting fails.
