# Check and correct descriptive variable names across the codebase

## Outcome and accepted decision

Check all project-owned code and maintained runnable examples for variable names that conceal what a value or
collaborator actually is, and make compatibility-safe corrections. John explicitly requested a codebase-wide
check on 2026-11-02: a TaskRepository property is `$taskRepository`, not `$tasks`. This is a bounded semantic-
naming chore, normally one PR, not a new architecture rewrite or an automated suffix replacement exercise.

## Scope

- Inspect properties, constructor-promoted properties, parameters, locals, closure captures and test doubles in
  all project-owned code: `src`, `tests`/fixtures, `release` PHP, `scripts` and maintained executable examples.
  Record language/path coverage and any unreadable/excluded owned scope. Apply idiomatic descriptive naming
  outside PHP rather than transplanting PHP conventions. Exclude vendor, generated site/build output, Git data,
  ignored runs, immutable historical snapshots/evidence and third-party quoted examples.
- Name capabilities by their actual responsibility: `$taskRepository`, `$noticeRepository`, `$sessionRepository`,
  `$phaseRepository`, `$observationRepository`, `$protectedContentRepository`, `$queryBus`, `$commandBus`,
  `$eventDispatcher`, `$transactionalUnitOfWork`. Use context-qualified names when two collaborators share a type.
- Distinguish repositories/readers/stores from returned collections or data: `$tasks` can be a real Task collection,
  not a repository; `$store` may still be too vague even when its type is legitimately a technical store. Apply
  the same judgment to `$data`, `$service`, `$result`, `$manager`, abbreviations and single-letter locals.
- Names describe the semantic role, not necessarily the entire concrete implementation class. Do not expand
  clear local mathematical indices or language idioms mechanically. Every changed name must improve meaning.
- Establish compatibility before renaming parameter/property names: released PHP named arguments, public/protected
  properties and extension contracts, serialization, reflection, attributes, ORM/framework metadata and callbacks
  can make a name observable. Preserve supported released names where a direct rename breaks them; record the
  exact exception/reason and future-major decision needed rather than silently change or call it compliant.
- Rename private/internal/provisional APIs and owned callers consistently. Do not add runtime magic, aliases,
  compatibility wrappers, new public methods or deprecated overloads solely to make an internal naming pass.
- Correct fresh refactor examples too, including the review's abbreviated `$tasks` repository spelling. Earlier
  tasks must already follow TASK-00183; this task completes the broader scan rather than postponing their naming.
- Keep production behavior, wire/database keys, public message/Tool IDs, schema and historical evidence unchanged.
  Update affected current examples/CONTEXT/CHANGELOG only for actual semantic or consumer-visible effects.

## Use cases and contracts

| Maintainer reads handler/coordinator code | Existing messages unchanged | Existing Queries unchanged | Existing facts unchanged | Recognize collaborators and values without inferring a hidden role from calls. |
| Consumer uses released named arguments or saved objects | N/A; compatibility operation | N/A | N/A | Same supported parameter/property/serialized-name behavior. |
| Builder runs existing product journeys | Unchanged | Unchanged | Unchanged | Same results, rejections, mutations, external effects and ordering. |

## Validation and permissions

Naming conveys no authority. Preserve all validation, grant checks, transaction boundaries, safe projections and
failure diagnostics. A rename must not change a framework binding, captured reference, magic access, payload key
or consumer parameter contract. Inspect dynamic references rather than relying on text search alone.

## Acceptance criteria

- [ ] A source-linked inventory accounts for all owned code/maintained examples, changes made and scoped compatibility exceptions; sampling alone is not described as a full check.
- [ ] Repository/bus/dispatcher/unit-of-work and other ambiguous collaborator names fully express their semantic role, including tests and examples.
- [ ] Collection/data variables remain distinguishable from capabilities; no blind type-suffix or long-name inflation occurs.
- [ ] Actual tagged consumer operations and name-sensitive framework/serialization/reflection paths are preserved; exceptions are explicit, not hidden exclusions.
- [ ] No business, wire, schema, permissions, ordering, support-floor or runtime behavior change is bundled with naming.
- [ ] Current references/examples are consistent, focused regressions remain meaningful and complete gate/independent acceptance evidence exists.

## Verification and evidence

Use search/static tools to inventory names, then inspect actual types/callers before changes; pattern matches alone
are not findings. Preserve existing behavior tests rather than add source-text tests of identifier spelling. Run
focused named-argument/serialization/framework checks where affected and full `./bin/build` with exact required
coverage. Do not add packaging/release-process tests while renaming release-owned implementation. Save actual
log/exit/warnings/content receipt and scan coverage/exceptions in the handoff. Independent Review and applicable
QA remain required. Nonvisual behavior/compatibility transcripts supply Before/After evidence.
