# Enforce strict ResultSet and Pagination construction

## Outcome

Every supported construction path enforces the current `strict()` input rules.

## Scope

Remove permissive behavior without inventing new bounds. Preserve valid calls and outcomes; document invalid values previously tolerated and migration examples. No unrelated repository or serialization changes.

### Bounded scope amendment — subscription test consolidation

The maintainer approved removing flaky tests if needed. For this TASK, that approval was narrowed to the
[main-branch consolidation in TASK-00214](00214-TASK.md#bounded-scope-amendment--subscription-test-consolidation):
remove only the SQLite default/configured cases of the combined subscription isolation journey, after checking
that equivalent coverage survives on `develop`. No other subscription rows, fixture timing changes, or
CodeIgniter removals are included.

The main-branch change cannot be applied as written. [TASK-00231](00231-TASK.md) already reduced the combined
journey on `develop` to one SQLite-configured case. Dropping it would remove the only end-to-end check of two
simultaneous streams reusing integer ID 7 in different scopes, exact live resource filtering, queued tool-signal
revocation, and polling for the exact retained tool notices after a source failure, on any backend. Other
journeys cover parts of that sequence, not the same combined behavior.

For `develop`, the maintainer directed Work to retain that coverage and address the gate blocker. The sole
configured SQLite case now sends both open requests before waiting for headers and prepares the notice writer
before either subscription opens. The two reader processes, behavioral assertions and stream lifetime remain
unchanged. No subscription or CodeIgniter cases were removed.

## Use cases and contracts

A caller constructs `ResultSet` or `Pagination` directly or through a supported factory. No new query or event. Valid input yields the existing value; invalid input is rejected under the strict contract.

## Validation and permissions

Check actual current factory validation, defaults and intentional named parameters. No external effects or new permissions.

## Acceptance criteria

- [x] Direct Unit tests prove valid calls, strict rejection of previously tolerated inputs, and consistent rules across supported paths.
- [x] Document both breaking changes and supply migration examples to TASK-00229.
