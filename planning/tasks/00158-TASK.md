# Record durable safe change notices

## Outcome

Trusted consumer composition can record bounded safe change notices through `CommandBus::execute()` and reconstruct
them from actual durable storage independently of live delivery. Deliver the complete recording path, including
admission, typed records, persistence/schema, retry integrity, recovery ordering and failure semantics in one normal PR.

John approved this first vertical slice of [TICKET-00045](../tickets/00045-TICKET.md), together with
[TASK-00159](00159-TASK.md)'s bounded authorized removal. There are no unfinished blockers. Existing CQRS/DBAL
contracts supply precedents, not a dependency on unfinished introspection, Prompts, live Subscriptions or Tasks.

## Scope

- In scope: trusted recording Commands/handlers, typed bounded safe metadata, stable identity and relationship
  preservation, producer/scope admission, dedicated DBAL storage/schema/composition, atomic retries and commit ordering.
- In scope: actual SQLite, MySQL and PostgreSQL qualification, storage-level bounded reconstruction/recovery support,
  safe post-commit fact handling where defined, compatibility, documentation and complete local verification.
- Out of scope: public history/polling Queries and MCP Tools (TICKET-00046), public removal (TASK-00159), live MCP
  delivery/subscriber inspection (TICKET-00047), Mercure translation (TICKET-00048), consumer UI or deployed client proof.
- Out of scope: Event Store/projection dependency, implicit outbox, atomicity with the originating application change,
  guaranteed recording of every change, exactly-once delivery, receipt ledger and consumer retention/scheduling policy.

## Use cases and contracts

Labels describe responsibilities, not final PHP names. Preserve the existing void `CommandBus::execute()` contract;
callers can supply a stable notice identity without requiring Commands to return application data.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Trusted producer records a safe change | Record notice | Internal scope/reference/identity checks; public reads deferred to TICKET-00046 | Safe recording facts where defined, distinct from causation | Commit notice, relationships, retry material and recovery position atomically before successful acknowledgment |
| Producer retries the same notice | Record notice | Internal versioned content comparison under current admission | No assumed replay or delivery retry | Identical content deduplicates while comparison evidence remains; changed content conflicts without overwrite |

### Accepted persistence and identity mechanics

Use dedicated DBAL notice storage on SQLite, MySQL and PostgreSQL. The adapter owns schema and transaction mechanics;
inward layers own typed contracts without a DBAL dependency. No filesystem/object storage, mandatory Event Sourcing,
asynchronous projection or reuse of execution observations as notice authority. Preserve supported dependency floors;
the existing Event Sourcing schema PHPStan exception does not authorize new suppressions.

Persist topic, notification type, occurrence time with honest supplied precision/unknowns, immutable server recording
time, and separately supplied subject Agent, intended recipients, author/producer and causation Command/event/action
references. Broadcast may have no named recipient. Unknown relationships remain explicit. Notice identity, protocol
request/subscription identity, planning TASK identity and authoritative application state remain distinct.

Retry identity is bound to trusted producer and scope. Identical accepted content deduplicates while the necessary
comparison record remains; changed content conflicts. Define deterministic versioned comparison of relevant notice
content/relationships, excluding immutable server recording time. Recheck admission on every retry. Do not adopt the
Event Store's identity-only payload comparison as the notice contract. Exact identity representation and finite
limits remain documented implementation details. Document the lifetime of comparison evidence and coordinate it
with TASK-00159; no indefinite duplicate suppression or hidden perpetual notice archive is promised.

Use a dedicated commit-ordered notice position, separate from identity and occurrence/recording timestamps. Within
the defined ordering scope, observing a later committed position must not allow a lower-position notice to become
visible afterward and be skipped by continuation. Serialize allocation through actual commit or prove an equivalent
contract; timestamp/UUID order and ordinary auto-increment allocation alone are insufficient. Existing
[ADR 0001](../adr/0001-event-sourcing-contract.md) and `DbalEventStore` illustrate transactional position allocation,
not a requirement to adopt its storage/payload/retry semantics or a global order across unrelated stores. Document
ordering scope, bounds/overflow and reconstruction behavior. Public continuation/access binding belongs to TICKET-00046.

### Transaction and publication boundary

Successful recording acknowledges only after the actual commit of all related notice/relationship/comparison/position
writes. Reconcile handler ownership with `TransactionalUnitOfWork` and concrete DBAL composition; an ORM unit of work
does not automatically enlist unrelated DBAL writes. Reject unsupported already-open transactions before writing,
never commit/roll back unrelated caller work, and never equate releasing a savepoint with durable acknowledgment.
An interrupted response may leave the caller uncertain; qualify safe retry against persisted evidence.

Any defined fact events contain safe facts only and occur after commit through existing event contracts. Later
dispatch/subscriber/publisher failure cannot erase the notice or be reported as storage rollback. Exact event catalog
and safe post-commit failure reporting remain implementation details to specify/test. Do not introduce automatic
publication replay or claim that retaining notices repairs originating changes/events that never produced a notice.

## Validation and permissions

Consumers supply trusted producer/scope and authoritative identity/causation meaning. Validate finite field counts,
lengths, relationship lists and total notice size, supported shapes and permitted references before acceptance.
Arguments, Agent/recipient IDs, topic names and SUPER_ADMIN labels are not credentials. Enforce admission on original
requests and retries without exposing concealed records through duplicate/conflict failures.

The retained feed contains safe notices/references, not protected messages, tool arguments/results, process output,
full MCP Task state or complete wire transcripts. Common enforces structural/content boundaries and supplied access
decisions; consumers select safe metadata and capture/redaction policy. Structural validation cannot universally
detect secrets in arbitrary strings. Keep public failures/fact events safe; private storage diagnostics stay private.

## Acceptance criteria

- [ ] A complete Command → handler → actual DBAL path commits admitted notices and survives connection/repository
  reconstruction on SQLite, MySQL and PostgreSQL, preserving all required relationship distinctions and unknowns.
- [ ] Invalid/oversized/out-of-scope records and references reject before writes; identity/recipient/causation fields
  grant no access, and safe-content boundaries exclude protected bodies/full Task state/wire transcripts.
- [ ] Same producer/scope/identity/content retries deduplicate with immutable recording time/position; changed content
  conflicts without overwrite. Concurrent duplicates/conflicts and changed admission obey the same contract.
- [ ] Injected failures across related writes roll back the owned transaction; successful return follows actual
  commit. Unsupported enclosing transactions reject before writes and leave caller-owned work untouched.
- [ ] Committed recovery ordering survives concurrent delayed writers, rollback, retry and reconstruction; no lower
  notice position can commit later after a returned later position within the documented ordering scope.
- [ ] Position/time/identity semantics and finite bounds are explicit, including source precision, overflow and
  database/application agreement; no causality, global cross-store order or delivery proof is inferred.
- [ ] Safe post-commit events where defined cannot expose protected data; later delivery failure leaves notices
  reconstructable and distinguishes committed recording from failed publication without an implicit replay/outbox.
- [ ] Storage supports bounded retained reconstruction and a documented seam for TASK-00159's atomic history-loss
  updates; public Queries/Tool integration remain with TICKET-00046 without a reverse dependency.
- [ ] Schema/public API compatibility, composition, limits, retry lifetime, failure/recovery semantics and consumer
  ownership are documented with CONTEXT.md aligned; no dependency floor or suppression is silently expanded.
- [ ] Relevant behavior tests, exact owned-code coverage and full `./bin/build` pass with retained local evidence.
