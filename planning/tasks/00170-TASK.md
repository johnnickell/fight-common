### Approved durable intent and observation direction

Persist cancellation intent separately from the actual outcome within TASK-00166's lifecycle. Acknowledge initial
admission only after actual durable commit and reconstruction through the shared read contract. Intent alone does not
create a cancelling protocol state, force cancelled, erase outstanding requests/answers or imply worker observation.
Maintain bounded original admission evidence; stale producer or input writes cannot clear or overwrite it. No reset,
retention renewal or new stop obligation follows from a repeat. Exact fields/versioning/storage layout remain design.

Make intent available through a currently authorized shared read contract to the consumer execution owner across
connections/processes. Observation is not destructive consumption or evidence that a worker stopped. A process crash,
missed event or failed callback cannot be the sole mechanism by which durable intent becomes permanently invisible
within retention. No live stream, guaranteed event delivery, worker polling schedule or guaranteed eventual cancellation
is required. Consumers decide whether/when stopping is safe, retain their own execution permissions, and report the actual
outcome through trusted producer transitions. No task handle or cancellation permission grants worker-control authority.

Reauthorize repeats and known terminal requests. For known, currently authorized completed/failed/cancelled Tasks,
return successful no-op acknowledgment without changing state, result/error or terminal evidence. This is the approved
package choice inside the released contract, not an assertion that the specification mandates a terminal error or no-op.
For unavailable/expired state, follow safe shared availability semantics rather than creating intent against absent work,
recreating a deleted Task or inferring the worker's outcome. Retention expiry/removal is not cancellation; do not retain
hidden payload copies or an unbounded cancellation ledger outside the established removal contract.

### Approved input, terminal and consumer-effect direction

Use the shared lifecycle concurrency mechanism for cancellation versus producer transitions and TASK-00169's actual
input admission. Input acceptance must preserve cancellation intent, accepted answers, immutable request identities
and single-use confirmation consumption. Intent alone is neither terminal state nor form refusal. Continuation must
expose current intent to the consumer's stopping decision without substituting Common policy for that decision or
promising atomicity with external effects. Revalidate applicable current authority; a previously accepted answer is
not a grant to continue after permission revocation.

Qualify both orderings of admission/continuation versus cancellation and terminal transitions. If an actual terminal
transition wins, stale input/producer writes cannot reopen it. If input/continuation admission wins first, later
cancellation cannot erase accepted evidence, restore consumed confirmation or claim already-performed work rolled
back. If cancellation intent wins first, later input cannot clear or bypass its visibility to the continuation
contract. Consumers may decide to continue despite cooperative intent; no automatic rejection of all input or automatic
confirmation refusal is inferred. Actual completed/failed outcomes remain possible after acknowledgment.

No network/job-control operation spans the admission transaction. Reconcile DBAL ownership with the existing unit-of-work
contract: reject unsupported enclosing transactions before mutation, leave unrelated caller work untouched and never
treat a savepoint release as durable acknowledgment. Define rollback/commit failure and uncertain response-loss outcomes.
If safe post-commit request facts are emitted, subsequent dispatch failure cannot erase intent or masquerade as rollback.
Do not copy private Task payloads/answers/diagnostics into general feeds or rely on an outbox introduced implicitly.

Consumer stopping is a separate effect. Record and test admission, observation, attempted stopping and actual outcome as
distinct facts. Failure/uncertainty cannot become a success acknowledgment for a failed durable admission, a forced
cancelled result, compensation proof or automatic retry of external stopping. Existing framework at-least-once delivery
under ADR-0024 grants no exactly-once job-control promise.

### Protocol and activation boundary

Implement actual tasks/cancel handling for the official io.modelcontextprotocol/tasks 2026-07-28 contract, with
per-request capability validation before mutation, bounded taskId/parameter shape, shared Command delegation and safe
errors. Success is an empty acknowledgment with resultType:complete, not the current Task payload or a stopped-job
receipt. Missing required client capability uses -32021 with the required shape; invalid/nonexistent taskId uses safe
-32602; internal failure stays distinct with safe -32603. Protect denied/cross-scope state and raw diagnostics.

Do not independently advertise partial extension support. TASK-00168 owns complete activation, existing guarded HTTP
composition, Mcp-Name/taskId and Mcp-Method mirrors, final outer serving-envelope qualification and combined Tool-start →
cancel → actual outcome/get journeys using this implementation. This TASK owns actual shared-use-case/method handling
and bounded semantic-output proof without waiting for activation. No circular implementation or evidence gate is added.

Do not use notifications/cancelled for durable Tasks. Existing McpToolExecution::cancel(), McpEventStream closure and
request-progress cancellation remain request-scoped and compatible. Original request or notification-stream disconnect,
TTL expiry and physical cleanup do not implicitly submit this cancellation Command. Polling/cancellation are independent
of Subscriptions/Mercure; no full-state notice-feed copy or live stopping guarantee is introduced.

## Validation and permissions

Current cancellation authority is independent from read, producer-update and execution-control permissions. Apply it
before mutation and on repeats/terminal no-ops; identifiers, capability declarations, human access and SUPER_ADMIN
labels confer no automatic grant. Use trusted scope/caller binding without introducing a principal issuer. Observation
and eventual status retrieval retain their own current disclosure checks. Do not reveal terminal outcome or retained
intent merely because cancellation acknowledgment is allowed.

Validate finite identities, parameter/status/error sizes and encoded output, including metadata, escaping and multibyte
cases at the owned boundary. No unchecked private reason/message or arbitrary status/result upload is introduced.
Use shared handlers/state invariants rather than presenter SQL or another permission policy. Bound bookkeeping and
storage, preserve removal/no-resurrection behavior, and distinguish storage failure from unknown/expired state safely.
