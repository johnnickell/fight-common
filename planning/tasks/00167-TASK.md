# Remove retained asynchronous Task data safely

## Outcome

An independently authorized consumer operation removes bounded selected asynchronous Task data, while shared reads
remain truthful about availability and late producer updates cannot silently recreate removed work. This is the
second approved slice of [TICKET-00049](../tickets/00049-TICKET.md), blocked only by TASK-00166's actual lifecycle.
It is an application removal/integrity use case, not a scheduled maintenance system or cancellation operation.

## Scope

- In scope: bounded explicit removal Commands/handlers and DBAL behavior for retained state, result/error, outstanding
  input and associated comparison material; current removal admission, atomicity and race/repeat semantics.
- In scope: actual creation/update/removal/Query evidence on SQLite/MySQL/PostgreSQL, compatibility/schema effects,
  documentation/CONTEXT.md, exact coverage and full build.
- Out of scope: automatic eligibility selection, schedules/jobs, mandatory archives/holds/recovery orchestration,
  cancellation/worker control, new MCP removal method and permanently retained hidden payload/tombstone stores.
- Out of scope: input/cancellation admission under TICKET-00050/00051, protocol activation TASK-00168 and live delivery.
  No reverse dependency on these consumers is needed to prove unavailable state through shared Queries.

### Approved mechanics and boundaries

Consumer composition selects a finite explicit set under current independent removal permission. Reading, creating or
updating a Task, knowing its ID, elapsed TTL and an administrative role label do not confer removal authority. Bound
selection count, identity sizes and database work; define atomic selection behavior and missing/repeat outcomes before
implementation. Do not silently skip denied entries and report an apparently complete deletion.

Remove state, original results/errors, outstanding input and associated retained comparison material coherently.
No hidden copy of protected payloads may survive in retry material solely to preserve an indefinite deduplication
promise. Define which comparison evidence is removed/retained and how its guarantee ends. Later producer updates to
an absent handle cannot upsert/recreate work. Define create/retry behavior after removal without claiming permanent
identity-memory or restoring an original result from data that no longer exists.

Coordinate creation/update/read/removal races using TASK-00166's actual persistence contract. Readers see a coherent
retained state or unavailable outcome, not a partially removed result/input map. Removal does not force terminal state,
cancel a consumer job, roll back external effects or authorize compensation. Future input/cancellation mechanics must
respect unavailable state and include their own integration evidence, without this TASK waiting on them.

TTL remains the duration from creation rather than a sliding inactivity timeout. Distinguish logical availability
and physical deletion, including retained rows past TTL and null/unlimited retention. Elapsed TTL alone does not prove
that data was deleted or work stopped. Removal eligibility, holds, policy/scheduling and external reconciliation remain
consumer responsibilities. Only assert a reason for absence if actually supported by retained safe evidence; no new
history/receipt ledger is required. Reads never become cleanup mutations.

Own actual atomic commit of the selected removal/integrity changes. Reject unsupported enclosing transactions before
writes and do not commit/roll back caller-owned work. Qualify pre-commit rollback and uncertain commit/response loss.
If safe removal facts are defined, dispatch them only after actual commit using existing contracts. Later subscriber
or publisher failure cannot restore data or masquerade as deletion rollback; no automatic outbox/replay is promised.

## Validation and permissions

Recheck trusted current removal authority for each request, including repeats/missing records. Conceal cross-scope
identities, presence, payloads and private diagnostics. Consumer eligibility is not a substitute for Common enforcing
the supplied authorization decision. Validate finite selection/identities and overflow before writes. Denial, invalid
selection and storage failure must not appear as successful complete removal. Shared reads retain their independent
current access rules; absence cannot grant access to cached/private comparison material.
