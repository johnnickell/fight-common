# Compose policy-free OAuth resource-server protection for MCP

## Outcome

Deliver the complete reusable OAuth resource-server use case around TASK-00105's guarded stateless MCP endpoint.
A consumer can publish configured protected-resource metadata, validate one Bearer credential through a strict
consumer implementation, hand only validated claims to consumer-owned authentication composition, and either
continue to MCP dispatch or return the protocol-correct HTTP authorization response. Existing HMAC remains a
separate, compatible consumer-selected composition rather than an alternate OAuth mode.

## Scope

- In scope:
  - Framework-neutral protected-resource metadata, validation requirements, validated-claims, typed failure, and
    Bearer-challenge contracts that implement the MCP `2026-07-28`, RFC 9728, RFC 6750, and RFC 8707 resource-
    server boundary without issuing credentials.
  - Strict extraction of one Bearer credential from `Authorization`; query-string and request-body token transport
    are unsupported, and an HMAC credential is never reinterpreted as Bearer.
  - A consumer-implemented token-validation port that receives the credential plus explicit issuer,
    audience/resource, expiration, not-before, purpose/type, allowed-algorithm, key-identity/rotation, and claim-
    shape requirements and returns neutral validated claims, including a normalized granted-scope set, only after
    every intrinsic token requirement succeeds. Common compares that trusted set with the current operation's
    required scopes after validation.
  - Resource-server orchestration that invokes a consumer-supplied validated-claims handoff before downstream MCP
    handling and maps missing credentials, malformed authorization requests, invalid tokens, and insufficient
    scopes to their distinct HTTP outcomes without JSON-RPC or Tool dispatch.
  - Optional PSR-15/PSR-17 metadata-response and Bearer-protection adapters over the project's existing required PSR
    contracts, but only when they preserve the complete neutral behavior. Consumers retain both routes and compose
    the claims handoff, validator, endpoint, and policy.
  - Package-owned conformance fixtures, consumer documentation, additive compatibility-manifest classification,
    and integrated acceptance ownership for TICKET-00027.
- Out of scope:
  - OAuth authorization-server operation, token issuance or introspection implementation, client registration,
    login, consent, refresh-token policy, authorization-code handling, or authorization-server discovery clients.
  - Routes or route selection, TLS/gateway/trusted-proxy deployment, Agent/user/principal types, authoritative
    principal lookup, permission checks, scope-to-permission mapping, Tool availability policy, or business
    authorization.
  - Selecting HMAC or Bearer for a consumer, requiring separate routes, accepting both schemes through one
    authenticator, or changing HMAC signing, credential, timestamp, signature, or nonce behavior.
  - Expanding `TokenDecoder` or `JwtDecoder` into OAuth validation, adding a default symmetric-JWT validator, or
    representing signature-only decoding as issuer/audience/time/purpose/key/scope validation.

## Validation and permissions

Protected-resource configuration must fail during composition for an invalid resource identifier, metadata URL,
empty `authorization_servers` list, invalid or duplicate authorization-server identifier, malformed or duplicate
scope, unsafe challenge value, or a missing intrinsic token-validation requirement. The metadata `resource` must be
the exact consumer-configured protected-resource identifier. Its `authorization_servers` field must preserve every
configured issuer in order without Common selecting one, and the consumer-owned well-known route must preserve RFC
9728 path/resource identity. Common renders configured metadata; it does not discover, choose, or operate an
authorization server.

Bearer extraction accepts exactly one case-insensitive `Bearer` scheme from the `Authorization` header and never
accepts a token from a URI query or request body. Missing authentication returns HTTP 401 with a Bearer challenge
and no error code where RFC 6750 forbids one. An invalid, expired, premature, malformed, wrong-signature/key,
wrong-issuer, wrong-audience/resource, wrong-purpose/type, disallowed-algorithm, unknown/retired-key, or otherwise
invalid token returns HTTP 401 with the protocol-safe `invalid_token` challenge. Malformed authorization transport
uses the pinned authority's HTTP 400 `invalid_request` behavior rather than being collapsed into authentication
failure.

After successful token validation, Common compares the accepted scope set with all scopes configured for the
current resource operation. Missing scope returns HTTP 403 with `error="insufficient_scope"`, every scope required
for that operation, and the protected-resource metadata location. It is an OAuth resource-access outcome, not a
Fight Common permission decision. Common never maps claims or scopes to a principal, Agent, user, permission, Tool,
or business authorization result. The consumer supplies the current-operation scope requirement to resource-server
composition before capability or Tool selection; Common does not derive it from an untrusted semantic request,
capability discovery, Tool arguments, or permission policy.

The consumer-supplied handoff receives only immutable validated claims after token and scope validation. It owns
mapping them to an authentication context and resolving an authoritative principal before downstream authorization.
No raw token, header collection, generic principal context, permission decision, or authorization policy enters the
MCP semantic request, capability, Tool, command, or query contract. Credentials, sensitive claim values, and
internal validation details are excluded from public bodies and redacted from diagnostics. A consumer-supplied
diagnostic port records the safe failure classification and unexpected `Throwable` details exactly once without
duplicating logs owned by TASK-00105's endpoint error path.

HMAC and Bearer use incompatible `Authorization` schemes. Documentation recommends separate routes while leaving
topology to the consumer. A consumer may choose another composition only if it keeps the two contracts unambiguous;
Common does not auto-select a scheme, share a nonce/key store, or fall through from one failed scheme to the other.

## Acceptance criteria

- [ ] A consumer-owned well-known GET can render configured RFC 9728 protected-resource metadata with exact
  resource identity, a non-empty `authorization_servers` array that preserves one or multiple configured issuer
  identifiers without selecting among them, HTTP 200, and `application/json`, without issuing credentials or
  making Common a route or authorization-server owner.
- [ ] A valid `Authorization: Bearer` request supplies one token and every required validation input to the strict
  consumer validator; only a complete success hands immutable neutral claims to consumer authentication composition
  before TASK-00105's endpoint can dispatch a capability.
- [ ] Intrinsic token validation covers signature/key identity and rotation, allowed algorithms, issuer, exact
  intended audience/resource, expiration, not-before, purpose/type, and claim shape, and yields a trusted normalized
  granted-scope set; signature-only `JwtDecoder` output is never accepted as equivalent proof.
- [ ] Missing authentication and invalid-token cases return their distinct HTTP 401 Bearer challenges, while a
  malformed authorization request returns the authority-defined HTTP 400 `invalid_request` outcome; none reaches
  claim handoff, capability selection, Tool invocation, command, query, or event dispatch.
- [ ] A fully validated token missing configured scopes returns HTTP 403 with one complete
  `insufficient_scope` Bearer challenge containing every current-operation scope and the protected-resource metadata
  location. It is never converted to JSON-RPC or a selected-Tool result.
- [ ] As a deliberate stronger interoperability requirement, every 401/403 challenge includes the protected-
  resource metadata reference and safely escapes configured values; missing credentials disclose no error detail,
  and public failures expose no token,
  claims, keys, personal data, internal class/storage detail, or consumer permission policy.
- [ ] A consumer-supplied redaction-aware diagnostic path records safe failure classification and unexpected
  `Throwable` details and traces exactly once in every environment; it never logs credentials or sensitive claim
  values, and public output remains deliberately classified or generic.
- [ ] Validated claims never become a Fight Common Agent, user, principal, permission, authorization decision,
  route, or authorization-server capability. The consumer owns claim mapping, authoritative principal resolution,
  authorization, and metadata/endpoint routing.
- [ ] Any PSR-15/PSR-17 adapters supplied preserve the complete metadata, extraction, validation, handoff, challenge,
  status, header, failure-ordering, and no-dispatch behavior of the neutral resource-server contracts; if that
  equivalence cannot be proved, no adapter is published and documented consumer composition retains the behavior.
- [ ] Existing `HmacAuthenticator`, `HmacRequestService`, nonce consumption, `Authenticator`, `TokenDecoder`, and
  `JwtDecoder` behavior remains unchanged. Bearer failure cannot consume an HMAC nonce or silently retry as HMAC,
  and HMAC failure cannot enter Bearer validation.
- [ ] Every public addition is classified in `compatibility/manifest.json` with explicit promised operations and
  behavior-focused additive evidence; this TASK covers every TICKET-00027 acceptance requirement end to end.

## Verification and evidence

Use focused unit/contract tests for metadata configuration, empty/invalid/duplicate and one/multiple authorization-
server identifiers, exact resource/path identity, JSON serialization, Bearer header parsing, duplicate/ambiguous/
malformed transport, immutable validated claims, typed validation inputs and outcomes, normalized granted scopes,
operation-required scope-set comparison, challenge quoting/escaping, public-safety, handoff ordering, and
suppression of every downstream effect. Consumer-validator fakes must prove every mandatory intrinsic validation
dimension is supplied and that partial validation cannot produce accepted claims. The same intrinsically valid token
must produce 403, never 401, when only a current-operation scope is absent.

Drive the neutral resource-server composition against TASK-00105's endpoint seam for metadata success, valid claim
handoff, missing credentials, malformed transport, representative invalid-token causes, insufficient scope, handoff
failure, and an unexpected redacted failure. Pair endpoint/capability/Tool/bus spies with those cases to prove no
dispatch before successful handoff. If PSR-15/PSR-17 adapters are supplied, repeat the matrix as adapter-conformance
tests; otherwise prove the documented consumer adaptation retains each neutral outcome. Diagnostic spies prove one
safe failure classification or unexpected failure with trace is recorded exactly once while credentials and
sensitive claim values are redacted; public responders expose only the classified safe error or a generic
unexpected-error message. Exercise an HMAC route beside the Bearer route to prove unchanged signature/nonce behavior
and no credential, failure, or state fallthrough. No Fight Access Control implementation is required.

This library/API change has no useful visual UI. Before evidence is TASK-00105's consumer-authentication placeholder,
the current signature-only JWT decoder, and the existing HMAC path. After evidence is a sanitized HTTP transcript
matrix for metadata, valid claims handoff, 400, distinct 401 cases, 403 insufficient scope, and unchanged HMAC
composition, with dispatch-spy counts. Save the artifacts, complete `./bin/build` log, independently captured exit,
tested-content identity, timestamps, warnings, and handoff under the TASK's ignored run directory. Hosted checks are
review/landing evidence for this public repository, not a builder polling requirement.
