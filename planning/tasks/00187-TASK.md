# Restore Task use-case ownership to CQRS handlers

## Outcome

Make the corresponding CommandHandler/QueryHandler the clear Application owner of each Task use case rather
than a payload-checking forwarder to a broad lifecycle service. John explicitly accepted this correction on
2026-11-02. Normally one cohesive Task Application refactoring PR.

## Scope

- Migrate orchestration from TaskLifecycle, TaskInputLifecycle and TaskCancellationLifecycle into their existing
  eight CommandHandlers and three QueryHandlers. Retain message identities and normal bus/filter dispatch.
- Each handler receives only the repository/read capability, existing TransactionalUnitOfWork, admissions,
  payload policy, clock and event dispatcher it actually needs. Name collaborators explicitly.
- Keep state-based transition/input/cancellation/retention rules with Task and its owned domain concepts.
  Handlers perform admission, loading, coordination, persistence and post-commit effects, not getter-based
  reconstruction of aggregate rules.
- Separate query coordination from mutation coordination. Remove provisional broad lifecycle services after
  migrating documented/owned callers; do not replace them with command/query managers or forwarding facades.
- Share real knowledge where needed, not scaffolding. Any extracted collaborator must have a demonstrated
  responsibility and observable contract; no one-class-per-private-method or configurable lifecycle engine.
- Preserve cancellation's committed reconstruction before initial acknowledgment and Task input's acquire-before-
  continuation semantics. No handler directly invokes another handler or bypasses bus filters.
- Keep ObservationRecorder: its coherent multi-command recording responsibility is outside this Task-specific
  removal. Notice orchestration and unrelated service registries are not blanket deletion targets.
- Update direct behavior tests, bus fixtures, composition examples, classification, Task guides, CONTEXT and
  CHANGELOG. Retain all current security/concurrency behavior.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Producer manages current retained Task | CreateTask, RecordTaskState, RemoveTasks | GetTask | TaskChanged, TaskDataRemoved | Same admitted atomic writes/removal and safe reads. |
| Supplier/consumer manages durable input | RequestTaskInput, SupplyTaskInput, AcquireTaskInput, RetireTaskInput | GetTaskInput | Existing TaskChanged | Same bounded forms, accepted answers and single-use acquisition. |
| Caller requests/observes cooperative intent | RequestTaskCancellation | GetTaskCancellation | Existing TaskChanged | Same durable intent and independent observation, never forced job stop. |

## Validation and permissions

Retain independent current grants and ordering: serialization before required admission, admission before concealed
lookup, active input validation before mutation, commit before fact delivery/acknowledgment. Do not combine grants
for constructor convenience. Safe null/rejection/error outcomes and protected data boundaries remain unchanged.

- [ ] Each Task handler visibly owns its named use case rather than forwarding the payload to a broad lifecycle object.
- [ ] Queries do not initiate business mutation/cleanup/TTL renewal; command transactions and post-commit effects stay explicit.
- [ ] Removed lifecycle classes have no replacement grab bag, forwarding graph or hidden handler-to-handler dispatch.
- [ ] Aggregate invariants, independent admissions, input consumption, cancellation reconstruction, expiry and retry semantics remain intact.
- [ ] Handler dependency sets are operation-specific and collaborator names describe the actual capabilities.
- [ ] Meaningful direct handler/bus/journey tests replace incidental lifecycle call-graph assertions without losing contract coverage.
- [ ] Current docs/classification and complete gate/independent Review/QA evidence exist.
