# Configure Notice persistence and recovery storage

## Outcome

Consumers independently name all four Notice tables and record, inspect, recover and remove Notices through the
separated persistence/transaction/recovery composition supplied by TASK-00186. Preserve ordered allocation, retained
retry evidence, truthful loss/continuation semantics and current independent permissions. This complete slice
normally owns one PR and supplies configured Notices to TASK-00201's combined live journeys.

## Scope

In scope:

- Explicit overrides with exact current defaults: `fight_notice_state`, `fight_notices`,
  `fight_notice_relationships` and `fight_notice_comparisons`; omitted names retain intentional defaults.
- Schema definition/install/validation/initialization, related FK/index checks, state/version/incarnation reads,
  position allocation/locking, repository lookup/append/removal, inspection and coherent recovery SQL using selected names.
- Apply names to TASK-00186's now-integrated separated repository, transaction and recovery-read implementations,
  not a duplicate conversion of its former combined store.
- Reuse TASK-00194's safe Adapter identifier mechanism, retaining data binding and inward contract separation.
- Preserve namespace incarnation/high-water/lost-through meanings, whole-notice ordering, comparison versions,
  deduplication/conflicts, exact-incarnation removal, confidential continuations and conservative loss/privacy rules.
- Existing post-commit publication/subscription consumers, relevant product tests, documentation and CONTEXT.md.

Out of scope: performing TASK-00186's refactor, Task/subscription conversion, new payloads/columns/continuation format,
new permissions or loss/replay/delivery guarantees, qualified names, implicit configuration/prefixes, migrations,
automatic renames/data transfer and unrelated architecture changes.

## Validation and permissions

Use shared ordinary-name validation and platform quoting in schema/runtime/FK and joined-read paths. Reject unsafe,
unsupported or qualified names without SQL interpretation or fallback; keep selection/scope values bound. Naming
remains consumer composition and never grants recording, removal, recovery, inspection or publication permission.

Preserve scope/identity/content admission, hidden/unknown/replaced-target indistinguishability, confidential
continuations and conservative cross-scope uncertainty. Empty rows in new selected storage do not prove that old
history was migrated or that continuity is complete. Preserve coherent recovery locking, caller-transaction rejection,
rollback/closure/uncertain-outcome and post-commit failure boundaries supplied by TASK-00186.
