# Bound MCP Request Reading and Decoding

## Outcome

Add finite request-byte and decode-depth safeguards to the existing guarded MCP `2026-07-28` endpoint. Read a
request within its configured budget before buffering or decoding unbounded content; reject excess safely without
capability dispatch. This is an independently useful endpoint feature, normally one PR, and can proceed before
Resources, Skills or Tools are complete. It does not reopen or reimplement the accepted HTTP foundation.

## Scope

- In scope:
  - Bounded body reading in the existing PSR HTTP handler, replacing the current unrestricted stream-to-string
    ingestion path. Enforce actual bytes consumed, not just a declared `Content-Length` or stream size.
  - Sensible finite request-byte and JSON decode-depth defaults with validated optional overrides and compatible
    composition. Validate decoder input before parsing; an already-allocated string is not retrospectively bounded.
  - Safe over-limit, malformed/deep JSON and stream-failure handling through the existing central transport/
    protocol response and sanitized diagnostic boundaries, without dispatching a truncated request.
  - Preservation of existing Origin, method/negotiation, metadata, mirror, protocol-version and invocation-guard
    ordering as applicable; compatible ordinary requests continue to dispatch normally.
  - Focused production/endpoint tests, behavior and API compatibility classification, consumer configuration and
    operational-boundary documentation, and a full product gate for this slice.
- Out of scope:
  - A replacement endpoint, generic HTTP body middleware, new framework adapter, authentication policy or route.
  - Reverse-proxy/PHP/PSR-factory/upstream middleware buffering, ingress admission, network timeouts or deployment
    configuration. Document these limits of the guarantee rather than claiming endpoint checks prevent earlier I/O.
  - Resource/Skill metadata, parser, raw-content and encoded-response implementation already owned by
    [TICKET-00028](../tickets/00028-TICKET.md) and [TICKET-00029](../tickets/00029-TICKET.md).
  - Tools, Skills, Resource-link output, combined endpoint qualification, SSE/cancellation, protected interactions,
    OAuth, Agent OS/Pi integration, release and deployment. [TASK-00122](00122-TASK.md) consumes this safeguard.

This TASK defines no new business commands, queries, events, schemas or Workflow transitions. Any domain effect
belongs to an existing capability after successful validation, never to rejected ingress. Reading the request and
sanitized diagnostics are technical effects. Invocation quotas and permissions remain consumer-owned decisions.

## Validation and permissions

Validate finite positive byte/depth configuration and reject unsupported or incoherent overrides. Preserve actual
byte accounting, including non-ASCII JSON. A declared content length or stream size may assist an early decision
but cannot replace bounded reading; absence, inaccurate values and non-seekable streams must not permit an
unbounded fallback. Avoid eagerly allocating the configured maximum or calling an unrestricted body conversion
before the limit check. A bounded lookahead may establish excess; never parse a truncated prefix as a complete
request or drain an oversized body merely to obtain a request ID.

Keep existing outer rejection order intact: a denied Origin must still be rejected before body access, and
method/content negotiation checks retain their pre-dispatch role. After a valid bounded decode, retain protocol,
standard/custom mirror and invocation-guard behavior before capability dispatch. The guard remains an invocation
policy seam, not a substitute for byte/depth limits or consumer authorization. Do not introduce credentials,
principals or permission policy into the decoder or bounded-reader boundary.

Use central protocol-safe/transport-safe rejection appropriate to the point of failure and the pinned protocol.
Only use a request ID established by valid processing; do not recover authority or identifiers by decoding an
unbounded/truncated body. Preserve existing malformed-request and unexpected-failure semantics where applicable.
Document any new bounded-ingress rejection mapping and its compatibility effect; do not invent an MCP-assigned
code or expose body fragments, credentials, paths, internal exception details or a successful truncated result.

The decoder currently relies on PHP's default JSON depth; this TASK makes the accepted finite depth policy and
validated overrides explicit. Existing valid in-budget semantic/HTTP consumers must remain compatible, including
construction/call patterns. Classify the deliberate new rejection boundary rather than claim all previously
accepted oversized requests remain accepted.

The guarantee starts at Common's reader/decoder. Upstream authentication middleware, the PSR implementation,
PHP/server infrastructure or a caller may already have buffered content; this change cannot undo that allocation.
Document consumer ingress responsibilities without adding a new deployment gate or silently modifying authentication.

## Acceptance criteria

- [ ] The existing guarded handler reads within a finite configured byte budget before unrestricted buffering or
  decode; misleading/missing length metadata cannot bypass the limit. No second endpoint or generic middleware.
- [ ] Valid requests below and exactly at the byte/depth boundaries preserve ordinary dispatch and response
  behavior; byte accounting includes multibyte text, and supported stream shapes include non-seekable bodies.
- [ ] Over-limit input is stopped using bounded work/read sizes without draining the full body or allocating the
  entire configured maximum eagerly. No truncated request or recovered partial ID is treated as valid.
- [ ] Excessive nesting, invalid overrides, malformed JSON, read failures and no-progress stream cases fail safely
  with no capability dispatch, no infinite read loop and no protected diagnostics in the public response.
- [ ] Existing Origin and other pre-body rejection checks still avoid body access. After valid decode, metadata,
  protocol, mirror and invocation-guard ordering remains effective before capability execution.
- [ ] Consumer authentication/authorization composition is unchanged. Tests make no claim to bound content already
  buffered by upstream middleware/infrastructure, and documentation clearly states that boundary.
- [ ] New public API/behavior changes are deliberately classified in `compatibility/manifest.json`; existing
  construction/call shapes and valid in-budget MCP/HTTP behavior remain compatible. Intentional rejection changes
  and safe error mapping are documented rather than hidden as signature-only compatibility.
- [ ] Consumer documentation covers defaults, validated overrides, finite reading/decode behavior, failure/recovery
  and upstream responsibilities. Keep applicable `CONTEXT.md` terminology aligned without changing policy ownership.
- [ ] Focused reader/decoder and real-handler evidence, the full `./bin/build` gate with exact owned-production
  coverage, and ordinary independent acceptance are recorded before completion. Nothing waits for TASK-00122.
