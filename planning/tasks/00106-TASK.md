# Register and discover explicitly opted-in MCP Tools

## Outcome

Deliver the explicit MCP Tool registration and discovery use case. A consumer registers only deliberately opted-in
`McpTool` implementations with complete method-level metadata, and `tools/list` returns a truthful,
availability-filtered, deterministically ordered page of safe Tool definitions. Invalid or duplicate registrations
fail during composition rather than becoming an accidental callable surface.

## Scope

- In scope:
  - Application-layer `McpTool`, method-level `#[McpToolInfo]`, `McpToolOutput`, and the minimal
    framework-neutral `McpProgressReporter` port required by the accepted Tool signature.
  - Tool metadata resolution and validation for canonical name, description, input schema, and output schema,
    including rejection of missing metadata, invalid schema declarations, duplicate canonical names, and
    capability metadata that contradicts the registered Tool set.
  - An explicit Tool registry and `tools/list` capability integrated with TASK-00104's generic MCP capability
    registry; no arbitrary Action, controller, or service discovery is permitted.
  - One request-scoped neutral availability boundary that receives resolved Tool metadata only. Filtering occurs
    before deterministic canonical-name ordering and cursor pagination.
  - Conservative `ttlMs: 0` and `cacheScope: private` list defaults, with an explicit consumer override only when
    the consumer owns a safe cache policy.
  - Additive compatibility-manifest classification and behavior evidence for every public declaration added by
    this TASK, plus consumer-facing registration and discovery documentation.
- Out of scope:
  - `tools/call`, argument validation, command/query mapping, output-schema runtime conformance, business-failure
    mapping, or CQRS envelope metadata enrichment, which belong to [TASK-00107](00107-TASK.md).
  - Live progress emission, response-mode selection, SSE, disconnect cancellation, and framework streaming proof,
    which belong to TICKET-00025. This TASK establishes only the stable reporter type required by `McpTool` and
    does not add deferred execution, generator callbacks, or partial result content.
  - Protected `input_required` interactions, OAuth resource-server behavior, consumer routes, framework responses,
    authentication, principals, credentials, Agent models, permission strings, and authorization policy.
  - Automatic framework collection unless implementation evidence proves that an existing supported composition
    seam can collect only explicitly opted-in Tools without broadening discovery.

## Validation and permissions

Validate `#[McpToolInfo]` on the accepted `McpTool::handle(ApplicationData $input, McpProgressReporter $progress):
McpToolOutput` method. Canonical identity, non-empty description, input schema, output schema, duplicate names, and
the schema dialect/shape supported by the implementation are composition concerns. Preserve the declared schemas
for discovery without treating PHP reflection or runtime-validation rules as an alternate schema source.

The neutral availability boundary receives resolved Tool metadata only. It may be request-scoped so a consumer can
close over its own authenticated context, but Common does not pass a principal, credential, raw arguments, headers,
permission, authorization decision, or generic principal-shaped object through the contract. The same availability
decision is consumed by TASK-00107 so direct invocation of an unavailable Tool is indistinguishable from an unknown
Tool. Fight Access Control owns any later Agent-aware implementation.

Cursor parsing, metadata validation, and cache-policy override validation reject malformed or unsafe input before
returning discovery data. Pagination must not index the unfiltered registry or allow cursor manipulation to reveal
an unavailable definition.

## Acceptance criteria

- [ ] A consumer can register an explicitly opted-in `McpTool` with method-level `#[McpToolInfo]`, and the Tool
  capability is advertised truthfully through TASK-00104's generic capability registry.
- [ ] Missing or malformed metadata, invalid canonical identity or schema declarations, duplicate canonical names,
  and contradictions between registered Tools and advertised capability metadata fail during composition.
- [ ] `tools/list` asks the request-scoped availability boundary about Tool metadata only, removes unavailable Tools
  before ordering and pagination, and never reveals the concealed Tool or the consumer's reason for concealment.
- [ ] Available Tools are ordered deterministically by canonical name and paginated with an opaque continuation;
  small result sets omit `nextCursor`, valid continuation is stable, and invalid cursors fail without discovery
  leakage.
- [ ] Discovery emits `ttlMs: 0` and `cacheScope: private` by default. A consumer override is explicit and cannot
  introduce a principal, authorization policy, or unsafe shared-cache default into Common.
- [ ] Discovery returns the declared names, descriptions, input schemas, and output schemas without reflectively
  discovering Actions or hydrating consumer commands/queries.
- [ ] The minimal `McpProgressReporter` public contract carries status/progress and cancellation observation only;
  it cannot carry final or partial Tool result content, and this TASK claims no live streaming behavior.
- [ ] Every public addition is classified in `compatibility/manifest.json`, its promised operations are explicit,
  and existing MCP-foundation, JSend, CQRS, validation, and consumer behavior remains unchanged.

## Verification and evidence

collisions, explicit capability registration, availability input isolation, filter-before-order behavior,
deterministic ordering, cursor continuation/rejection, cache defaults/overrides, and absence of automatic Action or
service discovery. Retain package-owned fixtures; no Fight Access Control implementation is required.

This is a library/API change with no useful visual UI. Before evidence is TASK-00104's generic semantic MCP
capability registry with no Tool capability. After evidence is an executable `tools/list` transcript and focused
dispatch/availability spies proving valid discovery, concealment, pagination, and representative composition
failures. Save those artifacts and the complete `./bin/build` log/exit receipt under the TASK's ignored run
directory. Run the canonical `./bin/build` before publication and surface warnings, notices, schema ambiguity, or
