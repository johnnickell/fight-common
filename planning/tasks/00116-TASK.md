# Restore DBAL schema-builder compatibility with supported dependencies

## Outcome

Restore the complete product gate after ordinary dependency resolution selects Doctrine DBAL 4.5, without
changing event-store, checkpoint, publication-cursor or publication-failure database schemas or installation
semantics. The maintainer authorized this separate repair after TASK-00115's build failed; at that implementation
checkpoint publication and merge were unauthorized. The later landing request authorizes PR publication, not merge.
The maintainer explicitly requires DBAL 4.4 support until version 2.0; raising the minimum is rejected for this repair.
The maintainer subsequently approved the exact four-site PHPStan compatibility exception and verification against
both DBAL versions.

## Diagnosis and reproduction

TASK-00115's `./bin/build` at base `5cbea189c10aca15df618a8587c57b82582a760b` selected DBAL 4.5.0 and
PHPStan 2.2.16. PHPStan reported four `method.internal` calls to `Doctrine\DBAL\Schema\Schema::__construct()`:

- `src/Adapter/EventSourcing/Dbal/DbalEventStoreSchema.php:29`
- `src/Adapter/EventSourcing/Dbal/DbalProjectionCheckpointStoreSchema.php:24`
- `src/Adapter/EventSourcing/Dbal/DbalPublicationCursorStoreSchema.php:24`
- `src/Adapter/EventSourcing/Dbal/DbalPublicationFailureRecorderSchema.php:25`

All four files are unchanged from that base. Installed DBAL marks the constructor internal since 4.5 and directs
callers to `Schema::editor()->create()`. Inspection of upstream DBAL 4.4.0 source confirms that editor API does not
exist there. `composer.json` currently allows `^4.4`; accepted ADR 0021 also names `^4.4` in the Slim composition.
A blind factory replacement therefore breaks the currently allowed lower range.

A disposable `method_exists` fallback qualification also fails the existing PHPStan configuration: the known
4.5 editor method makes the condition always true, and the legacy constructor call still violates `method.internal`.
At diagnosis no production fallback, analysis exception or dependency narrowing had been installed. The later
approved exception below changes only analysis configuration, not production calls.

## Accepted support and compatibility-exception decisions

The maintainer explicitly rejected removing DBAL 4.4 support before version 2.0. Preserve `^4.4` and the existing
consumer support contract. Version 2.0 is the earliest reconsideration point, not automatic removal authority.

The existing constructor remains runtime-compatible with installed DBAL 4.5: all four existing direct schema test
classes pass unchanged (**12 tests, 38 assertions**, PHP 8.5.7 / PHPUnit 13.3.5). The demonstrated failure is the new
upstream `@internal` annotation, not failed schema construction. Do not introduce reflection/dynamic indirection,
artificial database I/O, or a version-dependent branch merely to evade analysis.

The maintainer explicitly approved this smallest repair: retain the compatible production calls and permit only
the exact PHPStan `method.internal` constructor diagnostic at the four identified schema files, with one expected
occurrence per file, a documented compatibility rationale and a 2.0 review point. A missing match is allowed on
DBAL 4.4, where the constructor is public; more than one matching diagnostic per file remains a failure. Do not
suppress other internal calls or alter PHPStan severity/scanned paths. Verify unchanged runtime contracts against
both DBAL 4.4 and 4.5, then the ordinary complete gate. Retire the exception only when an authorized support-policy
change permits a fully supported replacement across the remaining range.

The exception received separate explicit approval after the support decision; it is not inferred from general
repair authority. Do not pin the ordinary build to an older DBAL or use release-only resolved mode to conceal failure.

## Integration qualification follow-up

The first full gate with the approved exceptions passed PHPStan, PHPCS, architecture, Rector and Unit coverage,
then exposed 13 existing `DoctrineDataTypeConsumerContractTest` failures on DBAL 4.5. The test constructed columns
before registering custom types, and registered them only in private `TypeRegistry` instances. DBAL 4.5's
`Column::setType()` now resolves the instance through `Type::getTypeRegistry()`. This is a test composition gap;
no production type conversion or stored schema change is required.

The bounded follow-up registers the legacy identity with the actual DBAL registry, proves its schema identity,
then overrides that same public type name with the canonical alternative and proves the same assertions. Each
case runs in an isolated PHP process so registry state cannot leak across cases or suites. All 13 type pairs and
91 assertions remain; both versions pass after correction. No additional analysis exception or new test harness
is added. Existing failing integration evidence is the regression-before-repair result for this test adjustment.
