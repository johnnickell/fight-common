# Configure durable Task storage

## Outcome

Consumers independently name the durable Task and schema/state tables and use existing lifecycle operations against
that storage. Schema installation, serialization, repository persistence and committed reads agree on the selected
names. This complete persistence/use-case slice normally owns one PR and supplies configured Tasks to TASK-00201's
combined live journeys.

## Scope

In scope:

- Explicit independent overrides for `fight_task_state` and `fight_tasks`, preserving exact defaults for omitted
  selections and released construction/named parameters.
- Schema definition/install/validation/initialization, state locking/version checks, repository save/get/remove,
  committed reads and all bounded payload/retry lookups using coherent configured names.
- Reuse TASK-00194's safe Adapter identifier handling without coupling to Event Store services or adding inward
  configuration contracts. Preserve the separate repository and transaction composition already accepted.
- Existing Task creation/producer updates, input/confirmation, cancellation intent, terminal integrity, revisions,
  polling/results, retention/removal and truthful committed visibility.
- Relevant fixtures, platform/use-case evidence, consumer documentation and CONTEXT.md alignment.

Out of scope: Notice/subscription conversion, new lifecycle or protocol operations, changing permissions/retention,
new worker/delivery guarantees, implicit configuration/prefixes, qualified names, migrations, automatic renames/data
transfer, payload/column changes and unrelated handler/value/namespace refactors.

## Validation and permissions

Apply the shared ordinary-name validation and platform quoting to every schema/runtime identifier, retaining value
binding. Reject unsafe/unsupported/qualified names without SQL interpretation or silent fallback. Consumers retain
connection/schema choice, database privileges, producer authority and independent Task/input/cancellation/read/
removal decisions. Naming grants no access and is never selected by MCP request fields.

Preserve idle installation requirements, partial/incompatible schema rejection, caller/nested transaction rejection,
rollback/reuse, closure/uncertainty and safe failure projection. A new selected table does not renew TTL, clear
accepted input, cancel work, prove completion or establish a successful migration.
