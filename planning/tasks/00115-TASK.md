# Adopt approved planning, ownership, and independent review conventions

## Outcome

Refresh Fight Common's planning navigation, work identity, ownership guidance, and independent review contract
without replacing its public-library architecture, compatibility promises, or verification gates.

The maintainer approved the bounded adoption recommendations and explicitly chose implementation-complete
`done`, the accompanying independent-review guidance, and preservation of existing release tests without new
packaging or release-process tests. This record is the implementation handoff, not evidence that the conventions
have already been installed. The local comparison evidence is under `.runs/notes/task-00115/adoption.md`.

## Scope

- In scope:
  - Planning-frontier generation and its local conventions, prospective TASK branch/PR identity, and completion semantics.
  - Independent Spec/Standards review, canonical review handoffs, and evidence-backed reconciliation of moving revisions.
  - Library-specific package/consumer ownership guidance and the release-test growth prohibition.
  - Reconcile affected instructions, project profile, standards, templates, terminology, links, and adoption digests.
- Out of scope:
  - Product PHP/API or namespace changes, dependency/version changes, consumer ruleset default changes, and a new test suite.
  - Release-tooling changes, deletion of existing release tests/probes, certification execution, or expanded packaging/release qualification.
  - Private workflow installation, other repositories, runtime enrollment, publication, merge, release, deployment, or archival.

## Accepted decisions

### Planning and work identity

1. Add a generated Roadmap planning frontier for non-terminal EPICs without TICKETs, TICKETs without TASKs, and
   parents whose children are all terminal and require explicit closeout review. Keep these planning actions
   distinct from executable TASK Board rows. Consider live and archived children so archiving cannot falsely
   make a parent undecomposed. Never close a parent automatically.
2. New TASK branches use `feature/task-NNNNN-<slug>` and TASK PR titles use `TASK-NNNNN — <TASK title>`.
   Preserve established branches/PR identities and the existing release/patch conventions. No retrospective renaming.
3. `done` means implementation acceptance and required local verification are complete. Mark implementation
   done before PR publication once those conditions hold; record independent review, publication, merge, release,
   and deployment separately. A green build alone does not establish acceptance, and `done` grants none of those
   later authorities. Keep pending review explicit in completion notes and handoffs. Preserve truthful historical
   records; do not manufacture review approval or rewrite prior outcomes to fit the new terminology.

### Independent review

4. Review independently attempts to disprove the exact TASK's acceptance claims. Disclose authorship, direction,
   repairs, and material evidence contributions; a material contributor cannot independently accept the work.
   One independent reviewer may conduct both named Spec and Standards passes. Replace the fixed two-agent/model
   requirement and percentage-scoring contract rather than layering another review system over them.
5. Adopt five Spec criteria: intended outcome/scope; validation/rejection/authorization at exposed entry paths;
   messages/state/side effects; failure/compatibility/recovery/security; and acceptance evidence. Adopt five
   Standards criteria: ownership/dependencies/injection; adapter boundaries/safe output/server authority;
   naming/PHP/documentation/local conventions; meaningful owned-behavior tests; and planning/delivery/verification
   hygiene. Account for every TASK acceptance criterion. Preserve the identity and meaning of historical criteria
   and findings rather than silently relabeling old reports into the new catalog.
6. Every criterion records `Pass`, `Fail`, `Unverified`, or justified `N/A`, with traceable evidence and limitations.
   `accept` requires all applicable criteria to pass, all TASK acceptance covered, and no blockers. Any Fail or
   Unverified requires `revise`. No percentage averaging or score override produces reviewer acceptance.
   Explicit human delivery decisions remain separate from the review verdict and cannot bypass verification or
   hosted protections. A review neither fixes implementation nor changes planning status, publishes, or merges.
7. The canonical handoff is `<base-worktree>/.runs/reviews/<TASK-ID>/review.md`, with a version-3 header identifying
   TASK, target branch, full base/head OIDs, target status, and verdict. Resolve the base through Git metadata and
   registered worktrees; keep the ignored report directory within that base without following symlinks. Retain
   previous history, atomically replace only the canonical report, and read it back. Record dirty snapshots with
   file identities/digests or retained patches. An unwritten/unreadable report is an incomplete handoff, not an
   actionable chat-only acceptance. Document how existing Common handoffs are reconciled without deleting history
   or asserting a prior report accepted different content. Existing version-2 canonical reports remain readable.
8. A changed commit ID alone neither proves a defect nor requires another independent review. Retain acceptance
   only with a recorded provenance bridge proving mechanical reconciliation: old/new base and head, effective
   diff, conflict resolutions, affected dependency interactions, and required fresh verification. Semantic changes,
   uncertain integration, or failed checks require renewed independent review. Do not rewrite the original verdict
   to pretend it covered new revisions. Preserve Common's GitFlow/merge policy and published history; this decision
   does not adopt a different landing workflow or authorize rebasing, force pushes, cleanup, or merge.
9. Review checks the effective diff, directly affected consumers, success/rejection/failure paths, and claimed
   evidence without widening into unrelated debt. Countercheck findings, retain IDs and dispositions across rounds,
   and distinguish demonstrated defects from missing evidence and advisory improvements. A verified builder receipt
   remains usable under the existing input-equivalence rule; do not rerun gates merely to accumulate receipts.
   Review may run the canonical gate when necessary to establish acceptance, reconciling the current blanket
   reviewer-rerun prohibition in Review/Testing together. Focused checks remain appropriate. Preserve exact unit
   coverage, complete gate requirements, public-repository hosted-check policy, warnings, and incomplete evidence.

### Library ownership and testing boundaries

10. Common owns reusable capabilities and their promised behavior. Consumers own application policy, permissions,
    routes, use-case composition, and operational choices unless an explicit package contract says otherwise.
    Use owning package contracts directly; avoid aliases or forwarding wrappers without demonstrated behavior.
    Consumer orchestration needs actual owned policy or coordination. Do not confuse these rules with Common's
    required public compatibility aliases, nor remove reusable framework integrations.
11. Preserve accepted Application-layer protocol semantics, the portable container, capability-first adapters,
    the exact CronExpression allowance, current transaction contracts, and inward dependency enforcement. Do not
    transplant application-only namespaces, protocol placement, or blanket external-effect transaction prohibitions.
12. Preserve existing release tests and certification probes/checks. Do not add new tests of packaging or the
    release process, in product suites, a release suite, or a renamed separate harness. Inventory the actual
    retained checks rather than assuming a legacy test directory is active; do not recreate a removed suite.
    Validate tooling directly with its owning commands when separately authorized. Ordinary product verification
    remains distinct from release certification, and this TASK requires no certification run.
13. The prohibition does not remove meaningful tests of published runtime behavior, the shipped coding standard,
    or framework integration contracts. Those are Common product capabilities, not release-process mechanics.
    Preserve ADR 0004's versioned ruleset contract, exact direct-unit statement coverage, and ordinary library
    dependency resolution. Do not weaken gates or expand the existing release suite to prove this adoption.
