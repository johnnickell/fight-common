# Align MCP aggregate namespaces and move concrete Tools to adapters

## Outcome

Make Domain/Application aggregate ownership consistent and move concrete MCP Tool input/output/schema mapping
out of Application use cases. Keep the approved Mcp umbrella and generic Application protocol engine. John
accepted this architecture recommendation on 2026-11-02. Normally one cohesive namespace/presentation PR after
the ownership/type refactors, not a repeat of TASK-00181's foundation namespace migration.

## Scope and target map

- Keep `Domain/Mcp/{Session,Phase,Observation,Detail,Notice,Task,Subscription}` concept ownership. Activity and
  Usage remain meaningful domain value branches rather than invented independently persisted aggregates.
- Align `Application/Mcp/Execution/{Session,Phase,Observation,Detail}` to `Application/Mcp/{Session,Phase,Observation,Detail}`.
  Keep handler, Data, Exception and semantic capability/Service branches with their owning concept. Place
  ObservationAdmission with Observation; transaction interfaces removed by TASK-00184 must not reappear.
- Move concrete execution inspection Tools to `Adapter/Mcp/Tool/{Session,Phase,Observation,Detail}` according to
  the Query they expose; move RecoverNoticesTool to `Adapter/Mcp/Tool/Notice`. Tool attributes, argument mapping,
  Tool schemas and public-safe result mapping are presentation, not a second Application workflow.
- Cohesive shared cross-aggregate Tool support may use `Adapter/Mcp/Tool/Execution`; do not copy schemas into
  every aggregate folder or add forwarding adapters around unchanged Tool implementations.
- Put aggregate-specific MCP DBAL persistence/readers under `Adapter/Mcp/Persistence/{Aggregate}/Dbal`.
  Shared execution serialization/schema support may use `Adapter/Mcp/Persistence/Execution/Dbal` when it owns
  real cross-aggregate storage knowledge. Task/Notice/Subscription storage follows the same meaningful capability
  structure. Keep generic DbalTransactionalUnitOfWork under `Adapter/Persistence/Doctrine`.
- Retain `Adapter/Mcp/Http`, native MCP integrations, `Adapter/ServiceContainer` and the generic semantic MCP
  engine/ports in Application. Do not move all protocol semantics merely because concrete Tools move outward.
- Reconcile ADR 0023 visibly with the approved destinations and preserve TASK-00177's historical acceptance.
  No speculative V1 folder, transport renaming or MCP identifier changes.
- Migrate owned imports, reflection/attribute registrations, fixture/runtime scripts, mirrored tests, public/internal
  manifest and maintained namespace/component/setup docs, CONTEXT, README examples and CHANGELOG together.
- Inspect tags at execution: directly move never-released types without snapshot bridges; maintain supported
  released names with proved operation-specific compatibility/deprecation, not a blanket alias/subclass strategy.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer opts into execution/Notice inspection Tools | No new mutations | Existing shared inspection/recovery Queries through QueryBus | None | Same Tool identifiers, schemas, bounded results and independent authorization. |
| Consumer registers aggregate handlers and DBAL adapters | Existing messages | Existing Queries | Existing facts | Clear aligned namespaces with identical lifecycle/storage behavior. |
| Released consumer retains a supported old name | Unchanged | Unchanged | Unchanged | Preserve actually promised operations for the required compatibility window. |

## Validation and permissions

Tool availability remains distinct from shared Query authorization; presentation always dispatches through the
configured bus. Safe projections never expose entities/protected bodies beyond current grants. Preserve request
limits, protocol metadata, response budgets, transport mirrors, guarded streaming and fresh disclosure ordering.
Namespace/registration presence grants no authority. Schema and external-effect behavior are unchanged.
