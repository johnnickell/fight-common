# Follow Tool and Resource changes through live MCP

## Outcome

Authorized clients can follow Tool/Resource changes through the existing guarded HTTP endpoint, with actual live
subscription delivery, technical lifecycle tracking and retained-notice recovery after delivery failure. Deliver
this complete vertical outcome in one normal PR, not a protocol transcript or interfaces awaiting later wiring.

John approved this first slice of [TICKET-00047](../tickets/00047-TICKET.md). Its only blocker is
[TASK-00161](00161-TASK.md), which supplies shared authorized retained recovery and its MCP polling Tool, transitively
including notice recording/removal. [TASK-00163](00163-TASK.md) adds operator-facing subscriber Queries;
[TASK-00164](00164-TASK.md) adds optional Prompt integration. Neither is a blocker for this live path.

## Scope

- In scope: explicit `subscriptions/listen` composition, Tool/Resource catalog changes and selected Resource updates,
  acknowledgment/filter/correlation semantics, current disclosure permission and finite HTTP stream lifecycle.
- In scope: cross-process notice sourcing through shared Queries, actual DBAL technical registration/freshness/closure
  storage on SQLite/MySQL/PostgreSQL, bounded cleanup, native response/emitter integration and polling recovery.
- In scope: compatibility, schema/composition, safe failure/diagnostics, tests, docs/CONTEXT.md and the full local gate.
- Out of scope: Prompt delivery (TASK-00164), public current-subscriber Queries (TASK-00163), Task-specific full-state
  notifications, Mercure, introspection, consumer dashboard/identity policy and deployed Agent OS/Pi qualification.
- Out of scope: extra transports/endpoints, `resources/subscribe`, HTTP GET subscriptions, automatic Resource reads,
  mandatory broker/outbox, historical audiences, receipt ledgers, exactly-once delivery or saved resumable subscriptions.

## Use cases and contracts

Operation labels describe responsibilities, not final PHP names. Preserve `CommandBus::execute()`,
`QueryBus::fetch()` and `EventDispatcher::trigger()`. Technical stream lifecycle writes do not require business
Commands/events; protocol notifications are not authoritative application or Workflow facts.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Client opens a supported stream | Protocol `subscriptions/listen`; no business mutation | Current capability/filter/access checks | `notifications/subscriptions/acknowledged` first | Register owned technical stream and acknowledge only accepted requested support |
| Safe retained change becomes available | Recording remains with TASK-00158 | Shared retained-notice Queries and fresh disclosure checks | Requested standard Tool/Resource notification | Emit bounded correlated metadata, not protected bodies or a delivery receipt |
| Stream idles or caller disconnects | Technical heartbeat/closure, not a Workflow Command | Bounded source checks | Transport keepalive where configured, not an invented MCP notification | Observe liveness within documented limits; release owned resources |
| Server closes or delivery/source/tracking fails | Technical closure | Safe failure assessment | Standard completion where a graceful close is possible | Stop delivery honestly; leave stored notices intact |
| Client recovers and reconnects | New independent listen request | TASK-00161 polling under current access | New acknowledgment, not replay proof | Retrieve retained notices independently and establish a new stream |

### Approved source and protocol mechanics

Follow MCP `2026-07-28` and the [subscription contract](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions).
Validate the requested filter, acknowledge its supported/permitted subset first and never send an unrequested type.
Support `toolsListChanged`, `resourcesListChanged` and selected `resourceSubscriptions` only when their actual
capabilities are enabled. Unsupported optional families, including Prompts until TASK-00164 is composed, must not
be advertised/acknowledged as available. Consumer topics are not invented standard filters or notification names.
Define malformed, empty, false, duplicate and unsupported filter/reference handling without disclosing hidden data.

Carry the originating JSON-RPC ID with its exact type in standard subscription metadata on acknowledgment,
notifications and graceful completion. It is not a globally unique registration key, notice ID or authority token.
Concurrent callers may reuse the same ID without sharing registrations, authority or frames. Resource URI matching
must follow the supported documented protocol cases without path/network inference or automatic target reads.

Use bounded reads through shared retained-notice Query contracts for cross-process sourcing, not only an in-process
event listener and not adapter SQL/duplicate permission policy in the HTTP presenter. Define the live starting boundary
and behavior for concurrent recording/removal, missing history and access change. A new listen is not historical
replay or a promise to bridge every gap; recovery remains TASK-00161's qualified Query/Tool contract. Unavailable source
or unestablished continuity cannot silently look healthy. Mapping accepts only explicitly supported safe changes;
notice fields do not become arbitrary wire payloads or grant permission to signal a concealed catalog change.

### Approved tracking and delivery mechanics

Common supplies actual DBAL technical registrations shared across processes on SQLite/MySQL/PostgreSQL. Record trusted
subscriber identity, requested versus accepted filters, permitted topic/reference context, ownership and observed
lifecycle/freshness. Owner-bound heartbeat/freshness expiry and bounded cleanup prevent permanent confidently active
abandoned rows. Late updates must not revive closed registrations or mutate another stream; reconnect owns a new
registration. Define state transitions, schema/versioning, cleanup limits, observation scope, clock assumptions,
concurrency and store-failure behavior. Do not retain credentials, hidden bodies or an unbounded historical audience.

Freshness means observed technical state, not a permission lease, saved subscription, confirmed client receipt or
processing. Abrupt death without a final write becomes stale/uncertain under the documented observation contract.
Storage faults cannot masquerade as healthy tracking; fail opening/stop delivery safely as appropriate. No transaction
spans a live stream or network wait, and technical writes must not commit/roll back unrelated caller work. TASK-00163
consumes these qualified records; basic lifecycle proof belongs here without a reverse dependency on public inspection.

Bound active registrations/streams, filters, scanned work, pending items/bytes, encoded frames and lifetime. Finite
waits and transport-level keepalives permit idle disconnect observation without unrequested MCP notifications. Account
for slow readers, actual encoded JSON/SSE framing and applicable metadata; never use an unbounded queue or silently
pretend dropped live output was delivered. Specify observable closure/failure and retained recovery. Recheck permission
before emission, including queued notices, rather than caching the opening decision. Already sent bytes cannot be retracted.

Extend guarded handler/response/emitter/native adapter composition without buffering subscriptions or bypassing Origin,
request limits, mirror validation, invocation admission and consumer authentication. Current `McpEventStream` drives
`McpToolExecution`; its concrete-type checks in emitters/native adapters do not automatically support subscriptions.
Reconcile registry rejection and conflicting capability flags with real enabled support; do not disable validation
globally. Preserve direct JSON and opt-in Tool progress. Document runtime timeout/backpressure limits and unsupported
buffering configurations; PHP-SAPI write behavior is not an instant-disconnect or preemptible-I/O guarantee.

## Validation and permissions

Consumers supply trusted identities/current scope and own authorization policy. Validate finite filter/reference/ID
inputs and output before disclosure. Apply fresh notification permission to topic, Resource and identity metadata and
to catalog-change signals themselves; an available family or small payload is not permission to reveal hidden activity.
Opening success, client capabilities, recipient IDs, SUPER_ADMIN labels and human access are not Agent grants.

Do not leak protected message/tool/output bodies, full Task state, concealed references or private exceptions through
acknowledgments, notifications, failure/completion or diagnostics. Structural validation does not universally redact
consumer-supplied metadata. Unknown/denied cases follow a safe documented contract. Subscriber inspection will require
separate authority in TASK-00163. Technical tracking is not application authority or evidence that anyone processed data.
