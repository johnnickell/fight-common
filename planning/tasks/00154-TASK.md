# Remove protected detail while preserving execution evidence

## Outcome

An authorized consumer operation can remove explicitly selected, bounded protected detail while preserving
session/phase summaries, referential integrity and truthful subsequent inspection. Deliver ordinary removal
Commands, current admission, atomic DBAL changes and integrated read/retry evidence together as the second approved
vertical slice completing [TICKET-00042](../tickets/00042-TICKET.md).

TASK-00153 supplies protected Queries and TASK-00152 supplies safe activity/reference Queries for the complete
removal outcome. Their dependencies transitively supply recording/storage and safe summary Queries. These are
implementation/evidence dependencies; neither earlier TASK depends on this one. Qualify SQLite, MySQL and PostgreSQL
using the existing database-backed detail implementation. No global execution priority is assigned.

## Scope

- In scope: ordinary authorized removal of explicitly selected bounded detail, related content/link changes,
  commit-before-acknowledgment, preserved summaries/integrity and explicit repeated/missing-record behavior.
- In scope: integrated protected/safe reads after removal, concurrent read/removal/recording retries, retained
  identity/comparison guarantees, safe removal facts where specified, compatibility, docs and full verification.
- Out of scope: retention eligibility/holds, completion-time cleanup policy, scheduling, job batching/recovery,
  archival, external filesystem/object-storage atomicity, MCP removal Tools, UI, Workflow transitions and capture.

Reuse the actual recording/storage transaction boundary from TASK-00147–00149; do not create a second body store
or change the void Command bus. All related database content/link changes for one Command commit together or not
at all, and successful acknowledgment follows the real commit. An inner savepoint is not enough if an outer
transaction remains uncommitted. Reject unsupported already-open transaction composition before writes rather than
committing/rolling back unrelated caller-owned work. A timeout can leave outcome uncertain; no atomicity extends
to external files or the consumer's multi-step maintenance job.

Preserve session/phase summaries and valid relationships after removal. Public safe and protected Queries must
agree with actual retained evidence; a missing body cannot still be advertised as available. Keep supplied
expired-content markers where applicable without inventing a reason from absence. Reads racing with removal must
have documented truthful semantics; no multi-page/chunk retention lease or guarantee to retract already returned
bytes is introduced. Do not retain deleted content merely to complete an older browsing sequence.

Coordinate with TASK-00149's recording owner: specify the effect of retaining or deliberately removing required
identity/comparison records on later identical/conflicting retries. No indefinite deduplication, undeclared copy of
protected bodies in safe retry material or silent automatic restoration is promised. Test both retained and removed
comparison-record cases using the appropriate owned operation/fixture, without expanding this TASK into a generic
metadata purge or maintenance orchestrator. Explicit later submissions must follow the documented recording rules.

If removal emits domain events, use safe observation facts, not raw content or Workflow transitions. Dispatch is
post-commit and may be lost; subscriber/dispatch failure cannot undo deletion or be represented as storage rollback.
No outbox, exactly-once publication or automatic delivery replay is required.

## Validation and permissions

Current consumer-supplied removal permission is independent of read permission. A trusted cleanup caller still
supplies permitted scope; a detail ID, read grant or previous successful removal is not authority. Validate bounded
selection, supported detail kinds and every scope/session/phase/detail relationship. Recheck admission for repeats
and handle unknown/denied identities without revealing concealed metadata or body content.

Consumers own retention periods, eligibility, holds, scheduling and archival coordination. Common enforces supplied
access decisions and integrity, not a completion-time eligibility rule or new human/Agent role hierarchy. Safe
errors and any events must not contain deleted bodies or other protected data.
