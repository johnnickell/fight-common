# Record durable execution sessions and phases

## Outcome

Trusted consumer instrumentation can record and reconstruct durable session/phase observations through shared
Commands and a working Doctrine DBAL adapter. Deliver the typed model, admission, handlers, schema composition,
retry/transaction behavior and safe post-commit events together as the first vertical slice of
[TICKET-00040](../tickets/00040-TICKET.md) under [EPIC-00009](../epics/00009-EPIC.md).

John approved three vertical feature TASKs and DBAL persistence qualified on SQLite, MySQL and PostgreSQL. This
TASK has no implementation blockers. No global execution priority is assigned; dependencies order the recording
slices. Planning approval is not authority to implement or publish, and map-wide TASK decomposition remains ongoing.

## Scope

- In scope: typed/versioned session observations with consumer scope/reference, observed timing and reported
  outcome; phase observations with session/parent links, performing Agent identity, name, attempt and observed
  timing/outcome. Preserve unknowns rather than inferring completion from a missing record or process result.
- In scope: trusted producer/scope admission, bounded namespaced extensions, stable observation identity and
  same-content retry comparison, explicit failures, per-Command atomic database writes and schema composition.
- In scope: a reusable DBAL adapter with actual SQLite, MySQL and PostgreSQL evidence; precise timestamp/full UUID
  storage, safe committed-observation events, public compatibility classification and usage documentation.
- Out of scope: activity/usage recording (TASK-00148), protected bodies (TASK-00149), public inspection Queries
  (TICKET-00041/00042), MCP presentation, UI, automatic capture/redaction, Agent directory, Workflow transitions,
  mandatory audit, OpenTelemetry, outbox/guaranteed delivery and maintenance/archival orchestration.

## Use cases and contracts

Labels describe operation responsibilities, not predetermined PHP names or a fixed table layout.

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Trusted instrumentation records session evidence | Record session observation through `CommandBus::execute()` | Internal reference/admission checks; no public inspection Query here | Safe session-observation fact after commit | Atomically persist versioned observation and related database records |
| Producer records phase evidence within its permitted session/parent scope | Record phase observation | Internal session/parent checks | Safe phase-observation fact after commit | Persist admitted phase relationships and performing Agent reference |
| Producer retries after uncertain acknowledgment | Repeat the recording Command with the same producer-scoped observation identity | Internal retained-identity/content comparison | Documented retry dispatch behavior; no guaranteed event replay | Deduplicate matching content, reject conflicts and preserve original recording time |
| A write or later event delivery fails | Same recording operation | Reconstruction demonstrates actual committed state | No event for rolled-back writes; later dispatch failure is distinct | Roll back related pre-commit writes or preserve committed records despite delivery failure |

Preserve the existing void Command bus and `EventDispatcher::trigger()` contracts. Observation identity is distinct
from the session/phase subject it describes; later evidence must not overwrite a conflicting observation under a
reused identity. Do not import Event Store stream retries, global positions or mandatory event-sourced aggregates
from [ADR 0001](../adr/0001-event-sourcing-contract.md) or [ADR 0002](../adr/0002-projection-delivery.md).

Define and document deterministic same-content comparison for versioned submitted data. Server-assigned recording
time must not turn an otherwise identical retry into a conflict. Retained identity/comparison records bound the
retry guarantee; deletion does not promise indefinite deduplication. Exact representation and event catalog belong
to implementation within the approved behavior, with documented finite limits rather than unbounded payloads.

Identify the owner of the actual database transaction. Reconcile the existing `TransactionalUnitOfWork` contract
with the chosen DBAL composition. An inner savepoint/released nested transaction is not commit-before-acknowledgment:
reject unsupported already-open transaction composition before writes rather than returning success before the
outer commit. Never commit or roll back unrelated caller-owned work to manufacture this guarantee. Successful
recording acknowledgment follows the real commit; a later dispatch failure cannot be reported as a storage rollback.
Timeout may leave commit outcome uncertain. No transaction with observed work or external effects is promised.

## Accepted design revision: ordinary aggregate roots

John requested aggregate-scoped namespaces and first-class Session and Phase models/repositories, then clarified
that **aggregate root means the general DDD responsibility**, not inheritance from
`Domain\EventSourcing\AggregateRoot` or adoption of event sourcing. This revision supersedes the combined
`ObservationStore` design and flat namespaces described in the historical implementation checkpoints below.
It is accepted design; the current implementation checkpoint below records local progress, separately from pending
independent Review and QA.

### Domain ownership and namespaces

Execution is the bounded context for recorded execution evidence, not one aggregate containing every session,
phase and observation. Define ordinary persisted Session, Phase and Observation aggregate roots, each with its own
Domain repository contract. No shared base class, event replay, stream versioning, Event Store persistence or
`EventSourcedAggregate` implementation is implied or required. Domain events do not imply event sourcing.

- `Domain/Execution/Session/Session.php` owns project-scoped session identity and its stable consumer relationship;
  `SessionRepository` retrieves and persists that aggregate.
- `Domain/Execution/Phase/Phase.php` owns project-scoped phase identity, session/parent references, performing Agent,
  name and attempt; `PhaseRepository` retrieves and persists that aggregate. References to other roots do not make
  them owned child objects requiring an unbounded graph load.
- `Domain/Execution/Observation/Observation.php` owns producer-scoped evidence identity and immutable submitted
  content; `ObservationRepository` retrieves and persists recorded evidence with its stable recording time.
  Define the existing `RecordedObservation` receipt's relationship to the root without creating a competing root
  or repository merely for the receipt.
- Commands belong beneath the owning aggregate: `Domain/Execution/Observation/Command/RecordSessionObservation.php`
  and `Domain/Execution/Observation/Command/RecordPhaseObservation.php`.
- The safe fact belongs at `Domain/Execution/Observation/Event/ObservationRecorded.php`.
- Place supporting values/references with their owning concept; references are not substitutes for the new roots.
  Keep private state and typed accessors throughout.

Session and Phase are first-class recorded subjects, not authoritative consumer Workflow state. Do not infer
success, terminal state or review acceptance from missing evidence, phase names or surrounding execution results.
Their persistence is supported by planned independent retrieval: [TASK-00150](00150-TASK.md) lists/summarizes
executions without counting observations as executions; [TASK-00151](00151-TASK.md) retrieves a selected execution
summary and paginated phases; [TASK-00152](00152-TASK.md) retrieves selected phase activity. Those public inspection
Queries remain in their existing TASKs. They may use dedicated read contracts/results instead of hydrating whole
aggregates or turning write repositories into reporting services. This revision does not add those Queries here.

### Application, repositories and atomicity

Group recording orchestration under `Application/Execution/Observation/`, using responsibility subnamespaces:
`CommandHandler/` for the two handlers, `Exception/` for recording failures and `Service/` for
`ObservationRecorder`. Place admission and transaction contracts according to their actual responsibilities;
do not create empty Session/Phase Application folders or forwarding services solely for symmetry.

Replace the combined store's responsibilities rather than simply renaming it. Domain repositories own aggregate
retrieval/persistence; Application owns current admission and use-case/transaction coordination; DBAL implements
the persistence and real transaction boundary. Domain repository interfaces must not inherit the Application-owned
`TransactionalUnitOfWork`. Repository implementations share the same transactional connection and recording
serialization boundary; separate repositories must not introduce separate commits or weaken independent-writer
retry and relationship integrity. Define the shared transaction composition explicitly before replacing the store.

Preserve admission before concealed lookups on every attempt, session/phase/parent consistency, immutable subject
relationships, producer-scoped same-content deduplication, changed-content conflict, atomic relationship/evidence
writes, original recording time on retry, caller-transaction rejection, honest uncertain outcomes and safe
post-commit dispatch. A matching retry emits no additional fact. Do not move SQL-specific locking into Domain or
make callers orchestrate repository writes. Consumer-facing recording remains a void Command bus operation.
