# Express Transport-Neutral Application Failures

## Outcome

Consumer command/query handlers express explicit failure intent through a reusable transport-neutral exception
vocabulary, retaining diagnostic/catchability behavior without importing HTTP or making diagnostics public-safe.
Deliver all eleven categories, validation reconciliation, complete behavior evidence and documentation in one
independently reviewable PR under [TICKET-00038](../tickets/00038-TICKET.md) and
[EPIC-00008](../epics/00008-EPIC.md).

John approved this code-first feature TASK and its recommended contracts on 2026-10-06. It has no TASK blockers or
execution priority. TICKET-00039 consumes this vocabulary and separately owns safe HTTP translation through
[TASK-00143](00143-TASK.md), followed by the independent Symfony/Laravel TASK-00144/TASK-00145 integrations. Existing validation cleanup/TASK-00127 is not a prerequisite or part of this slice. This is
additive next-minor scope subject to actual compatibility assessment, not an exact version or implementation/release
announcement. No checkout/worktree choice or implementation authority is supplied by planning approval.

## Scope

- In scope: abstract ApplicationException extending Common's Domain/Exception/SystemException and all eleven
  deliberately extensible categories under Application/Error/Exception, retaining the existing Catchable family.
- In scope: ordinary diagnostic message/integer-code/previous-Throwable behavior, explicit category semantics,
  optional neutral retry-delay metadata for RateLimitExceeded/ServiceUnavailable, and consumer Application subtypes.
- In scope: reconcile InvalidInput/RuleViolation with existing structured validation without mandatory replacement,
  direct category/subtype tests, representative synchronous handler propagation, compatibility/public classification,
  failure reference documentation, docs/validation.md and CONTEXT.md, full verification and independent review.
- Out of scope: HTTP statuses/headers/JSend/native responses in these exceptions, public-message/data APIs, arbitrary
  header/context bags, automatic classification of old infrastructure failures, authorization/authentication policy,
  Domain-to-Application dependencies, retry/scheduling/rollback mechanisms, bus redesign and generic policy engines.
- Out of scope: immediate legacy handler/default changes, validation-state repair, new business messages/schema/
  persistence, framework services, MCP/OAuth/publication-failure contract changes, downstream migration, required
  external dependencies, release/certification/deployment and new packaging/release-process tests.

## Use cases and contracts

| Use case | Commands | Queries | Events | Expected side effects |
|---|---|---|---|---|
| Consumer command handler refuses an operation | Existing consumer command; no Common command added | N/A; no new query | N/A; refusal invents no event | Throw the explicit category; preserve consumer policy and transaction/recovery responsibility. |
| Consumer query handler reports an intentionally missing resource | N/A; no mutation | Existing consumer query; no Common query added | N/A; no domain mutation | Throw ResourceNotFound rather than inferring intent from a lookup or HTTP exception. |
| Consumer catches a generic or specific declared failure | N/A; local failure recognition | N/A; local type/diagnostic access | N/A; no mutation | Catch ApplicationException, inherited Catchable or a category/subtype without selecting a transport response. |
| Consumer supplies diagnostic text/code/cause | N/A; exception construction | N/A; local diagnostic access | N/A; no mutation | Retain documented diagnostics and original previous Throwable identity, not public output authorization. |
| Worker/adapter inspects a delay hint | N/A; local metadata access | N/A; local hint read | N/A; no dispatch | Receive null or nonnegative integer seconds; caller still owns whether/how to retry or present the hint. |
| Existing consumer uses field validation | Existing workflow unchanged | Existing workflow unchanged | Existing workflow unchanged | Published validation factories, errors, causes and catchability remain available without migration. |

These are local failure construction, propagation and recognition use cases. They add no business command/query,
network effect, schema write, event, automatic retry or authorization enforcement. Throwing an exception does not
prove that earlier effects rolled back. Consumers own permission checks, authentication, application error intent,
transactions, cancellation and recovery; Domain retains its state-based decisions and domain-specific failures.

### Approved vocabulary

| Category | Intent |
|---|---|
| AuthenticationRequired | Consumer explicitly requires acceptable authentication for this operation. |
| PermissionDenied | Consumer explicitly refuses the operation on permission grounds. |
| ResourceNotFound | Consumer intentionally reports a missing resource; generic lookup failure is not equivalent. |
| StateConflict | Current/stale state conflicts with the requested operation. |
| ResourceGone | Consumer intentionally reports a resource no longer available. |
| PreconditionFailed | A required application precondition was not satisfied. |
| InvalidInput | Input is unusable for the use case without requiring a structured field-error map. |
| RuleViolation | The consumer deliberately reports a business-rule rejection, distinct from a mandatory field-validation replacement. |
| RateLimitExceeded | A consumer-defined invocation/admission limit was exceeded; no limiter is introduced. |
| ServerError | An explicit unexpected/server failure, not an expected-refusal or public-safe marker. |
| ServiceUnavailable | An explicit temporary service-unavailability outcome; no automatic timeout/storage mapping. |

The consumer chooses the meaningful category; the package does not infer authorization, resource visibility,
business conflict or retry policy. Domain-specific exceptions remain valid and may be retained as causes. Domain
must not import the new Application categories merely to fit this vocabulary.

## Validation and permissions

ApplicationException is an abstract public catch/extension point deriving from SystemException and therefore
Catchable/Exception. All eleven concrete categories deliberately support consumer Application subtypes, rather than
being made final by default. Classify callable/constructible/extensible promises independently under ADR 0009;
the abstract base is not directly constructible. Category recognition follows declared intent, not message parsing,
integer codes, generic SystemException membership or blanket recognition of arbitrary new base subtypes.

Preserve ordinary diagnostic string messages, arbitrary supported integer codes and previous Throwable identity,
including PHP Error causes. Codes are not required to be HTTP statuses. No category, cause or consumer contextual
property is automatically public-safe, even if text looks friendly or a code resembles an HTTP status. Do not add
a publicMessage()/HTTP-status/header/JSend contract, a diagnostic serializer or an arbitrary shared context bag.
Exact constructor/accessor/factory spellings and default diagnostic text remain routine design within these promises.

RateLimitExceeded and ServiceUnavailable support an optional neutral retry-delay hint: native integer seconds >= 0,
null meaning unspecified. Zero is a valid zero-delay hint, not permission to perform an immediate retry. Reject negative
supported metadata with DomainException; document native argument/type errors without a blanket Error wrapper. Retain
exact native integer values, including PHP_INT_MAX, without float conversion, clock defaults or a Duration dependency.
The hint grants no retry/scheduling guarantee or HTTP header authority; TICKET-00039 owns any deliberate validated
public/HTTP projection. Other category-specific metadata requires demonstrated use cases and explicit validation,
not speculative bags of raw entities, credentials or protocol fields.

Leave Application/Validation/Exception/ValidationException and Domain/Exception/ValidationException hierarchy,
constructors, fromErrors(), getErrors(), code/cause behavior and consumer subclass/factory behavior unchanged. The
existing exception owns structured field-validation results; InvalidInput is generic unusable-input intent, and
RuleViolation is deliberate business-rule rejection. Do not duplicate ErrorData/getErrors contracts in the new
generic categories, reparent an existing Domain exception into Application, introduce a mandatory wrapper or replace
ValidationService's published exception. Document their separate responsibilities without claiming every validation
rule is merely syntax or reclassifying existing failures automatically.

Generic LookupException, AuthException, storage failures, OAuthFailure outcomes and arbitrary timeouts remain their
existing contracts. A consumer may explicitly translate a known use-case outcome, retaining its cause; the package
does not install global conversion hooks. Existing MCP failure mapping remains exact-class explicit registration
with consumer-authored public constants; inheritance in this vocabulary does not broaden that mapping. Current
legacy HTTP paths remain capable of exposing diagnostics until consumers separately opt into TICKET-00039's safe
handling; type existence does not secure those paths or approve an incompatible default replacement.

## Verification and evidence

Inspected develop HEAD `e2160a70ce8314a84964bebf2eb5414e98e97178` has no Application/Error exception vocabulary.
Existing Application ValidationException extends Domain ValidationException, whose RuntimeException/SystemException
ancestors retain Catchable; the constructor owns the field-error map, code 0 and optional previous Throwable.
Application fromErrors() uses late-static construction and message 'Validation Failed'. Existing direct tests cover
maps, messages, causes and ancestors; the manifest explicitly promises consumer extension for these validation types.
AuthException already derives from SystemException. These source/test/manifest observations justify preserving
existing families, not reparenting them or copying Agent OS's final native-RuntimeException hierarchy.

Existing RoutingCommandBus and RoutingQueryBus directly invoke the matched handler. McpToolFailureMap explicitly
looks up the exact failure class and returns only registered consumer-authored constants; new subtype catchability
is not permission to change that protocol contract. Current HTTP leak evidence belongs to TICKET-00039 and is not
repaired by adding types. This planning session inspected source and existing evidence; it did not run new category
product tests, a fresh full gate/coverage result, downstream journeys or security/release qualification.
