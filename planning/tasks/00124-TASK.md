# Defer Dynamic Resource-Provider Validation Until Guarded Dispatch

## Outcome

Make Skills service construction validate wiring, configuration and already supplied immutable Skill inputs without
enumerating dynamic Resource providers. Validate current shared-provider metadata during admitted capability
handling, before disclosure or content opening. Preserve complete catalog ownership and serving-budget checks;
change when external provider work happens, not whether invalid results are rejected. Normally one PR owns this
bounded standalone refactor.

John explicitly approved moving dynamic validation out of Skills construction while static composition checks stay
eager. He also approved the separate optional metadata-aware seam in [TASK-00123](00123-TASK.md), scheduling both
refactors after [TASK-00121](00121-TASK.md)/[TASK-00122](00122-TASK.md), before v1.3 release qualification. The
approved change includes observable failure timing: dynamic catalog faults move from constructor failures to safe
request-time failures. This is not permission to weaken ownership, authorization or budget validation.

## Scope

- In scope:
  - Remove shared dynamic Resource-provider enumeration from `McpSkillDiscovery` construction, separating it from
    checks that can be answered using explicit wiring/configuration and already supplied immutable Skill snapshots.
  - Keep static checks immediate: readable Resources composition, exact shared Skill provider identity, finite
    configuration, immutable revision/entry structure and locally decidable entry/file budget relationships.
  - Preserve dynamic all-provider ownership, ordering, descriptor/scan/read/result bounds and actual central
    metadata checks during Skills handling before any successful disclosure or content opening.
  - Preserve independent Resource discovery/read behavior and the distinct direct-read versus catalog-scan paths.
  - Clarify constructor versus request-time failures, request-scope composition expectations and limits of the
    package guarantee; update meaningful tests, compatibility evidence and affected documentation.
- Out of scope:
  - Removing checks, skipping concealed descriptors, caching authorization/catalog validity across requests,
    normalizing Resource identities, tolerating collisions or returning truncated/partial successful entries.
  - Replacing the provider registry, adding startup scanners/warm-up APIs, introducing a catalog store, rewriting
    consumer I/O, changing provider ports or adding a generic lifecycle/framework abstraction.
  - The optional metadata-aware seam owned by TASK-00123, shared ingress bounds owned by TASK-00121 and Tool
    Resource-link/combined-journey implementation owned by TASK-00122.
  - Changing authentication/availability policy, progress/SSE, protected interactions, confirmation transactions,
    OAuth, routes, framework activation, concrete storage or Agent OS/Pi behavior.
  - New business messages, migrations, release tooling, publication or deployment.

No aggregate or business transaction changes. Provider metadata queries, bounded content I/O, invocation accounting
and redacted diagnostics are technical effects. Common does not own a provider's database query implementation or
its business authorization; those remain consumer responsibilities.

## Validation and permissions

### Accepted lifecycle and compatibility decision

The current call chain is `new McpSkillDiscovery(...)` → `validateCatalog([])` →
`McpResourceDiscovery::validateCatalog(...)` → each registered provider's `resources()`. That includes providers
unrelated to Skill files and may perform database work. It runs again while serving Skills. Existing tests
intentionally reject some provider collisions during construction; those expectations must change only for the
approved dynamic category.

After this TASK, constructors still reject bad wiring and invalid locally available immutable inputs. An external
provider's duplicate URI, malformed/unsorted descriptor or dynamic limit failure rejects during the admitted
request instead. Preserve the existing safe central failure mapping and diagnostic ownership; the change must not
leak provider details, become an empty success or allow a collaborator to choose public protocol errors.

Keep existing constructor signatures, provider ports and direct semantic call shapes. Classify failure timing as
a deliberate behavioral compatibility change in the existing manifest/contract authority even if signatures do
not change. Update the constructor-time collision tests to preserve the collision-rejection contract at its new
boundary. Do not discard their coverage or present unchanged tests as proof of the new timing.

### Safeguards and invariants

HTTP capability work remains after the existing authentication composition and Origin, method/negotiation,
metadata, mirrors, supported-version and invocation-guard checks as applicable. Exercise actual request-scoped
construction, not only a prebuilt endpoint whose constructor effects were omitted from counters. The package
cannot prevent consumer code from querying a provider before invoking Common, and cannot relocate a consumer's
authentication middleware. State these boundaries rather than promise that no upstream I/O ever occurs. Direct
semantic callers still trigger serving validation but retain responsibility for their own admission safeguards;
this TASK does not silently add HTTP authentication to the semantic responder.

Dynamic all-provider validation must still happen before Skill metadata is disclosed, including exact
`skills/get`. Retain duplicate ownership detection, strictly ordered descriptors, concealed-entry validation,
finite work budgets and read feasibility including the actual responder metadata. Static validation at construction
cannot establish a changing catalog's future validity, so do not add a cached startup-validation flag. No new
performance guarantee or constant-time direct Skill get is promised.

Current whole-Skill and general Resource availability remain authoritative at their existing serving boundaries.
A URI, cursor, manifest, previous successful request or successful constructor grants no read authority. Skill file
reads still use the same shared Resource capability and recheck permissions before opening. Resource-only
composition remains independent; its direct reads continue to use exact lookup, not listing membership or a newly
introduced full catalog scan.

Validation/acquisition of the consumer's supplied immutable Skill snapshots is distinct from probing dynamic
Resource providers. This TASK does not promise lazy source acquisition, change how `McpSkillRevision::fromFiles()`
validates supplied bytes, or bound arbitrary consumer work performed before those values reach Common.

## Acceptance criteria

- [ ] Constructing valid Resource/Skill serving objects does not enumerate external Resource providers or call
  their lookup/open methods. Already supplied immutable Skill snapshots may still be inspected locally.
- [ ] Invalid wiring, missing readable/shared-provider composition, invalid finite configuration and locally
  decidable immutable Skill/input budget failures still reject during construction without external provider I/O.
- [ ] Dynamic catalog checks occur during admitted Skills handling, before disclosure or content opening. Duplicate
  ownership, unsorted/invalid descriptors and exceeded work/metadata/read/result budgets still fail safely,
  including concealed providers/members and faults beyond the current page.
- [ ] Rejected authentication, Origin, negotiation/mirror/version or invocation-guard requests perform no dynamic
  provider enumeration or content opening in a real-handler journey with request-scoped service construction.
- [ ] Provider changes after construction are checked afresh; valid construction or a prior success does not cache
  catalog validity/authority. Unexpected provider failures use the existing sanitized errors and diagnostics.
- [ ] Actual responder metadata remains part of pre-disclosure/read-feasibility budgets. Shared capabilities do not
  retain another responder's identity. Final result bounds remain independent defense in depth.
- [ ] Whole-Skill/general Resource availability, exact identities, direct Resource reads independent of listing,
  complete manifests, selected-file-only opening, pagination and existing safe errors remain compatible.
- [ ] Existing public construction/call shapes and provider implementations remain supported. The specifically
  approved dynamic failure-timing change is classified and documented, not disguised as behavior-preserving.
- [ ] Tests preserve collision/budget rejection evidence at the new boundary and cover the constructor-versus-
  request distinction directly. Relevant combined Tools/Resources/Skills journeys and the full `./bin/build`
  gate pass with exact owned-production coverage; applicable conformance impact and warnings are recorded.
- [ ] MCP docs and applicable `CONTEXT.md` wording distinguish static construction checks, dynamic serving checks,
  consumer acquisition and upstream responsibilities. No broader no-I/O or authorization guarantee is claimed.
  Completion records required evidence and pending independent review separately from delivery.
