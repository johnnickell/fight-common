# ADR 0002: Checkpointed At-Least-Once Projections

- Status: accepted
- Date: 2026-08-01

## Decision

Projectors read the Event Store's global sequence in bounded batches. Each projector owns an independent checkpoint. A runner advances the checkpoint only after successful handling, producing at-least-once delivery. Projector writes must therefore be idempotent.

Within a fetched batch, the runner handles events in global order and saves the projector checkpoint after each successfully handled event. A failure at one event leaves the checkpoint at the preceding successful position, so retry resumes from the failed event rather than replaying the entire successful prefix of the batch.

Each projector statically declares the current event payload FQCNs it handles. Stable event aliases and legacy schemas remain inside the Event Store and Event Mapper; projectors receive only hydrated current payloads after upcasting. The runner invokes the projector for declared FQCNs and treats undeclared types as successful skips, advancing the checkpoint over both. Adding a handled type later requires resetting and rebuilding that projector from the appropriate position.

Each projector also declares an explicit stable projector name used as its checkpoint key. That name is durable processing identity rather than a PHP type, so renaming or moving the projector class does not silently create a fresh checkpoint.

Ordinary checkpoint saves are monotonic and reject lower positions. A separate administrative `reset(projectorName)` operation returns the checkpoint to zero for a full rebuild. The consumer must stop the worker and clear or recreate its read model before reset; Fight Common does not coordinate that external state. Arbitrary backward reset positions are excluded from 1.2.

If handling fails, the runner stops the batch immediately, does not process later positions, and propagates the exception. The consuming worker owns retry, backoff, and dead-letter policy; the core runner does not skip poison events or reorder delivery.

Global position has prefix-stable commit visibility: after a projector observes position N, no lower-positioned event can become visible later. Event Store implementations enforce that property by serializing position allocation through commit; an auto-increment event-table key is insufficient on MySQL because allocation order is not transaction commit order. A projector may therefore poll strictly after its checkpoint without skipping a late commit at a lower position.

Fight Common supplies batch execution and checkpoint adapters. Consuming applications own commands, scheduling, process supervision, and read-database schemas.

## Event Publication Is Not Projection

`ProjectionRunner` and `EventPublicationRunner` run as separate worker-facing services. The Event Publication Runner reads only committed stored events and dispatches their original event messages through the Event Dispatcher. Its `PublicationCursorStore` records the last position for which all matching subscribers were attempted, not a successfully projected state, and is a distinct contract from the projector checkpoint store even when adapters share persistence mechanics.

The Event Publication Runner depends specifically on `SynchronousEventDispatcher`, which can report completion and collected failures after attempting every matching subscriber. `MessengerEventDispatcher` and other asynchronous dispatchers acknowledge transport submission rather than downstream subscriber execution and are not valid publication-runner dependencies.

Each Event Publication Runner has an explicitly configured stable publication name. Cursor storage and publication failures are scoped by that name, so multiple independent subscriber pipelines may publish from one Event Store without sharing progress or failure identity.

Publication cursor saves are monotonic, and `PublicationCursorStore` has no reset operation in 1.2. Reset would implicitly redispatch stored history to subscribers that are not required to be idempotent. Whole-stream and targeted republication are deferred to a dedicated replay workflow.

The Synchronous Event Dispatcher keeps its `void` dispatch signature and existing two-phase ordering: event-specific handlers run by priority first, followed by `AllEvents` handlers by priority. Each handler invocation catches any `Throwable`, including PHP `Error` values such as `TypeError`, and continues within and across both phases. It then throws one `EventDispatchFailed` aggregate containing ordered `EventHandlerFailure` values and their original throwables. That aggregate is emitted only after both phases complete. The publication runner catches it, records the failures operationally, and advances its cursor after successful recording, so a subscriber failure does not automatically redispatch the event. Failures while resolving or preparing handlers, and any other dispatcher infrastructure failures, leave fan-out completion uncertain, propagate, and prevent cursor advancement. A crash before cursor advancement can still cause duplicate delivery; subscriber idempotence is therefore encouraged for published events but is not part of the general Event Subscriber contract.

Fight Common 1.2 supplies an `EventPublicationFailure` record and `PublicationFailureRecorder` port. At the beginning of each stored-event dispatch attempt, the runner captures the current time directly with `DateTimeImmutable` and normalizes it to UTC with microsecond precision; no new clock abstraction is introduced solely for this operational timestamp. When handlers fail, the runner records one aggregated failure for that stored-event attempt before advancing its cursor. The portable snapshot includes publication, stored-event, and message identity, that dispatch-start time, and each failed callable's description, exception FQCN, integer exception code, and bounded diagnostic message. Comparing the attempt time with the EventMessage creation timestamp can estimate storage-to-publication latency without treating either value as domain occurrence time. Diagnostic messages are normalized to valid UTF-8, stripped of unsafe control characters, and limited to 4 KiB. Fight Common does not attempt secret detection or redaction; consuming projects treat exception messages as user-surfaceable text and keep credentials and sensitive payload data out of them. The snapshot excludes original throwables, stack traces, event payloads, and message metadata. Subscriber methods use their current FQCN and method. Symfony's default service registration uses the subscriber FQCN as its service ID, so this pair is sufficient for project-owned targeted invocation while the class and method remain valid. Named functions use their function name, while closures use a diagnostic, non-replayable `Closure` descriptor. These are operational identities, not refactor-stable aliases; automatic replay and migration of historical handler identities remain outside 1.2. Recorder implementations persist or log the same snapshot, while full throwable diagnostics remain transient on `EventDispatchFailed`.

Fight Common supplies in-memory and DBAL recorder adapters plus a PSR-3 logging decorator. Following the existing mail and SMS logging-decorator convention, the logging adapter requires another `PublicationFailureRecorder`, logs the portable failure snapshot first, and then delegates that same snapshot to the recorder, such as the in-memory or DBAL adapter. Either logging or delegation failure propagates and prevents publication-cursor advancement. A delegate failure may therefore produce duplicate log entries on retry; publication name and global position provide their correlation key. Requiring the delegate makes logging compositional rather than an accidental replacement for recording. The DBAL adapter durably stores one record per publication name and global position. The durable record supports operations in 1.2; read/query and replay contracts remain deferred.

A successfully recorded publication failure does not block publication-cursor advancement. If failure recording or cursor storage itself fails, the runner does not advance, propagates the infrastructure error, and retries the publication attempt through its worker. Failure recorders must be idempotent because partial recording and crash recovery may repeat records; publication name plus global position is the deterministic reference key.

Automatic replay and targeted invocation of only failed subscribers are deferred. Consuming projects may implement that workflow independently, and a proven implementation may later be promoted into Fight Common.

Projection retains the stricter guarantee: ordered at-least-once handling, checkpoint advancement only after each successful projection, immediate stop on failure, and idempotent projector operations.
