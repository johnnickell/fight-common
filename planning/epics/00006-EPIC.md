# Reusable MCP Streamable HTTP Tool Support

## Destination

Provide a reusable, policy-free Fight Common capability that lets a consuming application explicitly expose
selected existing CQRS commands and queries as MCP Tools over MCP `2026-07-28` Streamable HTTP. The capability
keeps consumer use cases independent of MCP, retains the existing Action–Domain–Responder and CQRS boundaries,
and permits framework-native composition without making Fight Common choose a route, principal model,
authorization policy, or exposed-tool policy.

A consumer supplies its route, transport security, authentication composition, caller/principal resolution,
permission policy, and explicitly opted-in tools. Fight Common supplies the protocol foundation, tool discovery
and dispatch mechanics, framework-neutral contracts, and supported-framework adapters. Fight Access Control is a
future validating consumer, not the product this EPIC delivers.

## Acceptance boundaries

- Support only MCP `2026-07-28` Streamable HTTP and its JSON-RPC/MCP representation. Do not reuse JSend as an MCP
  wire format or provide legacy HTTP+SSE/session compatibility.
- Implement the shared Streamable-HTTP foundation and the complete MCP Tool capability, including
  `server/discover`, `tools/list`, `tools/call`, pagination, authorization-sensitive availability filtering,
  explicit schemas, progress, cancellation, and MCP `input_required` interaction flow. Resources, Prompts,
  Tasks, Apps, Skills, subscriptions/listChanged, and authorization extensions remain possible later
  capabilities, not permanent exclusions or first-EPIC scope.
- A consumer explicitly opts a tool into a Fight Common contract and supplies method-level discovery metadata
  containing its stable name, description, input schema, and output schema. Its Action-like invocation receives
  validated application data and request-scoped progress reporting, invokes existing command/query buses, and
  returns semantic tool output; no tool creates framework responses or MCP wire messages.
- Reuse the existing method-level `#[Validation]` and `ValidationService` over exactly
  `tools/call.params.arguments`. Explicit input and output schemas are required discovery metadata and require
  consistency/conformance evidence distinct from runtime validation.
- Preserve `CommandBus::execute()` as void. A command-backed tool may return a known acknowledgement, such as a
  generated identifier, or run an existing query only when necessary; favor one read or write per operation.
- MCP transport details stay out of command/query payloads. Optional Common `CommandFilter`/`QueryFilter`
  integration enriches envelopes with a small namespaced tool/correlation baseline and permits scalar,
  namespaced consumer audit metadata. Handlers neither inspect caller transport nor receive authorization policy,
  credentials, raw arguments, or headers through this mechanism.
- Tools return successful semantic output and throw typed existing application exceptions. A central responder
  maps protocol failures, expected tool-execution errors, and unexpected failures to MCP-required responses;
  selected-tool validation/business failures are `isError` results.
- Support direct JSON when no MCP progress token is present and timely, incremental request-scoped SSE when one
  is present. SSE includes progress before the final response, cooperative cancellation on stream closure, and
  no partial result content in progress events. This must work uniformly across every currently supported Fight
  Common framework adapter. Feasibility is unverified: an adapter exception or scope reduction requires an
  explicit decision, never a silent fallback.
- Common supplies layered capability registration: a focused Tool registry maps opted-in tools to canonical MCP
  names, while a broader capability registry receives required consumer server identity and derives the actual
  advertised capabilities. Exact public types and registration APIs remain decomposition decisions.
- Fight Common remains policy-free. A request-scoped neutral availability boundary filters discovery and
  invocation using tool metadata without receiving a principal or generic principal context. Fight Access
  Control supplies the standard Agent-aware integration, including planned `RequiresAgentPermission` metadata
  and enforcement; the consuming application wires current-Agent authentication and runtime composition. Once a
  command/query reaches its bus, it is already authorized. This is an accepted cross-project design
  responsibility, not a claim that the Access Control attribute already exists.
- Support consumer-selectable local HMAC machine-to-machine authentication and interoperable OAuth/Bearer
  resource-server composition. Common provides reusable protected-resource/Bearer validation boundaries, not an
  authorization server, Agent model, or permission policy. Consumers choose which authentication is supported on
  which routes; documenting separate routes is helpful, not mandatory.
- Require consumer configuration for a neutral invocation guard and `McpOriginPolicy`. The guard owns caller key,
  limits, exemptions, backing store, and policy; Common invokes it before dispatch and maps denial to HTTP 429
  with a JSON-RPC error where an id exists. The origin policy accepts exact scheme-host-port allow-list entries or
  explicit native-only deny-all; an absent Origin remains valid, while a supplied Origin must be allowed.
- Common validates the full Streamable-HTTP header/body mirror contract before dispatch: protocol version,
  method, tool name, and each declared `x-mcp-header`. Adapters extract headers and emit standardized responses;
  they cannot selectively omit validation.
- Support ordinary protected multi-step input with integrity-bound state and destructive-action confirmation with
  a consumer-provided atomic one-time interaction store. Both bind neutral caller identity, tool, original
  arguments, and expiry. Ordinary and interactive tools remain distinct; an interactive retry receives restored
  validated original arguments plus separately validated input responses without duplicating discovery metadata
  or initial validation declarations.
- Preserve existing consumers and public APIs. Any new public contracts, framework adapters, exceptions,
  serialization, or response behavior need compatibility classification and behavior-focused evidence.

## Evidence and unresolved design work

The [MCP-over-HTTP grill handoff](../wayfinder/research/fight-common-mcp-http-support-grill-handoff.md) and its
[closed map](../wayfinder/fight-common-mcp-http-support-map.md) record the source evidence, official specification
links, and accepted decisions. WF-041 closes the presentation and availability boundary. WF-042 closes with
package-owned Common fixtures as the verification strategy; no Access Control proof blocks this EPIC or later
decomposition.

Evidence is documentation-led and layered: official MCP research, focused Common unit/contract tests using
package-owned query-backed and mutation-backed tool fixtures, narrowly scoped adapter integration tests when a
framework seam requires them, and a small consumer fixture only when needed to prove real composition. A later
Access Control Agent mutation is independently owned adoption work, not an EPIC, planning, development, release,
or later-work gate.

## Decisions and exclusions

- MCP protocol fidelity governs representations and transport behavior where the specification is explicit. The
  relevant authority is the [Streamable HTTP specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http),
  [Tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), and
  [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).
- Tool discovery emits conservative `ttlMs: 0` and `cacheScope: private` defaults; consumers may provide a safe
  override. Pagination happens after availability filtering and deterministic ordering.
- No implicit pass-through invocation guard is allowed. No arbitrary HTTP Action discovery is allowed; tools are
  explicitly opted in. No HMAC request nonce is reused as interaction state.
- Agent identity, Agent permissions, permission strings, authorization decisions, route names, framework routing,
  TLS/gateway/deployment configuration, and an OAuth authorization server are consumer or Access Control work.
- Exact PHP interface shapes and registration APIs, schema implementation mechanics,
  detailed error-code taxonomy, logger/correlation fields, streaming emitter implementation, and framework-specific
  registration techniques belong in TICKET/TASK decomposition.

## Progress

Grilling established the EPIC scope, acceptance boundaries, and evidence posture. The Wayfinder map and all of
its decisions are closed. TICKET-00023 through TICKET-00027 now decompose the protocol endpoint, explicit CQRS
tools, supported-composition streaming and cancellation, protected `input_required` interactions, and policy-free
OAuth resource-server support. No unresolved product-policy decision currently blocks TASK decomposition.
TICKET-00025 retains the framework-wide SSE feasibility risk: any adapter exception or scope reduction requires an
explicit decision rather than a silent fallback. TASK decomposition and implementation are separate follow-on work.
