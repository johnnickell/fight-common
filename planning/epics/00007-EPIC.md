# Reusable MCP Resources and Structured Skills

## Destination

Provide reusable Fight Common server capabilities for authorized MCP Resources and static, structured multi-file
Skills over the existing guarded MCP endpoint. A consumer can expose revision-addressed documents and complete
Skill manifests, discover them alongside Tools, and retrieve individual files lazily without flattening content,
downloading an archive or loading every file at once. Retain the approved MCP `2026-07-28` protocol target and
its compatible stable `io.modelcontextprotocol/skills` extension.

Common owns protocol representation, provider contracts, composed discovery, bounded content serving and the
mechanics that apply injected consumer availability decisions. It does not own Agent OS permissions, catalog
policy, principal models, planning semantics, publication storage or the Pi client. Agent OS is a motivating
consumer, not a runtime dependency or a prerequisite for accepting this Common delivery.

## Acceptance boundaries

### Resources and structured Skills

- Support `resources/list` and exact authorized `resources/read` for explicitly registered text and binary
  content. Filter discovery before pagination, preserve correct URI/MIME representation, and return safe errors
  for unknown or unavailable content. Return an empty complete `resources/templates/list` initially; URI-template
  resolution is not required to serve known concrete URIs.
- Support `skills/list` and `skills/get` with complete static entries. Each immutable revision contains root
  `SKILL.md` plus nested references, ordinary template files, scripts, assets and other resources. Every manifest
  member remains individually addressable through the shared Resources capability. Complete entries stay atomic
  across pagination; direct authorized lookup must work even when a Skill is absent from a partial listing.
- Preserve all JSON-representable frontmatter, including unknown fields. Manifest sizes and SHA-256 digests
  describe exact original bytes; reads do not normalize line endings, Unicode or frontmatter. Validate structure,
  paths, metadata and manifest completeness without executing content. A manifest and its file readers describe
  the same immutable revision; historical URIs never silently return replacement bytes.
- Whole bundle means a complete revision and manifest, not flattened Markdown, mandatory archive retrieval or
  eager file loading. Discovery returns entries without requiring Skill-file reads by the client. A client may
  load only `SKILL.md`, then read one nested reference, template or script when needed. Serving template or script
  bytes does not render, execute or activate them, and does not grant authority through `allowed-tools`.
- Providers supply explicit content and immutable revision guarantees. Common validates and exercises that
  contract; it does not claim arbitrary consumer databases or filesystems are intrinsically immutable. No generic
  filesystem mount, automatic URL fetch or URI-to-arbitrary-path fallback is introduced.

### Authorization, composition and safe operation

- Apply injected, current consumer authorization decisions consistently to discovery, direct lookup and every
  Resource read. Whole-Skill authorization conceals a denied Skill and its files, while an allowed entry retains
  its complete manifest. Do not redact individual members or require duplicate variants merely for access
  filtering; separate content variants are warranted only when genuinely needed.
- Common receives neutral availability collaborators, not Agent OS permission strings, catalog rules or a generic
  principal model. The consumer resolves identity and policy. A URI, cursor, manifest, successful authentication
  or cached hash does not grant read permission. Changed consumer decisions must affect subsequent requests.
- Demonstrate Resources and structured Skills through the **existing guarded MCP endpoint**, coexisting with
  Tools. Compose truthful `server/discover` output and shared Resource method ownership; preserve duplicate-method
  and conflicting-registration rejection. Skills requires readable Resources. Compose distinct extension IDs
  without allowing contradictory same-ID settings to override one another.
- Preserve Origin, invocation-guard, authentication-composition and header/body-mirror behavior. In particular,
  Resource reads retain their URI mirror, while Skills methods use only mirrors defined by the protocol. Guard
  rejection must prevent content retrieval. Resource/Skill failures use central protocol-safe responses, not Tool
  `isError` envelopes; unexpected failures retain sanitized diagnostics.
- Provide sensible finite defaults and optional validated overrides for request/content processing, metadata,
  pagination, parsing and encoded responses. Limits must be mutually consistent: an advertised valid revision
  cannot contain a file that configured reads can never return. Respect the pinned protocol's interoperability
  requirements, account for encoding expansion, and reject excess safely rather than truncate verified content.
- Use conservative private cache behavior, with safe consumer-selected overrides where justified. Freshness and
  immutable bytes do not establish authorization or public visibility. Cursors carry no authority; safe ordinary
  retry and stale-cursor recovery do not require new approval prompts.

## Use cases and observable evidence

| Actor and trigger | Expected result / evidence |
|---|---|
| Consumer composes an endpoint with Tools, document Resources and structured Skills | One truthful discovery result exposes all three capabilities; a package-owned Tool returns a Resource link that survives serialization and can be read through the same endpoint. No parallel Tool dispatcher or endpoint is introduced. |
| Authorized client lists or directly reads a document | Filtered, bounded metadata and exact requested content; direct reads reapply the injected decision. Denied and unknown targets disclose no protected metadata or bytes. |
| Client discovers a Skill and requests selected files | Complete revision manifest contains nested references, templates, scripts and binary assets. The fixture client reads only `SKILL.md`, then one selected nested member; unrelated files are not delivered, rendered or executed. |
| Consumer changes availability after discovery | Later get/read requests deny the Skill and its files even with a previously obtained URI or manifest. Common proves enforcement using injected fixture decisions, without implementing Agent OS policy. |
| Invalid publication, malformed request or provider failure occurs | Invalid paths/frontmatter/manifests and inconsistent bytes fail safely; limits, pagination, cache separation and guard ordering are exercised with adversarial cases. No silent revision substitution or truncated success. |
| A consumer supplies a new revision | New manifest and bytes remain consistent; retained old revision URIs still return their original bytes. Package fixtures prove the contract, not production catalog storage. |

These operations are reads: no new business mutation commands, domain events, schema migrations or Workflow
transitions are required. The search Tool fixture uses existing Tool/query mechanics; actual planning search and
Apply commands remain consumer-owned use cases. Request diagnostics and optional cache effects are technical
side effects, not domain events. Loading content never authorizes a later application command.

## Completion evidence

Common completion requires all of the following, not merely a planning check:

- Package-owned behavior fixtures and focused unit/integration/functional evidence, including the guarded endpoint
  journey above with real Common Resources, Skills and Tools composition. Isolated semantic tests alone do not
  establish endpoint acceptance. Consumer authorization is injected and varied in fixtures.
- Applicable pinned official Resources/Skills conformance checks, with the exact source/version, exercised
  scenarios, outcomes and limitations recorded. Distinguish passing, failing, skipped, unavailable and genuinely
  not-applicable checks. Do not claim unsupported directory behavior, a skipped required path or a published
  conformance version without Skills coverage as a pass. Cover specification obligations with owned behavioral
  evidence where the official harness has gaps; report remaining gaps honestly rather than award a blanket badge.
- Compatibility classification and evidence for new public contracts, serialization, exceptions and observable
  behavior, preserving existing consumers and the Tools/HTTP contract.
- Consumer-facing documentation for composition, structured manifests, lazy file access, authorization injection,
  limits/overrides, cache/error behavior, security boundaries and deferred capabilities.
- The complete project `./bin/build` gate, including exact owned-production coverage, plus the applicable
  conformance evidence above and ordinary independent acceptance. No full gate or conformance run is claimed by
  this planning record.

The real Agent OS/Pi journey is separate downstream acceptance. Common fixtures do not prove Pi origin handling,
client no-prefetch/integrity rejection, session pinning, catalog persistence, live Access Control integration or
Workflow behavior. Official client scenarios and the additional host-internal checks belong to that downstream
proof; their absence here does not turn them into Common implementation requirements.
