# Generic MCP Prompts

## Destination

Let users discover and retrieve parameterized, role-guided instructions alongside reusable Skills through MCP.
For example, a consumer can offer “Review task X using this Skill” without copying the Skill's procedure into a
second instruction source. Common supplies reusable Prompt-serving mechanics; it does not execute the instructions,
run a model or assign an Agent persona.

Provide authorized, bounded `prompts/list` and `prompts/get` through Common's existing guarded HTTP composition,
with explicit capability registration, argument/response validation and truthful capability advertisement. The
initial content boundary is **text messages and Resource links**, returning a complete prompt from supplied
arguments. Message roles follow MCP's `user`/`assistant` contract, not remote system/developer authority.

This is the second EPIC handoff from the
[execution introspection and MCP evolution map](../wayfinder/mcp-execution-introspection-map.md). It is generic,
not restricted to introspection and not dependent on implementing that capability or the separate Subscriptions
and Tasks destinations.

| Common owns | Consumer or host owns |
| --- | --- |
| Explicit reusable Prompt registration, discovery and retrieval mechanics | Which Prompts exist and their canonical content sources |
| Bounded argument and response validation | Role/persona wording, persistent Agent identity and application vocabulary |
| Current access enforcement using supplied decisions | Authentication and permission policy |
| Protocol-compliant messages and Resource-link presentation | Host interaction, message insertion and Skill loading/approval |
| HTTP protocol/integration evidence and documented support limits | Actual client deployment qualification and runtime composition |

Prompt text is instruction content, not permission, Workflow authority or independent-review acceptance. Resource
links grant neither access to their targets nor automatic Skill activation. Consumers can reference a Skill or
reuse a canonical instruction source; Common does not require duplicate copies, a new content database or a
particular template engine. Repeatable instructions do not promise deterministic model output.

## Required use cases

### Discover available Prompts

An authorized caller requests `prompts/list` and receives only currently available Prompt definitions, including
their declared arguments and supported descriptive metadata. Discovery is bounded and paginated according to the
MCP protocol, with current consumer access decisions applied before disclosure. Availability must not depend on
remembered per-connection request history. Consumers can supply an empty catalog.

MCP catalog pagination is distinct from the execution introspection application's offset/limit Queries; this EPIC
does not change either contract. Exact page budgets, catalog storage/provider APIs and protocol pagination/cache
mechanics belong in subsequent requirements and design. Neither a catalog entry nor a prior listing establishes
continuing permission to retrieve content.

### Retrieve a complete parameterized Prompt

A caller selects a Prompt and supplies its arguments to `prompts/get`. Common rechecks current availability,
validates arguments before content processing, and validates the complete bounded response before disclosure.
Missing required arguments, invalid input, unavailable Prompts, unsupported output and provider failures must
produce safe protocol outcomes without exposing private provider diagnostics or concealed content.

Return consumer-supplied messages containing text or Resource links only. Resource-link metadata itself must be
safe for the recipient; subsequent target reads remain subject to their own current authorization. A reference
must not cause automatic network retrieval, filesystem access, Skill loading or instruction execution. The host
chooses how to present or use the messages. This first delivery does not request additional input across multiple
round trips and does not embed document bodies, images or audio as content blocks.

### Compose with existing MCP capabilities

Opt-in registration adds the Prompts capability alongside existing Tools, Resources and Skills on the existing
HTTP transport without changing their public behavior. Advertise only configured, available behavior under the
accepted MCP `2026-07-28` contract. Do not advertise Prompt list-change delivery in this EPIC; notifications belong
to the separately planned Subscriptions capability and cannot be inferred from ordinary HTTP/SSE support.

Reuse the existing authentication/resource-server boundary and consumer permissions rather than creating a new
principal or token system. Protocol availability does not replace application authorization. Discovery and retrieval
are reads; application data needed to build a Prompt uses shared Query use cases rather than adapter-level database
access or duplicated policy. Prompt retrieval must not dispatch business mutations or execute Tools/model work.
No new business Command, domain event or persistence workflow is required merely to list or retrieve instructions.

## Acceptance evidence

Future automated tests must demonstrate the complete user journey through existing guarded HTTP composition:
list permitted Prompts, select one, supply arguments, retrieve validated text/Resource-link messages and preserve
the host-owned loading boundary. Required evidence includes:

- Explicit registration, truthful discovery and independent coexistence with Tools, Resources and Skills.
- Authorized empty/nonempty catalogs, protocol pagination, bounded results and changed access between calls.
- Valid parameter substitution/content construction and rejection of missing or invalid arguments before processing.
- Valid `user`/`assistant` messages, text and Resource links; rejection of unsupported content or invalid responses.
- Safe failures, no protected metadata/content disclosure and no authorization implied by an identifier or link.
- Finite input/output limits and no automatic link fetching, Skill activation, Tool execution or model invocation.
- No false subscription/list-change, Completion, multimedia or interactive-Prompt support claims.

Exact APIs, numeric limits, cache/pagination behavior and individual failure cases are downstream planning details
within these guarantees, not new EPIC-scope choices. Document the supported content subset and composition, and
align CONTEXT.md when implemented. Applicable product suites, exact owned-code coverage and the complete local
`./bin/build` gate follow the [project profile](../agents/project-profile.md). These are accepted requirements;
TASK-00157's current checkpoint and Work receipt own actual checks, separate from independent Review/QA.
Actual Agent OS/Pi or other client deployment remains separate evidence,
not a prerequisite for Common package acceptance or a claim implied by package tests.

## Exclusions

- Embedded Resource/document content blocks, image/audio content and interactive requests for additional Prompt input.
- Argument Completion, Resource templates, Apps and URL-mode input, as already deferred by WF-048.
- Prompt list-change notifications or a subscription transport; these belong to Generic MCP Subscriptions.
- Model execution, automatic Skill activation, persona/identity assignment, permission grants or Workflow transitions.
- A consumer-specific Prompt library, content-authoring UI, mandatory template engine or persistent catalog product.
- New HTTP authentication policy, additional transports or modification of consumer planning/runtime records.
- Guaranteed model behavior, complete protocol-feature support, client qualification or any release/version commitment.
