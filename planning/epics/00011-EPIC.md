# Generic MCP Subscriptions

## Destination

Let authorized Agents receive live change notices or poll retained notices after missing an update. Supply shared
inspection Queries so a consumer-owned SUPER_ADMIN interface can browse the retained feed live, filter it by topic
and Agent relationships, and inspect current subscribers. Optional Mercure output keeps browser consumers updated
without making Mercure mandatory for MCP or polling.

Common delivers reusable subscription mechanics, durable bounded notice storage, shared CQRS use cases and protocol
adapters, not merely interfaces. A notice indicates that permitted data or a catalog changed; callers fetch current
authorized data rather than receiving protected message/tool/output bodies in broadcasts. Successfully recorded
notices remain recoverable during retention. This is not a guarantee that every application change produces a notice.

This is the third approved EPIC handoff from the
[execution introspection and MCP evolution map](../wayfinder/mcp-execution-introspection-map.md). It is generic:
introspection reads and MCP Task polling remain usable without it. Application Workflow state, execution observations,
retained notices and active transport subscriptions are distinct concepts.

identity and current authorization decisions. Every disclosed notice, topic, identity, causation reference and
subscriber record must respect the permitted scope; possession of a reference or subscription ID grants no authority.

## Required use cases and guarantees

### Record and retain a change notice

Consumer composition supplies a bounded safe notice through a Command with trusted scope/producer context. Common
validates and persists it with a stable identity so saved notices can be retrieved independently of a live stream.
Recording success means the notice has been durably saved; storage failure is explicit. Subsequent MCP/Mercure
publication failure cannot erase that saved notice or prevent otherwise authorized polling recovery.

Retain the following distinctions when the consumer can supply them:

- **Subject Agent:** whose work the notice concerns.
- **Intended recipients:** explicitly named Agent targets, not an inferred list of all subscribers.
- **Author/producer:** who originated the notice; this is distinct from the subject and recipient.
- **Causation:** the Command, event or action that caused the notice, distinct from its author.
- **Topic, time and notification type:** bounded metadata for selection and inspection.

Broadcasts may have no named recipient. Unknown identities/causation stay explicit; Common must not manufacture
relationships or treat supplied references as proof of authority. Notice identity is not the transport request ID,
a planning TASK identity or authoritative application execution state. Topic vocabulary is consumer-owned and is
not a new standard MCP filter merely because a consumer uses it internally.

The stored feed contains safe change notices, not a complete wire transcript or copies of protected content. Capture
and safe metadata selection remain consumer responsibilities; Common validates structure, limits and access.
Exact records, storage adapters, retry/conflict handling and event catalog are subsequent requirements/design within
these boundaries, not an implicit exactly-once or application-transaction guarantee.

### Follow changes through MCP

An authorized client opens `subscriptions/listen` over the existing guarded HTTP composition with explicit filters.
Follow MCP `2026-07-28`: send the acknowledgment first, reflecting the supported subset of requested filters; attach
the correct subscription identity to subsequent messages; never emit an unrequested notification type. Resource
updates and catalog-change notices must follow their actual protocol contracts, not the former `resources/subscribe`
RPC or an invented HTTP GET subscription endpoint.

Advertise only enabled notification behavior backed by the actual composition. Recheck current access before
notification disclosure; opening a stream does not freeze authority for its lifetime. Respect disconnects,
cancellation, graceful closure and finite resource/queue limits. Live streams do not promise exactly-once delivery,
receipt or processing. Stream interruption does not delete retained notices.

MCP subscription support and Mercure output are separate adapters, not interchangeable wire protocols. Prompt
list-change support, when composed with [EPIC-00010](00010-EPIC.md), belongs here rather than being a prerequisite
of ordinary Prompt retrieval. Exact supported-filter cases and optional capability integration are downstream
requirements; unavailable families must not be advertised or acknowledged as available.

### Poll missed notices and inspect retained history

An Agent can use a bounded shared Query, exposed through an explicitly registered MCP Tool, to retrieve retained
notices even without an open stream. This polling API is a Common capability built on Tools, not a standard MCP
`subscriptions/poll` method. Browser inspection uses the same application Queries without duplicate database logic.
Preserve `CommandBus::execute()` for mutations and `QueryBus::fetch()` for reads.

Provide summary-first inspection covering all currently authorized matches, with paginated detail filtered by
topic, subject Agent, intended recipient, time and notification type. Include permitted author/producer and causation
references in details. Use existing page/per-page offset/limit semantics for paginated inspection; no frozen browsing
session or browser navigation policy is added. Finite polling/result bounds and the precise way a caller identifies
its last retrieved notice belong in requirements/design, without silently dropping saved notices or asserting
complete catch-up solely from an empty page.

Each poll and detail read checks current access. If retention, missing history or another limitation prevents
establishing complete catch-up, report that limitation so the client can reload current authorized data. Recovery
covers successfully recorded notices still retained, not changes for which recording never succeeded. The consumer
owns reload behavior, polling cadence and any processing acknowledgment; re-reading a notice is not exactly-once
application processing.

Consumers choose retention duration and run cleanup. Common supplies bounded removal operations and truthful reads
when history expires or disappears; it does not introduce a retention-policy engine, scheduler, archive workflow or
indefinite recovery promise. Polling completeness must remain honest under concurrent recording, removal and changed
permissions. Exact recovery metadata and expiry mechanics are implementation-planning work with behavioral tests.

### Inspect current subscribers

An authorized operator can inspect the current subscriber list, trusted subscriber identities and requested topics/
filters through bounded shared Queries. Distinguish observed connection state, disconnects and stale/uncertain state;
do not confidently label an abandoned registration active. Exact lifecycle tracking and freshness mechanics remain
implementation design, including truthful behavior when process termination prevents a clean disconnect update.

Current subscribers are not a saved historical audience for every notice. Matching a topic/filter or naming an
intended recipient proves neither receipt nor processing. A reconnect establishes a new live subscription; current
subscriber inspection must not imply that protocol subscriptions survive disconnected transports or grant renewed
access without current checks.

### Keep a consumer browser feed live with optional Mercure

Offer a separate optional output from recorded notices through Common's existing Mercure publisher capabilities,
including private delivery where required by consumer access policy. The consumer can load its initial authorized
page/history through Queries, follow live changes through Mercure and recover retained notices after disconnects.
Common provides the reusable integration, not a SUPER_ADMIN dashboard or a deployed hub.

Consumer policy owns topic selection and disclosure boundaries. Private Mercure transport alone must not be treated
as complete application authorization or permission to broadcast protected bodies. Failed publication remains
observable and distinct from successful recording; neither a Mercure failure nor an unavailable hub rolls back a
saved notice. MCP and polling must work in a composition with no Mercure dependency enabled. No replay guarantee
is inferred from the hub; the retained Common feed supplies the approved recovery contract.

## Acceptance evidence

Future implementation must demonstrate the shared CQRS behavior, real persistence semantics, live HTTP subscription
behavior and optional Mercure translation/failure boundary. Required automated evidence includes:

- Authorized recording, explicit storage failure, stable retained identity and successful polling after live delivery fails.
- Filter acknowledgment before notifications, requested/supported-type filtering, subscription correlation and truthful
  capability advertisement through the guarded HTTP composition.
- Current access checks, project/scope isolation and no protected notice/subscriber metadata disclosure across callers.
- Summary-first selection, bounded pagination/polling and distinct subject, intended-recipient, author and causation data.
- Catch-up during retention, expiry/removal and honest incomplete-history responses under concurrent changes.
- Current-subscriber registration, disconnect and stale/uncertain-state behavior without fabricated receipt evidence.
- Optional private Mercure output with consumer policy, publication failure isolation and a Mercure-free composition.
- Bounded stream lifetime/resources, disconnect handling and graceful closure; stored notices surviving stream termination.

Apply the [project profile](../agents/project-profile.md), applicable product suites, exact owned-code coverage and
complete local `./bin/build` gate. Document composition, limits, supported notification types, retention/recovery
boundaries and failure behavior, and align CONTEXT.md when implemented. Tests must distinguish in-memory protocol
transcripts from actual live HTTP behavior and adapter evidence from deployed client/hub qualification. These are
future requirements, not checks already run for the new capability. Actual Agent OS/Pi or browser deployment remains
separate evidence, not a new Common package completion prerequisite.

## Exclusions and delegated details

- Guaranteed change-to-notice recording, an implicit outbox, exactly-once delivery or proof of receipt/processing.
  WF-047's permitted post-commit event loss remains unchanged; retaining a later notice does not repair a missing event.
- Historical per-notice subscriber snapshots, a delivery-audit ledger or complete MCP wire recording.
- Protected messages/tool bodies/process output in broadcasts or automatic Agent access to privileged content.
- Common-owned SUPER_ADMIN policy, consumer identity directory, topic vocabulary or Workflow authority.
- A browser UI, hub deployment/operations, archive orchestration, retention eligibility policy or cleanup scheduler.
- Additional transports, obsolete subscription APIs, automatic host/client qualification or release/version selection.
- Exact PHP APIs, database schema, storage adapters, finite limits, recovery-position mechanics, subscriber freshness and
  event catalog: subsequent requirements/design within the accepted guarantees, not unresolved product-scope decisions.
