# Fight Common 2.0 readiness

## Destination

Give maintainers a faster, trustworthy pre-submit gate and clearer project tooling and vocabulary. Give consumers a documented upgrade from published v1.5.1 to v2.0.0, including the steps to take before changing the package version. The [Wayfinder map](../wayfinder/fight-common-2-0-readiness-map.md) records the approved scope and evidence.

## Decisions and exclusions

- **CI speed.** Target a **10-minute median for the full hosted gate**, including setup and required checks, measured across at least three comparable fresh runs before and after. Start with the subscription capacity-lock matrix but examine the full critical path. Preserve exact 100% direct Unit coverage of owned production code, meaningful framework and integration checks, and retained release probes. Integration and Functional coverage may shrink if the lost assurance and reason are explicit. If the median exceeds ten minutes, the maintainer must explicitly decide whether to hold v2.0.0 or accept the measured outcome before tagging. See [WF-049](../wayfinder/tickets/WF-049-set-test-and-ci-runtime-target.md).
- **Glossary.** Introduce one short root `GLOSSARY.md`, move unique contracts and other live material to the docs that own them, update agent guidance, references, and the two messaging compatibility manifest entries, then delete `CONTEXT.md` without a stub. Verify links and contract locations. See [WF-050](../wayfinder/tickets/WF-050-define-the-glossary-cutover.md).
- **Tooling.** Retire all project-owned Python that can reasonably be retired. Inventory files and embedded snippets, remove unused code, and replace eligible logic with container-run PHP using Composer dev autoload or a thin host wrapper as appropriate. Move the quality runner first. Keep `bin/*` host-callable and preserve pre-image/pre-vendor offline planning, runtime setup, receipts, command and exit behavior, checkout isolation, and consumer autoload. Every retained Python item needs a concrete documented reason and a comparison with practical alternatives. This approved amendment broadens the original [WF-051](../wayfinder/tickets/WF-051-draw-the-tooling-runtime-boundary.md) scope without discarding its runtime boundaries.
- **Consumer upgrade.** Reconcile tagged and current contracts, remove verified eligible deprecations, and make `ResultSet` and `Pagination` construction enforce their current `strict()` input rules with no permissive path. Write root `UPGRADE.md` by component, covering each break, replacements or their absence, and any configuration, worker, queue, or stored-data steps required before upgrading. Check representative consumers. Prefer existing Domain helpers when equivalent, and add `Fight\Common\Domain\base64_url_encode()` and `Fight\Common\Domain\base64_url_decode()`: unpadded URL-safe output, optional correct padding on decode, `false` for malformed input. Preserve existing protocol and storage behavior when reusing helpers. See [WF-052](../wayfinder/tickets/WF-052-define-the-2-0-upgrade-contract.md).

This EPIC does not change dependency floors, authorize unrelated API removals, or authorize implementation, certification, signing, tagging, or publication. It adds no new endpoint, permissions, or event workflow. Any consumer data migration must be identified and documented as part of the affected contract, not silently performed by the upgrade.
