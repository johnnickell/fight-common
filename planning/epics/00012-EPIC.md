# Generic MCP Tasks

## Destination

Let authorized clients start supported long-running Tool operations without keeping their original connection
open, then obtain status, supply requested input, request cancellation and retrieve the eventual result/error.
Common supplies reusable durable Task handles and lifecycle mechanics through the official
`io.modelcontextprotocol/tasks` extension over the existing guarded HTTP composition.

Polling works independently. Optional live Task notifications provide timely full-state updates through the
Subscriptions capability, with Task-specific disclosure controls. Reconnecting clients recover the current state
through `tasks/get`; no replay of every intermediate notification is required.

This is the fourth and final EPIC handoff from the
[execution introspection and MCP evolution map](../wayfinder/mcp-execution-introspection-map.md). A protocol Task
represents an asynchronous operation, not a planning TASK, an authoritative Workflow, a review verdict or a job
executor. Consumers own application execution, scheduling and policy.

[official Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview) and
[versioned extension repository](https://github.com/modelcontextprotocol/ext-tasks) provide protocol evidence.
Use the official `2026-07-28` extension contract with the accepted core revision, not older experimental Task APIs
or an assumed SDK implementation of a different protocol generation.

| Common owns | Consumer owns |
| --- | --- |
| Durable handle/state/result/input storage and reusable lifecycle mechanics | Actual jobs, workers, scheduling and external-effect recovery |

A handle or client capability declaration is not authorization. All operations use trusted consumer context and
current permission decisions. Task identity, consumer job identity, application Workflow/phase identity and planning
TASK identity remain distinct even when the consumer links them. Common does not invent their business meaning.

## Required use cases and guarantees

### Start an explicitly supported asynchronous operation

The client declares Tasks support and the server explicitly enables and advertises it. A supported Tool operation
may return the ordinary complete result or a durably created Task handle according to the consumer's composition.
Never return a Task-shaped result to a client that has not negotiated the extension; unsupported combinations must
have truthful protocol behavior rather than silently starting inaccessible asynchronous work.

Persist the Task before acknowledging its handle, with its current state, retention/TTL information and polling
advice as required by the extension. Storage failure is explicit. Handle durability is not proof that a worker was
started, work completed or an external side effect succeeded. Consumer execution composition owns dispatch and
reconciliation; there is no implicit transaction with an external job or mandatory Common outbox/worker engine.

Preserve shared CQRS boundaries: Commands own state changes and Queries own reads through the existing buses.
Protocol adapters do not write a competing job/Workflow database or duplicate application policy. Trusted producer
updates pass through the reusable lifecycle contract; public `tasks/update` is not a generic status setter.
Exact classes, storage adapters, dispatch seams and retry/concurrency mechanics belong in subsequent requirements.

### Retrieve status and final results

An authorized client calls `tasks/get` with a handle and receives the current protocol state. Support `working`,
`input_required`, `completed`, `failed` and `cancelled` according to the extension. Terminal states remain terminal;
racing producer updates, cancellation and reads must not manufacture incompatible outcomes.

The terminal result/error represents the original operation's outcome under its protocol contract, with safe
projection and validation. Protocol completion does not itself mean business success, review acceptance or a
planning TASK reaching `done`. Missing or uncertain job evidence must not be invented from a quiet worker or stream.
Bound status text, input maps and result/error responses; raw private exceptions and credentials are not public data.

A client or authorized cron-driven caller may poll without any live subscription. Current access is checked on
every call, including after reconnects and permission changes. Handle possession alone grants no result access.
Retention and absence must be truthful: expired/unavailable records do not imply successful completion, cancellation
or a recoverable result beyond the supported retention period.

### Supply requested input

When the operation needs supported client input, retain its outstanding requests and expose `input_required` through
Task reads and, when authorized, live notifications. `tasks/update` supplies responses keyed to those requests,
following the extension's handling of unknown/already-satisfied keys. Validate active responses and apply current
authorization before the consumer continues work; repeated or concurrent submissions must not accidentally apply
the same accepted input twice.

Reuse the existing supported input/confirmation boundaries where applicable without weakening destructive-action
controls. Input acceptance is not proof that an external action finished and does not confer additional permissions.
This EPIC adds no URL-mode interaction, unrestricted remote Tool execution or new business-approval policy.
Exact request types, race handling and reuse seams belong in requirements within the existing supported scope.

### Request cooperative cancellation

An authorized `tasks/cancel` call requests cancellation. Acknowledging the request does not prove the job stopped,
roll back prior effects or force a `cancelled` terminal state. Preserve the actual terminal outcome when work
finishes or fails before cancellation takes effect. The consumer worker/execution owner decides how to stop work
safely and reports its outcome through the lifecycle contract. Cancellation remains distinct from a transport
connection closing or a stored handle expiring.

### Follow optional live Task state

Compose Task notifications through [Generic MCP Subscriptions — EPIC-00011](00011-EPIC.md) only when explicitly
enabled and supported by the client. Follow the Tasks extension's subscription/filter and notification contract;
polling and ordinary Task operations must remain usable in a composition without Subscriptions.

Standard Task notifications carry full Task state, potentially including results/errors or input requests. Apply
current Task-specific access checks before each disclosure. Generic catalog/change-feed permission, a topic match
or being an intended recipient is insufficient authority for protected Task state. Full-state notifications must
not be copied into EPIC-00011's general retained change-notice feed or indiscriminately broadcast through Mercure.
Consumer composition may separately publish safe “Task changed” references without including full payloads.

Live delivery is best-effort; failure or disconnect does not erase durable Task state. Reconnecting clients establish
a new subscription when desired and fetch current state through `tasks/get`. Exact ordering/race handling between
initial reads and live updates must avoid presenting stale state as newer, but complete intermediate-transition
history is not promised. A missed notification is recoverable as current state within retention, not necessarily
as the exact message that was missed. No per-message acknowledgment or receipt/processing claim is added.

## Acceptance evidence

Future automated tests must demonstrate the complete Tool-to-handle journey through existing guarded HTTP support
and actual reusable persistence, with consumer execution fixtures rather than a new production worker service.
Required evidence includes:

- Explicit extension negotiation, truthful advertisement and safe behavior for unsupported clients/compositions.
- Durable creation before handle acknowledgment, storage failures and state retrieval after client reconnects.
- Supported lifecycle transitions, terminal-state integrity and races between completion, input and cancellation.
- Current access checks and scope isolation across Task reads, input, cancellation and full-state notifications.
- Safe bounded result/error/input output and preservation of the original operation's protocol result semantics.
- Input validation, retained outstanding requests and protocol-correct repeated/unknown-response behavior.
- Cooperative cancellation distinguished from actual stop, rollback, disconnect and expiry.
- Retention/unavailable-state behavior, polling without Subscriptions and optional live notifications when composed.
- Current-state reconnect recovery without a false intermediate-history guarantee or stale-state presentation.
- Full-state notification isolation from the general retained feed and persistence surviving live-delivery failure.

Applicable product suites, exact owned-code coverage and the complete local `./bin/build` gate follow the
[project profile](../agents/project-profile.md). Document supported operations, lifecycle, retention, limits,
composition and failure behavior; align CONTEXT.md when implemented. Distinguish protocol transcript tests from
actual live HTTP delivery evidence. These are future requirements, not checks run for this capability. Package
acceptance does not establish actual Agent OS/Pi or other client deployment support; those remain separate evidence.

## Exclusions and delegated details

- A job scheduler/worker, execution authority, generic status setter, Agent directory or new permission policy.
- Exactly-once job execution, guaranteed notification delivery, forced cancellation or rollback of external effects.
- Intermediate-state notification replay, a full Task transition audit ledger or storing full Task payloads in the
  general retained change-notice feed.
- Treating a Task handle or its completion as planning TASK identity, Workflow completion, independent review,
  publication, signed release or deployment authority.
- Consumer-specific coordination, Agent OS record changes or an additional orchestration engine.
- Additional transports, URL-mode input or other previously deferred MCP capabilities.
- Exact PHP APIs, schema/storage mechanics, numeric limits, retention configuration, update concurrency and live/read
  ordering are downstream requirements/design inside the accepted contract. Release/version selection is unassigned.

### Consumer coordination possibility, not an added deliverable

John asked whether these handles could support Agent OS Team Lead/Engineer/Review/QA/Release Manager coordination.
They can expose authorized asynchronous application operations and link back to planning TASK, Workflow and phase
attempt references; they do not replace those records or enforce phase transitions. One planning TASK may have
multiple Workflow/phase attempts and multiple MCP handles. Authoritative consumer Commands still validate grants,
claims, current evidence, role independence and permitted transitions before continuing work. This is an illustrative
integration direction, not an approved Agent OS mapping, new Common orchestration requirement or claim of deployed
coordination. Existing consumer owners must reconcile it in their own planning if selected.
