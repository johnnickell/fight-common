# Strengthen Value Objects and Validation Invariants

## Destination

Give consuming applications dependable reusable values and safer validation boundaries without reorganizing
Fight Common's architecture. Repair demonstrated defects, strengthen existing identity and JSON capabilities,
and add focused internet, temporal and financial values. Extend boundary safety with transport-neutral application
failure categories and production-safe HTTP error presentation. Consumers can opt into stronger contracts in the
next minor while retaining supported existing APIs; incompatible enforcement/default replacement belongs in a
following major. One explicit exception is TICKET-00034/TASK-00130: at work intake John approved direct StreamId
promotion in the next minor with changed-behavior notes, reporting no external adopters. This supersedes the earlier
major-only planning decision; it does not make the collection/JSON changes backward-compatible. The scoped authority
and migration obligations are recorded in [TASK-00130](../tasks/00130-TASK.md#owner-amendment-at-work-intake).

Common owns construction invariants, immutability, value equality, hashing, comparison, reconstruction and
published representations. Consumers own application policy, authorization, accepted transaction currencies,
SMS addressing policy, scheduling and composition. Domain values remain framework-free and follow the existing
Value/ValueObject and Identifier conventions where suitable. Composite representations must be stable and
unambiguous; tuple components cannot collide through ambiguous delimiter concatenation.

John approved this EPIC after the value-object decision interview, including the temporal suite, historical
currencies, timezone-sensitive DateTime equality, strict DST construction, undefined monetary precision policy
and equal-endpoint range behavior. John subsequently approved application failure vocabulary, safe HTTP handling,
the additive-safe-minor/legacy-default-major migration and the resulting nine-TICKET split. This is approved
planning, not implementation or release acceptance.

## Decisions and exclusions

### Existing defects and compatibility-conscious strengthening

- **Validation isolation:** after a validator throws, the same ValidationService can validate unrelated input
  without stale validators/rules from the failed operation. Ordinary validation results and original failure
  propagation remain supported; cleanup must cover exceptional exits rather than disguise failures as success.
- **EmailAddress:** correctly extract the local/domain parts of accepted quoted addresses such as
  `"a@b"@example.com`, retaining local quotes/escape bytes and domain-literal bracket stripping. Preserve original-
  string representation/case-sensitive equality/hash and the separate lowercase canonical() operation. The repair
  does not expand accepted syntax or silently change rejection contracts.
- **Pagination:** add a strict named factory that validates positive page/page-size values, supported ordering
  directions and checked integer offset arithmetic. Preserve the existing constructor during the minor
  transition, including its zero-to-default and unknown-direction-to-ASC behavior. Deprecate legacy permissive
  construction as appropriate; incompatible enforcement waits for the major. A strict call must never return
  negative bounds, silently accept invalid ordering or fail through accidental float assignment on overflow.
- **JsonObject snapshots:** add opt-in snapshot construction, provisionally named `fromSnapshot()`, accepting
  JSON-encodable mixed data rather than arrays alone. Encode at construction to detach nested mutable objects
  and references. JsonSerializable objects contribute their JSON output, not retained PHP class identity.
  Every access exposing mutable output independently reconstructs it; modifying input or returned data cannot
  change snapshot JSON, equality or hash. Preserve existing `fromData(mixed)` and other legacy paths in the minor.
  Existing StrictJson and its MCP contracts remain supported and are not replaced by this work. Add opt-in
  snapshot-aware text reconstruction, provisionally `fromSnapshotString()`, because legacy fromString collapses
  empty/numeric-key objects and zero-fraction representations. Existing Doctrine hydration remains legacy; adding
  snapshots does not promise automatic persisted-value adoption or change the mapping.
- **StreamId:** own tuple-based equality, hashing, comparison and reconstruction through the existing Identifier
  contract, using ValueObject conventions where suitable. Do not make it a UUID-specific UniqueId. Preserve
  aggregate-name/identifier access and persisted stream identity fields. Equal tuples have equal hashes and
  reconstruct identically; different tuples remain distinguishable. Direct promotion targets the next minor under
  John's scoped work-intake exception; Identifier activation changes collection and JSON dispatch. Preserve component
  bytes with versioned ASCII framing and canonical JSON representation; use bytewise tuple ordering. Assess/document
  migration effects on hash/sorted collections and serialization, preserving the explicit exception and no persisted
  identity rewrite.

### Internet values

- Provide abstract `IpAddress` with final `IpV4Address` and `IpV6Address` implementations. Generic parsing returns
  the appropriate family; concrete factories reject the other family. Use dotted-decimal IPv4 and deterministic
  lowercase compressed IPv6; equivalent spellings, including dotted/hexadecimal mapped forms, normalize equally.
  IPv4-mapped IPv6 remains IPv6 and unequal to IPv4. Reject malformed/contextual forms with DomainException without
  adding address-category policy or changing existing Validate/Application rules. Values have stable string/JSON
  round trips; they do not establish network permission or reachability.
- Provide `E164PhoneNumber` with whole-string grammar `\A\+[1-9][0-9]{0,14}\z`: leading plus, nonzero first ASCII
  digit and at most fifteen digits total. Reject extensions, separators, whitespace/Unicode, unprefixed short codes
  and sender IDs with DomainException; add no arbitrary minimum, trimming or local-format conversion. A syntactically
  valid number does not establish assignment or reachability. Retain string-based SMS factories, message signatures
  and sender/recipient accessors; optional adoption uses explicit toString() conversion without implicit sending.
- CIDR, subnet membership, routing policy and automatic SMS API migration are excluded.

### Temporal values

- Add proleptic Gregorian `Date` for years 0001–9999 (`YYYY-MM-DD`), local `Time` from 00:00:00.000000 through
  23:59:59.999999 (`HH:MM:SS.ffffff`), zoned `DateTime` and native integer-backed `WeekDay` (Monday=1 through Sunday=7).
  Reject date/time rollover, 24:00 and leap seconds. Native component extraction uses the supplied local context.
  Retain existing Timezone and DateTimeImmutable contracts; native enum from/tryFrom behavior remains native.
- DateTime equality is exact instant plus native timezone identifier; ordering compares instant then identifier
  coherently, with separate same-instant comparison provisionally `isSameInstantAs()`. Preserve distinct IANA aliases
  and native identifier spelling, normalizing offset spelling as PHP does without changing existing Timezone identity.
  Interval membership uses instant ordering, not a zone tie-breaker. Instant-preserving conversion and strict local-
  component reinterpretation are distinct operations and must not masquerade as one another.
- Require explicit timezone context for zoned construction. Reject DST gaps; validate offset-in-seconds selection
  for overlaps, including non-hour/historical offsets and existing fixed-offset/abbreviation contexts. Native/instant
  import and serialized reconstruction preserve exact instant, microseconds and native timezone identifier, including
  either fold; detach mutable native input. Retain exact instant coordinates/identifier, not only wall time or minute-
  only offsets. Handle pre-epoch fractions exactly without new platform floors or changing native consumers.
- Add signed fixed elapsed `Duration` as integer microseconds bounded by PHP_INT_MIN/PHP_INT_MAX, with explicit
  exact integer-unit conversions and checked addition/subtraction/negation. Reject fractional/unrepresentable exact
  results, including minimum-integer negation. Zero/negative values are valid; consuming timeout/TTL positivity stays
  outside Duration. Exclude calendar months/years and new platform requirements.
- Add inclusive `DateRange` and half-open `InstantRange` `[start, end)`. Reject reversed endpoints. Equal dates
  form a one-date range; equal instants form an empty interval even with different zones. DateRange equality/hash
  reflects endpoint dates; InstantRange equality/hash/membership uses exact instant endpoints independent of zone
  labels. No range-length/Duration dependency is required. Preserve existing inclusive audit lookup semantics.
- Stepped sequences, recurring scheduling, calendar-month/year duration arithmetic, ambient timezone defaults and
  automatic adoption across existing APIs are excluded. Novuso's stepped DateRange is not the new interval contract.

### Financial values

- Add exact plain-string `Decimal` with normalized numeric identity (1, 1.0 and +01.000 equal; negative zero becomes
  zero), optional sign and no exponent/separators/whitespace/float factories. Bounds are 1,024 normalized coefficient
  digits, normalized/requested scale 0–1,024 and 4 KiB input. Exact arithmetic/finite division reject unsupported
  results; scaled/rounded operations require explicit native PHP RoundingMode. Use a plain-PHP baseline without
  required BCMath/GMP/third-party Domain arithmetic or binary-floating-point financial approximation.
- Add recognized ISO `Currency` with a versioned offline catalog and deliberately distinct current/historical
  status. No network lookup during construction. Historical withdrawal does not prevent representing an old
  currency; consumer policy decides eligibility for new transactions. Alphabetic code identifies the currency;
  display names and numeric-code reuse must not collapse distinct currencies. Preserve numeric metadata as three-
  character strings including leading zeros; catalog revision/status/name is not code identity. Historical rows
  alone do not imply global withdrawal if the code remains in the selected current catalog.
- Preserve metadata provenance/publication version. Historical precision requires supported evidence, not guessed
  defaults. ISO accounting precision, physical subdivision and cash-rounding policy are different concepts.
  Currency may represent a code whose precision is unavailable; minor-unit Money construction rejects it until
  a supported precision definition exists. Never silently substitute two decimal places for ISO N.A.
- Add signed native-integer minor-unit `Money`, including PHP_INT_MIN without a new 64-bit floor, checked compatible-
  currency/scale arithmetic and captured supported accounting definition/scale. Exact Decimal conversion/scalar
  calculation rejects fractional minor results unless rounding is explicit, with one monetary-boundary decision.
  Identity reflects code/captured scale/amount, not display metadata. Reject mismatch/unsupported precision/overflow.
- Allocate nonempty lists of nonnegative integer weights (at least one positive) by largest remainder, ties by original
  index. Compute magnitude/intermediates exactly, restore sign/original order, give zero weights zero and preserve
  signed totals including native minimum. Reject unsupported allocation inputs without financial policy inference.
- Versioned readers retain exact textual minor units, code/scale and supported definition context; catalog maintenance
  retains old supported reader meaning rather than applying new defaults, replacing codes or silently redenominating.
- Money, Currency and Decimal are new Fight APIs: no compatibility with Novuso constructors, metadata tables or
  serialization is required. Novuso is reference evidence, not authoritative Fight policy or a source-copy mandate.
- Exchange rates, automatic currency conversion, application financial policy and localized monetary formatting
  are excluded from this delivery.

### Application failures and safe HTTP presentation

- Add reusable Application/Error/Exception categories covering authentication required, permission denied,
  intentionally missing resource, state conflict, resource gone, failed precondition, invalid input, business-rule
  rejection, rate limiting, unexpected/server failure and temporary service unavailability. Reconcile existing
  validation exceptions rather than creating competing structured-validation contracts. Approved categories are
  AuthenticationRequired, PermissionDenied, ResourceNotFound, StateConflict, ResourceGone, PreconditionFailed,
  InvalidInput, RuleViolation, RateLimitExceeded, ServerError and ServiceUnavailable. Abstract ApplicationException
  extends Common's SystemException/Catchable family; concrete categories deliberately support consumer Application
  subtypes, without introducing Domain-to-Application dependencies.
- These exceptions express application intent without HTTP statuses, headers, JSend or framework dependencies.
  Preserve ordinary diagnostic messages, supported integer codes and previous Throwable identity, including PHP
  Error causes; contextual data is not automatically public-safe. No public-message/diagnostic-serialization API
  is introduced. Domain policy, authentication/authorization decisions, transactions and recovery remain owner-held.
- Preserve existing validation hierarchy/constructors/fromErrors/getErrors/catchability/subtypes unchanged.
  InvalidInput expresses unusable input without requiring a field-error map; existing ValidationException owns
  structured field validation; RuleViolation expresses deliberate business-rule rejection without mandatory migration.
- RateLimitExceeded/ServiceUnavailable support optional neutral retry-delay seconds: native integer >=0, null
  meaning unspecified, zero valid. Validate metadata without a clock default, Duration prerequisite, retry permission,
  scheduling or HTTP header authority; TICKET-00039 owns deliberate validated public/HTTP projection.
- Provide explicit opt-in safe HTTP handling for canonical Symfony, Laravel and PSR-15 adapters, with deprecated
  Symfony-path compatibility and migration evidence. Share safe classification/projection knowledge while retaining
  native responses, framework lifecycle and JSON negotiation. No unrequested framework-wide handlers are added.
- Recognized categories receive fixed safe defaults; custom public messages/data require explicit projection.
  Unknown Throwable receives a generic safe 500 response. Do not infer status/public text from arbitrary exception
  codes/messages or automatically interpret every lookup, auth infrastructure fault or timeout as a client failure.
- Adapters own correct statuses and validated protocol metadata, including consumer-configured authentication
  challenges, Allow and applicable retry metadata. HTTP-only routing, negotiation, size and gateway failures stay
  at the transport boundary; do not create an Application exception for every HTTP status.
- Follow [ADR 0018](../adr/0018-neutral-jsend-envelope-and-native-response-boundary.md): expected application/request
  refusals use JSend fail; unexpected server/infrastructure failures use error. Preserve explicit safe validation
  presentation, redaction-aware diagnostic ownership and trusted-only development detail configuration. Raw exception
  messages or validation context do not become safe by convention; diagnostics must not be lost or duplicated.
- Additive safe handling targets the minor. Keep legacy behavior functional, clearly document/deprecate its unsafe
  arbitrary-message output and supply concrete safe opt-in wiring. Replacing legacy defaults belongs in the major
  after the required deprecation window. This EPIC does not authorize immediate incompatible default remediation
  or a security compatibility exception; a requested urgent change requires separate assessment/authorization.
- Application vocabulary and HTTP translation are separate requirement areas; the latter depends on the former.
  No consumer/Agent OS source migration, new permission policy or changed MCP error mapping is included.

### Package compatibility and ownership

- Target primary delivery at the next minor with additive APIs and deprecation-first migration; direct StreamId
  promotion is the explicit TASK-00130 owner-approved exception to compatible-minor policy. Deprecated contracts remain
  functional for at least one released minor before incompatible change/removal in the major. No precise release number or
  signed release operation is assigned here.
- Classify behavior as well as signatures: pagination bounds, mutable-object isolation, stream collection equality,
  public error bodies/defaults, exception contracts, serialization and persisted data all matter. An unchanged PHP
  signature is not sufficient evidence of compatibility. Resolve material compatibility uncertainty before shipping;
  do not silently label
  a breaking change a fix or authorize a compatibility exception through this EPIC.
- Deliberately classify new declarations and supported consumer operations in the public API manifest under
  [ADR 0009](../adr/0009-public-api-manifest-baseline.md). Preserve dependency direction and existing adapters.
- General architecture reorganization, changed CQRS/event-delivery guarantees, new business authorization,
  automatic consumer migration and changes in other repositories are excluded.

## Use cases and observable evidence

| Actor and trigger | Expected outcome / evidence |
|---|---|
| Consumer reuses ValidationService after a validator throws | A subsequent unrelated validation has no stale validators, errors or rule state; the original failure still propagates correctly. |
| Consumer parses an accepted quoted email or creates pagination | Correct email parts with unchanged equality; strict pagination rejects invalid bounds, ordering and overflow while legacy constructor behavior stays documented during migration. |
| Consumer snapshots nested objects/references and then mutates input or returned output | Snapshot JSON, equality and hash remain unchanged; custom JsonSerializable output is detached and mutable outputs are fresh. Legacy JsonObject and StrictJson behavior remain supported. |
| Consumer reconstructs a stream identifier or inserts equal tuples into a value collection | Tuple identity round trips without collisions; equality, hashing and comparison agree. Compatibility evidence classifies any changed set behavior and preserves stored stream identity. |
| Consumer parses IP addresses or an E.164 phone number | Equivalent addresses normalize consistently with correct family; invalid syntax rejects. SMS sender IDs/short codes still work through existing string APIs. |
| Consumer constructs a zoned date-time at a DST transition or from native input | Gaps reject, overlaps require disambiguation, either native occurrence preserves its instant, and serialized round trips retain timezone and selected occurrence. |
| Consumer compares ranges or converts a fixed duration | Microsecond elapsed precision is exact; calendar and instant semantics are distinct; reversed/equal endpoints and inclusive/half-open containment match the approved contracts. |
| Consumer calculates and allocates money in current or historical currencies | Exact calculations and explicit rounding; allocation preserves signed totals deterministically; mismatches, overflow and undefined precision reject without coercion or automatic currency replacement. |
| Consumer-owned command/query handler reports an application failure | A transport-neutral category expresses intent without HTTP imports, invented authorization policy or automatically public diagnostic text. |
| Consumer opts into safe HTTP handling and a known/unknown failure reaches the boundary | Safe fail/error output, correct statuses/validated protocol metadata and owned redacted diagnostics; raw exception details do not leak and legacy behavior is not silently replaced. |

These are library construction, transformation, comparison, validation, failure-expression and HTTP-presentation
use cases. They introduce no new business commands, queries, events, outbound provider delivery, authentication
mechanisms or permission policy; those concerns are N/A here and remain consumer-owned. Existing consumer handlers
can throw the new categories without Common inventing their commands/queries. ValidationService remains its existing
application boundary. No database/schema migration is required; persisted stream identifiers and native timestamp
contracts stay unchanged. Any later migration proposal must be classified explicitly rather than inferred from
this plan. Snapshot encoding and validation cleanup are local effects; currency construction performs no I/O.
HTTP response creation and redaction-aware diagnostics are technical effects, not domain events or rollback guarantees.
