# Execution introspection

## Destination

Give human dashboards and authorized Agents a reusable way to answer **“What is happening, where did it stop,
and what evidence explains the outcome?”** Common records trusted execution observations and serves summary-first,
bounded detail Queries, including separately protected captured messages, tool arguments/results and process output.

The complete journey is permitted-scope summary → paginated executions → selected execution summary and phases →
selected phase activity and authorized detail. Summary statistics cover all authorized matches, not merely the page.
Unknown outcomes, partial capture, unavailable content and missing measurements remain explicit.

Common supplies the implementation, not merely interfaces: typed observation contracts, CQRS handlers, a reusable
persistence adapter, domain events and MCP presentation. Preserve `CommandBus::execute()`, `QueryBus::fetch()` and
`EventDispatcher::trigger()`. MCP and consumer dashboards use the same application Queries rather than direct
adapter database access or duplicated business logic. A dashboard implementation is not a Common deliverable.

Agent OS is the first planned consumer, not the owner of this generic library model. Its authoritative Workflow
state remains separate; Common must not introduce competing execution truth or silently amend consumer policy.

## Required use cases and guarantees

### Record trusted observations

Consumer instrumentation submits observations through Commands using trusted producer/scope context. Supplied
execution, phase, Agent or detail IDs are references, never credentials. Validate that related records belong to
the permitted project/scope and reject invalid structure, unsupported payload versions and exceeded bounds.

The typed core contains sessions with consumer scope/reference and observed timing/outcome; phases with session/
parent relationships, performing Agent identity, name and attempt; activities with producer, kind, safe summary and
occurrence/recording timestamps; and linked protected details with content type and capture-completeness information.
Bounded namespaced extensions support consumer vocabulary without admitting raw content into safe summaries.
Performing Agent identity is distinct from model identity and the instrumentation producer. Measured usage retains
units and provenance; missing values are not zero.

Each Command commits its related database changes together or not at all, including database-backed content/link
changes. Successful recording acknowledgment follows commit. This is not a transaction with external files or the
work being observed. Storage errors are explicit; a timeout may leave the caller uncertain whether commit occurred.
Same producer-scoped identity and content deduplicate; different content under that identity conflicts rather than
overwriting. Retry safety lasts while the required identity/content-comparison records remain stored, not forever
after deliberate deletion. Saved structured payloads are versioned and unsupported versions fail clearly.

Domain events describe observation facts, not authoritative Workflow transitions or review acceptance. Post-commit
dispatch outside the database transaction is permitted and may be lost. Dispatch/subscriber failure cannot undo
committed data and must remain distinguishable from storage rollback. No outbox or guaranteed delivery is required.
Consumers decide whether an observation failure interrupts their work; mandatory audit remains a separate contract.

### Inspect authorized summaries and activity

Humans and Agents use the same application Queries with caller-specific current access decisions. Summaries show
execution counts, known outcomes, measured usage and freshness for all permitted matching records. Summary
projections may lag; neither a stale projection nor missing completion evidence proves an outcome.

Execution, phase, activity and message collections use bounded live offset/limit pagination through existing
`Pagination` semantics (`page`/`per_page`). Each request independently supplies its selection and rechecks access.
Changing records may change totals or cause repeated/skipped rows across requests; no frozen result, remembered
search or cross-request snapshot is promised. Large individual outputs use bounded chunks. UI page resets and
live-update behavior are consumer concerns.

Default observation order is immutable server recording/receipt time descending, then full observation UUID COMB
descending. Preserve occurrence time separately; recorded time is neither commit order nor causal order. Qualify
microsecond precision where supported without inventing finer source precision. Full UUID comparison must agree
between storage and application; random suffixes give deterministic ties, not chronology.

### Inspect protected captured detail

A caller with separate current permission can retrieve bounded messages, tool arguments/results and process output.
Timeline access, a detail reference or human permission does not automatically authorize Agent access. Common keeps
raw bodies out of sanitized summaries, history/search projections and ordinary activity responses. Consumers select
capture and redact before submission; structural validation is not a universal secret detector.

Logical FK-linked session/phase/detail storage permits details to be removed while session/phase summaries remain.
Common owns separation, referential integrity, ordinary CQRS persistence operations and truthful absent-detail reads,
not a fixed three-table schema or a requirement to store every byte in a database row. Preserve consumer-supplied
expired-content markers; an absent row alone does not establish expiration. Never fabricate missing content or
present a dangling reference as available detail. Retention eligibility, holds, cleanup jobs and archival remain
consumer operations.

### Inspect through MCP without a second implementation

Provide explicit MCP presentation of the shared application use cases through existing guarded HTTP/Tool support.
The approved TICKET decomposition selects read-only inspection Tools initially: recording and removal remain
trusted application Commands, not MCP mutation Tools. Any future mutation exposure needs separately accepted scope
and must retain the trusted Command admission boundary. Protocol availability checks do not replace use-case authorization. Preserve safe/protected-content separation,
structured result validation and bounded responses across this adapter. Exact Tool names/catalog and response
shapes belong in subsequent requirements/design, not implicit generic database or Workflow mutation access.

## Acceptance evidence

Future implementation must demonstrate the complete summary-to-detail journey through shared Commands/Queries and
the MCP adapter, with a working reusable persistence adapter rather than interface-only or mock-only storage proof.
Automated behavior coverage must include:

- Version handling, validation/bounds and cross-project reference isolation.
- Related database writes committing together or rolling back, commit-before-acknowledgment and explicit failures.
- Same-content retries, different-content conflicts and the retained-record guarantee boundary.
- Current authorization on every read, distinct human/Agent permissions and absence of protected content in safe reads.
- Full-selection summaries, freshness, honest unknown/partial measurements, live pagination and deterministic ordering.
- Independent detail removal, truthful missing/expired information and bounded content reads.
- Committed persistence distinguished from subsequent event dispatch/subscriber outcomes.
- Equivalent application/MCP behavior through the existing HTTP composition without optional subscriptions.

Applicable product suites, exact owned-code coverage and the complete local `./bin/build` gate follow the
[project profile](../agents/project-profile.md). Document public contracts, composition, limits and failure behavior,
and align CONTEXT.md when the capability is implemented. This planning record claims none of those checks have run
for the new capability. Common package acceptance is not proof of a deployed dashboard, Agent OS runtime or real
MCP-client qualification; those integrations remain downstream evidence, not an extra Common completion gate.

## Exclusions and delegated details

- No authoritative Workflow engine, generic Workflow/status setter, Agent directory, permission grant or review verdict.
- No automatic transcript capture, universal redaction service, hidden-reasoning access or complete-output guarantee.
- No retention policy/eligibility engine, cleanup/archive orchestration or recovery of consumer maintenance jobs.
- No OpenTelemetry SDK, exporter or mapping; no required telemetry service.
- No dashboard UI, browser navigation contract, frozen browsing sessions or cursor-based application pagination.
- Generic MCP Prompts, Subscriptions and Tasks belong to separate EPIC destinations; this journey does not wait for them.
  Apps, URL-mode input, Resource templates and Completion remain deferred under WF-048.
- No Agent OS record changes. John owns reconciliation of its rich-detail requirements and existing privacy/history owners.
- Exact classes, schema/database mechanics, finite limits, event catalog and adapter composition are subsequent planning
  details within the accepted guarantees, not new EPIC-scope decisions. Release/version selection remains unassigned.
