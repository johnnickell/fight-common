# Make all Common-owned table names configurable

## Destination

Let a consuming application's integrator choose an individual name for every Common-owned database table,
without editing package source or accepting a mandatory naming prefix. Existing consumers that supply no
overrides continue to use today's table names and persistence behavior.

The actor is the consumer integrator or deployment operator. Configuration is supplied explicitly while composing
persistence adapters and schema installation, then governs the existing storage operations. This is a package
configuration capability, not a new application use case, public endpoint or database administration service.

## Accepted decisions and ownership

John approved the complete destination after the Grill interview:

- Cover every Common-owned table across persistence adapters, including internal schema/state, sequence and
  lock-bearing tables. No table is exempt merely because it is not a user-facing record table.
- Allow individual table-name overrides; a shared prefix alone does not satisfy the destination.
- Preserve current names as defaults and retain existing ORM mapping-based customization.
- Consumers supply names explicitly at adapter composition. Common does not read environment variables or
  global configuration implicitly; consumers may translate their own framework configuration at that edge.
- Schema definition, installation and validation, reads, writes, joins, cleanup and locking must consistently
  use the configured names for the same persistence capability.
- Accept ordinary table names only, with safe validation and platform-appropriate identifier quoting.
  Schema-qualified names such as `reporting.executions` are outside this destination; database/schema selection
  remains connection configuration.
- No migrations, automatic table renames or data movement. A changed name selects another table; it does not
  relocate existing data. Any operational rename or data transfer remains the consumer's responsibility.

Common owns coherent adapter behavior, safe identifier handling, unchanged defaults and documentation of these
boundaries. Consumers own the selected names, connection/schema configuration, database privileges, deployment
sequencing and any existing-data operations. Table-name configuration does not grant access or replace current
application permissions. Infrastructure naming stays at the Adapter/composition boundary, not in Domain or
Application contracts.

## Required outcomes and acceptance evidence

Future implementation evidence must demonstrate:

1. Each Common-owned table can be independently renamed, including state/sequence/lock tables, while omitted
   overrides retain their exact defaults. Partial overrides must not silently rename unrelated tables.
2. Schema creation and validation and all runtime paths agree on the selected names. Exercise actual writes,
   reloads, joins, transaction serialization and relevant removal/recovery paths, not only generated schema text.
3. Customized operation does not silently read or write the default tables when different names were selected.
4. Invalid or unsupported names reject safely rather than becoming executable SQL or silently falling back to
   defaults. Identifier handling works on the supported database platforms without weakening data binding.
5. Existing default compositions and ORM metadata-driven overrides retain their promised behavior. Preserve
   released public API compatibility, stored payloads, ordering, transaction guarantees and permission checks.
6. Configuration changes never rename, migrate, copy or rewrite existing tables/data. Existing explicit schema
   installation remains an operator action for the selected names, not an implicit runtime migration.
7. Consumer documentation explains complete per-table configuration, consistent schema/runtime composition,
   defaults, validation limits and the no-migration boundary. Align affected component guidance and CONTEXT.md
   when implementation changes the current API.

Existing Commands, Queries and Events retain their contracts; this capability adds none. Side effects remain
those of explicitly invoked schema installation and existing storage operations. No new HTTP, UI, authentication
or authorization surface is introduced. Preserve existing storage/schema rejection and recovery guarantees;
configuration must not disguise missing or incompatible tables as a successful data migration.

Applicable product tests, exact owned-code coverage, the complete local gate and independent Review/QA follow the
[project profile](../agents/project-profile.md). These are future acceptance requirements, not evidence of an
implemented capability or a release certification.

## Exclusions and delegated details

- Migrations, automatic renames, existing-data transfer, or compatibility migrations for development snapshots.
- Schema-qualified table names, cross-database routing, column renaming or consumer policy changes.
- A global configuration registry, implicit environment loading or a new mandatory prefix convention.
- Replacing existing ORM mapping configuration or taking ownership of framework/provider storage internals.
- Unrelated aggregate/namespace or transaction refactoring. Coordinate with the existing architectural correction
  sequence through [TASK-00183](../tasks/00183-TASK.md) without duplicating or changing its accepted scopes.
- Exact PHP configuration APIs, validation grammar/limits, quoting mechanics, related index/constraint handling,
  implementation dependencies and PR slicing remain downstream design within these approved boundaries.
- Release target, execution priority and checkout/worktree selection remain unassigned.
