# Operator Surfaces and Release Integration

## Problem Statement

Deterministic release commands are not sufficient by themselves. An operator still needs to identify the right
journey from repository state, change intent, affected release lines, urgency, and release class; invoke only
the command allowed for the current phase; understand stops and approvals; and hand the result to the next
phase without memorizing Git choreography.

Duplicating release rules in skills, catalog entries, CI workflow files, or runbook prose would create several
policy implementations that drift independently. Conversely, thin surfaces without verified routing, links,
postconditions, and traceability could send an operator to the wrong workflow or present incomplete hosted
checks as success.

## Solution

Add six thin Fight Common release skills, one catalog route, a state-first dispatcher, journey-card runbook,
and CI integration around the repository-owned release command. Operator surfaces inspect and explain state,
request one bounded approval, invoke only allowlisted commands, render the machine result, and expose one stop
or next action. They link to canonical policy and planning rather than copying it.

Use the same deterministic command and composed quality evidence locally, in offline routing fixtures, and in
CI. Finish with traceability validation from EPIC-00003 through all four PRDs, twelve implementation tickets,
journey acceptance evidence, commands, skills, catalog entries, and runbook cards.

## User Stories

1. As an operator, I want one top-level release dispatcher, so that I do not need to choose a workflow from
   memory.
2. As an operator, I want routing to inspect repository and release state before asking my intent, so that my
   preference cannot contradict the actual target ref or run state.
3. As an operator, I want routing to consider intent, affected supported lines, urgency, and release class, so
   that it selects the complete applicable journey.
4. As a contributor, I want a feature targeting `develop` routed to the feature journey, so that it cannot be
   mistaken for a released-line patch.
5. As a contributor, I want an unreleased defect to follow the ordinary `develop` journey, so that urgency
   does not invent a hotfix path.
6. As a patch operator, I want unknown affected-line evidence to stop routing, so that no maintenance base is
   guessed.
7. As a release operator, I want minor and major releases represented by one journey with explicit
   differences, so that their shared phases remain consistent without hiding topology or evidence changes.
8. As an operator, I want incomplete publication routed to reconciliation, so that I do not repeat external
   effects blindly.
9. As an operator, I want one skill for each release phase or maintenance responsibility, so that capability
   ownership is obvious.
10. As an operator, I want each skill to revalidate its input handoff, so that stale plans and unverified
    postconditions stop before action.
11. As an operator, I want skills to request approval only for the exact bounded effect they own, so that one
    interaction cannot authorize later phases.
12. As an operator, I want skills to display plan and run IDs, evidence, approvals, postconditions, stop state,
    and one next action, so that every handoff is auditable.
13. As an operator, I want a skill to stop after its own phase, so that invoking planning never packages and
    invoking certification never publishes.
14. As a policy maintainer, I want skills and catalog entries to link to canonical command and planning
    contracts, so that prompt prose does not become a second policy source.
15. As a policy maintainer, I want agent instructions to point to the release map through the existing
    repository hierarchy, so that release rules are not copied into general instruction files.
16. As an operator, I want one journey card shape, so that every workflow tells me when to use it, its inputs,
    approvals, commands, postconditions, stops, escalation, cancellation, resume behavior, and next handoff.
17. As an operator, I want troubleshooting limited to diagnosis, evidence, canonical recovery selection, and
    escalation ownership, so that runbook prose never improvises a mutation.
18. As an operator, I want cancellation to preserve run evidence, so that stopping work does not erase the
    audit trail.
19. As an operator, I want material input changes to require a new plan and run, so that resume does not hide
    supersession.
20. As a CI maintainer, I want hosted verification to invoke the canonical repository gate, so that workflow
    configuration does not reproduce release policy.
21. As a CI maintainer, I want composed evidence rather than one check name, so that a green hosted status
    cannot substitute for missing lanes.
22. As a contributor, I want local and hosted results to share stable machine semantics, so that failures and
    stops are interpreted consistently.
23. As a maintainer, I want catalog and runbook links checked automatically, so that operator entry points do
    not decay.
24. As an epic owner, I want traceability from the destination through each PRD, ticket, journey, and
    verification result, so that implementation completion is reviewable.
25. As a test author, I want routing and skill behavior exercised offline against deterministic command
    results, so that operator integration never requires a real release.

## Implementation Decisions

- The operator catalog exposes exactly six release skills: plan release, package release, certify release,
  publish release, maintain release line, and patch release line.
- Each skill owns one closed capability boundary and invokes only the deterministic release subcommands
  allowlisted for that phase. A capability mismatch is rejected before command execution.
- Skills are guided operator workflows, not policy engines. They inspect state, explain the machine result,
  request bounded approval, invoke one permitted command, verify postconditions, and present one handoff or
  stop.
- No skill invokes the next skill automatically. Advancing between planning, packaging, certification,
  publication, maintenance, and patch responsibilities requires an explicit operator action.
- Skills consume content-addressed handoffs and revalidate all bound inputs, approvals, evidence, and claimed
  postconditions. Missing or stale handoff fields stop in the owning phase.
- Skill output identifies `plan_id`, `run_id`, phase and status, bound object IDs and digests, performed or
  proposed effects, approvals, evidence references, verified postconditions, any stop state, and exactly one
  next action.
- Catalog entries and skills link to the canonical release map, PRDs, tickets, ADRs, runbook, and command help.
  They do not restate compatibility policy, state transitions, effect rules, polling schedules, or Git
  topology.
- Repository instructions continue to route release coordination through the canonical map. General agent
  instructions point to repository instructions rather than duplicating release links or rules.
- The top-level dispatcher classifies repository and release state first, followed by change intent, affected
  supported lines, urgency metadata, and release class. A user-selected journey cannot override a
  contradictory state classification.
- Supported operator journeys are feature, unreleased fix, supported-line patch, forward port, minor or major
  release, maintenance-line transition, and incomplete publication.
- Urgency and security remain metadata layered onto the selected ordinary journey. They affect visibility,
  impact, escalation, and timing presentation but not routing authority or gate requirements.
- Every journey card has one structure: selection criteria and routing decision; required inputs and evidence;
  approval gates and effect authorizations; phase-labeled command and skill links; expected postconditions;
  stop states and escalation ownership; cancellation and resume; and the next handoff.
- Every journey follows inspect, classify, plan, review and approve, execute one bounded effect, verify the
  postcondition, then hand off or stop.
- Stop states are valid documented outcomes. Troubleshooting may diagnose, collect evidence, select a canonical
  recovery command, and identify the escalation owner; it does not prescribe blind retry, destructive cleanup,
  or ad hoc provider mutation.
- Cancellation preserves the immutable plan, run transitions, results, and evidence. A material input change
  supersedes the old plan and starts a new run rather than rewriting history.
- Minor and major releases share one journey card with a comparison of release classification, compatibility
  evidence, approval, and branch-topology differences. Shared policy remains linked rather than copied.
- Patch and forward-port cards require explicit affected, unaffected, or unknown evidence for every supported
  line and display each newer port as a separate reviewed and certified step.
- Incomplete-publication routing verifies each possible Git, tag, GitHub Release, asset, Packagist, and
  clean-install postcondition independently before proposing a recovery effect.
- CI invokes the canonical repository quality and release-verification commands. Workflow configuration owns
  triggers, environment setup, permissions, and artifact transport, but does not reproduce command ordering or
  release classification.
- Hosted results remain inputs to the composed evidence manifest. A check that is queued, running, skipped,
  cancelled, or missing is not a passing lane.
- Final planning validation checks every epic-to-PRD, PRD-to-ticket, dependency, catalog, skill, runbook,
  acceptance, and verification link and reports drift as a failing machine result.

## Testing Decisions

- The primary seam is the operator journey from dispatcher input through a selected thin skill to the public
  release command's deterministic machine result, using offline repository and provider fixtures.
- Routing fixtures cover feature, unreleased fix, supported-line patch, forward port, minor release, major
  release, maintenance transition, urgent metadata, EOL, stopped run, and incomplete publication.
- Contradiction tests attempt to select a released patch journey for `develop`, a feature journey for an
  affected maintenance line, a mutation after EOL, and ordinary publication from partial state; each must stop
  before an effect.
- Skill contract tests prove exact command allowlists, one-phase ownership, handoff revalidation, bounded
  approval prompts, postcondition verification, machine-result rendering, and absence of automatic chaining.
- Capability tests substitute a command adapter that would accept extra operations and prove the skill still
  rejects out-of-phase invocations.
- Output tests assert the required plan, run, identity, evidence, approval, postcondition, stop, and next-action
  fields for successful and stopped journeys.
- Catalog and link tests resolve every skill, command, release map, PRD, ticket, ADR, and runbook reference and
  reject copied or orphaned policy surfaces where mechanically detectable.
- Journey-card tests assert that every supported journey contains the common sections and links to canonical
  phase contracts without duplicating normative command behavior.
- Patch-routing tests require complete affected-line classifications and prove unknown evidence stops before
  base selection.
- Urgent-mode tests compare routing, gates, and effects with the equivalent ordinary journey and assert that
  only visibility, impact, escalation, and timing presentation differ.
- Troubleshooting fixtures cover conflict, failed certification, indeterminate evidence, signing failure,
  GitHub ambiguity, Packagist timeout, and clean-install failure; each presents diagnosis, evidence, escalation
  owner, and one canonical next action without blind retry.
- Cancellation and supersession tests prove evidence is retained and material input changes create new plan
  and run identities.
- CI contract tests assert invocation of the canonical gate and verification command, required permissions and
  artifacts, and the absence of a duplicated release-policy sequence in workflow configuration.
- Hosted-status fixtures prove queued, running, skipped, cancelled, missing, and failed checks cannot satisfy a
  composed evidence lane.
- Traceability tests walk EPIC-00003 through PRD-00010 to PRD-00013, T-00032 to T-00043, their dependencies,
  journey evidence, and verification commands with no unresolved or contradictory links.
- Tests assert routing decisions, command invocations, results, rendered handoffs, links, and effect ledgers
  rather than prompt wording that does not change operator behavior.
- T-00038, T-00043, and T-00039 must pass the repository submit gate, planning validation, catalog and link
  checks, and the complete deterministic offline journey suite; no live publication or hosted mutation is
  required.

## Out of Scope

- Reimplementing release, compatibility, support, authorization, state, or recovery policy in skills, catalog
  entries, runbook prose, CI configuration, or general agent instructions.
- Automatically invoking the next release phase or bundling several effect authorizations into one approval.
- Building the plan, package, certification, publication, maintenance, or patch engines owned by earlier PRDs.
- Real release publication, branch protection changes, hosted-environment provisioning, credential handling,
  or external provider mutation.
- Improvised troubleshooting, blind retry, destructive rollback, or operator-selected routing that contradicts
  verified repository state.
- Treating one hosted check, workflow conclusion, or raw log as the composed evidence manifest.
- Creating a second hotfix or urgent release path.
