# Fight Common Contract Repair and Compatibility Certification

## Problem Statement

Fight Common is intended to provide a portable Domain and Application core plus optional infrastructure
adapters, but its current `1.2.0` candidate cannot yet be certified as an additive successor to `1.1.0`.
Published Scheduler construction changed incompatibly, JSend behavior is coupled to Symfony and raw arrays,
`Arrayable` promises a map even though existing collections also return lists, and framework or provider
adapters occupy inconsistent namespaces that obscure their capability and dependency.

The package also lacks a complete interoperability lane for capabilities that PHP-FIG standards can express
honestly. PSR-15 and PSR-17 should provide reusable HTTP/JSend integration, PSR-6 and PSR-16 should expose the
portable cache behavior, and a PSR-18 view should expose the synchronous half of Fight's larger HTTP-client
contract without pretending that arbitrary synchronous clients support Fight's asynchronous operation.
Neutral queued-message handlers and capability-scoped registrars are likewise needed so framework adapters can
reuse Fight behavior instead of duplicating it.

Finally, a green root build does not prove that legacy public APIs remain usable, optional framework packages
remain optional, or the distributable package works in real consuming applications. Fight Common needs one
consumer-facing certification model that combines library-owned adapter conformance, exported-package and
production-only installation evidence, and booted receipts from the five real starter repositories.

## Solution

Repair the `1.2.0` contract additively and establish the shared adapter foundation used by every supported
framework. Restore supported `1.1` Scheduler construction while adding a named portable runner path; introduce a
framework-neutral typed JSend envelope and native or standards-based response adapters; correct the base
array-shape promise without narrowing existing result sets; and publish capability-first canonical adapter names
while retaining independently functional deprecated legacy names throughout `1.x`.

Add shared PSR-15, PSR-17, PSR-6, PSR-16, and PSR-18 integrations only where translation preserves the observable
contract. Add neutral command-message and event-message handlers that invoke the synchronous Fight bus or
dispatcher, plus capability-scoped registration classes for Fight's own PSR-11 container. Preserve the narrower
transactional UnitOfWork and private-publication decisions already accepted for `1.2`.

Certify these changes through shared behavioral conformance suites and one exported-package black-box consumer
harness. The harness composes focused compatibility probes, locked and dependency-boundary lanes, a production
`--no-dev` install, and immutable booted receipts from the Symfony, Laravel, Yii, CodeIgniter, and Slim starters.
Missing or indeterminate required evidence fails the affected support claim rather than becoming a waiver.

   existing scheduled jobs continue to run.

   Symfony HttpFoundation.

   every framework produces the same response meaning.

11. As an API consumer, I want invalid UTF-8 and unencodable values rejected before native response construction,

## Implementation Decisions

- The public API manifest is authoritative for production declarations and functions. It classifies public and
  internal surface and records callable, constructible, extensible, and implementable compatibility separately.
  The current authority deliberately classifies 45 public additions and one internal addition after `1.1.0`.
- The Scheduler restores the published `1.1.0` constructor, named arguments, command execution, process factory,
  and conditional process behavior. A named `withProcessRunner` constructor provides the portable path. If the
  compatibility bridge cannot preserve legacy behavior, the required-runner-only design moves to `2.0.0`.
- Application HTTP owns immutable `JSendEnvelope` and `JSendStatus` types. The envelope owns JSend semantic data
  and final JSON encoding, but no HTTP status, headers, framework response, service lookup, or I/O.
- Typed JSend factories accept presentation values through `Arrayable`. Paginated `ResultSet` values remain
  valid only when each response record can be projected through `Arrayable`; other `ResultSet` consumers retain
  arbitrary record types.
- The base `Arrayable` contract permits `array<array-key, mixed>`. Implementations document narrower shapes.
- Invalid JSON encoding raises `JsonException` before native response construction. Legacy Symfony raw-array
  entry points retain their established encoding behavior throughout `1.x`.
- Runtime adapters use `Adapter\<Capability>\<Framework-or-Provider-or-Standard>\<Type>`. Framework service-
  container extensions use `Adapter\ServiceContainer\<Framework>\<Type>`. HTTP controllers, middleware,
  persistence implementations, and framework-neutral Application HTTP and service-container primitives use the
  canonical capability destinations accepted by ADR 0023.
- The namespace migration includes existing Symfony compiler passes, HTTP subscribers, middleware, controller,
  JSend response, filesystem, Messenger buses, Messenger serializer, message handlers, URL generator, and
  Doctrine data types and UnitOfWork. Existing Mail, Process, Mercure, and other already capability-qualified
  adapters remain canonical where they are.
- Every superseded public FQCN remains functional and deprecated without runtime warnings throughout `1.x`.
  Compatibility uses an alias only when construction, identity, extension, attributes, serialization, and real
  framework registration remain correct; otherwise it uses forwarding or an explicit compatibility class.
- Shared HTTP interoperability consists of PSR-15 JSON/JSend error middleware and a PSR-17 JSend response factory.
  These consume the neutral JSend envelope and do not invent framework lifecycle behavior.
- Canonical PSR-6 and PSR-16 cache adapters expose the complete cache behavior. Documentation distinguishes cache
  standards from unrelated PSR contracts and does not claim support from package presence alone.
- `Adapter\HttpClient\Psr18\Psr18Client` implements PSR-18 by composing Fight's
  `Application\HttpClient\Transport\HttpClient`. `sendRequest()` exposes the configured transport's synchronous
  `send()` operation; Fight's interface retains `sendAsync()`.
- The PSR-18 adapter returns 4xx and 5xx responses normally and translates request-construction and network
  failures into the exception contracts required by PSR-18. A generic synchronous-only PSR-18 client is never
  advertised as an implementation of Fight's larger interface.
- Service-container integrations may register one configured transport behind Fight `HttpClient` and a
  `Psr18Client` view behind PSR-18 `ClientInterface`.
- Neutral command-message and event-message handlers accept one complete Fight message and invoke the synchronous
  `CommandBus` or `EventDispatcher`. They contain no framework queue, retry, broker, worker, or serialization
  configuration.
- Fight's concrete PSR-11 container receives capability-scoped registrars. Registrars accept explicit maps for
  services, command and query handlers, event subscribers, filters, helpers, and other collaborators; they do not
  scan project code or add another general callback mechanism.
- `TransactionalUnitOfWork` owns transactional callback execution and closed-state reporting. Legacy `UnitOfWork`
  extends it and retains deprecated `commit()` throughout `1.x`; Doctrine continues to satisfy both contracts.
  Callback results are preserved, failures roll back, and nested transactions fail explicitly.
- `Publisher::push()` remains unchanged. `PrivatePublisher::pushPrivate()` is a separate Application port, and
  Mercure provides the reusable private-publication adapter without owning authorization, application envelope
  transformation, or browser subscription policy.
- Direct interface use needs no Fight-branded wrapper. No PSR adapter is published where translation would omit
  required Fight behavior; PSR-14 remains an explicit messaging mismatch.
- Framework and optional provider packages remain outside production requirements. Packages needed for adapter
  conformance are development requirements and Composer suggestions; normative supported ranges remain in
  framework support documentation.
- Fight Common owns one exported-package black-box harness, not five nested framework projects or one combined
  framework application. The real starters own their dependency graphs, native activation, lowest/latest
  resolution, booted journeys, and immutable receipts.
- The final `1.2.0` evidence set composes the API manifest and operation diff; Scheduler, JSend, namespace,
  UnitOfWork, private-publication, PSR, messaging-handler, and registrar conformance; the complete locked quality
  gate; lowest/latest root resolution; exported-package and production-only installation; and all required
  starter receipts.
- Every accepted addition is additive for `1.2.0`. A capability requiring an incompatible inward contract change
  moves individually to `2.0.0`. Later proven additive adapters may ship in `1.3.0`.

## Testing Decisions

- The highest Fight Common seam is one black-box consumer certification harness that installs an exported
  candidate into disposable Composer consumers and invokes only public package APIs.
- Shared adapter conformance suites define observable behavior once for JSend/HTTP, caching, PSR-18, queued
  message handling, container registration, UnitOfWork, private publication, and other reusable contracts.
  Provider-specific tests run the same suite wherever the contract is shared.
- Focused unit tests diagnose Scheduler execution and failures, JSend envelope states and encoding, native
  response construction, cache translation, PSR exception translation, message delegation, explicit registrar
  maps, `Arrayable` shapes, and unchanged `ResultSet` behavior.
- Scheduler consumer probes compile and execute every supported positional and named `1.1.0` construction form.
- Namespace probes load old and canonical FQCNs independently. Identity-sensitive compiler passes, subscribers,
  Doctrine types, handlers, and other framework extension points are exercised through real registration.
- Message-handler conformance reconstructs complete command and event messages and proves preservation of message
  identity, creation time, payload, and isolated metadata before synchronous delegation. Repeating delivery
  repeats the complete event fan-out.
- Container-registrar conformance boots a container with explicit service, handler, subscriber, filter, and
  collaborator maps and proves that unselected capabilities and package scans are absent.
- PSR-18 conformance proves successful responses, ordinary 4xx/5xx returns, request exceptions, network
  exceptions, and coexistence with Fight's asynchronous interface.
- Transaction conformance preserves callback return values, proves commit, rollback, terminal close behavior,
  and nesting rejection, and verifies unchanged legacy Doctrine behavior.
- The repository-locked lane runs the complete submit gate, exact complete production statement coverage, and
  the supported MySQL and PostgreSQL suites without skips.
- Root dependency lanes resolve the lowest and latest permitted sets and record exact versions and lock digests.
- The exported-package lane installs outside the repository root; the production lane installs with `--no-dev`
  and proves production autoload plus representative public behavior without optional framework packages.
- Each supported framework contributes one immutable receipt from a clean booted starter installation. PRD-00015
  defines the framework journeys; this PRD composes their results without recreating them.
- Receipt tests bind resolved versions, lock digests, baseline and candidate identities, API and behavior
  findings, dependency metadata, archive evidence, and starter results into certification.
- Unavailable, skipped, failed, conflicted, missing, or indeterminate required evidence cannot produce a
  certified result and yields one explicit resumable next action.
- Tests assert consumer-visible behavior, public identity, package isolation, and evidence integrity rather than
  internal forwarding structure, incidental service order, JSON whitespace, or object-key order.

## Out of Scope

- Implementing framework-native Laravel, Yii, CodeIgniter, Symfony, or Slim capability adapters; PRD-00015 owns
  their support contract and activation journeys.
- Implementing or publishing Fight AccessControl, authenticated-principal mapping, or framework guard adapters.
- Creating starter applications, frontend clients, database schemas, business handlers, routes, templates, or
  deployment configuration.
- Choosing broker topology, retry schedules, dead-letter policy, worker supervision, or an atomic outbox.
- Removing deprecated constructors, raw-array entry points, or legacy adapter FQCNs before `2.0.0`.
- Adapting PSR-14 or claiming that arbitrary synchronous PSR-18 clients implement Fight's async-capable client.
- Making any framework or optional provider an unconditional production dependency.
- Replacing composed certification evidence with one hosted workflow result or permitting silent waivers.
- Committing, publishing, tagging, or releasing the planning change itself.

## Further Notes

- This specification reconciles WF-014 and WF-024 with ADRs 0017 through 0019, ADR 0023, and ADR 0024.
- PRD-00015 owns supported framework lines, framework adapters, service-container activation, and booted starter
  journeys. PRD-00016 owns repository authority, PRD-00017 owns AccessControl behavior, and PRD-00018 owns the
  starter products and their production-strength acceptance.
- T-00047 has established the exact public API authority and installed-package consumer harness. T-00048 through
  T-00052 are complete. T-00053, T-00054, T-00056, T-00059, T-00060, and T-00069 now deliver the
  compatibility, namespace, shared-adapter, package-isolation, and final-certification work.
- T-00076 corrected serialization and AI-operation architecture drift, preserved the standalone `1.x`
  compatibility paths and webhook validation behavior, classified the new public Application serializers, and
  made `AGENTS.md` plus the planning conventions the canonical repository guidance.
- The approved test model has three levels: Fight Common adapter conformance, one booted journey in each real
  starter, and installed-package compatibility certification that composes both evidence sources.
- The support-evidence rule may be revisited if implementation proves it disproportionate, but only through an
  explicit planning decision that updates the affected support claim.
