# Fight Common Contract Repair and Compatibility Certification

## Problem Statement

Fight Common is intended to provide a portable Domain and Application core, but its current `1.2.0` candidate
cannot yet be certified as an additive successor to `1.1.0`. The Scheduler constructor replaced a published
construction contract, the JSend response is coupled to Symfony and raw arrays, `Arrayable` promises a map even
though existing collections return lists, and framework adapters occupy inconsistent namespaces that obscure
their capability and dependency.

The package also lacks one intentional public API manifest and the consumer-level evidence needed to prove old
and new contracts across locked, lowest, latest, isolated-framework, combined-framework, and production-only
installs. Without that evidence, a green repository build could still hide a consumer break, an optional-package
leak, or an adapter that works only in the root dependency set.

## Solution

Repair the `1.2.0` contract additively. Restore every supported `1.1` Scheduler construction path while adding a
named portable runner path; introduce a framework-neutral typed JSend envelope with native response adapters;
correct the base array-shape promise without narrowing existing result sets; and add capability-first canonical
names for all incorrectly placed Symfony and Doctrine adapters while retaining deprecated functional legacy
paths throughout `1.x`.

Certify the result through one black-box consumer harness that installs and exercises only the public package
surface. Compose that highest seam from focused behavioral tests, public API and legacy-consumer probes,
repository dependency modes, five isolated framework fixtures, the combined framework set, and a production
`--no-dev` install. Missing or indeterminate evidence stops certification rather than becoming a waiver.

## User Stories

1. As an existing Fight Common consumer, I want `1.2.0` to preserve supported `1.1.0` construction and behavior,
   so that a minor update does not require application code changes.
2. As a package maintainer, I want every production-autoloaded declaration inventoried against the published
   baseline, so that compatibility is decided intentionally rather than inferred from the current tree.
3. As a package maintainer, I want new declarations classified before release, so that an accidental public
   symbol does not silently become a permanent promise.
4. As a library implementer, I want callable, constructible, extensible, and implementable promises classified
   independently, so that visibility alone does not overstate compatibility guarantees.
5. As an existing Scheduler consumer, I want the published positional constructor to work unchanged, so that my
   scheduled jobs continue to run after upgrading.
6. As an existing Scheduler consumer, I want published named-argument construction to remain valid, so that a
   parameter rename or insertion does not break my application.
7. As an existing Scheduler consumer, I want legacy command execution and process-factory behavior preserved,
   so that compatibility is behavioral rather than signature-only.
8. As a new Scheduler consumer, I want a named `ProcessRunner` construction path, so that I can compose portable
   process execution without depending on a framework implementation in Application code.
9. As a maintainer, I want the legacy Scheduler process path visibly deprecated but functional throughout
   `1.x`, so that consumers receive a migration route before `2.0.0`.
10. As a controller author, I want to choose the HTTP status independently from the JSend semantic status, so
    that expected failures can accurately return `400`, `401`, `403`, `404`, `409`, `422`, or another outcome.
11. As a controller author, I want ergonomic success, fail, and error response factories, so that ordinary
    actions do not need to assemble an envelope in several steps.
12. As an application author, I want one framework-neutral JSend envelope, so that presentation semantics do
    not depend on Symfony or another native response type.
13. As an application author, I want a single result represented without pagination metadata, so that one
    resource is not disguised as a result page.
14. As an application author, I want a paginated result set to preserve page and total metadata, so that list
    endpoints retain their navigation contract.
15. As a collection author, I want `Arrayable` to permit list and map shapes, so that implementations can state
    their honest narrower return shapes.
16. As a repository consumer, I want `ResultSet` to continue accepting arbitrary record types, so that adding a
    presentation boundary does not narrow existing persistence behavior.
17. As an API consumer, I want each record in a JSend result page projected through its presentation contract,
    so that domain objects are not exposed accidentally.
18. As an API consumer, I want invalid UTF-8 or unencodable values to fail before response construction, so that
    I never receive silent partial JSON or a false body.
19. As a framework adapter author, I want the neutral envelope to own the final encoded body, so that native
    adapters cannot produce subtly different JSON.
20. As an existing Symfony consumer, I want raw-array JSend calls to continue working during `1.x`, so that the
    typed migration can be adopted deliberately.
21. As a new consumer, I want typed JSend entry points to accept presentation objects rather than arbitrary raw
    arrays, so that serialization boundaries remain explicit.
22. As a package consumer, I want adapter names organized by capability and then framework or provider, so that
    dependency and purpose are visible from the public type name.
23. As an existing adapter consumer, I want every old FQCN to remain functional in `1.x`, so that namespace
    cleanup does not become a minor-version break.
24. As a framework integrator, I want old and new compiler passes, subscribers, types, and handlers tested in
    their real registration roles, so that a convenient alias does not hide identity-sensitive breakage.
25. As a maintainer, I want the compatibility mechanism chosen per declaration, so that aliases are used only
    where construction, identity, extension, attributes, serialization, and registration remain sound.
26. As a maintainer, I want legacy paths deprecated through documentation and PHPDoc without runtime notices,
    so that upgrades do not add unsolicited production noise.
27. As a production consumer, I want optional framework packages excluded from runtime requirements, so that I
    install only the integrations I select.
28. As a Composer user, I want each optional adapter dependency named in package suggestions and support docs,
    so that activation requirements are discoverable.
29. As a framework integrator, I want a minimal isolated dependency fixture for my framework, so that another
    framework's packages cannot make my composition pass accidentally.
30. As a package maintainer, I want the five framework dependency sets resolved together, so that overlapping
    transitive constraints are proven compatible.
31. As a package maintainer, I want lowest and latest permitted resolutions exercised, so that declared version
    ranges describe real support rather than one favorable lock.
32. As a release operator, I want a production-only clean install and archive probe, so that development
    dependencies and repository files cannot conceal a broken distribution.
33. As a release operator, I want exact version, lock, behavior, API, package, and archive receipts, so that the
    `1.2.0` certification decision is reproducible.
34. As a release operator, I want unavailable, skipped, failed, or indeterminate lanes to stop certification,
    so that missing evidence cannot be reported as success.
35. As a downstream framework researcher, I want one contract-to-capability worksheet, so that I can compare
    native composition, existing adapters, starter wiring, and proposed shared adapters consistently.
36. As a starter maintainer, I want new shared adapters justified by walking-slice evidence, so that Fight
    Common does not accumulate redundant framework wrappers.

## Implementation Decisions

- The authoritative planning baseline contains 131 Domain declarations, 13 production-autoloaded Domain
  functions, 166 Application declarations, and 107 Adapter declarations. The 41 declarations introduced after
  `1.1.0` require deliberate manifest classification.
- The compatibility manifest records public and internal classification and treats callable, constructible,
  extensible, and implementable as independent consumer operations. A non-final class is not promised as an
  extension point without affirmative design or history evidence.
- The Scheduler restores the exact published `1.1.0` constructor and command-execution behavior for `1.x`. A
  named `withProcessRunner` constructor provides the portable composition path without changing legacy
  positional or named arguments.
- The legacy Scheduler process factory and conditional Symfony Process behavior remain functional and are
  deprecated through `1.x`. A focused compatibility prototype must prove the bridge faithfully. If it cannot,
  the required-runner-only design is deferred to `2.0.0`; the incompatible candidate constructor does not ship
  in `1.2.0`.
- Application HTTP gains immutable `JSendEnvelope` and `JSendStatus` types. The envelope represents only JSend
  status, typed data, required error message, optional integer error code, and semantic serialization. It owns
  no HTTP status, headers, native response, service lookup, or I/O.
- Envelope factories accept an optional `Arrayable` value for success, an `Arrayable` value for fail, and a
  message plus optional `Arrayable` data and integer code for error.
- Each native JSend response exposes `fromEnvelope` with an explicit HTTP status and optional headers, plus
  ergonomic success, fail, and error factories. The controller owns the HTTP outcome; the adapter owns native
  response construction and content type.
- The base `Arrayable` contract promises `array<array-key, mixed>`. It is not generic and does not promise a
  map. Every implementation documents its narrower actual shape.
- `ResultSet<TRecord>` retains arbitrary scalar or object record types and its existing pagination behavior;
  it gains no `Arrayable` generic bound.
- At the typed JSend boundary, one ordinary presentation object serializes directly as `data` without paging.
  A paginated `ResultSet` is accepted only when each record is `Arrayable`; every record is projected through
  `toArray` while page, per-page, total-page, total-record, and records fields are preserved. Non-`Arrayable`
  records remain valid for all other existing `ResultSet` consumers.
- `JSendEnvelope` owns the final response JSON. It encodes its semantic array with option `79` plus throwing
  error behavior. Invalid UTF-8 and other encoding failures raise `JsonException` before native response
  construction. Native adapters use the encoded body without re-encoding it.
- The deprecated Symfony JSend response retains raw-array input, its option-79 default, and caller-selected
  encoding options throughout `1.x`. Its deliberately different behavior is implemented explicitly rather
  than treated as a pure alias.
- Canonical adapters use `Adapter\<Capability>\<Framework-or-Provider>\<Type>`. Generic top-level framework
  extension buckets and provider-first Doctrine paths are not canonical destinations.
- The additive namespace migration covers 32 declarations: five messaging compiler passes move under
  Messaging/Symfony/DependencyInjection; the event-mapping compiler pass moves under
  EventSourcing/Symfony/DependencyInjection; the template-helper compiler pass moves under
  Templating/Symfony/DependencyInjection; two HTTP event subscribers move under Http/Symfony/EventSubscriber;
  the Symfony filesystem moves under Filesystem/Symfony; the new typed JSend response, error controller, and
  request middleware live under Http/Symfony; the Messenger command bus, event dispatcher, serializer, and two
  handlers move under capability-appropriate Messaging/Symfony paths; the Symfony URL generator moves under
  Routing/Symfony; and thirteen Doctrine data types move under Persistence/Doctrine/Type.
- Existing Mail/Symfony and Process/Symfony declarations remain in place. Mercure remains provider-qualified
  under Socket.
- No old public FQCN is removed or renamed in place. Every superseded path remains functional and documented as
  deprecated throughout `1.x`, then becomes eligible for removal in `2.0.0`.
- Compatibility is selected per declaration. A pure alias is allowed only when consumer probes prove
  construction, factories, `instanceof`, serialization, extension, attributes, framework registration, and
  relevant identity. Otherwise use a forwarding implementation, explicit compatibility implementation, or
  shared internal base.
- Framework extension points are identity-sensitive by default. Old and new compiler passes, subscribers,
  Doctrine types, handlers, and other registration-facing declarations receive independent consumer probes.
- Frameworks and optional adapter packages stay out of production requirements. The root development set is
  the mutually resolvable combined lane. Package suggestions name exact optional packages, while normative
  supported ranges live in documentation.
- Five minimal in-repository Composer fixtures cover Symfony, Laravel, Yii 3, CodeIgniter 4, and Slim. They are
  dependency manifests and black-box probes, not starter applications or separate repositories. Each requires
  the Fight Common candidate and only its selected framework-native dependencies.
- WF-015 owns exact framework package names and supported ranges. Tickets that activate framework-specific
  fixtures or combined constraints depend on that decision; the harness and framework-neutral contract repairs
  may proceed independently.
- Fixture locks are disposable inputs. Every run records resolved versions and a lock digest. The root combined
  lane resolves both latest and lowest when the final constraints make lowest resolution meaningful.
- The blocking `1.2.0` evidence set includes the intentional API manifest and operation diff; Scheduler legacy
  probes; old/new probes for all 32 migrations; legacy and typed JSend behavior; the locked full quality gate
  with exact coverage and both databases; root lowest and latest; isolated fixture lowest and latest; combined
  framework resolution and adapter behavior; exported-package and `--no-dev` installation; and composed version,
  lock, API, behavior, package, archive, and certification receipts.
- An unavailable, skipped, failed, or indeterminate lane produces a stop handoff with the missing evidence and
  exactly one resumable next action. No waiver or single hosted check substitutes for the composed evidence.
- The downstream worksheet records, for every capability and framework, selected maintained versions, exact
  constraints, native facility, existing Fight Common binding, starter-owned wiring, any evidence-backed new
  shared adapter, lowest and latest receipts, functional journey, and remaining unknowns.
- A new shared adapter is authorized only when a prototype demonstrates reusable translation or framework
  extension behavior that starter composition cannot express cleanly. Equal adapter counts are not a goal.

## Testing Decisions

- The primary seam is one black-box consumer certification harness that installs Fight Common into disposable
  Composer fixtures and invokes only public package APIs. It composes all required lanes and emits the evidence
  used to decide certification.
- Focused unit tests remain the diagnostic seams for Scheduler execution and failures, JSend envelope states
  and encoding, native response construction, `Arrayable` return-shape declarations, and unchanged `ResultSet`
  pagination and record behavior.
- Scheduler consumer probes compile and execute every published positional and named `1.1.0` construction form,
  including process factories and command jobs, against the candidate.
- JSend tests assert exact semantic fields for success, fail, and error; single versus paginated data;
  per-record presentation projection; controller-selected status; headers and content type; null and optional
  fields; preserved legacy raw arrays; and throwing invalid-encoding behavior.
- Namespace probes load every old and new FQCN independently. Pure relocation probes cover construction,
  factories, `instanceof`, serialization, and extension where promised; framework-extension probes additionally
  cover real registration, attributes, service identity, and behavior.
- Manifest tests compare the candidate with the authoritative published `1.1.0` source, reject unclassified
  production declarations and functions, and report operation-level changes separately from declaration
  presence.
- The repository-locked lane runs the complete submit gate, exact complete production statement coverage, and
  the supported MySQL and PostgreSQL suites without skips.
- Root dependency tests resolve the lowest permitted and latest permitted sets from the manifest and record the
  exact versions and lock digest before running the complete applicable gate.
- Each isolated framework fixture resolves lowest and latest supported versions and runs its native-response,
  dependency-injection, routing, transaction, and selected capability probes without unrelated framework
  packages present.
- The combined root lane resolves all five supported framework sets together and runs the complete adapter
  suite, preventing isolated locks from hiding transitive conflicts.
- Production-package tests export the candidate, install it with `--no-dev`, verify production autoloading and
  representative public behavior, and prove no optional framework package is required or eagerly loaded.
- Receipt tests bind exact resolved versions, lock digests, baseline and candidate identities, public API and
  behavior findings, package metadata, and archive evidence into the certification result.
- Failure fixtures prove unavailable, skipped, failed, missing, and indeterminate lanes cannot produce a
  certified result and each yields one resumable stop action.
- Tests assert consumer-visible behavior, package metadata, public identities, receipts, and final certification
  status rather than internal forwarding structure or incidental JSON whitespace and key ordering.

## Out of Scope

- Selecting exact Symfony, Laravel, Yii, CodeIgniter, Slim, or optional-package ranges; WF-015 owns those
  decisions and the solving evidence.
- Choosing a new framework-native shared adapter without a completed downstream worksheet and walking-slice
  prototype.
- Implementing or publishing the Fight AccessControl package or any starter repository.
- Building full starter applications, frontend clients, database schemas, authentication flows, or framework
  service-provider configuration.
- Removing deprecated `1.x` constructors, raw-array entry points, or old adapter FQCNs before `2.0.0`.
- Consolidating historically similar validation exceptions, router contracts, or other declarations merely
  because they appear duplicated.
- Making JSON whitespace or object-key order part of the compatibility promise.
- Making framework packages unconditional production dependencies.
- Replacing composed certification evidence with one hosted workflow conclusion or permitting lane waivers.
