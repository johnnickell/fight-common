# Release Lifecycle and Publication Recovery

## Problem Statement

The release lifecycle needs independently reviewable local packaging, composed certification, immutable
publication, downstream observation, and fail-closed recovery rather than one opaque automation command.

## Solution

Build plan, package, certify, and publish phases as separate consumers of immutable handoffs. Prove the
normal `develop` feature journey first, then add deterministic archives, all certification lanes,
signed-tag and GitHub publication, Packagist observation, clean-install proof, and independent recovery
for incomplete external effects.

## Acceptance

- Packaging presents and records an exact bounded local effect set before mutation.
- Certification emits one composed manifest covering quality, dependency, archive, API, compatibility,
  and Git/ref lanes; failure or indeterminacy produces a durable stop.
- Publication requires separate authorization for each merge, tag, push, GitHub Release, and Packagist
  effect, bound to the plan, candidate, baselines, version, and manifest.
- GitHub remains publication authority; Packagist is verified downstream projection.
- Partial publication stops automatic progress and reconciles each possible effect independently.
- Clean-install proof verifies the exact published version and approved public smoke behavior.
