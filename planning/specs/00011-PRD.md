# Release Lifecycle and Publication Recovery

## Problem Statement

Fight Common cannot yet turn an approved release plan into a deterministic package, compose sufficient
certification evidence, publish the exact certified candidate, or recover safely when an external effect is
uncertain. Treating these responsibilities as one automation command would blur local and external mutation,
make one authorization cover unrelated effects, and encourage retries based on command completion rather than
verified postconditions.

Publication also spans authorities with different guarantees. The signed Git tag and GitHub Release establish
the release, while Packagist is an eventually consistent downstream projection. A provider acknowledgement,
visible version, or successful hosted check alone cannot prove that the approved commit, tag, assets,
metadata, and installable package all agree.

## Solution

Implement plan, package, certify, and publish as separate phases that consume and produce immutable handoffs.
Prove the normal feature journey targeting `develop` first, then add deterministic packaging, composed
certification, signed-tag and immutable GitHub publication, bounded Packagist observation, clean-install
proof, and postcondition-driven recovery for every incomplete or uncertain external effect.

Packaging operates only on one explicitly approved local effect set. Certification is verification-only and
produces one content-addressed evidence manifest. Publication requires separate authorization for each merge,
tag, push, GitHub Release, and Packagist-affecting action, and it stops in a durable partial-publication state
whenever an effect may have occurred but cannot be verified.

## User Stories

1. As an operator, I want planning, packaging, certification, and publication invoked separately, so that I
   consciously accept each phase handoff.
2. As an operator, I want a normal feature targeting `develop` to follow one deterministic release journey,
   so that the first implementation slice proves the common path before exceptional paths.
3. As an operator, I want packaging to present its exact intended local effects before mutation, so that I can
   approve the real change set rather than a vague operation.
4. As an operator, I want changed packaging inputs or effects to invalidate approval, so that authorization
   cannot silently expand.
5. As an operator, I want packaging to bind the candidate commit OID, so that later phases never substitute a
   moving branch ref.
6. As a release consumer, I want a deterministic rootless archive, so that the same candidate and policy
   produce the same package bytes and digest.
7. As a release consumer, I want committed Composer exclusions to define archive contents, so that unexpected
   package-surface drift blocks the release.
8. As a certifier, I want quality, dependency, archive, planning, API, compatibility, and Git/ref evidence
   composed into one manifest, so that no individual lane or hosted check becomes release authority.
9. As a certifier, I want locked, lowest-permitted, and latest-permitted dependency lanes identified
   separately, so that their evidence and failures remain attributable.
10. As a certifier, I want structural and behavioral compatibility classified against explicit baselines, so
    that an unclassified finding cannot pass by omission.
11. As a certifier, I want failed or indeterminate evidence to produce a durable stop handoff, so that the
    candidate is not represented as certified.
12. As an authorizer, I want publication approval bound to the exact plan, candidate, version, baselines,
    manifest, and exceptions, so that it cannot be reused after drift.
13. As an authorizer, I want merge, tag, push, GitHub Release, and Packagist-affecting actions approved
    separately, so that one approval cannot authorize the rest of publication.
14. As a release signer, I want the approved signer fingerprint bound and verified, so that a valid signature
    from the wrong identity does not establish release provenance.
15. As a release signer, I want private signing material unavailable to CI, so that custody remains with the
    operator or hardware-backed signer.
16. As an operator, I want signer rotation, loss, or revocation to require a new plan, so that publication
    cannot continue under stale trust roots.
17. As a Git consumer, I want the annotated tag object and peeled candidate commit verified locally and
    remotely, so that the published ref points to the certified candidate.
18. As a GitHub consumer, I want release notes, archive, checksums, and evidence manifest attached to the exact
    tag, so that every approved release asset is attributable.
19. As an operator, I want public GitHub publication blocked unless immutable releases and the protected
    publication checkpoint are available, so that a mutable fallback cannot weaken provenance.
20. As a one-person maintainer, I want my signing, verification, and approval roles recorded honestly, so that
    the evidence does not invent independent review.
21. As a Composer consumer, I want Packagist treated as a verified projection of GitHub, so that metadata
    presence alone does not replace release authority.
22. As an operator, I want Packagist observed for a bounded interval, so that eventual consistency neither
    causes an immediate false failure nor leaves the workflow waiting forever.
23. As an operator, I want stale metadata, mismatched source, timeout, or install failure reported as
    `packagist_incomplete`, so that downstream incompleteness is explicit.
24. As a Composer consumer, I want the exact published version installed without development dependencies in
    a clean temporary project, so that distribution metadata and production autoloading are proved.
25. As a maintainer, I want a representative public API probe included in clean-install proof, so that package
    installation alone is not mistaken for usability.
26. As an operator, I want every possible external effect reconciled independently after ambiguity, so that
    recovery never repeats an effect blindly.
27. As an operator, I want verified already-satisfied publication postconditions to resume safely, so that a
    disconnect after success does not force duplication.
28. As an auditor, I want permanent manifest and clean-install receipts with bounded supporting logs, so that
    the release remains independently verifiable.
29. As a test author, I want all provider outcomes represented by fakes and effect ledgers, so that the full
    journey and every recovery branch can be proved offline.

## Implementation Decisions

- Plan, package, certify, and publish are separate phase consumers. Each accepts the prior immutable handoff,
  revalidates its bindings and postconditions, and emits either the next handoff or one classified stop.
- No phase automatically invokes the next phase. Planning is read-only except for planning control artifacts;
  packaging owns approved local mutations; certification is verification-only; publication owns only its
  separately authorized external effect.
- The first vertical journey is a normal feature targeting `develop`, carried through plan, package, and
  certify before broader publication and recovery behavior is added.
- Minor and major release preparation uses `release/<version>` from `develop`, a certified merge to `main`, a
  signed tag over the verified `main` merge, a merge back to `develop`, and maintenance-line creation from the
  signed release commit. Each effect remains separately authorized.
- Packaging emits a dry-run `packaging_effect_set` naming every intended branch, tracked-file,
  dependency-metadata, and candidate-artifact effect. Only that exact set may be approved and performed.
- A changed effect set or bound input requires fresh approval and, when plan inputs change, a new `plan_id`.
- Packaging produces and hands off one immutable `candidate_commit_oid`; downstream phases use that OID rather
  than a branch name.
- The release archive is rootless, named `fight-common-vX.Y.Z.zip`, and built from the candidate using committed
  Composer exclusions with normalized ordering and timestamps. Its SHA-256 digest is bound into the package
  handoff.
- Certification composes the complete repository quality gate; locked, lowest-permitted, and latest-permitted
  Composer lanes; archive installation and reproducibility; planning and public-API validation;
  compatibility classification; and Git/ref verification.
- Public compatibility includes the intentional API manifest, behavioral contracts, exceptions,
  serialization, persisted data, framework adapters, runtime environments, Composer package metadata, and the
  coding standard. Stable finding IDs bind exceptions and authorization.
- Every required certification lane is explicit and attributed. Failed or indeterminate lanes emit
  `certification_failed` or `evidence_indeterminate` stop handoffs; queued or running checks are not passes.
- Successful certification emits one immutable canonical evidence manifest whose `manifest_id` binds the
  candidate, version, baselines, support policy, lane results, approvals, and exact exceptions.
- New releases use one approved OpenPGP signer and a signed annotated `vX.Y.Z` tag. The signer fingerprint is
  plan-bound; private key custody remains outside CI and test processes.
- Existing lightweight tags remain historical and are never rewritten. New publication does not normalize or
  replace them.
- Publication authorization is per bounded effect: merge, signed-tag creation, push, GitHub draft or public
  release action, and any Packagist-affecting recovery. Every authorization binds the exact plan, candidate,
  version, baselines, manifest, and exceptions.
- GitHub is publication authority. The workflow verifies the remote tag object and peeled candidate commit,
  then associates approved release notes, deterministic archive, checksum manifest, and evidence manifest
  with that tag.
- A draft GitHub Release may be prepared before public approval. Making it public requires verified immutable
  releases and approval through the protected `release-publication` environment; mutable publication is not a
  fallback.
- The same named operator may sign, verify, and approve when no second operator exists. The evidence manifest
  records that dual role rather than implying separation.
- Packagist is observed after GitHub publication using waits of 15 seconds, 30 seconds, 1 minute, 2 minutes,
  and then 5 minutes until a maximum of 30 minutes.
- Packagist verification compares the exact version, source reference, distribution metadata, and expected
  package projection. Timeout, mismatch, stale metadata, or failed installation emits
  `packagist_incomplete`.
- Clean-install proof uses a temporary Composer consumer, installs the exact version with
  `--prefer-dist --no-dev`, verifies production autoloading, and runs an approved representative public-API
  probe.
- The immutable evidence manifest and clean-install receipt are permanent release assets. Detailed logs are
  bounded, redacted, digest-linked, and retained for 90 days.
- If an external effect may have occurred but cannot be verified, the run enters `partial_publication` and
  automatic progress stops. Recovery rechecks tag, remote ref, GitHub release, assets, Packagist projection,
  and clean installation independently before requesting the next authorization.
- A successful provider response is not a postcondition. Re-entry advances only from currently verified
  external state, and blind retry is never a recovery action.

## Testing Decisions

- The primary seam is the complete public release-command journey in a controlled temporary Git repository
  with deterministic filesystem, Git, signer, authorization, GitHub, Packagist, clock, and process fakes.
- Journey tests begin with a normal feature targeting `develop` and assert routing, phase isolation, immutable
  handoffs, candidate identity, evidence composition, effect ordering, and forbidden effects.
- Packaging tests cover exact effect-set approval, refusal, changed effects, input drift, already-satisfied
  postconditions, interrupted local effects, and a candidate that differs from the planned source.
- Archive tests build the same candidate repeatedly under varied filesystem enumeration and timestamps,
  asserting identical bytes, rootless paths, committed exclusions, normalized metadata, name, and digest.
- Temporary-consumer fixtures prove archive installation and production autoloading without relying on a
  developer checkout.
- Certification fixtures cover every lane independently and in composition, including pass, fail,
  indeterminate, missing evidence, stale evidence, baseline drift, unclassified API findings, and a hosted
  check that has not completed.
- Manifest tests prove canonical identity and demonstrate that changing a candidate, version, baseline,
  exception, approval, or lane result changes the manifest digest.
- Signing tests use deterministic sign/verify adapters to cover approved identity, wrong identity, invalid
  signature, missing signer, rotation, local success followed by uncertainty, and remote tag mismatch.
- Publication effect-ledger tests prove one authorization cannot perform another effect and that changed
  bindings invalidate an unused authorization.
- GitHub fixtures cover draft preparation, missing immutable-release capability, missing protected approval,
  asset mismatch, uncertain creation, already-published state, and immutable successful publication.
- Packagist tests use a controllable clock and response sequence to prove the exact observation schedule,
  successful convergence, stale metadata, mismatched source or distribution, timeout, and separately approved
  recovery.
- Clean-install fixtures cover resolution failure, wrong version, source or distribution mismatch, missing
  production autoloading, failed public probe, and successful receipt creation.
- Crash tests inject failure immediately before and after every external effect and before its postcondition
  recording, then assert independent reconciliation and absence of blind repetition.
- Recovery tests start from each possible subset of completed publication effects and assert the precise stop,
  verified postconditions, required approval, and next action.
- Tests assert externally observable commands, artifacts, Git object identities, provider state, machine
  results, and ledgers rather than private orchestration structure.
- T-00033, T-00034, T-00035, and T-00041 each pass the full repository submit gate and their relevant
  deterministic offline journey suites; no ticket requires live publication to complete.

## Out of Scope

- Real publication, real GitHub or Packagist mutation, real signing-key use, or provisioning hosted controls.
- Maintenance-line lifecycle, affected-line patch routing, and ordered forward ports, which belong to
  PRD-00012.
- Operator skill prose, catalog routing, final runbook content, and CI integration, which belong to
  PRD-00013.
- Replacing human version authorization, per-effect approval, compatibility judgment for indeterminate
  evidence, or reconciliation of unverifiable external state.
- Rewriting legacy lightweight tags or treating Packagist as release authority.
- Automatic or destructive rollback of an external effect whose postcondition is uncertain.
- Making external consumer builds a release gate unless Fight Common separately adopts and owns their
  behavioral contract.
