# Fight Package and Starter Repository Ownership

## Problem Statement

Fight's framework-portability work spans Fight Common, a new shared AccessControl package, and five
framework starter projects. Without an explicit ownership contract, shared Domain and Application behavior
could be copied into starters, framework integrations could leak into portable packages, and the umbrella
plan could continue competing with repository-local tickets after the new repositories exist.

Repository creation also needs a verifiable transfer of authority. A repository name or initial commit does
not prove that the package boundary is portable, that a starter owns its composition, or that future agents
have one canonical planning and quality workflow. Public visibility and version tags are separate decisions;
neither should be inferred merely from a stable branch.

## Solution

Establish six independently governed repositories with one-way package ownership. Fight Common owns shared
primitives, Application contracts, and reusable adapters without selecting runtime composition. Fight
AccessControl owns one framework-neutral Domain and Application implementation. The Symfony, Laravel, Yii,
CodeIgniter, and Slim starters consume those packages and own every framework-facing adapter, composition
root, persistence mapping, HTTP and presentation boundary, client, operational concern, test, and document
needed to deliver the shared behavior in that framework.

Fight Common remains the umbrella planning authority only until each repository is created with its own
architecture rules, planning workflow, agent guidance, and canonical noninteractive build. At that point,
detailed implementation and release authority moves to the repository that owns the work. The umbrella
retains dependency links and portfolio progress without copying local acceptance criteria or status.

Prove the boundary through six repository-owned clean-clone build receipts. Each repository's build verifies
its own dependency direction, package surface, tests, documentation, and distribution readiness. The five
starters additionally exercise shared behavior only through public Fight package contracts and their own
framework-native composition. Fight Common validates the cross-repository links, not the other repositories'
implementation details.

## User Stories

1. As a Fight Common maintainer, I want reusable primitives and Application contracts to have one owner, so
   that consumers do not fork foundational behavior.
2. As a Fight Common maintainer, I want reusable adapters owned by the capability package that publishes
   them, so that framework support remains discoverable without forcing runtime selection into the library.
3. As a Fight Common consumer, I want the package to remain usable without a framework composition root, so
   that I can bind its ports in the environment I choose.
4. As an AccessControl maintainer, I want Users, Roles, Permissions, authentication, recovery, verification,
   sessions, and authorization to have one shared Domain and Application implementation, so that framework
   projects preserve identical business behavior.
5. As an AccessControl maintainer, I want the package to depend on Fight Common's portable primitives rather
   than duplicate them, so that shared contracts retain one source of truth.
6. As an AccessControl maintainer, I want framework and infrastructure integrations excluded from the shared
   package, so that its Domain and Application layers remain portable.
7. As a Symfony starter maintainer, I want the project to own its native service loading, autoconfiguration,
   tags, compiler passes, aliases, and environment configuration, so that no Fight Common bundle controls the
   application.
8. As a Laravel starter maintainer, I want the project to own its service-provider composition, so that Fight
   packages integrate through Laravel's established model.
9. As a Yii starter maintainer, I want the project to own its configuration provider and dependency-injection
   composition, so that portable behavior does not dictate Yii infrastructure.
10. As a CodeIgniter starter maintainer, I want the project to own service configuration and module discovery,
    so that framework integration remains idiomatic.
11. As a Slim starter maintainer, I want the project to own explicit container definitions and handler maps,
    so that runtime wiring remains inspectable and deterministic.
12. As a starter maintainer, I want HTTP actions and presentation types owned by the starter, so that native
    response and routing concerns do not leak into shared Domain or Application code.
13. As a starter maintainer, I want security principals and providers owned by the starter, so that framework
    security identities remain adapters to the portable authenticated-principal contract.
14. As a starter maintainer, I want persistence records, mappings, repository adapters, and migrations owned
    by the starter, so that a framework may use its natural persistence facilities without changing shared
    aggregates.
15. As a starter maintainer, I want reference catalogs, fixtures, and console entry points owned locally, so
    that project policy and operational setup are not mistaken for package behavior.
16. As a frontend maintainer, I want each starter to own its complete editable client and SPA host, so that
    applications can evolve their user experience without depending on a shared runtime frontend package.
17. As an operator, I want deployment configuration and operational documentation owned by the deployed
    project, so that package repositories do not claim authority over an environment they do not run.
18. As a framework adopter, I want Domain and Application behavior movable between starters by replacing
    adapters and composition, so that portability is demonstrated rather than asserted.
19. As a project maintainer, I want one canonical noninteractive build in my repository, so that local and
    hosted verification share the same completion contract.
20. As an agent, I want repository-local architecture rules, planning instructions, and completion criteria,
    so that I can work without consulting a competing umbrella implementation plan.
21. As a portfolio maintainer, I want the umbrella map to retain cross-repository dependencies, so that the
    full-support sequence remains visible after authority transfers.
22. As a repository maintainer, I want local tickets and release plans to be canonical after repository
    creation, so that status is not synchronized manually in two places.
23. As a reviewer, I want a clean-clone build receipt from every repository, so that ownership and quality
    claims are backed by independently reproducible evidence.
24. As a reviewer, I want each starter to exercise shared behavior through public package APIs, so that copied
    or internal package code cannot make the composition appear portable.
25. As a reviewer, I want framework-specific assertions kept in the owning starter, so that the shared
    conformance contract does not require mechanical implementation parity.
26. As a package publisher, I want private initial development permitted for security and framework testing,
    so that unfinished work is not exposed accidentally.
27. As a package publisher, I want public visibility chosen deliberately by the repository owner, so that
    repository creation does not silently authorize publication.
28. As a release operator, I want stable branch promotion separated from version tagging, so that moving work
    to the stable branch does not invent a release.
29. As a Fight adopter, I want useful public pre-1.0 releases allowed independently, so that one ready package
    or starter need not wait for the coordinated suite announcement.
30. As a Fight adopter, I want the full-suite announcement gated on all five starters meeting their own
    approved contracts, so that "fully supported" means complete, independently verified journeys.

## Implementation Decisions

- The ownership graph contains six planned repositories: Fight AccessControl plus the Symfony, Laravel, Yii,
  CodeIgniter, and Slim starter projects. Their intended Composer identities are
  `johnnickell/fight-access-control`, `johnnickell/project-symfony`, `johnnickell/project-laravel`,
  `johnnickell/project-yii`, `johnnickell/project-codeigniter`, and `johnnickell/project-slim`.
- Fight Common owns reusable Domain primitives, Application ports and services, and generic or
  framework-specific adapters that provide genuinely reusable translation or extension behavior. It never
  selects concrete buses, transports, repositories, or infrastructure at runtime.
- Fight AccessControl owns framework-neutral Domain and Application behavior for Users, Roles, Permissions,
  authentication, password recovery, email verification, sessions, and authorization. It depends on the
  compatible Fight Common line, duplicates none of its primitives, and publishes no production Adapter
  layer.
- Agents, feature flags, and specialized business audit workflows remain outside the first AccessControl
  package boundary. Required security-audit contracts already approved for AccessControl remain part of its
  Application behavior; persistence and enrichment of that evidence remain consumer-owned.
- Every starter requires Fight Common and Fight AccessControl. A starter may not copy their Domain or
  Application source, redefine a shared use case, or reach through public contracts to depend on package
  internals.
- Every starter owns its framework-native composition root, HTTP actions, presentation data, principal and
  provider integration, persistence records or mappings, repository adapters, migrations, reference catalog,
  fixtures, console entry points, SPA host, complete editable client, deployment configuration, tests, and
  documentation.
- Runtime composition is project-owned. Projects choose and bind synchronous or asynchronous buses,
  transports, repositories, persistence, security, and configuration adapters without invocation-mode
  branches in portable Application behavior.
- Symfony receives no Fight Common bundle. Symfony owns service loading and compiler integration; Laravel
  owns service-provider integration; Yii owns its configuration-provider and dependency-injection model;
  CodeIgniter owns service and module discovery; Slim owns explicit container and handler-map composition.
- Shared use-case behavior is expressed once with Fight AccessControl. Each starter links to that contract and
  adds only framework-specific acceptance, composition, migration, presentation, and operational details.
- Fight Common planning is the temporary umbrella authority. Each creation handoff establishes repository-
  local agent guidance, dependency rules, canonical planning artifacts, triage vocabulary, and one
  noninteractive build before detailed implementation planning moves there.
- After transfer, the owning repository is canonical for implementation scope, ticket status, acceptance
  criteria, releases, documentation, and local sequencing. The umbrella records only cross-repository
  dependency links, milestone projections, and stop handoffs.
- A repository may remain private during initial framework and security testing. Its owner explicitly decides
  when it is ready for public inspection; planning approval and repository creation do not authorize that
  publication.
- Feature work integrates through `develop`; `main` represents a more stable state. Promotion to `main` does
  not require or imply a version tag.
- Fight AccessControl and starters may publish intentional public `0.x.y` releases independently. A coordinated
  full-support announcement waits until all five starters satisfy their repository-owned gates.
- WF-018 owns the repository creation handoffs, local implementation plans, cross-repository dependency order,
  and release gates. This PRD fixes ownership and transfer semantics without preempting those plans.

## Testing Decisions

- The primary seam is each repository's canonical noninteractive build executed from a clean clone or clean
  package installation. The portfolio accepts six independent repository-owned receipts rather than one
  umbrella command that reaches into every repository.
- Fight AccessControl's build proves that production dependencies and source obey the framework-free
  Domain/Application boundary, that Fight Common primitives are consumed rather than duplicated, and that
  its public behavioral contract passes without a framework package installed.
- Each starter's build proves that it installs the approved Fight packages, composes them through its native
  framework boundary, and exercises shared behavior only through public contracts. Framework-specific
  persistence, HTTP, security, presentation, migration, client, and operational checks remain local.
- A shared behavioral conformance suite defines user-observable AccessControl outcomes. Each starter applies
  that suite through its own adapters; it does not assert identical classes, schemas, containers, or internal
  call graphs.
- Architecture checks reject copied shared layers, framework dependencies in portable layers, package access
  through non-public internals, and inward dependencies on starter-owned types.
- Package-install probes verify production autoloading and the declared Composer dependency direction. Starter
  probes fail when a selected package is absent, shadowed by copied source, or made to pass by an unrelated
  framework dependency.
- Repository-bootstrap tests verify that the documented build is noninteractive, delegates the hosted gate to
  the same behavior, and names the repository's architecture, planning, and completion authority.
- Fight Common's planning validation verifies permanent links from the umbrella PRD and Wayfinder to the
  repository-local handoffs. It does not duplicate or evaluate local implementation acceptance criteria after
  authority transfers.
- Public visibility, stable-branch promotion, version tagging, pre-1.0 publication, and coordinated
  announcement are verified as separate states. Evidence for one must not imply another.
- Tests assert package boundaries, public behavior, dependency direction, reproducible receipts, and authority
  transfer rather than framework-mechanism parity or incidental repository layout.

## Out of Scope

- Creating, initializing, making public, or publishing any Fight AccessControl or starter repository.
- Writing repository-local implementation tickets or duplicating the WF-018 handoffs before their dependency
  is satisfied.
- Implementing AccessControl Domain or Application behavior, framework adapters, persistence, HTTP actions,
  migrations, clients, documentation sites, or deployment configuration.
- Selecting final licenses, repository settings, branch protections, Packagist metadata, or release
  automation.
- Proving the detailed persistence, transaction, authentication, realtime, client, or user-acceptance walking
  slices owned by WF-017.
- Requiring one central cross-repository build, one shared runtime composition, or identical adapter classes
  across all frameworks.
- Publishing an announcement or treating private planning artifacts as permission for external inspection.
- Treating a merge to `main` as a release or requiring all package versions to advance in lockstep.

## Further Notes

- This PRD is the permanent ownership specification synthesized from WF-010 and the compatible repository
  refinements accepted during WF-017.
- The approved highest test seam is repository-owned: six clean-clone builds provide independent evidence,
  while Fight Common retains only dependency and portfolio traceability.
- WF-016 remains the detailed AccessControl behavior and security decision source. WF-017 owns executable
  walking-slice evidence. WF-018 will create the implementation-ready repository handoffs without reopening
  the ownership boundaries fixed here.
- Composer identities are fixed by the ownership decision; final hosting URLs, licensing, Packagist metadata,
  repository settings, and release automation remain handoff decisions.
