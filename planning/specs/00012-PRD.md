# Maintenance-Line and Patch Workflows

## Problem Statement

Fight Common needs to maintain released minor lines without allowing an older branch to overwrite newer work,
guessing which versions contain a defect, or introducing a privileged hotfix path. A branch name or pull
request number does not prove the identity or review status of a fix, ancestry does not prove that a defect is
observable on a line, and one unchanged cherry-pick may be semantically wrong across divergent versions.

Support boundaries also change over time. A workflow that selects a base from mutable refs, starts work with
unknown affected-line evidence, or continues after an exclusive UTC support boundary could mutate the wrong
line. Urgency makes these risks more consequential; it must improve visibility and operator ergonomics without
weakening compatibility, review, certification, or authorization.

## Solution

Implement maintenance-line lifecycle and patch application as separate workflows on top of the deterministic
release foundation. Maintenance creates a line from its signed release commit, verifies protection and support
transitions, and preserves EOL history as read-only. Patching consumes an immutable already-reviewed fix,
classifies every supported line through focused behavioral evidence, and starts from the exact tip of the
oldest affected line.

Evaluate patch compatibility independently on each line. Carry the fix forward oldest to newest through a
separate reviewed and certified pull request per affected line, including a `main`-based current-line forward
port when required. Stop on unknown evidence, moved refs, conflicts, missing provenance, semantic differences,
expired support, or an absent exact compatibility exception.

## User Stories

1. As a release maintainer, I want maintenance-line lifecycle separate from patch application, so that line
   creation and support transitions cannot silently apply a fix.
2. As a release maintainer, I want a maintenance branch created from the exact signed release commit, so that
   its history starts from published authority.
3. As a release maintainer, I want branch protection and support state verified after creation, so that command
   completion alone does not establish a supported line.
4. As a policy owner, I want support transitions bound to canonical policy identity and exclusive UTC times,
   so that eligibility is deterministic.
5. As a policy owner, I want EOL branches preserved as read-only history, so that expiry does not erase
   provenance or permit new release effects.
6. As a patch operator, I want the workflow to accept only an immutable already-reviewed fix, so that release
   coordination never becomes implementation or code review.
7. As a patch operator, I want exact fix commit OIDs and merged-review provenance, so that a moving branch or
   pull request number cannot substitute for fix identity.
8. As a reviewer, I want base and head OIDs, approvals, required-check conclusions, and merge receipt bound to
   the fix, so that reviewed status is reproducible.
9. As a maintainer, I want focused behavioral evidence for every supported line, so that affected status is
   based on observable behavior rather than ancestry guesses.
10. As an operator, I want every supported line classified affected, unaffected, or unknown before routing, so
    that missing evidence stops before a base is selected.
11. As an operator, I want the oldest affected supported line selected first, so that the repair moves forward
    through history instead of backward from newer code.
12. As an operator, I want the exact current line tip bound as the patch base, so that a moved ref or unreleased
    maintenance content cannot be ignored.
13. As a maintainer, I want a predictable `patch/<version>-<slug>` work branch, so that the selected line and
    intended version remain visible.
14. As a certifier, I want patch eligibility evaluated independently on every affected line, so that divergent
    contracts cannot be hidden by one classification.
15. As a certifier, I want patches to add no public feature or deprecation, narrow no supported environment,
    and break no compatibility promise, so that patch releases remain consumer-compatible.
16. As an authorizer, I want any incompatible patch exception bound to one candidate, version, baseline set,
    finding set, and evidence manifest, so that it cannot be reused.
17. As a maintainer, I want each newer affected line to receive a separate forward-port pull request, so that
    adaptation, review, and evidence remain line-specific.
18. As a maintainer, I want forward ports ordered oldest to newest, so that every step carries explicit
    predecessor provenance.
19. As a maintainer, I want conflicts and semantic differences to stop for human judgment, so that the
    workflow never forces a mechanical cherry-pick.
20. As a current-line maintainer, I want the final forward port based on `main`, so that an older maintenance
    branch never replaces newer contents wholesale.
21. As an auditor, I want every affected-line and forward-port step to bind its fix, base, plan, review, and
    certification evidence, so that the chain is reconstructable.
22. As an operator, I want queued or running hosted checks rejected as incomplete evidence, so that urgency
    cannot reinterpret progress as success.
23. As an operator handling an urgent or security issue, I want one compact action packet, so that I can see
    the ordinary evidence, approvals, blockers, and next action without memorizing the choreography.
24. As an auditor, I want urgency recorded as metadata, so that it changes visibility and escalation without
    creating a second release policy.
25. As an operator, I want unfinished work to stop when a line reaches EOL, so that a stale plan cannot mutate
    an unsupported line.
26. As a test author, I want multi-line histories, policy clocks, review evidence, conflicts, and semantic
    differences represented offline, so that the complete workflow can be proved without real branch or pull
    request mutation.

## Implementation Decisions

- Maintenance-line lifecycle and patch application are separate command capabilities and operator workflows.
  Maintenance never applies a fix; patching never implements or reviews one.
- A maintenance line is created from the exact signed release commit for its `major.minor` version. Its plan
  binds the tag object, peeled commit OID, support-policy identity, intended branch, and expected protection
  state.
- Support policy uses canonical machine-readable data with exclusive UTC boundaries and immutable EOL history.
  The current minor receives bug and security fixes; the immediately previous minor receives security,
  data-loss, and critical-compatibility fixes for six months after the next minor is published; older lines are
  read-only.
- Only the latest patch release of a supported minor is supported. An EOL line cannot receive new branch,
  patch, forward-port, or publication effects.
- A patch input is an immutable reviewed fix identified by exact commit OIDs plus merged-pull-request
  provenance: base and head OIDs, approvals, required-check conclusions, and merge receipt. A branch or pull
  request number alone is insufficient.
- The patch workflow consumes the fix and its review evidence; it does not create, change, or review the
  underlying repair.
- Focused public behavioral evidence classifies every supported line as affected, unaffected, or unknown.
  Ancestry may support investigation but cannot establish affected status by itself.
- Any unknown classification stops before base selection. The workflow does not assume a line is affected or
  unaffected to make progress.
- The oldest affected supported line is selected first. The plan binds that line's exact current tip OID; a
  moved tip, ambiguous ancestry, or unreleased maintenance content produces a stop rather than fallback
  selection.
- Patch work uses `patch/<version>-<slug>` from the selected exact tip. Branch creation is a separately
  authorized effect.
- Patch eligibility is classified independently for each affected line. A patch adds no public contract or
  deprecation, narrows no runtime or dependency environment, and introduces no incompatible public behavior.
- An otherwise incompatible security, imminent-data-loss, or critical-interoperability patch requires one
  exact human-approved compatibility exception bound to its candidate, version, baselines, stable finding IDs,
  and evidence-manifest digest.
- After the oldest affected line is reviewed and certified, each newer affected supported line receives a
  separate forward-port branch, pull request, approval, quality gate, compatibility classification, and
  certification manifest.
- Forward ports proceed oldest to newest. Each step binds its source line, predecessor pull request and commit,
  current exact base, adapted candidate, review receipt, and certification evidence.
- Conflicts, missing provenance, changed bases, and semantic differences stop the chain. The workflow may
  require a line-specific adaptation, higher release class, or human decision; it never forces one commit
  unchanged across every line.
- When the repair must reach the current release line, its final forward port is a separate reviewed and
  certified pull request based on the exact `main` tip. An older maintenance branch is never merged wholesale
  over newer `main` contents.
- Every affected-line step revalidates support-policy identity and the exclusive UTC boundary before mutation
  and again before publication. Expiry emits `stopped_at_eol` and preserves the run evidence.
- Urgency and security are plan metadata only. Guided urgent mode composes the ordinary fix identity,
  affected-line evidence, checks, approvals, impact, blockers, and next action into one packet without changing
  any gate.
- Branch creation, protection changes, patch work, each forward port, and publication remain distinct bounded
  effects with separate authorization.

## Testing Decisions

- The primary seam is the public release command operating on controlled temporary Git repositories that
  model multiple maintenance lines, `main`, signed release points, pull requests, and reviewed fix commits.
- Support-policy tests use a controllable UTC clock and canonical policy fixtures to cover current, previous,
  EOL, exact-boundary, extended-before-expiry, stale-policy, and unknown-policy states.
- Maintenance tests assert exact signed-release ancestry, proposed branch and protection effects, separate
  authorization, postcondition verification, already-satisfied state, drift, and EOL refusal.
- Reviewed-fix contract tests reject branch-only identity, pull-request-number-only identity, missing OIDs,
  incomplete approvals, queued or running checks, absent merge receipts, and changed review provenance.
- Affected-line fixtures cover all affected, mixed affected and unaffected, unknown, behavior that differs from
  ancestry, no affected supported lines, and a defect present only on an EOL line.
- Base-selection tests prove the oldest affected supported line is chosen from evidence, bind the exact current
  tip, and stop on ref movement, ambiguity, or unreleased maintenance content.
- Patch-eligibility fixtures cover a compatible fix, new public feature, new deprecation, narrowed environment,
  incompatible behavior, valid exact exception, stale exception, and exception reuse against changed inputs.
- Multi-line journey tests assert oldest-to-newest order, one review and certification per step, predecessor
  provenance, independent plan and evidence bindings, and the final `main`-based port.
- Conflict fixtures cover textual conflict, clean cherry-pick with semantic incompatibility, missing
  predecessor provenance, changed target base, and a line-specific adapted candidate.
- Effect-ledger assertions prove no later line begins before the predecessor is reviewed and certified and no
  older branch replaces newer `main` content.
- Urgent-mode tests compare the ordinary and urgent journeys, asserting identical gates and effects while only
  visibility, escalation metadata, and packet presentation differ.
- Crash and resume tests interrupt each separately authorized branch or forward-port effect, then revalidate
  exact refs and postconditions before any continuation.
- Tests assert public results, Git identities, review and certification evidence, effect ledgers, stop states,
  and next actions rather than private routing methods.
- T-00036, T-00037, and T-00042 must pass the repository submit gate, planning validation, and deterministic
  offline maintenance and multi-line journey suites; no real maintenance branch or pull request is required.

## Out of Scope

- Implementing, adapting, or reviewing the defect fix supplied to the patch workflow.
- A `hotfix/*` branch model or any urgency-based bypass of review, compatibility, certification, evidence, or
  authorization.
- Patching unsupported or EOL lines, deleting historical branches, or rewriting released history.
- Automatically resolving conflicts or deciding that a semantically different implementation is equivalent.
- Reusing one pull request, certification manifest, approval, exception, or candidate across multiple lines.
- Merging an older maintenance branch wholesale into `main`.
- Real branch protection changes, hosted pull-request mutation, or release publication during implementation.
- Operator catalog, runbook, skill, and CI surfaces owned by PRD-00013.
