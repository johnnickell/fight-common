# Event-Sourced Aggregate and Stream Core

## Problem Statement

Fight Common has event payloads, event messages, and dispatchers, but it does not have a framework-free way to model an aggregate whose state is rebuilt from events or a durable contract for storing those events. Persisting serialized live messages directly would couple history to PHP class names, while exposing mutable metadata through a message would let technical context change behind an apparently immutable envelope.

The core must also define concurrency, retry, ordering, versioning, mapping, and schema evolution precisely enough that an in-memory implementation can serve as executable reference behavior for later durable adapters.

## Solution

Add an optional Event Sourcing core composed of effectively immutable message envelopes, an explicit event-sourced aggregate lifecycle, stable stream and event identities, immutable stored-event envelopes, explicit bidirectional event mapping, sequential upcasting, and a framework-free Event Store contract.

Provide an in-memory Event Store that implements the complete contract. It will be the primary high-level seam for aggregate and storage behavior and the reusable conformance reference for durable implementations.

## User Stories

1. As an existing message consumer, I want command, query, and event messages to isolate metadata, so that reading metadata cannot mutate an existing envelope.
2. As an existing message consumer, I want derived metadata envelopes to preserve `MessageId`, so that technical enrichment does not create a second occurrence.
3. As an aggregate author, I want a framework-free event-sourced aggregate contract, so that my domain model does not depend on Symfony or Doctrine.
4. As an aggregate author, I want a reference aggregate root, so that version and pending-event lifecycle are consistent without constraining my business state model.
5. As an aggregate author, I want to use my domain-specific identifier class, so that Event Sourcing does not weaken type safety with a generic aggregate ID.
6. As an aggregate author, I want recording to apply an event before exposing it as pending, so that failed state transitions cannot be persisted.
7. As an aggregate author, I want replay to apply historical events without recording them again, so that loading history does not create new work.
8. As an aggregate author, I want unknown historical events to fail closed, so that incomplete state cannot appear valid.
9. As an aggregate author, I want an explicit no-op transition for state-neutral history, so that intentional compatibility is distinguishable from an unhandled event.
10. As a repository author, I want aggregates to own reconstitution, so that private constructors and initialization rules remain under domain control.
11. As a repository author, I want pending events released once in recording order, so that persistence receives one deterministic batch.
12. As a repository author, I want aggregate and stream versions defined from zero, so that expected-version calculations are unambiguous.
13. As a consumer architect, I want stable aggregate names in stream identity, so that moving or renaming an aggregate class does not rename its history.
14. As an event author, I want a stable stored alias independent of my event class, so that refactoring code is not misrepresented as a new domain event.
15. As an event author, I want class renames handled by mapping changes rather than upcasters, so that schema transformations are reserved for payload changes.
16. As a bounded-context owner, I want to contribute typed mappings under a durable namespace, so that my stored names are explicit and composable.
17. As an Event Store owner, I want one complete mapper for every stored event, so that no history depends on reflection, convention, or fallback behavior.
18. As a schema maintainer, I want every old schema advanced through sequential one-version steps, so that evolution is reviewable and deterministic.
19. As a reader, I want unsupported aliases and schemas to fail before hydration, so that corrupted or unknown history cannot be silently skipped.
20. As an operator, I want exact append retries recognized by message identity and intended position, so that uncertain client responses do not duplicate events.
21. As an operator, I want partial or misplaced retry batches rejected, so that idempotency cannot conceal inconsistent history.
22. As a concurrent writer, I want expected-version conflicts reported explicitly, so that stale decisions cannot overwrite newer aggregate history.
23. As a checkpoint consumer, I want global positions to have prefix-stable visibility, so that polling after a checkpoint cannot miss a later commit at a lower position.
24. As a test author, I want an in-memory implementation of the full contract, so that aggregate and runner behavior can be tested without infrastructure.

## Implementation Decisions

- Every message envelope copies `Meta` at construction and returns a copy from `meta()`. `withMeta()` and `mergeMeta()` return a same-ID envelope with an isolated new snapshot. Standalone `Meta` remains mutable.
- Existing message method signatures remain compatible. Metadata isolation is an intentional behavioral correction that must be release-noted.
- `EventSourcedAggregate` is the framework-free lifecycle contract. `AggregateRoot` is an optional reference implementation that stores a consumer-provided `Identifier`, tracks version, and owns pending events.
- New and empty aggregates begin at version zero. Recording and replay each apply one event and increment version; only recording appends to pending events.
- Event application is explicit and fail-closed. Reflection-based `applyX` discovery is not used. An intentionally ignored historical event requires an explicit route to a no-op transition.
- Static aggregate reconstitution receives ordered plain `Event` payloads. It does not receive message identity, metadata, storage aliases, schemas, or positions.
- `releaseEvents()` returns pending events in recording order and clears them immediately. A failed save makes that aggregate instance invalid for retry; the caller reloads a fresh instance.
- A stream is identified by a stable aggregate name plus the string representation of a consumer-owned `Identifier`. Aggregate PHP classes do not define durable stream identity.
- `StoredEvent` contains stable aggregate and event identity, the original persisted schema version, stream version, global position, and a hydrated current `EventMessage`.
- The Event Store appends an ordered event-message batch against one expected stream version, reads streams in stream order, and polls committed events in global order after a supplied position with a bounded limit.
- Empty streams have version zero and read as empty. The first stored event has stream version one.
- `MessageId` identifies one event occurrence and payload. Metadata does not participate in append idempotency.
- An exact retry succeeds without writing when every message ID already occupies the intended consecutive stream positions after the supplied expected version. Partial matches, reordered or misplaced positions, and cross-stream matches fail closed.
- When none of the supplied IDs exist, a stale expected version raises a dedicated optimistic-concurrency failure.
- Each Event Store owns one explicit bidirectional `EventMapper` complete for that store. Aliases are unique within the store.
- Each `EventMappingProvider` declares a durable namespace and typed local mappings. The mapper composes them into canonical aliases such as `orders.order-placed`.
- Mapping registration rejects duplicate aliases, duplicate current classes, invalid schema versions, and classes that are not events. Reflection, attributes, naming conventions, and FQCN fallback are excluded.
- Each mapping declares its current event class, current schema version, and complete upcaster chain. Schema versions start at one; each upcaster advances exactly one version and transforms one event payload into one event payload.
- A class rename updates the current mapping without changing the alias or requiring an upcaster. Upcasters address payload-schema evolution.
- Reads retain the persisted schema on `StoredEvent`, upcast payload data in memory, hydrate the current event class, and reconstruct the current message. Stored history is never rewritten.
- Unknown aliases, future schemas, and incomplete upcast paths raise dedicated mapping failures. The reader does not downcast, skip, or best-effort hydrate them.
- Append snapshots stable identity, current schema, payload data, isolated metadata, message ID, and the original message creation timestamp in UTC with microsecond precision.
- Stream and global positions define ordering. Message time is technical envelope creation time, not guaranteed domain occurrence time.
- Global visibility is prefix-stable: once a position is readable, no lower position may become readable later.
- The in-memory Event Store is the executable reference adapter and implements atomic append behavior without simulating database-specific mechanics.

## Testing Decisions

The highest test seam is the public aggregate-and-store journey using the in-memory Event Store: record events, release and append them, read the stream, and reconstitute current state. Tests assert observable state, versions, pending events, stored envelopes, and failures rather than internal collections or routing method names.

A reusable Event Store conformance suite defines append success, empty streams, optimistic concurrency, exact retry success, partial and misplaced retries, stream ordering, bounded global polling, prefix-stable visibility, metadata snapshots, timestamp fidelity, mapping failures, and current-event hydration after upcasting. The in-memory adapter must pass the suite and becomes prior art for DBAL.

Focused public-contract tests cover metadata isolation for all three message-envelope types, same-ID derivation, aggregate record/replay/release behavior, aggregate-owned reconstitution with private construction, event-mapping registration, and complete upcaster chains. Every production class requires complete coverage.

## Out of Scope

- Aggregate repositories and durable DBAL storage.
- Projection and event-publication runners.
- Symfony provider autoconfiguration.
- Snapshots, sagas, event deletion, stream splitting or merging, and split or merge upcasting.
- Reflection or attribute-driven event registration.
- A generic aggregate identifier class.
- Rewriting stored history during upcasting.
- A new message factory or clock abstraction.

## Further Notes

The core is additive to current CQRS behavior. Only events persisted in an Event Store require mappings; events used solely for live dispatch remain valid without registration.
