# Framework Supported Lines and Default Capability Compositions

## Problem Statement

Fight Common promises one idiomatic, documented, tested composition of every public Application contract
in Symfony, Laravel, Yii 3, CodeIgniter 4, and Slim, but no exact framework versions or per-capability
default compositions were selected. Without exact constraints the repository-owned Composer lanes cannot be
solved, the persistence walking-slice implementations cannot be built, and each starter would
invent its own integration instead of following a deliberate Fight Common policy.

The frameworks' own support policies differ and cannot be adopted wholesale: CodeIgniter 4 maintains only
its latest line, Yii 3 has no line model, and Slim 3 is architecturally incompatible with the PSR-7 v2
contracts Fight Common already uses. Previous maintained lines (Symfony 7.4, Laravel 12, Slim 3) force a
lower Symfony or PSR-7 floor onto the combined resolution lane. Capabilities without a first-party native
facility are at risk of silent omission, or of accumulating a new redundant shared adapter for every gap.

## Solution

Fight Common supports each framework's **current stable major line only**, widens to **current + previous**
when the framework ships its next major, and tightens (drops the oldest line) when the framework stops
maintaining it. The supported window is never wider than two majors per framework. The selected constraints
are Symfony components `^8.1`, `laravel/framework ^13.0`, `codeigniter4/framework ^4.7`, `slim/slim ^4.15`
plus one opinionated stack, and the current Yii 3 `yiisoft/*` package set.

Each starter owns **one documented default composition** for every public contract, composed from
framework-native facilities, existing portable Fight Common adapters, or well-supported Composer packages.
There is no unsupported capability: every contract without a native facility receives a recommended,
Composer-installable composition. Integration is starter-owned and no Symfony bundle is shipped. A new
shared Fight Common adapter is authorized only when a walking-slice prototype proves a translation seam
that starter composition cannot express.

## User Stories

1. As a package maintainer, I want one deliberate Fight Common supported-line policy per framework, so that
   the supported window is decided intentionally rather than inherited from each framework's own policy.
2. As a package maintainer, I want each framework's current stable major certified first, so that the
   certification and fixture burden stays small while the `1.2` lanes land.
3. As a package maintainer, I want the window to widen to current + previous when a framework ships its next
   major, so that consumers on the immediately-preceding line keep a supported upgrade path.
4. As a package maintainer, I want the oldest widened line dropped when the framework stops maintaining it,
   so that Fight Common never silently carries a line past the framework's own maintenance boundary.
5. As a Composer user, I want the exact supported constraints recorded (Symfony `^8.1`, Laravel `^13.0`,
   CodeIgniter `^4.7`, Slim `^4.15`, current Yii 3 set), so that my dependency ranges describe real support.
6. As an existing Symfony consumer, I want Fight Common's own components pinned to the current `^8.1` line,
   so that the combined lane stays simple without a premature two-line union.
7. As a package maintainer, I want Laravel 12 and Slim 3 excluded while Fight Common pins Symfony `^8.1`,
   so that a conflicting Symfony or PSR-7 floor cannot enter the combined lane.
8. As a package maintainer, I want each widened previous line proven independently in its owning starter
   repository, so that widening never extends a supported set blindly.
9. As a release operator, I want all supported ranges re-resolved when PHP 8.6 or the next framework major
   ships, so that the PHP 8.6 horizon never becomes a silent break.
10. As a framework integrator, I want each real starter repository to own its framework dependency graph, so
    that another framework's packages cannot make my composition pass accidentally.
11. As a portfolio maintainer, I want independent immutable receipts from all five starters, so that
    cross-repository compatibility is proven without one combined project in Fight Common.
12. As a framework integrator, I want my repository resolved at both lowest and latest permitted versions, so
    that the declared ranges describe real support rather than one favorable lock.
13. As a starter maintainer, I want the composition worksheet to record the native facility, existing
    binding, starter wiring, and new-shared-adapter decision for every capability, so that compositions are
    decided consistently across frameworks.
14. As a starter maintainer, I want "no new shared adapter" as the default decision for every row, so that
    Fight Common does not accumulate redundant framework wrappers.
15. As a package maintainer, I want a new shared adapter authorized only by prototype evidence of a
    translation seam, so that equal class counts are never the goal.
16. As a Laravel starter user, I want the default composition to use Laravel's native queue and event
    discovery, so that the integration follows framework best practice.
17. As a Laravel integrator, I want a ServiceProvider with `extra.laravel` auto-discovery, so that package
    activation is idiomatic.
18. As a Yii 3 starter user, I want async dispatch behind a forward-compatible seam, so that a future stable
    `yiisoft/queue` can replace the starter transport without breaking the public contract.
19. As a Yii 3 integrator, I want a configuration provider via `yiisoft/config`, so that services, events,
    routes, and bootstrap groups assemble through the canonical plugin.
20. As a CodeIgniter 4 starter user, I want the official `codeigniter4/queue` and `codeigniter4/tasks`
    packages as the default, so that queue and scheduling behavior stays native.
21. As a CodeIgniter 4 integrator, I want `Config\Services` extending the framework base service, so that
    Fight Common services register through auto-discovery.
22. As a Slim starter user, I want the one opinionated Slim stack installed from Composer, so that a working
    default composition exists without inventing per-capability wiring.
23. As a Slim integrator, I want an explicit php-di container used through `AppFactory::createFromContainer`,
    so that dependencies compose in the starter rather than in a shared package.
24. As a Symfony starter user, I want projects to own service loading, autoconfiguration, compiler-pass
    registration, aliases, and environment configuration, so that no Symfony bundle is required.
25. As a package maintainer, I want no framework to be forced onto a shared stack when its native facility
    provides the simpler composition, so that portability stays honest.
26. As a consumer, I want a recommended, documented, Composer-installable composition for every capability
    without a native facility, so that nothing is silently unsupported.
27. As a CodeIgniter 4 consumer, I want queue, scheduler, process, SMS, metrics/health, and event-store
    compositions that install from Composer, so that every Fight Common contract has a working path.
28. As a Yii 3 consumer, I want HTTP client, process, scheduler, metrics/health, and cache compositions
    through portable adapters, so that gaps are filled without a released first-party package.
29. As a Laravel consumer, I want an event store from existing DBAL/in-memory/logging stores and metrics from
    StatsD/null (with Pulse documented as an alternative), so that the two native gaps have recommended
    compositions.
30. As a Symfony consumer, I want portable metrics/health and an event store composed from Messenger,
    persistence, and EventDispatcher, so that the two first-party gaps are filled by composition.
31. As a Slim consumer, I want SMS, metrics/health, event-store, and scheduling composed from portable
    adapters on top of the opinionated stack, so that every non-HTTP capability is covered.
32. As a frontend author, I want each starter's SPA host templating default to be the framework's own
    best approach (Blade, Twig, `yiisoft/view` with Twig, or native View), so that the host template follows
    convention.
33. As a Slim frontend author, I want Twig as the SPA host templating default where no native facility
    exists, so that every starter still has one documented templating path.
34. As a starter maintainer, I want every default composition replaceable from the composition root, so that

35. As a framework integrator, I want a forward-compatible async seam for Yii, so that a released queue can
    slot in later without a breaking change.
36. As a Laravel integrator, I want the adapter-event shape that forwards Fight Common domain events onto
    Laravel's native machinery settled during prototype work, so that the composition is proven before it is
    promised.

## Implementation Decisions

- The supported-line policy is Fight Common's own: current-only now, widened to current + previous when a
  framework ships its next major, tightened when the framework stops maintaining the oldest line, and never
  wider than two majors per framework.
- The selected supported ranges are:

| Framework | Supported range (current-only now) | Widen trigger (current + previous) | Excluded |
| --- | --- | --- | --- |
| Symfony | components `^8.1` | `^8.2 \|\| ^8.1` when 8.2 ships (≈Nov 2026) | 7.4 LTS, 6.4 |
| Laravel | `laravel/framework ^13.0` | `^14.0 \|\| ^13.0` when Laravel 14 ships (≈Q1 2027) | 12.x, 11.x |
| Yii 3 | current `yiisoft/*` package set (`yiisoft/di ^1.4`, `yiisoft/config ^1.6`, `yiisoft/yii-http ^1.1`, `yiisoft/event-dispatcher ^1.1`, `yiisoft/router ^4.0`, `yiisoft/router-fastroute`, `yiisoft/view`, `yiisoft/view-twig`, `yiisoft/validator`, `yiisoft/mailer ^6.1`, `yiisoft/cache ^3.2`, `yiisoft/db` + `yiisoft/db-mysql`/`yiisoft/db-pgsql`, `yiisoft/session`, `yiisoft/log`) | Not applicable — no Yii 3 line model | `yiisoft/yii-web` (unreleased), Yii 2.0 |
| CodeIgniter 4 | `codeigniter4/framework ^4.7` | `^4.7` already admits future 4.x minors; CI4 maintains only the latest line | 4.6.x (EOL, no PHP 8.5 support) |
| Slim | `slim/slim ^4.15` + the opinionated stack | `^5.0 \|\| ^4.15` when Slim 5 reaches stable | 3.x (PSR-7 v1) |

- Fight Common's own Symfony components pin `^8.1`. Laravel 13's `^7.4 || ^8.0` Symfony floor and the Slim
  stack's `^7.4 || ^8.0` floors resolve to Symfony 8.1 under PHP 8.5, so no lower Symfony floor is needed
  while the window is current-only.
- All ranges are PHP-8.5-current with a PHP 8.6 re-resolution horizon (Guzzle `<8.6`, Slim `~8.5.0`,
  Symfony `polyfill-php86`). Re-resolution is required when PHP 8.6 or the next framework major ships.
- Composer verification lives in the five real starter repositories. Each repository requires the Fight
  Common candidate plus its selected framework set, resolves lowest and latest, and emits an immutable
  repository-owned receipt. Fight Common retains no nested framework roots and no combined project lane.
- Each widened previous line receives an independent proof in the owning starter repository before support is
  widened. Laravel 12 and Slim 3 remain outside the supported window while Fight Common pins Symfony `^8.1`.
- The capability worksheet records the native facility, existing reusable Fight Common binding, starter-owned
  wiring, new-shared-adapter decision, functional journey, and remaining unknown for every contract and
  framework. The new-shared-adapter decision is **no** for every row.
- A new shared Fight Common adapter is authorized only when a walking-slice prototype demonstrates a
  translation seam that starter composition cannot express cleanly. Equal class counts are not a goal.
- Fight Common ships no Symfony bundle. Integration is starter-owned: Laravel gets a ServiceProvider with
  `extra.laravel` auto-discovery; Yii 3 gets a configuration provider via `yiisoft/config`; CodeIgniter 4
  gets `Config\Services` extending the framework base service; Slim gets an explicit php-di container through
  `AppFactory::createFromContainer()`; Symfony projects own service loading, autoconfiguration, compiler-pass
  registration, aliases, and environment configuration.
- The one opinionated Slim stack is `slim/slim ^4.15`, `slim/psr7 ^1.8`, `php-di/php-di ^7.1`,
  `slim/twig-view ^3.4`, `doctrine/orm ^3.6`, `doctrine/dbal ^4.4`, `symfony/messenger ^7.4 || ^8.0`,
  `symfony/console ^7.4 || ^8.0`, `symfony/http-foundation ^7.4 || ^8.0`, `slim/csrf ^1.5`,
  `symfony/validator ^7.4 || ^8.0`, `symfony/mailer ^7.4 || ^8.0`, `symfony/process ^7.4 || ^8.0`,
  `monolog/monolog ^3.10`, `guzzlehttp/guzzle ^8.0`, `league/flysystem ^3.35`, `symfony/cache ^7.4 || ^8.0`.
- Async and event composition defaults: Laravel uses native Queue and event discovery through the
  ServiceProvider, with an adapter event composing Fight Common domain events onto native machinery (shape
  settled during prototype work); Yii 3 composes the synchronous portable buses with a starter-owned
  transport behind a forward-compatible seam so a future stable `yiisoft/queue` plugs in without breaking
  the contract; CodeIgniter 4 adopts the official `codeigniter4/queue` and `codeigniter4/tasks` packages with
  the portable buses and Scheduler as fallback; Slim uses Symfony Messenger from the opinionated stack.
- SPA host templating defaults: Laravel uses Blade, Symfony uses Twig, Yii 3 uses `yiisoft/view` with Twig,
  CodeIgniter 4 uses its native View (the View Parser is not Twig), and Slim uses Twig via `slim/twig-view`.
- Recommended compositions fill every capability without a first-party native facility, built from existing
  portable adapters and Composer-installable packages; none is recorded as unsupported.
- Frameworks and optional adapter packages stay out of production requirements. Package suggestions name
  exact optional packages, while normative supported ranges live in documentation.

## Testing Decisions

- The primary seam is five independent clean-clone starter-repository builds. Each repository installs Fight
  Common plus its selected framework dependencies and proves that its default composition works without any
  unrelated framework package or nested Fight Common project.
- Each starter resolves and records both the lowest and latest permitted supported set, including exact
  resolved versions and lock digests, then runs its framework's composition probes: native response
  construction, dependency-injection or service-registration wiring, routing and URL generation, transaction
  composition, and the other capabilities selected by the worksheet.
- Repository locks are local lane inputs; every required lane emits a stable receipt that the umbrella may
  link without recreating or reinterpreting the repository's acceptance result.
- Framework and optional adapter packages remain outside production requirements, and activation packages are
  named in suggestions and normative version documentation.
- An unavailable, skipped, failed, conflicted, or indeterminate repository set fails its lane and
  produces one resumable next action rather than a waiver.
- Downstream, the WF-017 walking-slice prototypes are the composition seam that proves the persistence
  compositions (Eloquent, Yii DB, CodeIgniter Models, Doctrine) functionally, including aggregate hydration
  and native transactions, and that settles the Laravel adapter-event shape and the Yii forward-compatible
  async seam.
- Tests assert consumer-visible resolution, receipt, and documented-journey behavior rather than internal
  wiring details or incidental lock ordering.

## Out of Scope

- Installing framework packages, creating starter repositories, or implementing adapters in this change;
  repository bootstrap and walking-slice implementation are owned by PRD-00016 and PRD-00018.
- Specifying the Fight AccessControl extraction and authentication model (WF-016).
- Building persistence and transaction walking-slice prototypes (WF-017) or the full-support implementation
  handoffs (WF-018).
- Creating starter applications, frontend clients, database schemas, authentication flows, or service-provider
  configuration for any repository.
- Publishing packages or public starter repositories.
- Removing deprecated `1.x` paths or changing public contracts before the `2.0.0` boundary.
- Making framework packages unconditional production dependencies.
- Testing every replaceable composition alternative; defaults are composition-root choices.
- Forcing all frameworks onto a shared stack (Doctrine, Twig, Symfony Messenger) when a native facility is
  the simpler composition.
