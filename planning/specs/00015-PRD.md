# Framework Adapter Support and Capability Composition

## Problem Statement

Fight Common already contains substantial Symfony and Doctrine integration, but consumers of Laravel, Yii,
CodeIgniter, and Slim do not have an equivalent reusable adapter surface or a consistent way to activate it.
The earlier plan placed most framework integration in starter repositories and authorized no new shared adapter
by default. That premise would duplicate queue jobs, transactions, response conversion, routing, templating,
mail, broadcasting, and service-container wiring across starters even when the framework exposes a stable,
reusable extension point.

Framework capability names are also deceptively similar. A queue may transport a payload without preserving a
complete Fight message; a transaction wrapper may not satisfy UnitOfWork close and nesting behavior; a native
cache may omit part of Fight's contract; and a logger, HTTP client, or response implementation may already satisfy
a PSR directly. Treating every similarity as support would hide behavioral gaps, while forcing every framework
through Symfony or a third-party package would ignore useful native facilities.

Fight Common therefore needs an explicit framework-by-capability support contract: which adapters ship in the
library, which native integrations begin as conformance prototypes, which standards and existing providers are
wired unchanged, which service-container classes activate each capability, and which operational configuration
remains starter-owned. That contract must be compatible with `1.2.0`, dependency-isolated, and proven in real
starter installations before five-framework support is claimed.

## Solution

Publish optional adapters for Symfony, Laravel, Yii, CodeIgniter, and Slim when they provide reusable translation
or framework lifecycle integration for a public Fight capability. Organize runtime adapters by capability and
framework or provider, and organize compiler passes, service providers, configuration providers, service
delegates, and portable registrars together under ServiceContainer. Activation is capability-scoped and explicit;
there is no provider that silently enables every optional adapter.

Use framework-native facilities first when they can satisfy the complete Fight contract. Mark clear translations
as **ship**, uncertain native translations as **prototype**, and direct standards or existing provider
compositions as **wire**. A prototype becomes supported only after the same Fight Common conformance suite passes;
if it cannot satisfy the contract, document the exact gap and use the accepted tested fallback. Framework and
provider packages remain development dependencies and Composer suggestions in Fight Common, while each starter
requires only its selected runtime stack.

Deliver queued commands and events in Symfony, Laravel, and CodeIgniter by transporting one complete Fight
message and delegating to neutral synchronous handlers. Delivery is at least once and post-commit where the
framework supports it, but broker topology, retries, failure policy, worker supervision, and atomic outbox design
remain project-owned. Stable Yii Queue support remains deferred until its upstream queue and production broker
packages publish compatible stable releases.

Prove every supported adapter twice: first through Fight Common behavioral conformance, then through one booted
installed-package journey in the corresponding real starter. Compose those immutable receipts into the package
certification specified by PRD-00014.

## Implementation Decisions

- Supported lines follow Fight Common's current-only policy and widen to current plus previous only when the next
  major ships and the owning starter proves both lines. The window never exceeds two maintained majors.
- The initial constraints are Symfony components `^8.1`, Laravel `^13.0`, CodeIgniter `^4.7`, Slim `^4.15`, and
  the current Yii 3 package set accepted by ADR 0020. PHP 8.6 and future framework majors trigger re-resolution.
- Domain values, collections, specifications, messages, repositories, and other framework-free primitives require
  no framework adapter. Framework-neutral Application coordinators and services are wired directly unless a
  framework lifecycle or concrete infrastructure translation is required.
- The delivery states are **ship**, **prototype**, and **wire**. Ship means a clear reusable adapter required for
  the support claim; prototype means a native API must prove the complete Fight contract before becoming public;
  wire means an accepted PSR or existing provider adapter already fulfills the capability.
- Native framework APIs are attempted first. A native adapter ships only after complete conformance; a failed
  prototype reports the exact gap and uses the matrix's tested fallback. Official companion packages are chosen
  case by case rather than automatically preferred or rejected.
- Framework service-container integrations are capability-scoped and explicit. Laravel uses bounded service
  providers, Symfony uses capability compiler passes, Yii uses configuration groups and service providers,
  CodeIgniter uses service delegates, and Slim or standalone consumers use Fight container registrars. There is
  no provider that activates all optional adapters.
- Framework and provider packages used to test adapters are development requirements and Composer suggestions in
  Fight Common. Each starter requires only its selected runtime framework and provider stack.

- The shared PSR lane consists of PSR-15 JSON/JSend error middleware, a PSR-17 JSend response factory, canonical
  PSR-6 and PSR-16 cache adapters, and a PSR-18 client view over Fight's configured synchronous send behavior.
- The same configured HTTP transport may be registered behind Fight `HttpClient` and behind a decorating PSR-18
  `ClientInterface`; arbitrary synchronous-only PSR-18 clients do not satisfy Fight's async-capable interface.
- Stable asynchronous adapters transport one complete `CommandMessage` or `EventMessage`, preserving message ID,
  creation time, payload type and value, and metadata. Framework jobs delegate to neutral handlers, which invoke
  the synchronous Fight bus or dispatcher.
- Async delivery is at least once. Framework-native post-commit submission is used where available, but it is not
  an atomic outbox. A retried event repeats complete synchronous fan-out.
- Broker selection, queue names and topology, serialization configuration beyond the adapter contract, retry and
  failure policy, failed-job storage, worker supervision, and durable outbox implementation remain starter-owned.
- Yii Queue is not a stable `1.2` adapter while its core and production broker packages lack compatible stable
  releases. A starter may experiment behind the neutral handler seam. Stable upstream releases may enable an
  additive `1.3` adapter after queue serialization, acknowledgement, retry, failure, signal, and long-running
  state behavior is proven.
- Framework authentication guards, challenges, sessions, identities, and principals are not adapted behind the
  current boolean PSR-7 `Authenticator`. Fight AccessControl owns project-level authentication and principal
  mapping; Fight Common adapts only exact security seams.
- Symfony retains its real Messenger command bus, event dispatcher, and serializer. Existing framework-specific
  handlers move to canonical names only when they are Symfony extension points; reusable dependency-free message
  handlers become neutral.
- Slim receives no branded copies of shared adapters. It adds only the named-route translation and uses Fight's
  concrete container with explicit capability registrars plus the selected provider stack.
- Every ship item is required before `1.2.0` claims support for its framework. A prototype failure does not block
  the claim when a documented tested wire fallback remains; it does block when no supported composition remains.
- Additive support may ship in `1.3.0`. Removing legacy namespaces or changing an inward contract incompatibly is
  reserved for `2.0.0`.

## Testing Decisions

- The first authority seam is Fight Common adapter conformance. Each adapter runs the shared behavioral suite for
  the inward Fight contract or outward PSR contract it claims, using the framework or provider package only as a
  development dependency.
- Conformance tests assert the complete observable contract, including values, failure translation, lifecycle,
  transaction results, rollback and nesting behavior, message preservation, response semantics, and optional
  dependency boundaries. They do not accept partial methods as support.
- Prototype tests run the same suite as ship adapters. Passing evidence promotes the native implementation;
  failing evidence records the exact gap and proves the selected fallback before the support matrix is updated.
- Async conformance proves complete envelope round-trip for commands and events, synchronous delegation, repeated
  delivery of the same message identity, complete event fan-out on retry, and post-commit submission where the
  framework exposes it. It does not simulate an atomic outbox.
- Service-container conformance activates one capability at a time and proves its public services, aliases,
  handler or subscriber maps, and lifecycle. It also proves that unrelated capabilities and optional packages are
  not activated.
- The second authority seam is one clean booted installed-package journey in each real starter. The starter
  installs the Fight Common candidate plus only its framework stack, activates selected capability integrations,
  resolves them from the native container, and exercises representative behavior.
- Each starter journey covers native response creation, dependency registration, routing and URL generation,
  transactional work, selected messaging delivery, and at least one representative adapter from every capability
  state claimed by that framework.
- Each starter resolves the lowest and latest permitted dependency sets and records exact versions, lock digest,
  selected capabilities, adapter states, executed journeys, and result in an immutable receipt.
- Framework packages remain absent from Fight Common production requirements and unselected optional packages
  remain absent from each starter runtime graph.
- Symfony registration tests cover compiler-pass identity and Messenger serialization. Laravel tests boot the
  application and selected providers. Yii tests load selected configuration groups and providers. CodeIgniter
  tests boot selected service delegates. Slim tests boot the explicit PSR-11 container and route collector.
- Yii's `1.2` receipt must identify stable queue support as unavailable rather than skipped. Experimental queue
  evidence is non-normative until the release gate is satisfied.
- The five starter receipts are consumed by PRD-00014's installed-package certification. An unavailable, skipped,
  failed, conflicted, or indeterminate required journey fails the affected support claim and provides one
  resumable next action.
- The two-part evidence rule may be changed only by an explicit planning decision if implementation demonstrates
  disproportionate cost; tests and documentation may not weaken it silently.
- Tests assert consumer-visible behavior and framework lifecycle, not private adapter structure, incidental
  registration order, or every replaceable provider combination.

## Out of Scope

- Framework guards, sessions, authenticated-principal mapping, authorization policy, and Fight AccessControl
  project adaptation.
- Application-owned command handlers, event subscribers, repositories, routes, controllers, templates, mail
  content, credentials, or business configuration.
- Broker provisioning, queue topology, retry schedules, failed-job policy, worker supervision, deployment, or an
  atomic outbox.
- Stable Yii Queue support before compatible stable upstream packages and production-broker evidence exist.
- Testing every interchangeable provider or framework package combination; the matrix owns one supported path.
- Forcing every framework onto Doctrine, Symfony Messenger, Twig, Monolog, or another shared stack when its native
  facility satisfies the complete contract.
- Publishing a redundant framework wrapper where a PSR or existing provider interface is wired directly.
- Adding framework packages to Fight Common production requirements or installing all frameworks together in a
  consumer project.
- Removing deprecated `1.x` namespaces or weakening existing inward contracts; those changes belong to `2.0.0`.
- Implementing starter products, publishing packages, tagging a release, or modifying external repositories in
  this planning change.
