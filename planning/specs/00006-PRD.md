# Integration Guide and 1.2 Release Acceptance

## Problem Statement

Even precise contracts are difficult to adopt when consumers cannot see how aggregate recording, mapping, persistence, projection, and publication fit together. The two worker processes have deliberately different guarantees, and misuse of metadata, checkpoints, cursors, or failed aggregate instances can create subtle production errors.

Fight Common also needs an explicit release boundary. Event Sourcing is additive, but message metadata isolation changes observable behavior while retaining method signatures. Optional Symfony convenience must not become a hidden dependency or block the portable 1.2 release.

## Solution

Publish an integration and operations guide that walks through the complete Event Sourcing lifecycle using the accepted ubiquitous language. Document manual mapper construction, aggregate and repository wiring, durable store concerns, projector and publication workers, failure recording, recovery, migration, and deferred capabilities.

Optionally provide Symfony autoconfiguration for mapping providers as a non-release-blocking stretch goal. Complete compatibility, conformance, coverage, architecture, style, static-analysis, modernization, planning, and documentation checks before declaring additive 1.2.0 acceptance.

T-00015 delivered that optional Symfony integration through container-tested provider auto-tagging and
reference composition into the portable Event Mapper registration and validation path. T-00016 delivered the
corresponding integration and operations guide with single-source executable public-contract examples. T-00017
remains the release-acceptance boundary.

## User Stories

1. As a consumer developer, I want one end-to-end integration guide, so that I can understand how aggregates, messages, mappings, stores, repositories, and workers connect.
2. As a framework-free consumer, I want manual construction documented first, so that Symfony is optional rather than assumed.
3. As a bounded-context owner, I want examples of stable namespaces and local event mappings, so that I can choose durable names independently of PHP namespaces.
4. As an event maintainer, I want class-refactor and schema-change guidance separated, so that I know when to update a mapping and when to write an upcaster.
5. As an aggregate author, I want failed-save guidance to require discard and reload, so that stale aggregate instances are not retried.
6. As a projector author, I want at-least-once delivery and idempotency guidance, so that read-model updates survive replay and crashes.
7. As an operator, I want the checkpoint-reset procedure documented, so that a projection rebuild coordinates worker shutdown and read-model clearing.
8. As a subscriber author, I want publication failure and duplicate-delivery behavior documented, so that I can add idempotent protection where side effects require it.
9. As an operator, I want projection checkpoints distinguished from publication cursors, so that I do not apply a reset or retry policy to the wrong workflow.
10. As an operator, I want failure-recorder configuration and diagnostic limits documented, so that recording, logging, and sensitive-message policy are explicit.
11. As a Symfony consumer, I want mapping providers auto-collected when the stretch integration is available, so that bounded contexts can register mappings declaratively.
12. As a non-Symfony consumer, I want direct provider registration to remain supported, so that framework integration does not alter the portable core.
13. As an existing CQRS consumer, I want public method compatibility demonstrated, so that upgrading does not require adopting Event Sourcing.
14. As an existing message consumer, I want the metadata isolation change clearly release-noted, so that code mutating metadata through getters can be corrected.
15. As a release owner, I want all conformance suites and repository gates to pass, so that the new adapters obey one tested contract with complete coverage.
16. As a release owner, I want the Symfony stretch goal explicitly non-blocking, so that optional convenience cannot delay the core release.

## Implementation Decisions

- Public documentation covers message metadata isolation, aggregate lifecycle, stable stream identity, event mapping and upcasting, Event Store append and reads, repository use, projections, publication, and failure recording.
- Documentation uses the repository's canonical Event Sourcing vocabulary and clearly separates payloads, live messages, stored events, checkpoints, and publication cursors.
- Manual construction and registration of `EventMappingProvider` contributions is the portable baseline.
- If the stretch integration ships, Symfony auto-tags mapping providers and composes them into the configured mapper during container compilation through the same core registration API.
- Invalid or duplicate Symfony-collected mappings fail through existing mapper validation rather than a second framework-specific ruleset.
- Symfony autoconfiguration is non-release-blocking and is documented only if delivered.
- Operations guidance covers prefix-stable polling, projector idempotency, checkpoint reset prerequisites, publication crash duplicates, subscriber failure isolation, recorder failures, and the absence of publication reset or replay in 1.2.
- Migration guidance covers selecting stable names, adding mappings and upcasters, preserving message identity, snapshotting metadata once, rebuilding read models, and discarding aggregates after failed saves.
- Release notes present Event Sourcing as additive and explicitly describe metadata getter isolation as a signature-compatible behavioral change.
- Existing CQRS event triggering and dispatch remain supported without Event Store registration.
- Acceptance requires all public-contract, adapter-conformance, and compatibility tests plus every repository submit gate and planning validation.
- The release targets 1.2.0 and does not rewrite existing release tags.

## Testing Decisions

Documentation examples are reviewed as complete public journeys and must use only supported contracts. Where examples are executable, they should be covered through the same public seams as the production behavior rather than copied into an isolated implementation.

If Symfony autoconfiguration ships, container-level tests prove provider auto-tagging, composition into the intended mapper, validation failures, and continued manual construction without Symfony.

Release acceptance runs the aggregate/repository journey, Event Store conformance suite against in-memory and DBAL implementations, runner tests with in-memory operational state, synchronous dispatcher contract against both implementations, operational-store conformance tests, and message-envelope compatibility tests. The full non-interactive repository gate must pass with exact complete statement coverage.

## Out of Scope

- Consumer-specific aggregate, event, read-model, worker, or deployment implementation.
- Requiring the migration pilot to complete before release.
- Making Symfony autoconfiguration a release blocker.
- Framework-specific worker commands or process supervision.
- Snapshots, sagas, event deletion, history rewriting, publication reset, automatic replay, and targeted-replay APIs.
- Secret detection or redaction of consumer exception messages.
- Breaking existing CQRS method signatures or requiring stored-event mappings for dispatch-only events.

## Further Notes

The guide is part of the product contract, not a post-release explanation. Any behavior too complicated to explain consistently should be resolved before release acceptance rather than delegated to consumer interpretation.
