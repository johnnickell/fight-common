# Isolate Release Tooling from the Consumer Runtime Surface

## Problem Statement

Fight Common's release coordination is repository-maintainer tooling, but its PHP classes currently occupy the
consumer runtime `Application` and `Adapter` layers. Composer therefore exposes them through the production
autoload mapping, which makes internal release orchestration appear to be supported library functionality and
places it in a consumer's IDE completion surface. Release scripts, helpers, fixtures, and tests are also spread
across general-purpose repository directories, making the release command harder to navigate and allowing future
maintenance tooling to expand without a clear ownership boundary.

The documentation theme override has a similar locality problem. Its custom `404.html` template lives in a
root-level `overrides/` directory even though it exists only to support the documentation site. Its purpose and
relationship to MkDocs are not apparent from the repository structure.

## Solution

Establish one top-level `release/` module for all maintainer-owned release implementation, scripts, tests,
fixtures, and module documentation. Give its PHP implementation the dedicated `Fight\Release\` namespace and
load that namespace only through the root package's Composer development autoloader. Keep `bin/release` as the
single stable repository command while preventing release classes from becoming production-autoloaded consumer
contracts.

Move the documentation theme override under `docs/overrides/`, configure MkDocs to use it there, and exclude the
override directory from ordinary documentation content. Preserve all existing release behavior and verification
while making the repository's consumer runtime, maintainer tooling, command surface, and documentation support
files visibly distinct.

## User Stories

1. As a Fight Common consumer, I want production autoloading to expose only library capabilities, so that
   repository release machinery is not mistaken for a supported application API.
2. As a Fight Common consumer, I want release implementation classes absent from IDE completion, so that the
   package's intended runtime surface is easier to understand.
3. As a consumer installing without development dependencies, I want no release namespace registered, so that
   maintainer tooling cannot be resolved accidentally.
4. As a maintainer, I want release implementation collected in one top-level module, so that release work has an
   obvious home.
5. As a maintainer, I want release policy, boundary adapters, scripts, tests, and fixtures colocated, so that
   understanding one release journey requires less navigation across unrelated repository layers.
6. As a maintainer, I want a dedicated release namespace, so that repository coordination concepts cannot be
   confused with Fight Common's reusable Domain, Application, or Adapter contracts.
7. As a maintainer, I want the release namespace available in development mode, so that the repository command
   and its tests continue to use ordinary Composer loading.
8. As a maintainer, I want exactly one `bin/release` entry point, so that command routing, runtime isolation,
   machine results, and policy cannot drift across scripts.
9. As a maintainer, I want supporting scripts hidden behind the release module and command, so that `bin/` stays
   small and intentional.
10. As a future release implementer, I want a documented rule for adding release classes and scripts, so that
    later packaging and publication work extends the module consistently.
11. As a test author, I want release tests and fixtures to mirror the release module, so that test ownership is
    apparent without weakening journey coverage.
12. As a reviewer, I want the quality gate to inspect release PHP and Python sources explicitly, so that moving
    them outside the consumer runtime tree does not create an unverified island.
13. As a reviewer, I want exact statement coverage to include release production classes, so that development-only
    does not mean lower quality.
14. As an architect, I want runtime layers forbidden from depending on release tooling, so that the consumer
    library remains independent of repository operations.
15. As an architect, I want release policy and adapters checked within their own orthogonal module, so that the
    existing dependency discipline survives the move.
16. As a release operator, I want existing commands, machine results, exit codes, artifacts, crash semantics, and
    resumable handoffs preserved, so that this refactor does not alter release authority.
17. As a package certifier, I want the intentional package-surface relocation recorded, so that archive drift is
    reviewed rather than silently accepted.
18. As a package certifier, I want a clean no-development install to prove the release namespace is unavailable,
    so that repository checkout behavior is not confused with installed-package behavior.
19. As a documentation maintainer, I want theme overrides beside documentation sources, so that their ownership is
    immediately clear.
20. As a documentation reader, I want the custom not-found page to continue working, so that the structural move
    does not regress the published site.
21. As a documentation publisher, I want theme templates excluded from ordinary page discovery and static copying,
    so that implementation templates do not appear as documentation content.
22. As a contributor, I want the release module and override conventions documented, so that root-level tooling
    does not sprawl again.

## Implementation Decisions

- `src/` remains exclusively the production-autoloaded Fight Common library surface. No release coordination
  declaration remains below it, and no compatibility alias re-exposes a moved declaration through
  `Fight\Common`.
- `release/` is an orthogonal repository-maintainer module. It contains module documentation, PHP source,
  command implementation scripts, Python helpers, tests, and fixtures beneath one ownership boundary.
- Release PHP declarations use the `Fight\Release\` namespace. The initial move preserves the existing
  Application, boundary, Adapter, and fake seams inside that namespace so the relocation remains behavioral;
  redesigning those internal interfaces is a separate decision.
- Composer maps `Fight\Release\` only through root `autoload-dev`. Release tests use a dedicated development
  test namespace mapped to the release test tree. Composer's production autoload contains no release namespace.
- The release source files may remain in distribution archives. This PRD does not add archive exclusions merely
  to hide them; the required isolation is that dependency installs ignore root-only development autoloading and
  therefore do not register the namespace.
- `bin/release` remains the only stable release entry point. It delegates to the release module's command script
  and preserves the canonical PHP runtime, environment isolation, authenticated machine-result transport, exit
  semantics, and crash behavior.
- Supporting PHP and Python scripts are implementation details of the release module. No additional top-level
  `bin/*` release commands are introduced.
- Release fixtures, reusable conformance test cases, unit tests, runtime tests, and public-command journey tests
  move with the module. Tests continue to assert behavior through the highest practical seam rather than the old
  filesystem layout.
- PHPUnit, coverage, PHPStan, PHPCS, Rector, PHP and Python syntax checks, and Deptrac explicitly include the
  release module. The canonical quality gate must fail if release code becomes unassigned or unverified.
- Architecture enforcement treats release tooling as orthogonal to Domain, Application, Adapter, and Standards.
  Consumer runtime and Standards code may not depend on it. Release-internal dependency direction remains
  explicit and fail-closed.
- Process fixtures and quality-gate contract tests are updated alongside path changes so they continue to prove
  the canonical commands rather than stale locations.
- The package-surface and public-API evidence records the move as an intentional internal tooling relocation.
  No moved declaration is added to the consumer public API manifest.
- The MkDocs theme override moves to `docs/overrides/404.html`. MkDocs uses that directory as its custom theme
  directory and excludes `/overrides/` from ordinary documentation discovery and copying.
- `release/README.md` documents purpose, namespace and autoload rules, the one-command policy, internal layout,
  extension guidance, and verification expectations. General contributing documentation links to that module
  guide without duplicating release policy.

## Testing Decisions

- The primary release seam is process execution of `bin/release` in a maintainer checkout using the development
  autoloader and deterministic fixtures. Existing inspect, plan, prepare, crash, credential-isolation, artifact,
  and resume behavior must remain unchanged.
- A Composer development-autoload test proves a representative `Fight\Release\` declaration resolves in a
  maintainer checkout.
- A clean temporary Composer consumer installed with `--no-dev` proves the package installs while no
  `Fight\Release\` declaration can be autoloaded. The test observes Composer behavior rather than IDE-specific
  implementation details.
- A source-surface assertion proves no release namespace or release coordination declaration remains under the
  production-autoloaded tree and no `Fight\Common` compatibility alias points to the new namespace.
- Release unit and conformance tests retain complete coverage of every release production class after relocation.
  Coverage aggregation treats both consumer runtime source and release source as mandatory production code for
  repository quality purposes.
- Static analysis, coding standards, automated refactoring checks, syntax checks, and architecture enforcement
  each receive a focused assertion that the release module is included.
- The documentation build uses the repository's pinned Material for MkDocs line and proves the moved override is
  accepted. Rendered output is inspected to confirm the custom not-found page remains and the override template is
  not emitted as ordinary documentation content.
- Planning validation and the full canonical non-interactive submit gate are required. A focused pass is useful
  during the move but is not completion evidence.

## Out of Scope

- Adding packaging, certification, publication, maintenance, patch, or forward-port behavior.
- Changing release plan schemas, state transitions, machine results, findings, exit codes, evidence authority,
  effect authorization, or recovery policy.
- Redesigning the existing release Application, boundary, Adapter, or fake interfaces beyond the namespace and
  ownership relocation required for isolation.
- Adding another release executable, Composer binary declaration, global command, or consumer-facing release API.
- Excluding all maintainer files from distribution archives or changing unrelated Composer package contents.
- Publishing a release, changing Git refs, using production credentials, or mutating GitHub or Packagist.
- Redesigning the documentation theme or changing page content beyond the override's location and explanation.
- Refactoring unrelated scripts, tests, runtime layers, or root directories.

## Further Notes

- ADR 0009 requires intentional classification of production-autoloaded declarations. Removing release classes
  from production autoload avoids creating an accidental consumer compatibility promise.
- ADR 0013 treats production autoload mappings and archive contents as versioned package-surface evidence. The
  implementation must distinguish intentional development-only namespace isolation from unexpected archive drift.
- ADR 0014 retains authority over the single release executable and its deterministic behavior. This PRD changes
  code ownership and discovery, not release policy.
- PRD-00010 and T-00040 provide the completed behavior that must survive the move. This PRD and T-00068 complete
  before T-00033 adds the first package journey.
