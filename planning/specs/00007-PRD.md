# Reusable Fight Coding Standard

## Problem Statement

Fight Common and Omphalos currently express the desired PHP conventions in different places. The more
complete Omphalos standard contains reusable rules and custom sniffs, but it is owned by a consuming
application rather than the shared package. That makes the conventions difficult to adopt consistently,
allows the two repositories to drift, and leaves other consumers without a supported configuration model.

Simply copying the ruleset into Fight Common would not produce a dependable public standard. Consumers need
stable sniff identifiers and configuration properties, predictable release compatibility, an explicit way
to load the rules without changing Fight Common's package identity, and freedom to own their scanned paths
and exclusions. Fight Common also needs to prove that the adopted standard can govern its existing source
without baselines or grandfathered violations.

## Solution

Publish one optional, opinionated `FightCommon` PHP_CodeSniffer standard from Fight Common. It reproduces the
accepted Omphalos production conventions, includes independently tested custom sniffs, and becomes the
canonical implementation after parity is proven. Consumers load the installed standard explicitly from
their own PHP_CodeSniffer configuration and remain responsible for scan paths, exclusions, selected sniffs,
and property overrides.

Migrate Fight Common to the complete standard in reviewable stages: first mechanical rules, then member
layout, then semantic documentation. Each stage finishes green without a baseline or suppression file. The
standard name, custom sniff identifiers, diagnostic codes, and configurable properties are treated as
versioned public contracts so routine dependency updates do not unexpectedly break compliant consumers.

## User Stories

1. As a Fight Common maintainer, I want one canonical coding standard, so that repository conventions cannot
   drift between duplicated implementations.
2. As an Omphalos maintainer, I want Fight Common to own the reusable standard, so that Omphalos can eventually
   consume rather than maintain shared tooling.
3. As a consumer maintainer, I want to opt into the standard explicitly, so that installing Fight Common does
   not silently change my development workflow.
4. As a consumer maintainer, I want a copy-ready configuration example, so that I can adopt the standard
   without reverse-engineering package internals.
5. As a consumer maintainer, I want to choose my scan paths, so that a shared standard does not assume my
   repository layout.
6. As a consumer maintainer, I want to declare my own exclusions, so that generated code and repository-local
   exceptions remain under my control.
7. As a consumer maintainer, I want to include or exclude individual sniffs, so that I can stage adoption
   deliberately.
8. As a consumer maintainer, I want to override documented sniff properties, so that supported configuration
   does not require copying the standard.
9. As a consumer maintainer, I want stable sniff and diagnostic identifiers, so that suppression tooling and
   CI annotations remain valid across compatible releases.
10. As a consumer maintainer, I want compatible releases to preserve previously compliant defaults, so that a
    routine package update does not unexpectedly fail my build.
11. As a Fight Common maintainer, I want custom sniffs tested independently, so that a framework upgrade or
    tokenization change cannot silently weaken enforcement.
12. As a Fight Common maintainer, I want parity fixtures against the Omphalos behavior, so that canonical
    ownership transfers without changing the accepted conventions accidentally.
13. As a Fight Common maintainer, I want the standard isolated from runtime layers, so that development policy
    does not become an application dependency.
14. As a library consumer, I want coding tools to remain optional development dependencies, so that runtime
    installation stays lightweight.
15. As a contributor, I want mechanically fixable changes separated from semantic documentation work, so that
    reviews can detect behavioral mistakes.
16. As a contributor, I want every migration stage to end with a green complete ruleset, so that later tickets
    never rely on a growing violation backlog.
17. As a reviewer, I want documentation changes to describe real behavior, so that satisfying a sniff does not
    replace domain meaning with generic prose.
18. As a release maintainer, I want stricter default rules reserved for major releases, so that the standard
    follows an understandable compatibility policy.
19. As a release maintainer, I want new opt-in capabilities allowed in minor releases, so that the tooling can
    evolve without surprising existing consumers.
20. As an Omphalos maintainer, I want its consumer migration planned separately, so that Fight Common's release
    is not blocked by work in another repository.

## Implementation Decisions

- The public standard is named `FightCommon` and represents one canonical profile rather than separate base
  and strict variants.
- Reusable PHPCS tooling belongs to the orthogonal Standards layer in the
  `Fight\Common\Standards\Phpcs` namespace. Standards cannot depend on Domain, Application, or Adapter, and
  runtime layers cannot depend on Standards.
- Fight Common remains an ordinary Composer library. PHP_CodeSniffer and Slevomat are development
  dependencies for package verification and are advertised as optional consumer requirements through
  Composer suggestions.
- Consumers load the installed ruleset explicitly. Fight Common does not change its Composer package type
  and does not require the PHP_CodeSniffer Composer installer plugin.
- The published ruleset selects rules only. It does not select consumer paths or exclusions.
- Consumer documentation demonstrates complete-standard loading, repository-owned paths and exclusions,
  individual sniff inclusion and exclusion, and configurable property overrides.
- Omphalos custom sniffs and their supporting helpers move into the Standards surface after behavior parity
  is established with representative accepted and rejected fixtures.
- Fight Common becomes the canonical implementation when the packaging work is accepted. The Omphalos copy
  is temporary from that point forward, and its removal is owned by separately planned Omphalos work.
- The standard name, custom sniff identifiers, diagnostic codes, and documented configurable properties are
  public compatibility contracts.
- Patch releases may correct false positives, compatibility, documentation, or performance without creating
  new default violations for previously compliant code.
- Minor releases may add opt-in sniffs and backward-compatible configuration, but may not make the canonical
  defaults stricter.
- A major release is required to enable a new default rule, tighten accepted syntax, or remove or
  incompatibly rename a public sniff, diagnostic code, or property.
- Fight Common adopts the completed ruleset in three ordered migrations: mechanical formatting, member
  layout, and semantic documentation.
- Each migration removes all violations in its scope before enabling the corresponding canonical rules. No
  baseline, suppression file, or grandfathered violation is permitted.

## Testing Decisions

- The primary seam is PHP_CodeSniffer's command-line behavior against fixture projects that explicitly load
  the installed `FightCommon` ruleset.
- Acceptance fixtures prove that compliant source passes and noncompliant source fails with the expected
  stable sniff and diagnostic identifiers.
- Consumer-configuration fixtures prove full ruleset loading, repository-owned scan scope and exclusions,
  individual sniff selection, individual sniff exclusion, and documented property overrides.
- Focused custom-sniff tests cover token and whitespace edge cases that are difficult to express clearly in
  a broad consumer fixture.
- Parity fixtures execute equivalent representative inputs against the temporary Omphalos implementation and
  the Fight Common implementation before ownership transfers.
- Compatibility tests protect the public standard name, identifiers, diagnostic codes, and documented
  property names.
- Migration tests are the complete Fight Common PHPCS scan rather than snapshots of automatically rewritten
  files. Review and the existing test suite protect behavior while each rule group is adopted.
- Custom sniff production code maintains complete coverage under the same PHPUnit coverage contract as the
  rest of Fight Common.

## Out of Scope

- Automatically configuring PHPCS in a consuming repository.
- Selecting consumer scan paths, exclusions, or adoption policy.
- Requiring PHP_CodeSniffer or Slevomat as runtime dependencies.
- Publishing multiple strictness profiles in the 1.2 release.
- Completing the Omphalos consumer migration as part of Fight Common's release.
- Introducing stricter defaults that are not part of the accepted Omphalos parity target.

## Further Notes

- The initial repository scan found 524 violations across 137 production files, including 326 reported as
  automatically fixable. The staged migration exists to keep that review tractable.
