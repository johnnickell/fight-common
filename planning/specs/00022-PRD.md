# Atlas Deck Presentation and GitHub Pages Delivery

## Problem Statement

Fight Common already uses MkDocs Material and GitHub Pages, but the current presentation does not express the
approved Fight identity or the capability-led product hierarchy. The publication workflow writes a branch
directly, presentation behavior is not yet proven beneath the `/fight-common/` project base, and broad theme
customization could easily become a brittle fork that loses Material's search, navigation, snippets, tabs,
syntax highlighting, copy controls, or accessibility behavior.

The new design also needs a proportionate acceptance boundary. It must be polished and accessible without
turning ordinary documentation changes into a long-running browser, screenshot, or performance-test program.

## Solution

Implement the approved Atlas Deck homepage and article shell as a narrow extension of a release-pinned MkDocs
Material toolchain. Preserve native Material behavior wherever it satisfies the fixed point, and use
repository-owned styles, assets, page-specific templates, small partial or block overrides, and only the
JavaScript required for approved interactions.

Build one disposable documentation artifact from the same pinned inputs locally and in continuous integration.
Pull requests validate but do not publish it. A successful build from `main` uploads and deploys that artifact
through GitHub Pages after John separately approves the `develop` to `main` merge. Before initial deployment,
perform the approved focused human review; after deployment, verify the real hosted site separately.

## User Stories

1. As a first-time visitor, I want the promise, installation command, and architecture proof to establish a clear
   hierarchy, so that I know what Fight Common offers before browsing the atlas.
2. As a component-first visitor, I want the complete atlas visible in the primary page flow, so that visual
   presentation does not hide direct discovery.
3. As an article reader, I want component navigation, focused prose and code, and a local table of contents, so
   that dense technical guidance remains navigable.
4. As a mobile reader, I want navigation, diagrams, tabs, controls, and code to reflow without page-level
   clipping or overflow, so that the same content remains usable on a narrow screen.
5. As a keyboard user, I want skip navigation, visible focus, usable menus, search, theme controls, copy controls,
   tabs, and article links, so that every essential interaction works without a pointer.
6. As a screen-reader user, I want semantic regions, headings, labels, and tab relationships, so that the visual
   hierarchy and interactive state have equivalent meaning.
7. As a reader using light or dark mode, I want each theme treated as a complete peer, so that text, controls,
   warnings, code, and identity assets remain legible.
8. As a reader who reduces motion, I want the interface to remain understandable without animation, so that
   motion is never required to perceive state or navigation.
9. As a developer copying code, I want controls that are easy to activate but do not stretch across the code
   block, so that the interaction is usable without distorting the layout.
10. As a framework user, I want equivalent configuration formats selectable by pointer and keyboard with a
    format-specific copy action, so that examples remain both accessible and practical.
11. As a reader, I want consequential warnings to be prominent but restrained, so that important behavior is
    unmistakable without making every note feel urgent.
12. As a reader following a broken or old link, I want a branded custom 404 with a working route to the project
    base, so that the `/fight-common/` deployment context never strands me.
13. As a search user, I want generated search to include every canonical guide and route correctly, so that the
    custom presentation does not weaken lookup behavior.
14. As a maintainer, I want one exact documentation dependency set and one strict build path, so that local and
    hosted output do not drift.
15. As a reviewer, I want pull requests to validate the generated artifact without publishing it, so that review
    never changes the public site.
16. As John, I want to review the responsive design in Brave before first deployment, so that visual judgment
    remains lightweight and under human control.
17. As an operator, I want deployment to use an uploaded Pages artifact from `main`, so that publication does not
    mutate a separate generated-output branch.
18. As an operator, I want hosted verification distinguished from local success, so that a passing build is not
    reported as a working public deployment.
19. As a maintainer, I want a simple launch asset-size baseline, so that real future regressions can be
    investigated without imposing speculative performance scores today.
20. As a contributor making an ordinary prose edit, I want fast deterministic checks, so that presentation
    quality does not make every documentation change expensive.
21. As John, I want the footer to identify his authorship and the project's public routes, so that the site ends
    with a restrained copyright, GitHub, contribution, and MIT-license context.

## Implementation Decisions

- Retain MkDocs Material and Markdown. Pin the complete documentation toolchain and CI Python version exactly in
  repository-owned configuration.
- Keep explicit navigation authority in MkDocs configuration. Generated site output is disposable and untracked;
  Markdown, configuration, templates, styles, scripts, fonts, and assets are the owned inputs.
- Extend Material at its narrowest stable seams. Prefer native search, syntax highlighting, copy, tabs,
  navigation, palette, and snippet behavior over custom replacements or a theme fork.
- Implement the Atlas Deck homepage with the promise and Composer command first, a full-width Adapter to
  Application to Domain architecture chain, three equal entry routes, and the complete directly linked atlas.
- Implement the article shell with component navigation, breadcrumbs, ownership and dependency metadata, focused
  content, copyable examples, a local table of contents, relationship diagrams, warnings, and explicit next
  steps.
- On compact layouts, convert component navigation to a usable horizontal rail and remove the local table of
  contents from the primary reading flow. Stack the architecture chain only below the approved narrow breakpoint.
- Use Open Sans SemiBold for headings and structural labels, Source Sans 3 for reading, and Fira Code with
  programming ligatures for code. Self-host release-pinned, appropriately subset font assets with system
  fallbacks; disable ligatures only where exact character comparison requires it.
- Apply the approved cold-steel and carbon themes with kiln orange reserved for action, crossings, active seams,
  and consequential callouts. Use only restrained gradients and low-opacity shadows where structure or action
  needs depth.
- Keep interaction motion within the approved short feedback range, with no ambient or scroll animation and an
  effective reduced-motion mode.
- Configuration tabs expose only genuine equivalent formats, preserve semantic tab and panel state, support
  pointer and arrow-key selection, label formats and filenames, and provide per-format copy controls.
- Keep controls at the approved 44px target without allowing flex behavior to stretch copy buttons. Code scrolls
  within its own surface when necessary and never creates page-level horizontal overflow.
- Display a restrained `© 2026 John Nickell` footer with routes to GitHub, contribution guidance, and the MIT
  license. Derive the year from build or site configuration when practical.
- Build the production site for `https://johnnickell.github.io/fight-common/` with `/fight-common/` as the project
  base. Emit correct base-relative assets, canonical URLs, search entries, sitemap, anchors, and custom 404
  behavior.
- Pull requests build and validate but do not deploy. Publication occurs only from `main` through an uploaded
  GitHub Pages artifact and the protected Pages environment; direct generated-branch writes are removed rather
  than run in parallel.
- Roll back by redeploying a known-good artifact when available or reverting the responsible source change and
  rebuilding it.
- No PHP public API or runtime behavior change belongs to this presentation and delivery requirement.

## Testing Decisions

- The highest automated seam is the strict production documentation build and its generated artifact beneath
  `/fight-common/`. Validate routes, assets, navigation, search, snippets, canonical metadata, sitemap, article
  anchors, configuration tabs, copy controls, and the custom 404 with fast deterministic checks.
- Pull-request checks do not launch browsers, calculate Lighthouse or Core Web Vitals scores, compare screenshots,
  or publish Pages.
- Before initial deployment, require a clean-checkout documentation build and one human Brave review of the
  homepage, Architecture, Quick Start, Mail, and Messaging through narrow mobile, tablet, and wide desktop sizes.
- The human responsive review confirms that content, global and component navigation, layer diagrams, relationship
  diagrams, tabs, controls, callouts, and scrolling code remain available without page-level overflow, clipping,
  or unusable layout. Repeat it only when shared presentation changes or new content creates a materially new
  visual pattern.
- Before initial deployment, perform one lightweight keyboard and screen-reader smoke check covering landmarks,
  headings, skip navigation, visible and unobscured focus, search, menus, themes, copy controls, configuration
  tabs, links, and state announcements.
- Verify WCAG 2.2 AA color contrast in both themes, color-independent meaning, reduced motion, reflow, zoom, and
  readable code behavior. This is practical acceptance, not exhaustive assistive-technology certification.
- Record a simple initial size baseline for generated HTML, CSS, JavaScript, fonts, images, and the search index.
  Investigate material growth or observed slowness; do not establish speculative performance score gates.
- After a separately approved deployment, smoke-test the real hosted homepage, representative canonical routes,
  assets, search, theme behavior, canonical metadata, sitemap, and 404. Report this as hosted evidence distinct
  from the predeployment build.
- The repository's canonical submit gate remains required before any implementation commit or pull request.

## Out of Scope

- Migrating to another documentation generator while MkDocs Material preserves the approved behavior.
- Forking Material or rebuilding native search, syntax highlighting, navigation, snippets, copy, tabs, or palette
  behavior without a proven gap.
- Routine cross-browser matrices, browser automation, Lighthouse gates, Core Web Vitals thresholds, screenshot
  approval systems, or visual-regression suites.
- Committing generated site output or continuing direct deployment to a generated-output branch.
- Treating a local or pull-request build as proof that the hosted Pages site works.
- Merging `develop` to `main`, deploying Pages, publishing the GitHub-profile adaptation, or cleaning task-owned
  resources without separate authorization.
