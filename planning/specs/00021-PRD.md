# Capability-Led Documentation and Information Architecture

## Problem Statement

Fight Common's existing documentation contains substantial technical reference material, but its top-level
organization asks readers to understand the repository before they can find the capability they need. The
Quick Start assumes Symfony, the architecture page concentrates on repository enforcement, and component pages
do not yet share a task-oriented structure. A developer who wants to wire Mail should be able to see Mail under
Connect Systems immediately, while an architect should be able to choose a prominent Hexagonal Architecture and
CQRS path without treating that conceptual material as a quick-start detour.

The redesign permits one deliberate route reset because current adoption is negligible. That opportunity must
produce a coherent canonical inventory rather than simply rename pages. Once published, the new routes and
important anchors become compatibility commitments.

## Solution

Reorganize the documentation around three equal homepage entry routes: Architecture, Quick Start, and Explore
Components. Follow them with a complete capability atlas grouped by the problems readers are solving, exposing
every component link directly inside its group and showing Domain, Application, and Adapter ownership plus
optional dependency needs at a glance.

Create a framework-neutral Quick Start, a prominent diagram-led guide to Hexagonal Architecture and CQRS, and a
consistent component-guide contract. Use Mail as the approachable reference implementation and Messaging as the
dense multi-layer stress case, then bring every advertised component into trustworthy alignment with the public
source. Framework pages own activation and composition; contributor material owns development and coding
standards.

## User Stories

1. As an experienced PHP developer new to Fight Common, I want to see what problems the library solves, so that
   I can evaluate it without learning its repository layout first.
2. As a developer looking for Mail, I want to see it directly under Connect Systems on the homepage, so that I
   do not need to open an intermediate category page.
3. As a developer looking for any advertised component, I want every atlas label to link to a useful guide, so
   that the homepage never promises dead or placeholder content.
4. As an architect, I want Architecture to be a prominent entry route alongside Quick Start and Components, so
   that the library's intended patterns are treated as adoption context rather than optional trivia.
5. As an architect, I want diagrams explaining Adapter, Application, and Domain dependency direction, so that I
   can understand how Fight Common supports Hexagonal Architecture.
6. As a developer learning CQRS, I want commands, queries, events, buses, handlers, filters, and dispatchers
   related to their layers and responsibilities, so that examples make architectural sense.
7. As a developer ready to try the package, I want one short framework-neutral Quick Start, so that I can learn
   the core composition before selecting framework-specific wiring.
8. As a Symfony, Laravel, Yii, CodeIgniter, Slim, or framework-free adopter, I want supported composition guidance
   clearly separated from component semantics, so that framework details do not redefine the capability.
9. As a component adopter, I want to know required and optional dependencies before copying an example, so that
   I can install only what the selected adapter needs.
10. As a component adopter, I want the shortest realistic framework-neutral example first, so that the portable
    contract remains visible beneath adapter configuration.
11. As a framework user, I want tabs for equivalent supported configuration formats, so that I can use YAML,
    XML, PHP, attributes, or another format only where the underlying framework genuinely supports it.
12. As a developer, I want consequential behavior called out clearly, so that details such as Mail recipient
    override replacement cannot be mistaken for decorative notes.
13. As an operator, I want component failure modes and operational concerns documented where relevant, so that
    adopting an adapter includes its real tradeoffs.
14. As a maintainer, I want public symbols, examples, and dependency claims checked against the source, so that
    the documentation does not preserve renamed or removed behavior.
15. As an existing reader, I want a deliberate canonical route inventory, so that the one accepted URL reset
    establishes stable locations rather than ongoing churn.
16. As a reader using search, navigation, or article links, I want all three paths to reach the same canonical
    pages and anchors, so that discovery method does not change the answer.
17. As a contributor, I want maintenance and coding-standard guidance outside the product component atlas, so
    that adopter guidance and repository development guidance remain distinct.
18. As a reader finishing one guide, I want related components and concrete next steps, so that I can continue
    without returning to the homepage.
19. As a reader, I want examples that can be copied and understood in context, so that documentation serves
    implementation rather than acting as a class inventory.
20. As John, I want explanatory accuracy judged by a human where automation would become brittle, so that the
    project does not accumulate a slow pseudo-documentation test suite.

## Implementation Decisions

- Serve experienced PHP developers and architects first, existing adopters second, and contributors third. The
  documentation assumes PHP, Composer, and dependency-injection familiarity but no prior Fight knowledge.
- Use the working promise “adopt focused PHP building blocks without coupling Domain or Application code to a
  framework” as positioning guidance. Final prose must support it with real architecture and capabilities rather
  than generic quality claims.
- The homepage presents Architecture, Quick Start, and Explore Components as equal entry routes, followed by the
  complete component atlas. Installation and a compact three-layer proof appear before the atlas.
- Group the atlas as Model the Domain; Coordinate Application Behavior; Connect Systems; Operate Workloads; and
  Integrate Frameworks. Expose component links directly within each group.
- Show Domain, Application, and Adapter ownership and required optional dependencies on atlas cards and component
  guides without making readers decode the layers before finding a capability.
- Architecture is a first-class conceptual route, not an atlas component. Cover inward dependencies, ports and
  adapters, CQRS responsibilities and message flow, framework boundaries, and how Fight Common composes those
  ideas through labeled diagrams and linked examples.
- Quick Start provides one short framework-neutral working path, then branches to component and supported
  framework guidance. It does not attempt to install every optional adapter or begin with Symfony.
- Component guides use a flexible common sequence: problem; layer placement; dependencies; shortest portable
  example; available adapters and framework composition; behavior, failure, and operational concerns; related
  components; and next steps. Omit sections only when they genuinely do not apply.
- Mail is the approachable component reference. Messaging is the dense cross-layer stress case. Their content
  patterns guide the rest of the corpus without forcing identical prose lengths or empty sections.
- Present alternate configuration formats only when they are behaviorally equivalent and supported. Every tab
  identifies its format and filename where useful; presentation symmetry never justifies invented examples.
- Reserve kiln-orange warning callouts for consequential behavior. Every warning includes an explicit label,
  icon, and explanatory text so meaning never depends on color.
- Establish canonical grouped routes for Quick Start, Architecture, Components, Frameworks, and Maintenance. No
  redirects are required from the current low-traffic routes during this one approved reset.
- After first publication, canonical routes and important linked anchors are compatibility commitments. Later
  removal requires a working alias or redirect.
- Keep titles, descriptions, canonical metadata, sitemap membership, and social claims accurate and modest. Do
  not add popularity claims or bespoke structured-data machinery.
- Preserve all public PHP behavior. Documentation may correct or clarify usage but may not change the runtime API
  to make the presentation easier.

## Testing Decisions

- The highest automated seam is the complete generated documentation artifact: its canonical route inventory,
  navigation, atlas links, article anchors, search entries, snippets, metadata, sitemap, and base-relative links
  must agree.
- Run a strict documentation build and lightweight deterministic contract checks on pull requests. These checks
  should remain materially faster than the PHP suite and avoid browser startup.
- Verify every advertised atlas capability has a canonical guide containing its purpose, architectural
  ownership, dependency requirements, realistic example, supported variants, consequential behavior where
  relevant, and useful next steps.
- Execute representative PHP journeys where doing so proves important copied behavior. Apply pragmatic syntax
  checks to representative configuration formats and verify referenced public classes and repository links.
  Do not attempt to execute every prose fragment or format permutation.
- Use the homepage, Quick Start, Architecture, Mail, and Messaging as the acceptance sample for hierarchy,
  coverage, route consistency, search discovery, and the common guide contract.
- Human review remains authoritative for explanatory accuracy, diagram truthfulness, and whether examples teach
  the intended pattern. Record corrections instead of inventing automation that approximates editorial review.
- Verify direct discovery explicitly: each atlas group exposes all of its component links and Mail is reachable
  directly from Connect Systems without an intermediate category route.
- Confirm the one-time route reset before publication. After publication, add compatibility evidence whenever a
  canonical route or important linked anchor changes.
- Do not add routine browser, Lighthouse, visual-regression, exhaustive snippet-execution, or cross-framework
  configuration matrices to this requirement.

## Out of Scope

- Rewriting Fight Common's PHP API or moving runtime classes to match a documentation taxonomy.
- Treating Architecture as a brief Quick Start section or forcing new readers through it before component
  discovery.
- Inventing unsupported framework integrations or equivalent configuration formats.
- Exhaustive API-reference generation, automatic execution of all prose, or a test for every Markdown sentence.
- Publishing the GitHub-profile adaptation or duplicating these guides in another repository.
- Deploying Pages or declaring hosted routes successful before separate post-deployment verification.
