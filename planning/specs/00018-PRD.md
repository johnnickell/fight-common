# Framework Starter Product and Walking-Slice Acceptance

## Problem Statement

Portable package contracts do not prove that an application boots, routes requests, persists identities,
authenticates browsers, delivers email, publishes private updates, or gives a developer a useful starting
product. Five repositories could all depend on the same packages and still diverge in user behavior, hide
missing integrations behind another framework's dependencies, or ship incomplete documentation and clients.

Fight Common must not solve that problem by carrying five nested applications or one cross-repository build.
Each starter needs an independently useful, framework-native implementation and one canonical acceptance
workflow while preserving the same AccessControl outcomes and API contracts.

## Solution

Create private Symfony, Laravel, Yii, CodeIgniter, and Slim starter repositories after Fight AccessControl is
bootstrapped. Each starter owns its full runtime composition, persistence, migrations, HTTP boundary,
security integration, client application, operations, tests, and documentation. Shared behavior comes only
from public Fight Common and Fight AccessControl contracts.

Deliver one ordered user-valued use case through all five repositories before starting the next. Each use case
forms a slice packet: one Fight AccessControl ticket when shared behavior changes, followed by one local ticket
in each starter. A passing repository stays green while a shared defect returns to the owning package. Detailed
implementation tickets and status remain local after bootstrap.

The highest seam is each repository's clean-clone `./bin/build`, framework-native functional and browser tests,
and human UAT card. The portfolio accepts five independent receipts; Fight Common stores dependency links and
handoff state, not copied acceptance criteria or a central runtime.

## User Stories

1. As a framework adopter, I want a starter that boots through my framework's normal composition model, so
   that Fight does not require foreign container or bundle machinery.
2. As a framework adopter, I want one complete editable React client, so that I can change the product without
   depending on a shared runtime frontend package.
3. As a developer, I want public documentation at `/` and `/docs`, so that installation, architecture, API,
   operations, and customization are discoverable from the running starter.
4. As a developer, I want the administration SPA mounted at configurable `/admin` by default, so that changing
   its route does not change Application behavior.
5. As an API consumer, I want identical `/api/v1/access` journeys and typed JSend representations, so that
   framework selection does not redefine the product contract.
6. As a starter maintainer, I want HTTP versioning confined to adapters, so that shared Domain and Application
   names do not acquire transport versions.
7. As a Symfony maintainer, I want service loading, compiler integration, aliases, and environment configuration
   owned by the project, so that no Fight bundle controls the application.
8. As a Laravel maintainer, I want native service-provider, Eloquent, queue, security, and Reverb composition,
   so that the starter follows Laravel conventions.
9. As a Yii maintainer, I want native configuration-provider, DI, persistence, middleware, and queue seams, so
   that the starter remains recognizable to Yii developers.
10. As a CodeIgniter maintainer, I want native services, modules, filters, models, and CLI integration, so that
    portable behavior does not replace CodeIgniter conventions.
11. As a Slim maintainer, I want explicit container definitions, middleware, handlers, Doctrine composition,
    and selected supporting packages, so that the small-stack wiring stays inspectable.
12. As a database operator, I want every starter verified on PostgreSQL and MySQL or MariaDB, so that declared
    portability is behavioral rather than inferred from one database.
13. As a framework maintainer, I want to own migrations, records, mappings, and repository adapters, so that
    each framework can use an idiomatic persistence model without leaking it into AccessControl.
14. As a reviewer, I want shared persistence invariants with framework-native physical schemas, so that equal
    behavior does not require byte-identical DDL.
15. As an administrator, I want a seeded active user and exact fake credentials, so that the first login journey
    can be verified without inventing local data.
16. As a user, I want login, restoration, logout, sessions, refresh, password recovery, and account lifecycle
    behavior to match every other starter, so that security does not depend on framework choice.
17. As an administrator, I want paginated users, roles, permissions, and sessions in the editable client, so
    that the starter demonstrates complete read and management journeys.
18. As a super administrator, I want sensitive user and session operations authorized and audited, so that the
    starter proves security policy rather than only happy-path CRUD.
19. As a project maintainer, I want Managed Roles and Permissions reconciled through a deterministic CLI, so
    that version-controlled authorization definitions and persistence cannot drift.
20. As a frontend maintainer, I want generated TypeScript types from the canonical OpenAPI and realtime schemas,
    so that handwritten client mirrors cannot diverge.
21. As a reviewer, I want the build to reject stale generated client output, so that schema changes are visible
    in code review.
22. As a user, I want private cross-browser updates on the administrator user list, so that relevant changes
    appear without leaking private User state in public messages.
23. As a Laravel operator, I want Reverb used for the native realtime composition, so that the starter follows
    the selected Laravel stack.
24. As a non-Laravel operator, I want an authenticated Mercure Hub composition, so that private updates use the
    approved reusable transport without enabling legacy compatibility behavior.
25. As a user, I want realtime reconnect and refetch to recover authoritative state, so that transport gaps do
    not leave a stale client.
26. As an operator, I want monitoring, failure recovery, disconnect or revocation behavior, and key rotation
    completed before public readiness, so that a demo transport is not presented as production-ready.
27. As an inviter, I want Mailtrap-backed human UAT for security email while ordinary builds use a deterministic
    fake, so that external delivery is proven without making CI depend on a third party.
28. As an operator, I want asynchronous delivery and event workers to preserve the same Application behavior,
    so that invocation mode is a composition choice rather than a use-case branch.
29. As a security reviewer, I want required audit persistence or durable handoff proved within each sensitive
    mutation slice, so that audit correctness cannot be deferred to a later platform project.
30. As a developer, I want one noninteractive `./bin/build` shared by local and hosted verification, so that a
    green workflow has one meaning.
31. As an agent, I want canonical local planning, architecture rules, and completion criteria, so that work can
    proceed without consulting or updating a duplicate umbrella ticket.
32. As a reviewer, I want every human-facing slice accompanied by fake credentials, exact URL, expected result,
    and cleanup, so that automation and human acceptance prove the same outcome.
33. As a maintainer, I want capability documentation updated in the ticket that changes behavior, so that docs
    do not become one late and untestable project.
34. As a repository owner, I want a final local documentation and security audit before public visibility, so
    that unfinished private assumptions do not leak into a public starter.
35. As a package publisher, I want public source visibility separated from release tags and distribution, so
    that review does not silently create an installable version.
36. As a portfolio maintainer, I want all five repositories on the same use-case frontier, so that “supported”
    describes complete journeys rather than whichever framework advanced fastest.

## Implementation Decisions

- Each starter depends on public Fight Common and Fight AccessControl contracts and may not copy their Domain
  or Application source or reach into package internals.
- Every repository owns its framework-native composition root, persistence, migrations, HTTP actions,
  presentation data, principal/provider adapter, queues, mail, JWT, realtime, client, deployment, tests, and
  documentation.
- Symfony may begin by extracting and adapting proven Symfony behavior. Laravel, Yii, CodeIgniter, and Slim
  implement independently from shared behavior and conformance contracts; Symfony infrastructure is not a
  template for the other frameworks.
- Repository foundations are bootstrapped in parallel only after Fight AccessControl establishes its own
  planning and build authority. Foundation work does not require completed login or public package tags.
- Login implementation begins when the required Fight Common and Fight AccessControl contracts, behavioral
  conformance tests, schema assets, and UAT contract are green at immutable private commit references.
- Use cases follow the order fixed by WF-017: login; cold-load restoration; current-session logout; user active
  sessions; authorized user listing; super-admin session revocation; refresh continuity; invitation; activation;
  delivery recovery; password-reset request and completion; authenticated password change; email-change
  request, confirmation, cancellation and expiry; assisted email change; disable; enable; delete and restore;
  pending-invitation correction; Role and Permission inspection; reconciliation; and custom Role administration.
- Each use case is a slice packet. Fight AccessControl receives a shared Domain/Application ticket only when
  shared behavior changes; every starter receives one independently executable local implementation ticket.
  The next use case waits until every required ticket in the packet is green.
- A shared-contract defect pauses the shared frontier, is fixed in the owning package, creates a new immutable
  commit reference, and reruns relevant conformance across all five starters. Framework-specific defects and
  fixes stay local.
- Each starter owns its migrations and physical schema. Shared invariants include canonical-email uniqueness,
  stable User identity, grant uniqueness and expiry, optimistic concurrency, session rotation and revocation,
  and atomic mutation/audit outcomes.
- Both PostgreSQL and MySQL or MariaDB must pass repository-owned migrations, concurrency behavior, persistence
  conformance, functional journeys, and cleanup. Mechanism parity and identical DDL are not required.
- HTTP actions use native framework request and response facilities while emitting the canonical versioned
  JSend contract. Controllers perform no Domain work and Application handlers receive no framework objects.
- The complete editable React application lives under `/client`; generated HTTP and realtime types are
  committed, regenerated in the build, and compared byte-for-byte with canonical schema output.
- The SPA host is framework-native, configurable, and proves at least one alternate mount. `/` and `/docs`
  remain the public documentation experience.
- Security-email automation uses a deterministic fake. An opt-in Mailtrap integration and human UAT prove real
  delivery with environment-owned credentials that never enter fixtures, logs, receipts, or public docs.
- Realtime enters with the authorized user-listing slice. Laravel uses Reverb; the other starters use the
  approved Mercure line. The minimum slice proves private authorization, two-browser invalidation, reconnect,
  and authoritative refetch.
- Monitoring, transport failure recovery, server-side session disconnect or revocation, and secret/key
  rotation are separate repository-local hardening tickets that block public readiness.
- Required security auditing is part of each classified mutation slice. A starter proves one same-database
  atomic commit or an atomic durable handoff to its selected audit store.
- Bootstrap documentation establishes repository purpose, setup, architecture, planning, build, security, and
  contribution guidance. Each capability ticket updates its API, configuration, operations, UAT, and
  troubleshooting guidance. One local documentation audit precedes public visibility.
- `0.1.0` is eligible only when the authentication-core slices defined by PRD-00017 are green across all five
  starters. `0.2.0` completes the remaining account lifecycle. Later `0.x` milestones group coherent product
  capabilities; `1.0.0` is not automatic.
- A repository may become public independently after its compatibility, security, documentation, and clean-
  clone gates pass and public visibility receives approval. Tagging, Packagist publication, template enablement,
  and create-project distribution remain separate approved release effects.

## Testing Decisions

- The primary seam is each starter's canonical noninteractive clean-clone `./bin/build`. Hosted CI delegates to
  the same ordered gate rather than defining a second completion contract.
- The build includes exact production-code coverage, static analysis, PHPCS, architecture enforcement,
  dependency validation, frontend lint/type/test/build checks, documentation checks, security checks, and both
  supported database families where applicable.
- Framework-native functional tests boot the real kernel or request pipeline and prove routing, middleware or
  filter ordering, native response construction, cookies, CSRF/CORS, authorization, transactions, and errors.
- Browser tests exercise the complete editable client against the real local application. A focused fixture is
  not sufficient evidence for login, session restoration, mail journeys, or private realtime behavior.
- Every user-facing ticket supplies a UAT card with setup, fake credentials, exact local URL, expected visible
  result, failure expectations, and cleanup. Human UAT is a required gate, not a substitute for automation.
- Each starter applies the Fight AccessControl behavioral conformance suite through public package contracts
  and its own adapters. Tests assert outcomes and invariants, not identical record classes or containers.
- Concurrency tests use real supported databases for canonical-email claims, grants, audit atomicity, session
  rotation, and any other behavior whose correctness depends on database isolation or uniqueness.
- Schema generation tests prove canonical OpenAPI and realtime schemas generate the committed TypeScript and
  fail when source and generated output differ.
- Realtime tests use two authenticated browser contexts and the real selected transport. They prove private
  authorization, safe envelopes, reconnect/refetch, denial after revocation, and absence of private-field leaks.
- Clean-clone receipts record resolved package identities, framework and database versions, build result, UAT
  contract, and cleanup. Fight Common links the receipt but does not rerun or reinterpret local acceptance.
- An unavailable, skipped, failed, or indeterminate required lane leaves the repository not ready for the next
  shared frontier or public transition and records one local resumable next action.

## Out of Scope

- Implementing shared AccessControl Domain or Application behavior inside a starter.
- Adding framework adapters, starter applications, nested Composer projects, generated clients, or runtime
  receipts to Fight Common.
- One central cross-repository build, one shared database, one shared deployment, or synchronized ticket status.
- Testing every replaceable framework package or forcing Doctrine, Twig, Symfony Messenger, Symfony Security,
  or one container when the selected native facility is simpler.
- Sharing `/client` as a runtime package or requiring identical visual styling and framework plumbing.
- Public self-registration, multi-tenancy, unrelated business domains, or proprietary application behavior.
- Making repositories public, tagging releases, publishing to Packagist, enabling templates, or distributing
  create-project artifacts merely because this specification or a bootstrap ticket exists.
