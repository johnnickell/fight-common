# Durable Storage and Aggregate Repository

## Problem Statement

The in-memory Event Store can define behavior but cannot provide durable history or prove that the contract survives real transaction semantics. A naive DBAL implementation can allocate unique global numbers while still exposing commits out of order, causing a checkpointed reader to skip an event permanently. Durable storage must also make expected-version checks, retry detection, position allocation, and append one atomic operation.

Consumers additionally need a generic repository that connects their aggregates to the Event Store without leaking aliases, schemas, metadata, or storage envelopes into domain reconstitution.

## Solution

Provide a Doctrine DBAL Event Store that implements the shared Event Store contract on supported SQLite and MySQL-compatible databases. Store complete append-only event records, preserve stable identities and UTC microsecond timestamps, and serialize global-position allocation through commit so polling remains safe.

Provide a generic `EventSourcedRepository` configured by one `AggregateDefinition`. It will load ordered stored history, pass plain current event payloads to aggregate-owned reconstitution, release and append new messages with the correct expected version, and return `null` when no stream exists.

## User Stories

1. As an application owner, I want event history stored durably through DBAL, so that Event Sourcing does not require a proprietary persistence system.
2. As an operator, I want SQLite and MySQL-compatible schemas to enforce stream and message uniqueness, so that concurrent or repeated writes cannot corrupt history.
3. As a concurrent writer, I want expected-version validation and append committed atomically, so that only one decision based on a stream version succeeds.
4. As a checkpoint consumer, I want global positions allocated in commit-safe order, so that polling cannot miss a late lower-positioned commit.
5. As an event reader, I want payloads, metadata, aliases, schemas, IDs, versions, and timestamps to round-trip, so that durable behavior matches the in-memory contract.
6. As an adapter maintainer, I want one conformance suite shared with the in-memory store, so that database behavior cannot redefine the public contract.
7. As a repository consumer, I want one repository configured for my aggregate type and stable name, so that storage identity remains independent of PHP classes.
8. As an application service, I want `find()` to return `null` for missing history, so that the use case decides whether absence is exceptional.
9. As an aggregate author, I want reconstitution to receive only plain current events, so that my domain remains unaware of Event Store machinery.
10. As a command handler, I want saves to use the aggregate's pre-batch version, so that optimistic concurrency reflects the state on which my decision was made.
11. As a command handler, I want saving an aggregate with no released events to be a no-op, so that no empty append or version change occurs.
12. As a command handler, I want failed saves to invalidate the released aggregate instance, so that retries cannot reuse stale state.

## Implementation Decisions

- The DBAL adapter persists one append-only record per event with stable aggregate name and identifier, stable event alias, original schema, stream version, global position, message ID, message creation time, payload data, and metadata snapshot.
- Database constraints enforce unique stream versions and globally unique message IDs. Adapter behavior additionally enforces exact-batch retry semantics from the core contract.
- Expected-version validation, idempotency classification, global-position allocation, and event insertion occur within one transaction.
- MySQL-compatible storage uses a transactional sequence state held through commit for global-position allocation. Event-table auto-increment allocation alone is insufficient because allocation order is not commit order.
- SQLite uses its serialized write transaction behavior while satisfying the same externally observable prefix-stable visibility contract.
- JSON payload and metadata representations and UTC timestamps with microsecond precision round-trip without changing the current hydrated message behavior.
- The DBAL Event Store owns the same complete `EventMapper` used for append and read; persistence does not expose raw records as current events without mapping and upcasting.
- `AggregateDefinition` pairs one stable aggregate name with one current event-sourced aggregate class. Each generic repository handles one aggregate type; no global aggregate registry is introduced.
- `find(Identifier)` reads the stable stream, returns `null` for empty history, unwraps current payloads from stored messages, and invokes the aggregate's static reconstitution contract.
- Repository lookup does not impose an application-level not-found exception. Services and handlers decide that policy.
- Save releases the aggregate's pending events, calculates expected version as current aggregate version minus released batch size, creates event messages through the existing event-message contract, and appends one ordered batch.
- Saving an empty released batch performs no append.
- The repository does not inspect or manage aliases, schemas, upcasters, metadata persistence, or global positions.
- A failure after release is fail-stop for the aggregate instance. Callers discard and reload; only the store may perform safe internal retries while it still owns the released batch.

## Testing Decisions

The durable adapter must pass the reusable Event Store conformance suite established by the in-memory implementation. The suite is exercised against supported SQLite behavior and the supported MySQL-compatible contract, with focused integration coverage for transactional position allocation and database constraints.

The repository's highest seam is a public round trip with an in-memory Event Store: save an aggregate with recorded events, find it by its typed identifier, and assert reconstituted domain state and version. Additional contract tests cover missing streams, empty saves, stable aggregate names, expected-version derivation, ordered unwrapping, private aggregate construction, and save failure behavior.

Tests should assert committed visibility and observable ordering, not internal SQL statement order. Complete coverage remains required for all production classes.

## Out of Scope

- Supporting database platforms beyond the declared SQLite and MySQL-compatible contract.
- Exposing raw persistence records to aggregates.
- Application-specific repository interfaces or not-found exceptions.
- Retrying a decision on an aggregate instance after released events fail to save.
- Multiple aggregate types in one generic repository definition.
- Snapshot persistence, event deletion, or history rewriting.

## Further Notes

The repository and DBAL store solve different concerns. The repository translates aggregate lifecycle into Event Store calls; the Event Store owns durable identity, mapping, schema evolution, idempotency, ordering, and persistence.

T-00008 completed the durable-storage half with SQLite and MySQL 8.4 conformance, transactional sequence
allocation, exact post-rollback retry classification, and complete adapter coverage. T-00009 remains the
ready work that connects aggregate lifecycle to this Event Store through `EventSourcedRepository`.
