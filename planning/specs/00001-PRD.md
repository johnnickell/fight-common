# Existing-Application Migration Evaluation

## Problem Statement

Fight Common can provide a sound Event Sourcing foundation without proving that its contracts fit the applications that will actually adopt it. Fight CMS, the current Fight project template, and Omphalos have different persistence models, event flows, deployment constraints, and tolerance for migration risk. Choosing a pilot without examining those differences could validate an artificial example while missing the seams and operational constraints that matter in production.

This evaluation must inform the library without coupling the 1.2 release to a consumer migration. The work requires human architectural judgment and access to each consumer's current state; it is not an implementation task inside Fight Common.

## Solution

Compare the three candidate consumers against the accepted 1.2 Event Sourcing contracts. Identify their existing aggregate-like boundaries, event creation and dispatch paths, persistence transactions, read-state needs, and operational recovery mechanisms. Recommend one deliberately small pilot with a clear aggregate boundary, migration sequence, rollback boundary, risks, and exclusions.

The recommendation will explain what the pilot can prove about Fight Common and what it cannot. Any consumer changes remain owned, planned, and delivered in that consumer's repository. The evaluation does not block the Fight Common 1.2 release.

## User Stories

1. As a Fight Common maintainer, I want the pilot candidates compared against the same accepted contracts, so that the recommendation is based on relevant evidence rather than familiarity.
2. As a consumer architect, I want the current write, event, and read paths documented, so that the migration boundary reflects how the application actually behaves.
3. As a consumer architect, I want aggregate candidates evaluated for history size, invariants, concurrency, and read-model needs, so that the pilot is neither trivial nor dangerously broad.
4. As a delivery owner, I want one bounded pilot recommended with explicit reasons, so that follow-up planning has a concrete starting point.
5. As a delivery owner, I want rejected candidates and excluded capabilities named, so that the recommendation does not silently expand later.
6. As an operator, I want the cutover and rollback boundaries explained, so that a failed pilot can return to the existing source of truth safely.
7. As an operator, I want projection, publication, retry, and observability risks identified, so that the pilot includes the operational work needed to run it.
8. As a maintainer, I want mismatches between consumer needs and the 1.2 contracts called out, so that later library changes are based on real adoption evidence.
9. As a release owner, I want the evaluation to remain non-blocking, so that uncertainty in a consumer repository cannot hold the additive library release hostage.
10. As a consumer team, I want implementation work to remain in our repository, so that ownership, deployment, and rollback stay with the affected application.

## Implementation Decisions

- Evaluate Fight CMS, the current Fight project template, and Omphalos; do not substitute a synthetic sample application for the comparison.
- Use the accepted aggregate, stream, event-mapping, projection, and publication language from Fight Common when describing each candidate.
- Trace evidence from current consumer contracts and flows. Treat missing evidence as unknown rather than assuming a capability is absent.
- Recommend exactly one bounded pilot and one aggregate boundary. The recommendation must state why that boundary is useful, reversible, and representative.
- Describe a staged migration sequence, including how existing writes coexist with or transition to the Event Store, how read state is established, and where rollback remains possible.
- Identify risks involving historical data, dual writes, optimistic concurrency, event aliases, schema evolution, projections, subscriber side effects, deployment ordering, and operational recovery when applicable.
- Keep all consumer implementation, ticketing, and release work in the owning repository.
- The evaluation is advisory and non-release-blocking for Fight Common 1.2.

## Testing Decisions

This PRD produces an evidence-backed architectural recommendation rather than executable Fight Common behavior. Its quality seam is review against the current consumer repositories and the accepted Fight Common contracts.

The review must confirm that each material claim has current evidence, the same comparison criteria were applied to all candidates, the recommended boundary can be described end to end, and rollback does not depend on an unstated irreversible change. Any proposed proof-of-concept or consumer test belongs to a separately approved plan in the owning repository.

## Out of Scope

- Implementing the pilot in any consumer repository.
- Migrating production data or changing a consumer deployment.
- Blocking Fight Common 1.2 on the recommendation or its adoption.
- Selecting a complete Event Sourcing migration strategy for every bounded context.
- Expanding Fight Common contracts solely to satisfy an unvalidated hypothetical need.

## Further Notes

The strongest outcome may be a narrow pilot or a recommendation to defer all three candidates until a prerequisite is met. Either is valid when supported by evidence. Proven consumer implementations may later be promoted into Fight Common, but that is a separate decision.

## Outcome

The evaluation selected Omphalos Metis `Operation` as the one bounded migration pilot. T-00001 records the
equal-criteria comparison, staged migration, authority and rollback boundary, operational risks, unknowns,
and exclusions. Chronos Platform Halt remains a follow-up candidate with its emergency file override
independent; Fight CMS Commerce remains a separate, unspecified greenfield opportunity. Consumer
implementation and adoption do not block Fight Common 1.2.
