# Checkpointed Projections and Event Publication

## Problem Statement

Rebuilding query-oriented state and notifying event subscribers both consume committed events, but they require different failure semantics. A projector must not advance beyond an event it failed to apply because the read model would become incomplete. A subscriber failure should not prevent later subscribers from seeing an event that already happened, and automatically redispatching the whole event could repeat successful non-idempotent side effects.

Treating both workflows as one bridge, checkpoint, or retry policy would obscure these guarantees. Fight Common needs separate worker-facing services, state stores, and failure behavior while preserving the existing event-dispatch contract and handler ordering.

## Solution

Provide `ProjectionRunner` for ordered at-least-once read-state processing and `EventPublicationRunner` for post-commit subscriber fan-out. Give each projector a stable checkpoint and each publication pipeline a separate stable cursor.

Strengthen synchronous dispatch so every matching handler is attempted and failures are aggregated after fan-out. Publication records a portable aggregated failure before advancing past completed fan-out; projection stops immediately and leaves the failed event uncheckpointed. Supply in-memory and DBAL operational-state adapters and a PSR-3 failure-recorder decorator.

## User Stories

1. As a projector author, I want to declare the current event classes I handle, so that I work with hydrated payloads rather than storage aliases or old schemas.
2. As a projector author, I want a stable projector name independent of my PHP class, so that refactoring code does not reset durable progress.
3. As a projector author, I want events delivered in global order, so that read-state transitions observe history consistently.
4. As a projector author, I want each successful event checkpointed immediately, so that a later failure does not replay the successful prefix of a fetched batch.
5. As a projector author, I want undeclared event types treated as checkpointed skips, so that unrelated events do not stall my projection.
6. As a projector author, I want a failure to stop the batch and remain uncheckpointed, so that the failed state transition is retried before later events.
7. As an operator, I want projector checkpoints stored independently by stable name, so that multiple read models progress at their own pace.
8. As an operator, I want an explicit reset to zero, so that I can rebuild one read model after stopping its worker and clearing its state.
9. As an operator, I want ordinary checkpoint saves to reject backward movement, so that accidental rewinds cannot silently replay history.
10. As a subscriber author, I want later handlers to receive an event even when an earlier handler throws, so that one integration does not suppress unrelated reactions.
11. As a subscriber author, I want event-specific handlers to remain ahead of `AllEvents` handlers and priorities preserved within each phase, so that existing dispatch ordering remains predictable.
12. As a subscriber author, I want all handler failures reported together after fan-out, so that completed delivery and its failures can be observed without stopping early.
13. As a publication operator, I want only committed stored events published, so that subscribers never react to events that failed to persist.
14. As a publication operator, I want a stable publication name and independent cursor, so that separate subscriber pipelines can consume one Event Store safely.
15. As a publication operator, I want handler failures recorded before cursor advancement, so that operational evidence survives without automatically resending the event.
16. As a publication operator, I want unexpected dispatcher infrastructure failures to leave the cursor unchanged, so that uncertain fan-out is retried.
17. As a security-conscious operator, I want failure records to omit payloads, message metadata, traces, and live throwables, so that operational storage is bounded and portable.
18. As an operator, I want exception diagnostics bounded and normalized, so that malformed or oversized messages cannot break persistence or logging.
19. As an operator, I want failure records idempotent by publication and position, so that crash recovery does not create duplicate durable records.
20. As an operator, I want publication cursors to have no reset in 1.2, so that the library cannot casually redispatch history to subscribers that may not be idempotent.
21. As an adapter consumer, I want in-memory and DBAL checkpoint, cursor, and failure stores to share behavior, so that testing and production use the same contracts.
22. As an observer, I want a logging decorator that still delegates to durable or in-memory recording, so that logging cannot accidentally replace failure storage.
23. As a consumer team, I want targeted replay left open for project-specific implementation, so that we can prove the workflow before it becomes a shared contract.
24. As a worker owner, I want scheduling, retry backoff, supervision, and dead-letter policy left to my application, so that Fight Common remains a library rather than a daemon framework.

## Implementation Decisions

- `Projector` declares an explicit stable projector name and the current payload FQCNs it handles. The Event Store has already resolved aliases, upcasted data, and hydrated current messages.
- `ProjectionRunner` reads bounded global batches strictly after the projector checkpoint, preserves global order, and handles one stored event at a time.
- A declared event invokes the projector. An undeclared event is a successful skip. Either outcome advances the checkpoint to that event's global position immediately.
- A projector exception stops processing, propagates, leaves that event uncheckpointed, and prevents all later positions in the batch from running.
- Projector operations are required to be idempotent because a crash after the read-state write but before checkpoint persistence can repeat an event.
- Checkpoints are independently keyed by stable projector name. Normal saves are monotonic. A distinct administrative reset returns one named projector only to zero.
- Consumers stop the projector worker and clear or recreate its read model before reset. Arbitrary backward reset positions and coordinated read-model replacement are excluded.
- `SynchronousEventDispatcher::dispatch()` retains its `void` signature and two ordered phases: event-specific handlers by priority, followed by `AllEvents` handlers by priority.
- Each invoked handler catches any `Throwable` and fan-out continues through both phases. After completion, one `EventDispatchFailed` contains ordered `EventHandlerFailure` values with callable descriptors and original throwables.
- Object methods are described by current FQCN and method, named functions by function name, and closures by a diagnostic non-replayable `Closure` descriptor.
- Handler resolution or preparation failures are infrastructure failures outside `EventDispatchFailed`; they propagate immediately because completed fan-out cannot be proven.
- `EventPublicationRunner` has an explicit stable publication name, reads only committed stored events, and dispatches each stored message through `SynchronousEventDispatcher`.
- `PublicationCursorStore` tracks the last global position for which all matching handlers were attempted. It is distinct from projection checkpoints, monotonic, and has no reset in 1.2.
- A dispatch with no handler failures advances the cursor after completion.
- When `EventDispatchFailed` proves complete fan-out, the runner creates one `EventPublicationFailure`, records it, and then advances the cursor. Subscriber failure does not automatically redispatch the event.
- Any other dispatcher failure propagates without cursor advancement. Recorder and cursor-store failures also propagate and block advancement.
- A crash before cursor advancement can duplicate publication. General subscribers are encouraged, but not universally required, to protect idempotently.
- Each publication failure contains publication name, stored-event and message identity, event alias and positions, dispatch-start timestamp, and ordered handler-failure snapshots.
- Dispatch-start time is captured directly when dispatch begins, normalized to UTC with microsecond precision, and can be compared with message creation time for operational latency. No new clock abstraction is introduced.
- Each handler-failure snapshot contains callable description, exception FQCN, integer code, and a diagnostic message normalized to valid UTF-8, stripped of unsafe control characters, and limited to 4 KiB.
- Durable failure snapshots exclude original throwables, stack traces, event payloads, and message metadata. Original throwables remain transient in `EventDispatchFailed`.
- Fight Common does not perform secret detection or redaction. Consuming projects must keep credentials and sensitive payload data out of exception messages.
- Failure recorders are idempotent by publication name and global position. DBAL stores one aggregated record for that identity.
- The PSR-3 recorder is a required-delegate decorator. It logs first, then delegates the same portable failure. Either failure propagates and prevents cursor advancement; duplicate retry logs remain correlated by publication and position.
- In-memory and DBAL adapters implement the same monotonic checkpoint and cursor contracts and the same idempotent failure-recording contract.

## Testing Decisions

The primary projection seam is `ProjectionRunner` with an in-memory Event Store and checkpoint store. Tests cover ordered declared handling, undeclared skips, per-event checkpoint advancement, immediate failure stop, retry of the failed event, crash-duplicate behavior, monotonic saves, reset to zero, and the rebuild required when a projector adds a handled type.

The primary publication seam is `EventPublicationRunner` with an in-memory Event Store, synchronous dispatcher, cursor store, and failure recorder. Tests cover committed-only reads, success, complete fan-out with one or multiple handler failures, failure recording before advancement, unexpected infrastructure failures, recorder and cursor failures, crash duplicates, diagnostic normalization, and independent publication names.

The synchronous dispatcher contract is exercised against both the simple and service-aware implementations. Tests assert the same message reaches all resolvable handlers, event-specific and `AllEvents` phase ordering remains intact, all `Throwable` values are collected in order, callable descriptions are portable, and resolution failures remain immediate.

Reusable operational-store conformance tests run against in-memory and DBAL checkpoint, cursor, and failure adapters. The logging decorator is tested for log-before-delegate ordering and propagation from either collaborator. Tests assert external behavior and persisted snapshots, not private loop structure. Complete coverage is required.

## Out of Scope

- Combining projection and publication into one worker or progress store.
- Framework-specific commands, worker daemons, scheduling, supervision, retry backoff, or dead-letter policy.
- Skipping failed projections or processing later events out of order.
- Arbitrary projection checkpoint rewind positions.
- Publication cursor reset or whole-stream republication.
- Automatic replay or a shared targeted-replay API for failed subscribers.
- Durable handler aliases across subscriber refactors.
- Requiring every general event subscriber to be idempotent.
- Query APIs for durable publication-failure records.

## Further Notes

Projection progress means successfully established read state; publication progress means completed fan-out was attempted. Their storage mechanics may look similar, but their contracts and recovery consequences are intentionally separate.
