WF-017: reconnect without trusting the event stream as state

Drive two administrator browsers through subscription, invalidation, offline recovery, and session revocation. Socket messages only mark cached data stale. The users API remains authoritative.

Guided walkthroughs

  1. Both browsers authorize, subscribe, then fetch an authoritative snapshot.
  2. Browser A commits a user deletion; the public event contains only an invalidation.
  3. Both browsers coalesce the invalidation and refetch instead of patching cached users.
  1. Browser B drops offline before Browser A commits a deletion.
  2. B misses the socket event.
  3. On reconnect, B authorizes, subscribes, and only then refetches, closing the missed-event gap.
  1. Browser B is connected when its authoritative session is revoked.
  2. The existing transport cannot be retroactively revoked by the authorization endpoint.
  3. The starter's 45-second rotation closes the transport when renewal is denied.

Candidate policy: authorize → subscribe → refetch on every initial connection and reconnect; coalesce invalidations into authoritative refetches; rotate at 45 seconds against a 60-second credential. This bounds compliant-client exposure but is not server-side socket revocation.
