WF-017: what must survive the post-commit crash gap?

Compare a delivered invalidation with a process crash after database commit but before queue enqueue. The users API remains authoritative, every protected request revalidates server state, and a compliant client closes and reauthorizes its realtime transport every 45 seconds.

Guided walkthroughs

  1. Browser B connects and fetches authoritative revision one.
  2. A user deletion commits, then the invalidation job is enqueued and published.
  3. B treats the event as a hint and refetches authoritative revision two.
  1. The user deletion commits, but the process crashes before enqueue.
  2. B receives no event and temporarily shows a stale list.
  3. Planned credential rotation reauthorizes, resubscribes, and refetches at 45 seconds.
  1. B's session is revoked, then the invalidation is lost in the same crash gap.
  2. B's next protected API request is denied immediately from authoritative state.
  3. Rotation clears the remaining stale client shell; realtime never grants access.

Candidate verdict: do not require an atomic outbox for best-effort page or current-user invalidations. A lost hint may leave a compliant UI stale for at most 45 seconds, but cannot authorize an operation; rotation and reconnect always refetch authoritative state.

Durability boundary: work whose eventual execution is part of the business outcome—such as pending security-email delivery—must be persisted atomically with the mutation. It cannot use this lossy invalidation policy.
