WF-017: does one authentication session model survive cold loads, races, and revocation?

Drive two independent device sessions through atomic login, SPA bootstrap, proactive refresh, concurrent API failures, bounded replay, logout, and remote revocation. Access JWTs exist only in client memory; every protected request revalidates authoritative user and refresh-session state.

Guided walkthroughs

  1. Login atomically creates Browser A's refresh session and audit record.
  2. A full reload erases the in-memory access JWT but retains the HttpOnly refresh cookie.
  3. Bootstrap awaits refresh before rendering authenticated state and rotates the refresh credential.
  1. At ten minutes, two protected requests arrive while proactive refresh is due.
  2. Both await one shared refresh promise and only one server rotation occurs.
  3. One eligible failed request is replayed once; the non-replayable mutation is not retried.
  1. Browsers A and B authenticate as independent device sessions.
  2. A lists sessions and remotely revokes B without revoking itself.
  3. B's next request is denied from authoritative state despite its unexpired access JWT.
  1. Browser B refreshes, rotating its opaque refresh credential.
  2. The predecessor credential appears outside the conflict window.
  3. Only B's device family is revoked; Browser A remains active.

Candidate verdict: use one authoritative refresh-session family per device. The SPA waits for cold-load refresh, keeps access JWTs only in memory, shares one refresh promise, and allows at most one replayable retry. Every protected request still revalidates server state, so logout and remote revocation do not wait for JWT expiry.

A refresh conflict is not automatically theft. A losing request inside the bounded conflict window waits for the winning browser context and retries once; predecessor reuse outside that window revokes only the affected device family and requires fresh login there.
