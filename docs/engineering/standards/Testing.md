# Testing and completion evidence

Features: write testable code first, then tests. Bugs: reproduce locally, capture useful evidence, add one meaningful failing regression test proving the defect, then repair it. Verify that the initial failure is the expected bug rather than broken test setup. Keep the regression test and add coverage for the finished behavior. If reproduction is blocked, report why; never fabricate a red result.

Aim for 100% coverage of owned production lines/statements through unit tests first, with appropriate mocks. Use meaningful adapter integration/functional tests when boundaries need proof. Follow the project's exact coverage gate and metadata. Resolve frontend metrics/exemptions explicitly; do not silently assert an unconfigured metric passed.

Choose collaborators according to what a test proves. A handler unit test may mock a specification. A specification may test against controlled repositories/services. Container integration may resolve them together with a mocked database boundary; label that as composition proof, not real database integration. Prefer real value objects, but do not reject a test arrangement merely because the reviewer prefers different mocks.

Cover failure paths and business effects, not only successful calls. Use project fixtures/builders, test naming, namespaces, and assertion conventions. Avoid tests that mirror implementation or mechanically inspect text.

## Gate boundaries

Use focused checks while iterating. Implementation and changes to build inputs require the complete canonical product gate before commit/PR: tests, exact coverage, style, static analysis, architecture checks, docs/planning validation, and frontend build/type checking as applicable. For documentation-only follow-ups, apply the evidence-reuse rule below. Hooks must succeed; never bypass them to claim a completed gate.

**Workflow:** `work` implements and establishes local verification; independent `review` assesses that content and evidence; authorized `land` pushes and creates or updates the PR. Neither work nor review requires publication to obtain hosted CI. Commit, push and PR creation remain distinct permissions; work does not publish merely because it can commit locally.

**Implementation scope:** the builder must establish local pre-submit evidence: run the full gate for implementation/build-input changes, or retain a verified earlier full pass plus the targeted checks permitted below. Retain and report actual results. Hosted CI is not a builder or pre-publication review gate in either public or private repositories. Label it “not run before land” rather than implying a pass; do not scan runs, poll checks or fetch hosted logs merely to complete work or review. Reviewers first validate the builder's saved full-gate result against the reviewed content; a trustworthy receipt remains usable. Do not rerun gates merely to accumulate receipts. If evidence is missing, stale or contradictory, identify the exact gap and request the needed proof or run the canonical gate when necessary to establish acceptance. Focused checks to investigate a finding remain appropriate; review never applies repairs.

Preserve existing release tests and certification probes/checks; do not add new tests of packaging or the release process, whether in product suites, a separate release suite, or a renamed harness. Do not recreate a removed suite. The actual retained inventory is in the [project profile](../../../planning/agents/project-profile.md#retained-release-verification). Release qualification remains separate from product coverage/default builds and requires separate authority to run its owning command. Do not add tests for Markdown, wrapper/config text, generated files, or planning validators to product suites; validate them directly. A feature does not inherit a fake-SSH or long deployment rehearsal suite.

This boundary does not prohibit meaningful tests of Common's published runtime behavior, shipped coding standard, or reusable framework integrations: those are product capabilities. Preserve ADR 0004's versioned consumer ruleset contract and the project's exact direct-unit statement coverage gate. Do not weaken coverage or move product behavior out of its denominator to avoid proving it.

Surface warnings, notices, deprecations, and non-failing advisories. Fold easy relevant fixes into the current TASK; record larger issues and their impact. Do not quietly disable checks or suppress newly introduced failures. A passing local build is distinct from hosted CI, release certification, and production qualification. Unavailable, skipped, or unreadable hosted evidence is not a pass; follow the project's documented policy or obtain the missing decision.

## Local acceptance and hosted delivery

The builder must save a durable local gate receipt beside its complete build log and actual process exit result in the TASK's ignored run directory, and link it from the build handoff. Identify the repository/TASK, command and execution environment, start/end times, tested revision or content snapshot, result, warnings and evidence paths. After publication, record the resulting commit and its mapping to tested content. A fresh run starts as running and becomes passed only after the canonical command actually exits zero; an interrupted/missing result remains incomplete. Never reuse an old exit file or report the exit of a logging process as the build's exit. Existing equivalent logs and reconstructed receipts are acceptable if their provenance can be established; a new receipt format alone does not require rerunning the build.

**Local verification and sufficient acceptance evidence support independent acceptance regardless of repository visibility.** An absent PR or hosted run does not make a review criterion Unverified or require draft publication before acceptance. Workflow files, previous CI usage and hosting configuration do not create pre-land acceptance prerequisites. Do not query repository visibility solely to decide whether local review may accept.

After publication, `land` handles any explicitly required hosted delivery checks recorded in the project profile. Missing or infrastructure-failed required delivery evidence keeps delivery incomplete, not the already-established local technical acceptance. A demonstrated product defect still requires repair and independent review; optional CI is not permission to ignore such a defect. Never label missing or skipped checks passed. Host-enforced merge checks remain binding and may not be bypassed. This separation does not authorize merge, release or deployment.

A future exception requiring hosted proof before technical acceptance needs a new explicit human decision, a named requirement and a publication plan. Generic historical requirements that workflows pass refer to post-publication delivery under this workflow; they must not recreate a circular review-before-publication dependency.

## Reusing a full-gate result after documentation-only follow-ups

A new commit hash alone does not invalidate a successful local full-gate result. For follow-ups limited to non-executable standards, documentation, planning prose/metadata or their generated Markdown views, retain the earlier full pass and run the applicable current documentation, link, planning and view-consistency checks instead of rebuilding the unchanged product.

First inspect the complete intervening diff from the tested revision/content snapshot through the reviewed state, including uncommitted changes. Confirm production code, tests/fixtures, dependencies, runtime/build configuration, scripts, migrations, generated executable artifacts and other relevant gate inputs are unchanged. Classify by effect, not filename or commit message: executable examples consumed by tests, schemas, generator inputs or configuration embedded in documentation do not receive a prose-only exemption. Changes to verification policy still require review of the new requirements and proof that the retained evidence satisfies them.

Record in the ignored handoff the successful run/log/exit result, its tested revision or reconstructable content snapshot, current revision, intervening files and why they cannot affect retained product checks, plus the targeted check results. Existing Git/run records can establish the mapping; the original receipt need not literally contain the later commit hash. An unexplained exit-zero file or timestamp alone is insufficient. If the source or input equivalence cannot be established, identify the specific uncertainty and request missing evidence or a justified engineer rerun. Do not require a rerun solely because hashes differ.

Report “Earlier full gate retained; documentation/planning checks passed for current content,” rather than claiming a fresh full build ran at the new head. Actual implementation/build-input changes require a new full gate from the engineer. Review the changed documentation and applicable standards normally; this rule does not carry old review acceptance forward automatically or waive explicitly required post-publication delivery checks. A justified reuse decision is valid verification evidence, not an acceptance override or an Unverified criterion merely because the full run used an earlier hash.

## Evidence

**Explicit exclusion — planning-only sessions:** authoring or updating maps, EPICs, TICKETs, TASKs, Boards and other planning records requires no screenshots or Before/After section. Verify the records, links, dependencies and generated views as applicable, and summarize that verification in the handoff or PR. This exclusion does not waive an explicit screenshot request or evidence for implementation included in the same session.

For visible changes, capture a before screenshot before editing and an after screenshot demonstrating the same scenario after implementation. Rendered documentation and Boards count as visible changes outside the planning-only exclusion above. Include a reproduced bug where feasible. Keep viewport, scenario and relevant state comparable; explain intentional differences. For APIs/libraries with no useful visual, use request/response transcripts or executable behavior proof and explain why that evidence is appropriate.

Record scenario, environment/URL, capture timestamp, source revision, expected result and actual result. If the work is already implemented, a verified prior revision or saved baseline may be rendered retrospectively; identify its source and actual capture time. A screenshot of the new state is not before evidence. Sanitize credentials and personal data.

Store logs and captures under the TASK's ignored run directory. Outside that exclusion, the PR must have a labeled **Before/After evidence** section containing the useful screenshots, embedded through attachments or an approved location accessible to its intended reviewers. Provide captions tying each image to the behavior and revision. Keep `.runs` ignored; do not stage scratch evidence or add images to product assets merely to obtain a URL.

If screenshots add no useful proof, state the reason in that section and include the nonvisual evidence. If capture or upload is blocked, state the specific obstacle, available local artifacts, useful accessible alternative and remaining human step in both the PR and handoff. “When possible” is not permission for silent omission. Required acceptance proof that is still missing remains unverified; recording an obstacle does not make it pass.

After creating or updating the PR, read back its published description and verify that the evidence links resolve and images render for the intended audience. A local filesystem path, saved screenshot, or unexecuted upload instruction does not prove publication. Preserve the chronology of failures and subsequent focused/full reruns. A detached run needs its final exit status and complete log; partial output is not completion evidence.
