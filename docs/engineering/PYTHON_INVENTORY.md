# Python tooling inventory

The quality runner moved from Bash to PHP without removing Python. This inventory records decisions for the remaining Python tooling and identifies alternatives to evaluate for open items. Those alternatives do not authorize new prerequisites.

## Offline planning — TASK-00222

| Tracked file | Entry point or caller | Runtime and disposition |
| --- | --- | --- |
| `scripts/planning_portfolio.py` | `bin/planning-check` (read-only or `--write`); `bin/build` calls the read-only path before setup and again through `bin/.build-full`. Planning and role handoffs also call it directly. | **Retain.** The Python 3 standard library handles record validation, dependency cycles, parent rollup and deterministic Markdown rendering. Git checks the selected checkout's ignore rules. No image, Composer dependency or network access is needed. |
| `scripts/archive_planning.py` | `bin/archive-planning` (dry run or explicit `--apply`); apply invokes `bin/planning-check --write` after moves and link rewrites. | **Retain.** The Python 3 standard library handles terminal-state checks, filesystem moves and relative Markdown links. Apply uses Git's NUL-separated file list to include tracked and unignored Markdown, preserves link anchors and delegates view refresh to the planner. Porting only archive would not remove Python from its apply path. |

[Local tooling](LOCAL_TOOLING.md) already requires host Python 3 and Git. Host PHP CLI, Node, Ruby or a standalone Perl runtime could implement the logic, but none is a declared host prerequisite. Container PHP (even without Composer autoload) needs an image before either command can run; the current build validates planning before preparing images. A precomputed view cannot validate uncommitted records, and Git can list files but cannot apply planning rules or rewrite Markdown links.

POSIX shell and standard text tools would avoid another interpreter, but this would not be a thin wrapper. The planner would need a replacement for the dependency graph and cycle walk, multi-block view replacement, and validation before writes. Archive would still need safe NUL-delimited path handling (not supported by POSIX `read`), normalized relative paths and link rebasing in both moved and unmoved documents. Replacing those standard-library operations with shell code would add parsing and portability work while the supported host already has Python. Keep both entry points unchanged.

[The TASK record](../../planning/tasks/archive/00222-TASK.md#completion-notes) summarizes the offline command comparisons, including refused writes, byte-equivalent generated views and archive apply on synthetic records only.

## Host build, runtime and databases — TASK-00223

These paths operate where checkout bytes, native Docker/Compose, Git registrations and receipts are visible. A PHP container or Docker socket mount is not a replacement for this boundary. Evaluate thin host wrappers and removal of obsolete entry points before considering a language change that would add a host prerequisite.

## Docs, identity and image trust — TASK-00224

The docs image (`etc/docker/python/Dockerfile`, `requirements.txt`) supplies pinned Python, MkDocs and validator dependencies. The Docs workflow and `bin/.build-full` call `bin/docs validate`; `bin/.build-prepare` prepares the image. `bin/docs preview` and `build` invoke third-party MkDocs, which is outside the migration scope. The PHP tooling image no longer installs Python for its OS trust check.

| Tracked file or embedded path | Entry point or caller | Runtime and disposition |
| --- | --- | --- |
| `scripts/generate_identity_assets.py` | `bin/docs validate` uses `--check`; `docs/identity.md` documents manual generation and check. | **Retain.** The generator owns polygon rasterization, PNG chunk/CRC and compression bytes, multi-size ICO packing, SVG formatting and a sorted manifest. The PHP image has zlib but no GD; even an image-library substitute would not reproduce these bytes by contract. A hand port would have to reproduce the same raster, serialization and compression choices and qualify both runtimes. Check-only re-rendering detects actual drift that a static checksum of checked-in files cannot. |
| `scripts/identity_geometry.py` | Imported by generator and validator. | **Retain with both callers.** The shared SVG linear-path grammar and contour handling must agree between rendering and validation. Porting just the parser would require two implementations or a cross-runtime call in both commands. |
| `scripts/validate_identity_assets.py` | `bin/docs validate` and the manual command in `docs/identity.md`. | **Retain with the generator.** PHP XML and zlib are available, but they do not supply the shared geometry or this validator's SVG bounds, PNG/ICO dimensions and palette checks. Replacing validation with only the generator's byte comparison would drop diagnostics and its separate ability to validate a supplied asset directory. |
| `scripts/validate_readme.py` | `bin/docs validate` checks the repository README and mirrored site inputs. | **Retain.** It renders with the installed Python-Markdown engine before checking image variants, raw HTML, links and fragments. A text scanner misses rendered semantics; PHP DOM can inspect HTML but can't produce equivalent Markdown HTML itself. A separate PHP Markdown engine would need a parity suite for link, anchor, HTML and local preview behavior. |
| `scripts/validate_docs_artifact.py` | `bin/docs validate` checks generated `site` after MkDocs. | **Retain.** It checks routes and internal links, HTML elements and metadata, font hashes, SVG and CSS rules including contrast. PHP DOM and URL helpers cover some parsing, not the current HTML-parser events and path normalization or the CSS contracts. Splitting checks across runtimes would add a dependency on the separate PHP image and risk checking different output paths; grep cannot replace route and structure checks. |
| `scripts/validate_docs_workflow.py` | `bin/docs validate` checks `.github/workflows/docs.yml`. | **Retain.** The existing PyYAML dependency handles structured YAML with a local resolver that keeps unquoted `on` as a key and `false` as a boolean. The default PyYAML loader does not preserve that key. Shell text matching would miss semantic changes; the PHP image has no YAML extension and porting would require a parser with qualified resolver behavior and a separate runtime for this check. |
| `etc/docker/python/Dockerfile` | `bin/docs` and build preparation. | **Retain the two embedded assertions.** The pre-install command imports pip's vendored certifi to get its actual version and inspects Python's loaded OS roots; the post-install command imports installed certifi separately. `pip show certifi` cannot identify pip's vendored copy. Shell path or metadata guesses would not verify the modules pip and Python actually load. An OpenSSL CLI bundle scan could replace only the OS portion; it would not remove either Python call and would no longer exercise Python's default SSL context. |
| `etc/docker/php/Dockerfile` | `bin/up`, build preparation and release certifier image preparation. | **Replace.** Use the base PHP CLI's OpenSSL support to parse certificate subjects in the same default OS bundle. No Composer packages, extension build or Python install is needed. The helper rejects unreadable, empty and malformed bundles as well as the affected common name. |
| `docs/contributing.md` image audit | Manual network-disabled checks of the PHP and docs images. | **Split.** Use the PHP image's own bundle helper and Debian package metadata for that image. Retain Python only in the docs image, where actual import paths distinguish installed certifi from pip-vendored certifi and `ssl` loads each bundle independently. `openssl` and `sha256sum` could report bundle contents and hashes but cannot identify those modules or their bundle paths without Python. Missing certifi imports now fail the docs-image audit instead of silently omitting a store. |

## Release — TASK-00225

| Tracked file or embedded path | Entry point or caller | Runtime and disposition |
| --- | --- | --- |
| `bin/release` lane setup heredoc | `bin/release certify`, before running default/latest/lowest dependency lanes; documented in `release/README.md`. | **Retain.** Before a certifier image is prepared, the host resolves each exported lane's physical path, reads and writes its JSON without changing other settings, and emits the path and project as a tab-separated locator. The project is `fight-common-release-` plus the first 16 SHA-256 hex digits of that physical path. Shell and a host hash tool can produce the suffix but cannot safely rewrite structured JSON without a parser. `jq` or host PHP could do the JSON work but neither is a supported host prerequisite. Container PHP would require moving image preparation before lane identity is recorded or depending on another image. |
| `bin/release` lane cleanup heredoc | Release cleanup, after the lane's guarded `bin/down`; imports the lane's own `local_tooling`. | **Retain.** The lane is a standalone exported repository, so `bin/down` treats it as canonical and does not retire its named volumes and image tags as it would for a registered worktree. The host snippet rechecks the hash-derived identity, runs the candidate's ownership/consumer guard before the sweep and before each removal, and confirms native absence before allowing source deletion. Compose alone does not provide those checks; a shell or PHP port would have to duplicate them or call back into the same candidate-owned Python modules retained in TASK-00223. A container would also need host Docker access and the original checkout identity. |

Both snippets use the host Python 3 already required by `bin/up`, `bin/build` and `bin/down`; moving just the snippets would not remove that prerequisite. Moving the cleanup into a new shared command would relocate release-specific policy without removing Python. Keep both snippets together with their caller and leave the candidate, archive and installed-consumer steps unchanged. See the [TASK evidence](../../planning/tasks/archive/00225-TASK.md#completion-notes) for the bounded checks and their limits.

## Inventory boundary

Checked the tracked tree for `*.py`, interpreter shebangs, Python commands/imports, heredocs and documented invocations, then followed the scripts, wrappers, local/CI configs and release guide. The baseline has 21 tracked `.py` files and one extensionless Python executable (`bin/database-runtime`). Historical planning examples (including the older TASK-00174 image audit) are evidence, not additional live entry points. Generated `vendor`, bytecode, output and local evidence are not owned sources. Package dependencies and MkDocs plugins are not migration targets; the pinned image definition, Python calls in wrappers and trust probes above are owned.
